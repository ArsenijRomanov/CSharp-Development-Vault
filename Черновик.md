Да, **идти последовательно точно стоит**, но я бы строил порядок не только по году появления, а прежде всего по **уровню решаемой проблемы**. Тогда не возникнет ощущения, что `MVC`, `DDD` и `Clean Architecture` — конкурирующие архитектуры одного класса. Они вообще могут одновременно существовать в одном приложении.

И я бы действительно начал с **MVC**, но сразу зафиксировал его масштаб.

### Как я бы выстроил конспект

**0. Сначала короткий вводный блок — уровни архитектурных решений**

```text
уровень представления
→ как организовать UI / обработку входящих запросов

архитектура приложения
→ как разделить business logic, application logic, infrastructure

моделирование домена
→ как представить сложные бизнес-правила

архитектура системы
→ как несколько приложений / сервисов взаимодействуют между собой

deployment / distributed level
→ процессы, сервисы, сети, брокеры, БД и т.д.
```

Это потом будет постоянно спасать от терминологических конфликтов.

### 1. MVC

Начать с него нормально.

Но сразу сказать:

> **MVC — прежде всего pattern организации presentation layer, а не полная архитектура backend-приложения.**

Он разделяет взаимодействие с пользователем на `Model`, `View`, `Controller`; Fowler тоже относит MVC именно к web presentation patterns. ([martinfowler.com](https://martinfowler.com/eaaCatalog/?utm_source=chatgpt.com "Catalog of Patterns of Enterprise Application Architecture"))

```text
Controller
→ принимает input

Model
→ данные / состояние / логика модели

View
→ отображение
```

И потом очень полезно будет вернуться к нему в Clean Architecture: сам Мартин прямо помещает MVC в слой **Interface Adapters**. ([Clean Coder](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture?utm_source=chatgpt.com "Clean Coder Blog"))

То есть:

```text
Clean Architecture
└── Interface Adapters
    └── MVC
```

Уже на этом примере видно, почему разные паттерны можно комбинировать.

---

### 2. Layered Architecture + 3-layer / 3-tier

Вот это уже первый переход к **архитектуре приложения целиком**.

Классическая схема:

```text
Presentation
     ↓
Business Logic
     ↓
Data Access
```

Здесь надо отдельно обязательно разобрать:

```text
Layer
→ логическое разделение кода

Tier
→ физическая/deployment граница
```

Потому что `3-layer` и `3-tier` очень часто неправильно используют как синонимы.

И здесь появляется фундаментальная проблема традиционной layered architecture:

```text
Business
   ↓
Data Access
   ↓
Database
```

Бизнес-логика начинает зависеть от инфраструктуры.

И вот уже после этого Hexagonal/Onion будут восприниматься не как «ещё одна картинка с кружками», а как **ответ на конкретную проблему layered architecture**. Palermo именно так и сравнивал Onion с традиционной layered architecture: основной вопрос — направление coupling и вынос infrastructure наружу. ([Programming with Palermo](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/?utm_source=chatgpt.com "The Onion Architecture : part 1 | Programming with Palermo"))

### 3. Enterprise Application Patterns

Вот сюда я бы вставил Fowler'а, потому что мы уже частично это обсуждали.

Не как одну архитектуру, а как **набор более локальных решений внутри архитектуры приложения**:

```text
Domain Logic:
→ Transaction Script
→ Domain Model
→ Service Layer

Data Access:
→ Active Record
→ Data Mapper
→ Repository
→ Unit of Work

Presentation:
→ MVC
→ Front Controller
→ Page Controller
```

Это очень полезный промежуточный уровень. Fowler действительно классифицирует эти паттерны именно таким образом. ([martinfowler.com](https://martinfowler.com/eaaCatalog/?utm_source=chatgpt.com "Catalog of Patterns of Enterprise Application Architecture"))

Тогда у тебя перестанет возникать вопрос:

> Repository — это архитектура или DDD?

Нет:

```text
Repository
→ более локальный enterprise/data-access pattern

DDD
→ подход к моделированию сложного domain

Clean
→ архитектура зависимостей приложения
```

Они могут пересекаться.

---

### 4. DDD

Вот здесь я бы **не откладывал DDD до самого конца**.

По хронологии книга Эванса вышла в 2003 году, то есть раньше Hexagonal 2005, Onion 2008 и Clean 2012. ([martinfowler.com](https://martinfowler.com/bliki/DomainDrivenDesign.html?ref=dma-nav&utm_source=chatgpt.com "Domain Driven Design"))

Но ещё важнее: DDD отвечает **на другую проблему**.

Не:

> как направить зависимости?

А:

> как вообще моделировать сложный бизнес?

```text
Strategic DDD
→ Domain
→ Subdomain
→ Bounded Context
→ Ubiquitous Language
→ Context Map

Tactical DDD
→ Entity
→ Value Object
→ Aggregate
→ Domain Service
→ Repository
→ Domain Event
```

Fowler как раз подчёркивает, что ключевая идея DDD — богатая модель сложного domain, а Strategic Design организует большие домены как сеть Bounded Contexts. ([martinfowler.com](https://martinfowler.com/bliki/DomainDrivenDesign.html?ref=dma-nav&utm_source=chatgpt.com "Domain Driven Design"))

Поэтому:

```text
DDD
не является следующей версией Clean Architecture

DDD ⟂ Clean Architecture
```

Они ортогональны и прекрасно комбинируются.

### 5. Hexagonal Architecture / Ports & Adapters — 2005

Вот тут начинается семейство архитектур:

```text
Hexagonal
Onion
Clean
```

с очень близкой фундаментальной идеей.

Hexagonal отвечает на проблему:

> **application core не должен зависеть от UI, БД и прочих внешних устройств**

Cockburn прямо формулировал цель так: приложение должно работать независимо от UI и базы данных, а внешние технологии подключаются через ports и adapters. ([Alistair Cockburn](https://alistair.cockburn.us/hexagonal-architecture?utm_source=chatgpt.com "hexagonal-architecture"))

```text
           HTTP Adapter
                ↓
              Port
                ↓
        Application Core
                ↓
              Port
                ↓
          DB Adapter
```

И здесь впервые очень хорошо вводить:

```text
Driving / Primary adapters
Driven / Secondary adapters

Input ports
Output ports
```

---

### 6. Onion Architecture — 2008

После Hexagonal Onion воспринимается очень естественно.

Palermo делает больший акцент на **слоях вокруг Domain Model и направлении compile-time dependencies внутрь**. ([Programming with Palermo](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/?utm_source=chatgpt.com "The Onion Architecture : part 1 | Programming with Palermo"))

```text
Infrastructure
      ↓
Application Services
      ↓
Domain Services
      ↓
Domain Model
```

Главное правило:

```text
dependencies → toward the center
```

И вот здесь отлично привязывается уже изученный DIP:

```text
IOrderRepository ← внутренний контракт

EfOrderRepository
→ внешний implementation
```

Palermo прямо связывает Onion с Dependency Inversion и выносом database/infrastructure наружу. ([Programming with Palermo](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/?utm_source=chatgpt.com "The Onion Architecture : part 1 | Programming with Palermo"))

---

### 7. Clean Architecture — 2012

И только после Hexagonal + Onion я бы разбирал Clean.

Потому что тогда становится видно, что Clean — **не революционно новая идея**, а попытка собрать общее ядро целого семейства архитектур.

Сам Robert Martin в оригинальной статье перечисляет:

```text
Hexagonal
Onion
Screaming Architecture
DCI
BCE
```

и пишет, что у них очень похожие цели: separation of concerns, независимость business rules от внешних деталей и направление dependencies внутрь. ([Clean Coder](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture?utm_source=chatgpt.com "Clean Coder Blog"))

Тогда его круги:

```text
Entities
↑
Use Cases
↑
Interface Adapters
↑
Frameworks & Drivers
```

будут восприниматься не как набор терминов для заучивания, а как развитие уже понятной идеи.

### А дальше уже можно подниматься ещё выше

После этого логично идти в:

```text
CQRS
Event Sourcing
Vertical Slice Architecture
Modular Monolith

SOA
Microservices
Event-Driven Architecture

distributed architecture patterns
```

Потому что там уже меняется масштаб:

```text
MVC
→ кусок приложения

Repository / UoW
→ конкретная техническая задача внутри приложения

Layered / Hexagonal / Onion / Clean
→ организация приложения

DDD
→ организация и моделирование предметной области

Modular Monolith
→ организация большой application/system boundary

Microservices / SOA / EDA
→ взаимодействие нескольких independently running частей системы
```

### По поводу годов

**Годы указывать стоит**, но не как показатель «чем новее, тем глубже».

Скорее как историческую линию:

```text
MVC
→ конец 1970-х

DDD
→ 2003

Hexagonal
→ 2005

Onion
→ 2008

Clean
→ 2012
```

Для Hexagonal, Onion, DDD и Clean даты хорошо привязаны к оригинальным публикациям/книгам. ([Alistair Cockburn](https://alistair.cockburn.us/hexagonal-architecture?utm_source=chatgpt.com "hexagonal-architecture"))

Но **Layered / 3-tier** я бы не пытался привязать к одной красивой дате и одному автору: это эволюционировавшее семейство идей, а не один конкретный паттерн, опубликованный в конкретной статье.

И я бы зафиксировал в начале всего конспекта одну мысль, она потом будет лейтмотивом:

```text
MVC
Layered
DDD
Hexagonal
Onion
Clean
CQRS
Microservices

не образуют взаимоисключающий список

они решают проблемы
разного масштаба
и разных осей архитектуры

поэтому одно приложение
может использовать несколько
из них одновременно
```

Так что **да, следующий блок имеет смысл начать с MVC**, затем Layered/3-tier, после этого enterprise patterns, DDD, Hexagonal → Onion → Clean. Это даст гораздо более цельную эволюцию, чем просто пройти подряд по модным названиям архитектур.
