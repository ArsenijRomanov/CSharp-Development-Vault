
**Workstation GC** и **Server GC** — два режима работы .NET GC. Главное отличие — в том, **как GC использует CPU и организует heap**, чтобы оптимизироваться либо под меньший расход ресурсов, либо под высокий throughput.

### Workstation GC

Использует в основном **один managed heap** и меньше выделенных GC-ресурсов.

Подходит для приложений, где важнее:

- небольшой memory footprint
- умеренная нагрузка
- отсутствие необходимости активно распараллеливать работу GC

Типичный сценарий — desktop/client applications.

### Server GC

Использует **несколько managed heaps и несколько GC threads**, чтобы выполнять сборку параллельно и лучше масштабироваться под большой allocation rate.

В классической модели количество heaps ориентируется на количество **логических процессоров, доступных процессу**.

В современных версиях .NET фактическое количество heaps может динамически уменьшаться или увеличиваться, поэтому правило `1 logical CPU = 1 heap` — базовая модель, а не абсолютная гарантия.

Основная цель Server GC:

```
больше heap'ов
+
параллельная работа GC threads
+
использование нескольких CPU
=
более высокий throughput под нагрузкой
```

Цена — обычно больший расход памяти и CPU.

### Server GC не убирает Stop-the-World

**Server GC не означает concurrent GC без остановок приложения.**

Сборки **Gen0 и Gen1 остаются blocking**: managed threads приложения на время collection останавливаются.

При этом в Server GC сама работа сборщика может выполняться параллельно:

```
Managed threads
───────|        STOP        |───────

        GC thread 0 → Heap 0
        GC thread 1 → Heap 1
        GC thread 2 → Heap 2
        GC thread 3 → Heap 3
              работают параллельно
```

То есть:

```
blocking
= приложение остановлено

parallel
= несколько GC threads одновременно выполняют сборку
```

Server GC может быть одновременно **blocking и parallel**.

Background GC — отдельный механизм. Он позволяет значительную часть Gen2 collection выполнять concurrently с приложением, но даже он не означает полного отсутствия Stop-the-World фаз.

### Кучи Server GC не изолированы

Несколько heaps в **Server GC** существуют прежде всего для того, чтобы **распараллелить allocation и работу GC между несколькими логическими CPU**. Они не являются независимыми областями памяти приложения. Microsoft прямо указывает, что все heaps доступны пользовательскому коду, а объекты из разных heaps могут ссылаться друг на друга.

При сборке GC учитывает ссылки между heaps так же, как любые другие ссылки, поэтому объект не станет мусором просто потому, что ссылка на него находится в другом heap.

### Суть

```
Workstation GC
→ обычно один heap
→ меньше памяти и GC-ресурсов

Server GC
→ несколько heaps
→ несколько GC threads
→ heaps ориентированы на доступные logical CPUs
→ GC может собирать heaps параллельно
→ ориентирован на throughput и высокую серверную нагрузку
→ Gen0 / Gen1 всё равно Stop-the-World
```

Для нагруженных backend-приложений Server GC обычно предпочтительнее именно потому, что позволяет **использовать несколько CPU для работы GC**, а не потому, что устраняет паузы сборщика.

### Сборка нескольких heaps в Server GC

В Server GC heaps **не собираются независимо друг от друга**. Когда запускается GC, начинается единый цикл сборки, в котором GC threads параллельно обрабатывают соответствующие heaps.

Например, если текущая сборка выбрана как Gen0:

```
Heap 0 → Gen0 ── GC thread 0
Heap 1 → Gen0 ── GC thread 1
Heap 2 → Gen0 ── GC thread 2
Heap 3 → Gen0 ── GC thread 3

        одна Gen0 collection
        работа выполняется параллельно
```

Если выбрана Gen1:

```
Heap 0 → Gen0 + Gen1
Heap 1 → Gen0 + Gen1
Heap 2 → Gen0 + Gen1
Heap 3 → Gen0 + Gen1
```

То есть самое старшее собираемое поколение является общим для текущего GC-цикла, а работа распределяется между GC threads по нескольким heaps. В реализации Server GC состояние текущей collection, включая выбранное поколение, координируется между heaps.

При этом слово «одновременно» стоит понимать как **одна согласованная параллельная сборка**, а не как гарантию, что каждый GC thread начнёт и закончит работу в одну и ту же наносекунду. Один heap может содержать больше работы, чем другой.

Это также необходимо для корректной обработки ссылок между heaps: object graph приложения общий, хотя физически объекты распределены между несколькими heaps.
