**Garbage Collector** — механизм автоматического управления managed memory в .NET. Он выделяет память под новые объекты, определяет достижимые объекты и освобождает память объектов, которые больше недоступны приложению.

## 1. Области managed heap

Managed heap логически разделён на несколько областей с разным поведением.

### SOH — Small Object Heap

**SOH** предназначен для небольших объектов — обычно меньше `85 000` байт. Он разделён на поколения:

- Gen0 
- Gen1 
- Gen2

Новые небольшие объекты создаются в **Gen0**. Пережившие сборку объекты могут продвигаться в следующее поколение. Сборка поколения всегда включает все более молодые поколения:

```
Gen0 GC → Gen0
Gen1 GC → Gen0 + Gen1
Gen2 GC → Gen0 + Gen1 + Gen2 + LOH + POH
```

### LOH — Large Object Heap

**LOH** предназначен для крупных объектов — обычно размером от `85 000` байт. Перемещение больших объектов дорого, поэтому LOH обычно **не дефрагментируется**, а освобождённые участки памяти сохраняются и могут повторно использоваться при следующих аллокациях. LOH собирается вместе с Gen2.

### POH — Pinned Object Heap

**POH** предназначен для объектов, которые создаются сразу как pinned и поэтому не должны перемещаться GC.

Это позволяет отделить долгоживущие pinned-объекты от обычного SOH, где они мешали бы compaction и создавали фрагментацию. Поскольку объекты POH нельзя перемещать, освобождённые промежутки также приходится переиспользовать как свободные блоки.

## 2. Аллокация памяти

### SOH — bump allocation

Все новые маленькие незапиненные объекты помещаются в Gen0.
Основной fast path для них очень простой: runtime поддерживает **указатель на следующее свободное место**.

```
     allocation pointer
            ↓
[A][B][C][D][           free space             ]
```

Для объекта `E`:

```
[A][B][C][D][E][        free space             ]
              ↑
        pointer moved
```

То есть аллокация концептуально сводится примерно к:

```
address = allocationPointer
allocationPointer += objectSize
```

Такая аллокация очень дешёвая: не нужно искать подходящую дыру среди свободных блоков. В реальном GC быстрый путь работает внутри allocation context, выделенного runtime.

Такой подход особенно хорошо подходит SOH, потому что обычная сборка может перемещать и уплотнять живые объекты. Поэтому нет необходимости при каждой маленькой аллокации тщательно искать и переиспользовать отдельные дыры: GC периодически снова формирует большие непрерывные области свободной памяти.

### LOH и POH — free lists

В LOH и POH перемещение объектов либо слишком дорого, либо вообще невозможно. Поэтому после удаления объектов могут оставаться дыры

Эти свободные блоки сохраняются в **expicit free list**:

При новой аллокации runtime может подобрать подходящий свободный блок и разместить объект туда.

Для LOH это оправдано тем, что постоянное копирование многомегабайтных объектов во время compaction стоило бы дорого. Для POH compaction принципиально невозможен для pinned-объектов, поскольку их адрес должен оставаться стабильным.

# 3. Выбор поколения для сборки

Когда возникает необходимость выполнить GC, **самое старшее собираемое поколение определяется до начала tracing**.

То есть GC не работает так:

```
собрали Gen0
  ↓
"освободили мало"
  ↓
решили продолжить в Gen1
  ↓
"всё ещё мало"
  ↓
пошли в Gen2
```

Вместо этого:

```
GC triggered
      ↓
анализ состояния heap
      ↓
выбирается Gen0 / Gen1 / Gen2
      ↓
только после этого начинается tracing
```

При выборе самого старшего поколения для текущей сборки GC учитывает состояние памяти и статистику предыдущих сборок:

- сколько памяти было выделено с момента предыдущих сборок
- сколько объектов переживало предыдущие сборки и переходило в старшие поколения
- сколько памяти занято в каждом поколении
- насколько сильно память фрагментирована
- сколько памяти доступно процессу и насколько велико общее давление на память
- насколько эффективно предыдущие сборки освобождали память

На основе этой информации **до начала самой сборки** GC определяет, что именно будет собираться: только Gen0, Gen0 + Gen1 или все поколения.

# 4. Tracing и определение живых объектов

Для определения достижимых объектов GC начинает обход от **корневых ссылок (GC roots)**. К ним относятся:

- ссылки на объекты из стеков выполняющихся потоков
- ссылки, находящиеся в регистрах процессора и относящиеся к текущему выполнению методов
- статические ссылки
- специальные ссылки, зарегистрированные через GC handles
- ссылки, связанные с объектами, ожидающими финализации

Все объекты, до которых можно добраться от этих корневых ссылок, считаются достижимыми и сохраняются. Остальные объекты в собираемой области памяти могут быть освобождены.

От этих ссылок строится граф достижимых объектов. Далее (концептуально) начинается **трёхцветный алгоритм**.

# 5. Частичная сборка поколений

Важное свойство generational GC: **при Gen0 GC не нужно обходить весь Gen1 и Gen2**.

Например:

```
Gen0:  20 MB
Gen1:  50 MB
Gen2:  5 GB
```

Если ради каждой Gen0 collection пришлось бы снова трассировать все `5 GB` Gen2, поколения практически потеряли бы смысл.

Поэтому если собирается Gen0, объекты Gen1 и Gen2 в рамках этой collection считаются сохраняемыми автоматически. GC не пытается определить, являются ли они мусором.

# 6. Ссылки из старших поколений в младшие

Здесь появляется проблема.

Допустим:

```
 Root
   ↓
Gen2 A
   │
   ▼
Gen0 B
```

При Gen0 GC мы **не хотим обходить весь Gen2**, но `B` нельзя удалить — на него существует ссылка из `A`.

Наивное решение:

```
при каждой Gen0 GC
→ просканировать весь Gen1
→ просканировать весь Gen2
→ найти все ссылки в Gen0
```

слишком дорого.

Поэтому runtime **учитывает изменения ссылок во время нормальной работы приложения**.

Когда происходит присваивание наподобие:

```cs
oldObject.Child = youngObject;
```

runtime дополнительно фиксирует метаданные о том, что в соответствующей области старшего поколения **потенциально появилась ссылка в молодое поколение**. Эти метаданные поддерживаются при изменениях ссылок так, чтобы GC не мог пропустить нужную `old` $\rightarrow$ `young` связь.

GC не хранит обязательно точный глобальный список.

Достаточно **консервативно помнить области, которые нужно проверить**.

Лишняя пометка допустима:

```
проверили область
  ↓
young reference там уже нет
  ↓
ничего страшного, только лишняя работа
```

Но нужная ссылка не должна быть пропущена — иначе живой молодой объект мог бы ошибочно быть признан мусором. В CoreCLR эта информация обновляется непосредственно механизмом, сопровождающим запись managed-ссылок.

# 7. Что происходит после tracing

После marking GC уже знает:

```
reachable → live
unreachable → garbage
```

Дальше концептуально возможны два основных варианта.

### Compact

Живые объекты сдвигаются друг к другу.

После перемещения runtime обновляет ссылки на новые адреса объектов.

Для SOH это типичный и очень важный сценарий: он устраняет фрагментацию и снова создаёт непрерывную свободную область, удобную для дешёвой bump allocation.

### Sweep

Объекты не перемещаются. GC просто обнаруживает свободные участки и делает их доступными для будущих аллокаций.

Такой подход характерен для LOH, POH и Gen2.

Упрощённо полный цикл можно представить так:

```
Allocations
    ↓
GC trigger
    ↓
выбор самого старшего собираемого поколения
    ↓
получение roots
 +
учёт ссылок из несобираемых старших поколений
    ↓
Mark / tracing
    ↓
определение live / garbage
    ↓
планирование освобождения памяти
    ↓
Compact или Sweep
    ↓
обновление ссылок при перемещении
    ↓
promotion переживших объектов
    ↓
приложение продолжает работу
```

# 8. Stop-the-World и конкурентность GC

## 8.1 Сборки Gen0 и Gen1

Сборки **Gen0 и Gen1 всегда выполняются с остановкой managed-потоков приложения**. На время такой сборки возникает **Stop-the-World**. Background/concurrent режим применяется только к Gen2.

Во время паузы GC может выполнить:

- поиск живых объектов
- освобождение мусора
- планирование уплотнения
- обновление ссылок
- перемещение объектов при дефрагментации

После завершения сборки managed-потоки продолжают работу.

Молодые поколения специально делаются небольшими, поэтому такие блокирующие сборки обычно значительно дешевле full GC.

---

## 8.2 Сборка Gen2

Сборка Gen2 является **full GC** и включает также Gen0 и Gen1. При этом она может выполняться двумя способами:

```
Gen2 GC
├── Background GC
└── Blocking GC
```

### Background Gen2 GC

В стандартном background-режиме большая часть Gen2-сборки выполняется **конкурентно с приложением**. Background GC применяется только к Gen2.

Сначала требуется короткая остановка приложения для подготовки сборки, затем managed-потоки продолжают работу одновременно с GC. Позже GC ещё раз кратковременно останавливает приложение, чтобы завершить маркировку, после чего освобождение памяти может продолжаться конкурентно. 

**Background Gen2 не выполняет обычную дефрагментацию Gen2.** Вместо перемещения объектов выполняется sweep: промежутки между живыми объектами превращаются в свободные блоки и добавляются во **free list**.

Таким образом Gen2 может оставаться фрагментированным, зато GC не приходится перемещать большое количество долгоживущих объектов во время конкурентной сборки.

---

## 8.3 Gen0/Gen1 во время Background Gen2

Пока идёт Background Gen2, приложение продолжает создавать новые объекты. Поэтому Gen0 может заполниться ещё до окончания Gen2-сборки.

Тогда background GC временно приостанавливается и выполняется обычная blocking-сборка молодого поколения.

То есть наличие background Gen2 **не делает Gen0 и Gen1 конкурентными** — они всё равно требуют Stop-the-World.

---

## 8.4 Blocking Gen2 GC

Gen2 может быть собран и полностью **в блокирующем режиме**:

В этом случае GC может выбрать между:

```
compaction
или
sweep
```

Если compaction выгодна, GC обновляет ссылки и перемещает живые объекты, пока managed-потоки остановлены. Если compaction невыгодна, выполняется sweep, а освобождённые промежутки попадают во **free list**.

Это и решает проблему безопасного перемещения объектов: **GC не перемещает Gen2-объекты конкурентно с работающим managed-кодом**.
