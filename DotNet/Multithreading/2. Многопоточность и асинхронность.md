# 1. Конкурентные коллекции

- `System.Collections.Frozen` - неизменяемые коллекции, создаются один раз и оптимизированы для частого чтения и поиска
	
- `System.Collections.Immutable` - любое изменение коллекции создает ее копию
	
- `System.Collections.Concurrent` - изменяемые потокобезопасные коллекции для конкурентного чтения и записи

---

## 1.1. `System.Collections.Frozen`

Неизменяемые коллекции, которые создаются редко, но оптимизированы для частого поиска и перебора

При создании анализируются:

- тип элементов или ключей
- используемый компаратор
- количество и конкретные значения элементов
- распределение хеш-кодов
- количество возможных коллизий

На основе этого выбирается специализированная реализация, оптимально распределяются элементы по бакетам и компактно размещаются внутренние данные

Создание `Frozen`-коллекции дороже обычной, но после создания структура больше не изменяется и может быть лучше оптимизирована для чтения

#### 1. `FrozenDictionary<TKey, TValue>`

Неизменяемый словарь ключей и значений

#### Создание

```cs
using System.Collections.Frozen

Dictionary<string, int> source = new()
{
    ["one"] = 1,
    ["two"] = 2
}

FrozenDictionary<string, int> dictionary =
    source.ToFrozenDictionary()
```

#### 2. `FrozenSet<T>`

Неизменяемое множество уникальных элементов

#### Создание

```cs
using System.Collections.Frozen

FrozenSet<string> set =
    names.ToFrozenSet()
```

## 1.2. `System.Collections.Immutable`

Операции изменения не меняют текущий экземпляр, а возвращают новую версию

```cs
ImmutableList<int> first = ImmutableList.Create(1, 2, 3)
ImmutableList<int> second = first.Add(4)
```

```cs
first  = [1, 2, 3]
second = [1, 2, 3, 4]
```

Новая версия обычно переиспользует неизменившиеся части внутренней структуры старой версии. Это называется **структурным разделением**.

### Основные коллекции

- `ImmutableArray<T>`
- `ImmutableList<T>`
- `ImmutableDictionary<TKey, TValue>`
- `ImmutableHashSet<T>`
- `ImmutableSortedDictionary<TKey, TValue>`
- `ImmutableSortedSet<T>`
- `ImmutableQueue<T>`
- `ImmutableStack<T>`

---

### `ImmutableList<T>`

Внутри хранится АВЛ-дерево

Порядок элементов определяется не их значениями, а положением узлов в дереве

```
       3
      / \
     2   5
    /   /
   1   4
```

При изменении создаются новые узлы только на пути от изменённого места до корня

```
Старая версия          Новая версия

       A                     A'
      / \                   /  \
     B   C                 B    C'
        / \                    /  \
       D   E                  D    E'
```

Узлы `B` и `D` не изменились, поэтому обе версии ссылаются на одни и те же объекты

Старая и новая коллекции имеют разные корни, но общие неизменившиеся ветви

Добавление, удаление и замена обычно создают `O(log n)` новых узлов.

---

### Внутреннее устройство остальных коллекций

- `ImmutableArray<T>` — оболочка над обычным массивом `T[]`, при изменении обычно создаётся новый массив
	
- `ImmutableDictionary<TKey, TValue>` — АВЛ-дерево по хеш-кодам ключей, элементы с одинаковым хеш-кодом хранятся в бакете
	  
- `ImmutableHashSet<T>` — АВЛ-дерево по хеш-кодам элементов с бакетами для коллизий
	  
- `ImmutableSortedDictionary<TKey, TValue>` — АВЛ-дерево, упорядоченное непосредственно по ключам через `IComparer<TKey>`
	  
- `ImmutableSortedSet<T>` — АВЛ-дерево, упорядоченное по элементам через `IComparer<T>`
	  
- `ImmutableStack<T>` — односвязная структура из головы и ссылки на оставшуюся часть стека
	  
- `ImmutableQueue<T>` — две неизменяемые стопки: одна для извлечения, другая для добавления

## 1.3. `System.Collections.Concurrent`

Применяют различные `lock-free` алгоритмы и сегментные блокировки.


### 1. `ConcurrentBag`

- неупорядоченная коллекция
- для каждого потока своя очередь элементов
- добавление объектов не блокирует коллекцию
- внутри использует `Interlocked.CompareExchange` для добавления элемента
- читаем сначала в своей очереди, потом идём в другие
- в своей очереди читаем с конца
- в чужой очереди читаем с начала
- пишем в начало
- в лучшем случае блокировок вообще не будет

#### Основные методы

```cs
bag.Add(item)                  // добавить элемент
bag.TryTake(out item)          // удалить и вернуть некоторый элемент
bag.TryPeek(out item)          // вернуть элемент без удаления
bag.IsEmpty                    // проверить, пуста ли коллекция
bag.Count                      // получить количество элементов
bag.ToArray()                  // получить снимок в виде массива
bag.Clear()                    // удалить все элементы
```


### 2. `ConcurrentStack`

- упорядочен
- односвязный список
- `Pop` и `Push` используют `CompareExchange`

#### Основные методы

```cs
stack.Push(item)                 // добавить элемент
stack.TryPop(out item)           // удалить вершину
stack.TryPeek(out item)          // прочитать вершину
stack.PushRange(items)           // атомарно добавить несколько элементов
stack.TryPopRange(items)         // атомарно удалить несколько элементов
stack.IsEmpty                    // проверить пустоту
stack.Count                      // подсчитать элементы
```


### 3. `ConcurrentQueue`

- упорядочена
- связный список сегментов 
- один сегмент - кольцевой массив
- `Enqueue` и `Dequeue` используют `CompareExchange` и `SpinWait`
- при записи и чтении в разных сегментах блокировки не происходит

#### Основные члены

```cs
queue.Enqueue(item)             // добавить в конец
queue.TryDequeue(out item)      // удалить из начала
queue.TryPeek(out item)         // прочитать первый элемент
queue.IsEmpty                   // проверить пустоту
queue.Count                     // получить количество элементов
queue.ToArray()                 // получить снимок
```


### 4. `ConcurrentDictionary`

- массив бакетов, каждый бакет - односвязный список
- используется массив локов, каждый из которых отвечает за группу бакетов 

Обозначения:

- `N` — количество элементов
- `B` — количество бакетов
- `K` — количество внутренних блокировок
- `B₀` — начальное количество бакетов, восстанавливаемое после `Clear()`

| Операция       | Время          | Дополнительная память | Блокировки |
| -------------- | -------------- | --------------------- | ---------- |
| `ContainsKey`  | `O(1)`         | `O(1)`                | `0`        |
| `TryGetValue`  | `O(1)`         | `O(1)`                | `0`        |
| `TryAdd`       | `O(1)`         | `O(1)`                | `1`        |
| `TryRemove`    | `O(1)`         | `O(1)`                | `1`        |
| `TryUpdate`    | `O(1)`         | `O(1)`                | `1`        |
| `Clear`        | `O(B + K)`     | `O(B₀ + K)`           | `K`        |
| `Count`        | `O(K)`         | `O(1)`                | `K`        |
| `IsEmpty`      | `O(B + K)`     | `O(1)`                | `K`        |
| `Keys`         | `O(B + N + K)` | `O(N)`                | `K`        |
| `Values`       | `O(B + N + K)` | `O(N)`                | `K`        |
| Полный перебор | `O(B + N)`     | `O(1)`                | `0`        |

# 2. Терминология

**Многопоточность** - это организация выполнения программы с использованием нескольких потоков внутри одного процесса

**Параллелизм** — это физически одновременное выполнение нескольких задач на разных логических процессорах

**Асинхронность** — это организация выполнения, при которой операция может приостановиться на время ожидания, не блокируя поток, и продолжиться позже

---

## 2.1. `Thread`

Виды потоков в .NET:

1. Managed:
	- создаются рантаймом
	- выполняют управляемый код
	- принадлежат Thread Pool-у
	- или созданы через `new Thread()`


2. Unmanaged:
	- не контролируются рантаймом 
	- выполняют неуправляемый код
	- не останавливаются во время фаз GC

---

## 2.2 `Thread Pool`

- ﻿﻿Механизм, управляющий потоками, выполняющий «единицы работы» (делегаты), сохраняя при этом баланс в количестве созданных потоков за счёт их переиспользования
	  
- ﻿﻿Собирает аналитику, чтобы оптимальней управлять количеством потоков
	  
- ﻿﻿Два вида потоков: WorkerThreads и I/O completion threads
	  
- ﻿﻿Количество потоков всегда в диапазоне между настройками  
    MinThreads и MaxThreads, но не менее количества логических  
    ядер и не более некоторого ограничения, зависящего от платформы
	
- ﻿﻿Все потоки background и равноприоритетные
	
- CPU нагрузкой (вычислительная нагрузка на процессор) и с I/O нагрузкой (ожидение ответа от периферии)

### Очереди задач в Thread Pool

1. ﻿﻿﻿Локальная очередь потока                                                                 
2. ﻿﻿﻿Очередь высокоприоритетных задач
3. ﻿﻿﻿Глобальная очередь завязанных на конкретный поток задач    
4. ﻿﻿﻿Глобальная очередь

### Порядок поиска задачи потоком `ThreadPool`

Упрощённо свободный поток ищет работу в таком порядке:

1. **Собственная локальная очередь** — задачи извлекаются в порядке `LIFO`
2. **Высокоприоритетная очередь** — внутренняя срочная работа рантайма
3. **Очередь задач, привязанных к текущему потоку** — если такие задачи есть
4. **Глобальная очередь** — общие задачи, обычно обрабатываемые в порядке `FIFO`
5. **Очереди задач, привязанных к другим потокам** — выбирается доступная задача
6. **Локальная очередь другого потока** — поток крадёт старую задачу с противоположного конца очереди

### Hill Climbing

**Hill Climbing** — адаптивный алгоритм `ThreadPool`, который подбирает количество активных рабочих потоков для достижения максимальной пропускной способности

- периодически измеряет количество завершённых задач за единицу времени
- изменяет количество активных потоков небольшими волнами
- сравнивает изменение числа потоков с изменением пропускной способности
- если дополнительные потоки повышают производительность — увеличивает их количество
- если производительность снижается — уменьшает их количество
- использует частотный анализ с компонентами Фурье, чтобы отделить эффект изменения потоков от шума нагрузки
- учитывает загрузку процессора и не добавляет потоки при слишком высокой загрузке CPU
- работает в пределах установленных `MinThreads` и `MaxThreads`
- управляет целевым количеством активных потоков, а не изменяет само значение `MaxThreads`
- может быть отключён 

Алгоритм не предсказывает будущую нагрузку по размеру очереди, а постоянно адаптируется по результатам уже выполненной работы

# 3. `Task`

`Task` позволяет работать с операциями, абстрагируясь от управления потоками напрямую

- представляет выполняемую или будущую операцию
- позволяет запускать работу
- хранит состояние выполнения
- поддерживает отмену через `CancellationToken`
- хранит результат в `Task<TResult>`
- сохраняет исключение при неуспешном завершении
- позволяет дождаться завершения синхронно или асинхронно

---

## 3.1. `TaskScheduler`

`TaskScheduler` — абстракция, определяющая, где и как будет выполняться `Task`

- управляет постановкой задач на выполнение
- стандартный `TaskScheduler.Default` использует `ThreadPool`
- `TaskScheduler.Current` возвращает планировщик текущей задачи
- пользовательский планировщик может задавать порядок выполнения, отдельный поток или ограничение параллелизма
- не управляет процессорным временем — этим занимается планировщик ОС

```
Task → TaskScheduler → ThreadPool → поток ОС → процессор
```

---

## 3.2. Создание/запуск задач

### 1. Конструктор `Task`

Создаёт задачу, но не запускает её

```cs
Task task = new Task(
    action: Work,
    cancellationToken: token,
    creationOptions: TaskCreationOptions.None
)

task.Start()
```

Параметры:

- `Action action` — выполняемая работа
- `CancellationToken cancellationToken` — токен отмены
- `TaskCreationOptions creationOptions` — настройки создания задачи

Если задачу не запустить через `Start()`, она останется в состоянии `Created`

---

### 2. `Task.Factory.StartNew`

Создаёт и сразу планирует задачу на выполнение

```cs
Task task = Task.Factory.StartNew(Work)
```

Полная форма:

```cs
Task task = Task.Factory.StartNew(
    action: Work,
    cancellationToken: token,
    creationOptions: TaskCreationOptions.None,
    scheduler: TaskScheduler.Default
)
```

Позволяет явно передать:

- выполняемую работу
- состояние
- токен отмены
- параметры создания
- планировщик задач

Применяется, когда нужен более точный контроль над созданием задачи

---

### 3. `Task.Run`

Создаёт и сразу запускает задачу через стандартный планировщик и `ThreadPool`

```cs
Task task = Task.Run(Work)

Task<int> resultTask = Task.Run(Calculate)

Task task = Task.Run(Work, token)
```

Это основной способ отправить CPU-bound работу в `ThreadPool`

---

### 4. `TaskCreationOptions`

```cs
[Flags]
public enum TaskCreationOptions
{
    None = 0,
    // Стандартное поведение без дополнительных настроек

    PreferFairness = 1,
    // Просит планировщик выполнять задачи примерно в порядке постановки
    // Обычно задача помещается в глобальную очередь ThreadPool

    LongRunning = 2,
    // Сообщает о длительной работе
    // Стандартный планировщик обычно создаёт отдельный поток вне ThreadPool

    AttachedToParent = 4,
    // Присоединяет задачу к родительской
    // Родитель не завершится, пока не завершится дочерняя задача

    DenyChildAttach = 8,
    // Запрещает дочерним задачам присоединяться к текущей задаче

    HideScheduler = 16,
    // Скрывает текущий TaskScheduler от кода внутри задачи
    // TaskScheduler.Current будет возвращать TaskScheduler.Default

    RunContinuationsAsynchronously = 64
    // Не позволяет продолжениям выполняться прямо в потоке завершения задачи
    // Продолжения ставятся на асинхронное выполнение
}
```

---

### 5. Пользовательский `TaskScheduler`

Позволяет выполнить задачу через нестандартный планировщик

```cs
Task task = Task.Factory.StartNew(
    action: Work,
    cancellationToken: CancellationToken.None,
    creationOptions: TaskCreationOptions.None,
    scheduler: customScheduler
)
```

Также можно создать связанную с ним фабрику:

```cs
TaskFactory factory = new(customScheduler)
Task task = factory.StartNew(Work)
```

---

### 6. Дочерняя задача

```cs
Task parent = Task.Factory.StartNew(() =>
{
    Task child = Task.Factory.StartNew(
        Work,
        TaskCreationOptions.AttachedToParent
    )
})
```

`AttachedToParent` связывает завершение дочерней задачи с родительской: родитель считается завершённым только после завершения присоединённых задач

---

## 3.3 Отмена задач

### `CancellationTokenSource`

Управляет состоянием отмены и создаёт токен.

```cs
using var source = new CancellationTokenSource()

CancellationToken token = source.Token
```

С автоматической отменой по таймауту:

```cs
using var source = new CancellationTokenSource(TimeSpan.FromSeconds(10))
```

Основные методы:

```cs
source.Cancel()
// Немедленно запросить отмену

source.CancelAfter(TimeSpan.FromSeconds(10))
// Запросить отмену через указанное время
```

`Cancel()` устанавливает состояние отмены и вызывает зарегистрированные обработчики, но не останавливает операцию принудительно.

### `CancellationToken`

Передаётся по всей цепочке отменяемых методов.

```cs
await LoadAsync(token)
await SaveAsync(token)
```

Основные члены:

```cs
token.IsCancellationRequested
// Проверить, запрошена ли отмена

token.ThrowIfCancellationRequested()
// Выбросить OperationCanceledException при отмене

token.Register(callback)
// Зарегистрировать действие, вызываемое при отмене

token.CanBeCanceled
// Может ли этот токен быть отменён
```

### Связанные токены

Объединяют несколько причин отмены.

```cs
using var source =
    CancellationTokenSource.CreateLinkedTokenSource(
        requestToken,
        shutdownToken
    )

source.CancelAfter(TimeSpan.FromSeconds(10))

await WorkAsync(source.Token)
```

Итоговый токен отменится при отмене любого исходного токена или по таймауту.

### Проверка токена

При длительных вычислениях токен проверяют периодически:

```cs
void Process(CancellationToken token)
{
	if (token.IsCancellationRequested)
	{
		token.ThrowIfCancellationRequested();
	}
	
    for (int i = 0; i < 1000; i++)
    {
        token.ThrowIfCancellationRequested()

        ProcessItem(i)
    }
}
```

Для цикла, который должен работать до отмены (например какой нибудь консьюмер):

```cs
while (!token.IsCancellationRequested)
{
    DoWork()
}

token.ThrowIfCancellationRequested()
```

Отменяемым операциям токен достаточно передать дальше:

```cs
await Task.Delay(1000, token)
await semaphore.WaitAsync(token)
await httpClient.GetAsync(url, token)
```

## 3.4. Состояние `Task`

Текущее состояние задачи хранится в свойстве:

```cs
TaskStatus status = task.Status
```

```cs
public enum TaskStatus
{
	// Основные:
	
    Created,           // Создана, но не запущена    
    Running,           // Выполняется
    Canceled,          // Отменена
    Faulted,           // Завершилась с исключением 
    RanToCompletion,    // Успешно завершена
    
    // Остальные:
    
    WaitingForActivation,
    // Ожидает активации или завершения другой операции
	
    WaitingToRun,
    // Передана TaskScheduler и ожидает выполнения
	
    WaitingForChildrenToComplete
    // Ожидает завершения присоединённых дочерних задач
}
```

~~~mermaid
    A[Created] --> B[Running]
    B --> C[Faulted]
    B --> D[RanToCompletion]
    B --> E[Canceled]
~~~

## 3.5 Получение результата

### 3.5.1. Синхронное получение результата

~~~mermaid
flowchart LR
    A[Поток 1] --> B[Task]
    B --> C[Результат]
    C --> D[Поток 1]
~~~

Это плохой вариант, такого надо избегать. 

Пример:

```cs
using var httpClient = new HttpClient()

Task<string> requestTask =
    httpClient.GetStringAsync("https://example.com")

Console.WriteLine("Запрос запущен")

string response = requestTask.Result
// Если Task не завершён, текущий поток блокируется

Console.WriteLine(response.Length)
```

`Result` синхронно получает значение из `Task<TResult>`

- если задача уже завершена, результат возвращается сразу
- если задача не завершена, текущий поток блокируется до её завершения
- поток не выполняет другую работу, хотя HTTP-запрос ожидается асинхронно
- исключение возвращается обёрнутым в `AggregateException`

Другие способы синхронного ожидания:

```cs
task.Wait()
// Блокирует поток до завершения задачи

Task.WaitAll(firstTask, secondTask)
// Блокирует поток до завершения всех задач

int index = Task.WaitAny(firstTask, secondTask)
// Блокирует поток до завершения одной задачи
// Возвращает её индекс
```

### 3.5.2 Асинхронное получение результата

Асинхронное ожидание не блокирует вызывающий поток. После завершения операции выполняется продолжение, возможно на другом потоке

Два способа:

- Callback (`ContinueWith`) — явная регистрация продолжения
- `async/await` — продолжение создаётся компилятором и записывается в последовательном виде

##### 1. Callback

```cs
using var httpClient = new HttpClient()
using var source = new CancellationTokenSource()

CancellationToken token = source.Token

// Запускаем HTTP-запрос и сразу получаем Task<string>
// Вызывающий поток не блокируется
Task<string> requestTask =
    httpClient.GetStringAsync("https://example.com", token)

// Регистрируем callback, который запустится после успешного завершения requestTask
// ContinueWith создаёт и возвращает новую задачу Task<int>
Task<int> lengthTask = requestTask.ContinueWith(
    continuationFunction: completedTask =>
    {
        // Исходная задача уже успешно завершена
        // Поэтому Result возвращается сразу и не блокирует поток
        string response = completedTask.Result
	
        Console.WriteLine("Ответ получен")
	
        // Возвращаем результат продолжения
        return response.Length
    },
	
    // Может отменить запуск продолжения
    cancellationToken: token,
	
    // Callback запускается только при успешном завершении requestTask
    continuationOptions: TaskContinuationOptions.OnlyOnRanToCompletion,
	
    // Продолжение выполняется через стандартный планировщик и ThreadPool
    scheduler: TaskScheduler.Default
)

// Регистрируем следующий callback
// Он запустится после успешного завершения lengthTask
Task printTask = lengthTask.ContinueWith(
    continuationAction: completedTask =>
    {
        // completedTask здесь имеет тип Task<int>
        int length = completedTask.Result
	
        Console.WriteLine($"Размер ответа: {length}")
    },
	
    cancellationToken: token,
	
    continuationOptions: TaskContinuationOptions.OnlyOnRanToCompletion,
	
    scheduler: TaskScheduler.Default
)

// Ожидаем завершения всей цепочки без блокировки текущего потока
await printTask
```

##### 2. AsyncAwait

`async` позволяет использовать `await`. Асинхронный метод обычно возвращает:

```cs
Task       // операция без результата
Task<T>    // операция с результатом типа T

void       // стоит избегать, поскольку такой метод нельзя await-ить, и нельзя
           // ловить из него исключения 
```

```cs
static readonly HttpClient httpClient = new()

async Task<string?> PostAsync<T>(
    string url,
    T content,
    CancellationToken token)
{
    // Запускаем HTTP-запрос и асинхронно ожидаем ответ
    // Текущий поток во время ожидания не блокируется
    HttpResponseMessage response =
        await httpClient.PostAsJsonAsync(url, content, token)

    if (!response.IsSuccessStatusCode)
        return null

    // Асинхронно читаем тело ответа
    string result =
        await response.Content.ReadAsStringAsync(token)

    // Возвращаем string, а компилятор завершает Task<string?>
    // этим значением
    return result
}
```

В `async Task<T>` возвращается обычный `T`, а не `Task<T>`:

```cs
async Task<int> CalculateAsync()
{
    await Task.Delay(1000)

    return 42
    // Компилятор оборачивает 42 в результат Task<int>
}
```

## 3.6. `SynchronizationContext`

- Абстракция, определяющая, где выполняются callbacks и продолжения после `await`
- Реализация зависит от среды выполнения
- Специальные контексты используются в WPF, WinForms, .NET MAUI и Xamarin
- В ASP.NET Core специального `SynchronizationContext` нет
- При отсутствии контекста продолжение выполняется через `ThreadPool`

---

## Промежуточный итог

- ﻿﻿За то, где будет выполнена задача внутри `Task`, отвечает  `TaskScheduler`
	
- ﻿﻿По умолчанию `TaskScheduler` = `ThreadPoolTaskScheduler`  
		
    - Он запускает делегаты в `ThreadPool`  
    - при `TaskCreationOptions.LongRunning` в отдельном потоке
    
- ﻿﻿`SynchronizationContext` задаётся для потока. Указывает, где выполнится код после `await`, по умолчанию - в `ThreadPool`
	
- ﻿﻿`Task.ConfigureAwait(false)` говорит игнорировать `SynchronizationContext` и специфический `TaskScheduler` и ставит продолжение выполнения в `ThreadPool`

# 4. Машина состояний `async/await`

```cs
async Task<string> LoadAsync()
{
    Console.WriteLine("Код до await");
    
    string result = await LoadDataAsync()
	
    Console.WriteLine("Код после await");
    
    return result.ToUpper()
}
```


### Основная логика:

- до `await` метод выполняется как обычный синхронный код
- если ожидаемый `Task` уже завершён, приостановки нет
- если `Task` не завершён, сохраняются состояние метода и данные, необходимые после `await`
- метод возвращает вызывающему коду свой незавершённый `Task`
- после завершения операции продолжение отправляется в захваченный `SynchronizationContext`, нестандартный `TaskScheduler` либо выполняется через обычную инфраструктуру `ThreadPool`
- затем выполняется код после `await`, а возвращённый методом `Task` завершается
