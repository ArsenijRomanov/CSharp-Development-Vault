**BASE** — подход к проектированию распределённых систем, который отдаёт приоритет доступности и масштабируемости, допуская временную неконсистентность данных

```
B — Basically Available
S — Soft State
E — Eventual Consistency
```

BASE — не строгий стандарт, а набор архитектурных принципов

## Basically Available

**Базовая доступность** — система старается продолжать обслуживать запросы даже при отказах узлов или разрыве сети

При этом ответ может быть:

- основан на устаревших данных
- получен только от доступной части кластера
- частично ограничен по функциональности
- обработан позже через очередь

```
Реплика A недоступна
Реплика B доступна

Клиент → B → получает ответ
```

Это не обязательно формальная `Availability` из CAP, а более общее практическое стремление сохранять работоспособность

## Soft State

**Мягкое состояние** — состояние системы может изменяться без нового пользовательского запроса

Причины:

- асинхронная репликация
- истечение TTL
- фоновое разрешение конфликтов
- повторная доставка сообщений
- восстановление отставших реплик

## Eventually Consistent

**Консистентность в конечном счёте** — если новые изменения перестанут поступать, все реплики со временем сойдутся к одному состоянию

При этом eventual consistency сама по себе не гарантирует:

- когда именно реплики сойдутся
- что чтения будут монотонными
- что клиент сразу увидит собственную запись
- что конфликты разрешатся ожидаемым бизнесом способом

## BASE и ACID

```
ACID
→ строгие транзакционные гарантии
→ изменения применяются атомарно
→ сильнее согласованность

BASE
→ доступность и масштабируемость
→ асинхронное согласование
→ временная неконсистентность
```

Они не являются абсолютными противоположностями

## Связь с CAP и PACELC

BASE обычно ассоциируется с системами, которые делают выбор в сторону:

```
CAP:     AP
PACELC:  PA/EL
```
