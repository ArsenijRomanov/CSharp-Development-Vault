**Двухфазный коммит** — протокол атомарного завершения распределённой транзакции между несколькими независимыми участниками

Цель:

```
Либо все участники фиксируют изменения
Либо все участники откатывают изменения
```

## Участники протокола

- **Coordinator** — управляет транзакцией и принимает итоговое решение
- **Participants** — базы данных или сервисы, выполняющие локальные транзакции

## Фаза 1 — Prepare

Координатор спрашивает каждого участника, готов ли тот зафиксировать транзакцию:

```
Coordinator → PREPARE → Participant A
Coordinator → PREPARE → Participant B
```

Каждый участник:

1. Выполняет изменения внутри локальной транзакции
2. Проверяет ограничения
3. Записывает состояние транзакции в журнал
4. Блокирует необходимые ресурсы
5. Отвечает `YES` или `NO`

```
Participant A → YES
Participant B → YES
```

После ответа `YES` участник обещает:

> Я смогу выполнить `COMMIT`, даже если процесс будет перезапущен

При этом изменения ещё не считаются окончательно зафиксированными

## Фаза 2 — Commit или Rollback

### Все ответили `YES`

Координатор принимает решение:

```
GLOBAL COMMIT
```

И отправляет его участникам:

```
Coordinator → COMMIT → Participant A
Coordinator → COMMIT → Participant B
```

Участники фиксируют локальные транзакции и освобождают ресурсы

### Кто-то ответил `NO`

Координатор принимает решение:

```
GLOBAL ROLLBACK
```

```
Coordinator → ROLLBACK → Participant A
Coordinator → ROLLBACK → Participant B
```

Все участники отменяют подготовленные изменения

## Проблемы в ходе выполнения 2PC

- **Участник недоступен до `PREPARE`** — координатор не может получить согласие и обычно инициирует откат
	
- **Участник отвечает `NO`** — вся распределённая транзакция должна быть отменена
	  
- **Участник падает до отправки ответа** — координатор не знает, успел ли участник подготовиться
	  
- **Участник падает после ответа `YES`** — после восстановления он обязан сохранить состояние `PREPARED` и ждать решения
	  
- **Координатор падает до принятия решения** — участники могут не знать, будет `COMMIT` или `ROLLBACK`
	  
- **Координатор падает после принятия решения** — часть участников могла получить решение, а часть ещё нет
	  
- **Теряется `PREPARE`** — участник не начинает подготовку, а координатор ждёт ответ
	  
- **Теряется ответ `YES` или `NO`** — координатор не знает состояние участника
	  
- **Теряется `COMMIT` или `ROLLBACK`** — участник остаётся в `PREPARED`, пока не получит решение повторно
	  
- **Участник зависает в `PREPARED`** — он уже обещал выполнить решение и не может самостоятельно откатиться
	  
- **Решение доставляется участникам в разное время** — одни уже завершили транзакцию, другие ещё удерживают ресурсы
	  
- **После сбоя нужно восстановление из журнала** — координатор и участники должны восстановить состояние транзакции
	  
- **Транзакция остаётся зависшей** — иногда требуется ручное определение итогового решения

## Общие проблемы 2PC

- **Блокирующий протокол** — после `PREPARE` участники вынуждены ждать итогового решения
	  
- **Долгое удержание ресурсов** — блокировки, соединения и память остаются занятыми до завершения протокола
	  
- **Низкая отказоустойчивость** — координатор выступает единой точкой отказа
	  
- **Потеря доступности при partition** — без связи участники не могут безопасно продолжить работу
	  
- **Высокая задержка** — требуется минимум две фазы и несколько сетевых обменов
	  
- **Плохая масштабируемость** — чем больше участников, тем выше вероятность отказа и время ожидания
	  
- **Требование поддержки `PREPARE`** — каждый ресурс должен уметь хранить подготовленную транзакцию
	  
- **Сложное журналирование** — состояние и решения должны надёжно сохраняться на диске
	  
- **Сложное восстановление** — после сбоя нужно разбираться, на каком этапе находилась каждая транзакция
	  
- **Риск накопления зависших транзакций** — они могут долго удерживать блокировки и мешать другим операциям
	  
- **Плохо подходит для долгих процессов** — бизнес-операции могут длиться минуты или часы, а ресурсы нельзя держать так долго
	  
- **Плохо подходит для микросервисов** — сервисы могут использовать разные БД и не поддерживать общий транзакционный протокол
