**Теорема CAP** — эвристическое утверждение о том, что в любой реализации распределённых вычислений возможно обеспечить не более двух из трёх следующих свойств:

- Consistency (согласованность данных) — во всех вычислительных узлах в один момент времени данные не противоречат друг другу ([[Модели консистентности#1. Линеаризуемость|линеаризуемость]])
	
- Availability (доступность) — любой запрос к распределённой системе за конечное время завершается откликом, однако без гарантии, что ответы всех узлов системы совпадают
	
- Partition tolerance (устойчивость к фрагментации) — способность распределённой системы сохранять заданный контракт при потере связи между группами узлов

## Доказательство Гильберта-Линч

Рассмотрим распределённый регистр `x` с начальным значением `0`.

Сеть разделена на две изолированные части:

```
G₁    ×    G₂
```

Сообщения между `G₁` и `G₂` не доставляются.

Предположим, что система одновременно обеспечивает `C`, `A` и `P`.

1. В `G₁` выполняется операция:

```
Write(x, 1)
```

По свойству `A` запись должна завершиться.

2. После завершения записи в `G₂` выполняется:

```
Read(x)
```

По свойству `A` чтение также должно завершиться.

3. `G₂` не получил информации о записи в `G₁`. Для `G₂` неразличимы два исполнения:

```
E₁: в G₁ произошла Write(x, 1)
E₂: запись не происходила
```

В исполнении `E₂` чтение обязано вернуть `0`. Следовательно, в `E₁` узел `G₂` также должен вернуть `0`, поскольку его локальное состояние идентично.

4. В исполнении `E₁` запись `Write(x, 1)` завершилась до начала `Read(x)`. По линеаризуемости чтение обязано вернуть `1`.

Получаем противоречие:

```
Read(x) = 0 — из неразличимости исполнений
Read(x) = 1 — из линеаризуемости
```

Следовательно, при разделении сети невозможно одновременно гарантировать `C` и `A`.

## Вывод

При наличии partition система должна выбрать:

```
CP: отказать или заблокировать часть запросов ради линеаризуемости
AP: завершать запросы, допуская временное рассогласование данных
```

# Варианты поведения

## 1. `CP` — Consistency + Partition Tolerance

При partition система сохраняет согласованность, но отказывает в обслуживании части запросов

```
Нет связи с кворумом
        ↓
Запрос не выполняется
        ↓
Расхождения данных нет
```

Типичное поведение:

- запись разрешена только лидеру
- для подтверждения требуется кворум
- меньшая часть кластера перестаёт принимать изменения
- запрос может завершиться ошибкой или таймаутом

### Пример с PostgreSQL

При синхронной репликации primary может ждать подтверждения от требуемой standby перед подтверждением `COMMIT`

```
Primary → отправляет WAL → Standby
Primary ← ожидает ACK  ← Standby
```

Если связь потеряна и обязательного подтверждения нет, `COMMIT` продолжает ждать

```
Сохраняем C
Теряем A
Получаем CP-поведение
```

## 2. `AP` — Availability + Partition Tolerance

При partition обе части системы продолжают обслуживать запросы, временно допуская расхождение

```
До partition:

A: x = 0
B: x = 0

Во время partition:

A принимает Write x = 1
B принимает Write x = 2
```

После восстановления связи система должна разрешить конфликт:

```
A: x = 1
B: x = 2
        ↓
правило разрешения конфликта
        ↓
A: x = 2
B: x = 2
```

### Пример с Cassandra

Cassandra позволяет настраивать число реплик, необходимое для подтверждения каждой операции

При низком consistency level, например `ONE`, запрос может завершиться после ответа одной реплики:

```
Одна реплика доступна
        ↓
Запрос выполняется
        ↓
Другие реплики могут временно отставать
```

Это повышает доступность, но допускает устаревшие чтения и временное расхождение реплик. Cassandra затем использует механизмы восстановления и согласования данных. При кворумных настройках система может сдвигаться в сторону более сильной консистентности ценой доступности.

## 3. `CA` — Consistency + Availability

`CA` возможно только при условии, что сетевое разделение исключено или не рассматривается

Пример:

```
Клиенты → один экземпляр базы данных
```

Пока сервер работает:

- данные согласованы
- запросы обслуживаются

Но это не partition-tolerant распределённое хранилище

Для распределённой системы `CA` можно считать нормальным режимом работы до возникновения partition:

```
Сеть работает → C + A

Partition произошёл:
    сохраняем C → становимся CP
    сохраняем A → становимся AP
```

Поэтому выражение «выбрать CA» обычно означает:

> система обеспечивает консистентность и доступность, пока сеть исправна, но не обещает продолжать работу при разделении

# Итог

```
CAP не говорит:
«Всегда выбери любые две буквы»

CAP говорит:
«Когда сеть разделилась, невозможно одновременно
гарантировать строгую консистентность и доступность»
```

```
CP
    → не отвечаем без достаточного согласования
    → сохраняем актуальное единое состояние

AP
    → продолжаем отвечать
    → временно допускаем разные состояния

CA
    → применимо, пока partition исключён
    → при реальном partition всё равно придётся выбрать C или A
```
