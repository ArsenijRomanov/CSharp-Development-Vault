
**Причинная согласованность** — модель согласованности, при которой система сохраняет **причинно-следственный порядок операций**: если операция $A$ могла повлиять на $B$, то все узлы должны наблюдать $A$ раньше $B$.

## 1. Причинный порядок

Причинность задаётся отношением **happens-before** ($\rightarrow$).

Это наименьшее (по включению множества пар) транзитивное отношение, для которого выполняются правила:

1. **Порядок внутри одного процесса**  
   Если событие $A$ произошло раньше $B$ в одной последовательности выполнения, то:
   $A \rightarrow B$
	>   
	 Процесс (в контексте исходной модели Лампорта) — это множество событий, снабжённое априорно заданным полным порядком (локальным, в рамках одного процесса он полный), определяющим последовательность событий внутри данного процесса.

2. **Передача информации**  
   Если $B$ наблюдает результат $A$ — например, получает отправленное $A$ сообщение или читает записанное $A$ значение, то:
   $A \rightarrow B$

> В строгой модели Лампорта **передача сообщения** — это связь между двумя событиями разных процессов:
> 	• событие `send(m)` в процессе-отправителе
> 	• соответствующее событие `receive(m)` в процессе-получателе
>Для каждого сообщения `m` вводится отношение: 
	  $send(m) \rightarrow receive(m)$

3. **Транзитивность**  
   Если  $A \rightarrow B$  и  $B \rightarrow C$,  то  $A \rightarrow C$

Если не выполняется ни $A \rightarrow B$, ни $B \rightarrow A$, события считаются **конкурентными**: $A || B$, и их взаимный порядок не обязан совпадать на всех узлах.

Причинная согласованность требует, чтобы все узлы соблюдали порядок: если $A \rightarrow B$, система не должна позволять наблюдать $B$, не наблюдая предшествующее ему $A$.

### Частичное упорядочение

Отношение $\rightarrow$ задаёт **частичный порядок**:

- причинно связанные операции упорядочены
- конкурентные операции могут оставаться несравнимыми

В отличие от этого линеаризуемость задаёт **полный порядок** всех операций.

Хорошая аналогия — история Git: внутри ветки версии имеют причинный порядок, но независимые ветки могут развиваться параллельно и сравниваться только после объединения.

### Зачем ослаблять линеаризуемость

Полный глобальный порядок требует координации между узлами и может снижать производительность и доступность при сетевых задержках и разделениях.

Причинная согласованность сохраняет важные зависимости, но не требует согласовывать порядок независимых операций.

> Причинная согласованность — наиболее сильная модель согласованности, которая может сохранять доступность при сетевых разделениях без необходимости глобальной координации каждой операции.

## 2. Временные метки Лампорта

**Временные метки Лампорта** — механизм логического времени, позволяющий упорядочивать события в распределённой системе и построить полный порядок.

Каждый узел хранит локальный счётчик `c`:

```
1. Перед локальной операцией:
   c = c + 1

2. При отправке сообщения:
   к сообщению прикладывается c

3. При получении сообщения с меткой t:
   c = max(c, t) + 1
```

Главная гарантия:  $A \rightarrow B \Rightarrow L(A) < L(B)$

Если событие $B$ причинно зависит от $A$, его метка обязательно будет больше.

Обратное неверно:  $A \rightarrow B \not\Rightarrow L(A) < L(B)$

Поэтому по меткам Лампорта **нельзя определить, были ли события причинно связаны или конкурентны**.

Для построения полного порядка при одинаковых значениях счётчика можно использовать идентификатор узла:

```
(timestamp, nodeId)

(5, 1) < (5, 2)
```

> [!note] Временные метки Лампорта и векторы версий
> **Lamport timestamp**
> - хранит одно число на узел
> - позволяет построить порядок операций
> - метаданные имеют постоянный размер
> - хорошо масштабируется по числу узлов
> - не позволяет определить конкурентность событий
>
> **Version vector**
> - хранит отдельный счётчик для каждого узла
> - позволяет определить причинное предшествование и конкурентные версии
> - требует больше метаданных, размер которых растёт с числом участников
>
> Главное преимущество векторов версий — возможность отличить:
>  $A \rightarrow B$ от $A || B$
>
> Метки Лампорта этого различия не сохраняют

## 3. Ограничение временных меток Лампорта

Метки Лампорта позволяют однозначно упорядочить уже известные операции, но не позволяют узлу понять, что он уже получил все операции, которые должны находиться раньше текущей.

Например, увидев операцию с меткой `10`, узел не знает, не существует ли ещё не доставленной операции с меткой `8`.

Следовательно, для принятия решения недостаточно иметь полный порядок — необходимо также знать, что соответствующий префикс порядка окончателен и новые операции уже не смогут быть вставлены перед ним.
