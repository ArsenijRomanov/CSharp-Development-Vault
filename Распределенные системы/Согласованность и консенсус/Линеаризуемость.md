
**Линеаризуемость** — модель согласованности, при которой распределённая система внешне ведёт себя так, как будто существует **единственная копия данных**, а каждая операция чтения или записи выполняется **атомарно в некоторый момент времени** между её началом и завершением.

## Основная гарантия

Если запись успешно завершилась, то любое чтение, начавшееся **после завершения этой записи**, уже должно вернуть последнее актуальное значение (гарантия актуальности)

## Порядок операций

Для всех операций можно построить единый последовательный порядок, причём он должен быть согласован с реальным временем:

Пусть начальное значение регистра `x = 0`, а клиент выполняет:

```
write(x, 1)
```

Линеаризуемая система предполагает, что где-то **между началом и завершением записи** существует единственный момент, в который значение атомарно меняется:

```
0 → 1
```

Чтение, завершившееся до начала записи, обязано вернуть `0`, а чтение, начавшееся после завершения записи, обязано вернуть `1`.

Чтения, которые выполняются **конкурентно с записью**, могут вернуть как старое, так и новое значение — в зависимости от того, по какую сторону точки линеаризации они оказались. Система, эмулирующая "единственную копию данных", так работать не должна.
![[Pasted image 20260929012757.png]]
Но есть дополнительное требование: как только какое-либо чтение вернуло новое значение `1`, все последующие чтения должны также возвращать `1`, даже если сама операция записи ещё формально не завершилась.

Недопустима история:

```
read → 1
read → 0
```

поскольку после наблюдения нового значения точка линеаризации записи уже должна считаться произошедшей.

> [!note] Линеаризуемость и сериализуемость
> - **Сериализуемость** — свойство изоляции транзакций, при котором результат конкурентного выполнения эквивалентен некоторому последовательному выполнению транзакций. Этот порядок не обязан совпадать с реальным временем
> - **Линеаризуемость** — гарантия для операций чтения и записи отдельного объекта: операции выглядят атомарными и соблюдают реальный порядок
>
> БД может обеспечивать обе гарантии одновременно — это называется **строгой сериализуемостью**
>
> **2PL** и фактическое последовательное выполнение обычно обеспечивают и сериализуемость, и линеаризуемость
>
> **SSI** сериализуема, но не линеаризуема: чтение выполняется из фиксированного снимка состояния, который может не содержать более свежие записи

## Где нужна линеаризуемость

- **Распределённые блокировки и выбор лидера**  
    Все узлы должны однозначно соглашаться, кто владеет блокировкой или является лидером, иначе возможен [[Распределенные системы/Согласованность и консенсус/Определения#^2|split-brain]]
    Примеры: ZooKeeper, etcd
    
- **Гарантии уникальности и глобальные ограничения**  
    Конкурентные операции должны атомарно определить единственного победителя  
    Примеры: уникальный username/email, отсутствие двойного бронирования, запрет отрицательного баланса, предотвращение продажи товара сверх остатка
    
- **Синхронизация через несколько каналов связи**  
    Если одна операция передаётся через разные системы, например БД и брокер собщений, обработчик не должен получить команду раньше, чем ему станет видна соответствующая запись  
    Линеаризуемое хранилище гарантирует чтение актуального состояния и устраняет такую гонку
    

> Линеаризуемость особенно нужна там, где несколько участников должны принимать решения на основании **единого актуального состояния** системы.

## Реализация линеаризуемых систем

#### 1. Репликация с одним ведущим узлом

Потенциально линеаризуема. Если операция записи обслуживется ведущим узлом или синхронно обновляемыми ведомыми, то они могут быть линеаризуемыми. 

Необходимо, чтобы всегда было известно, какой именно узел ведущий.

Также возможность линеаризуемости зависит от архитектуры СУБД. Если в ней используется SSI, линеаризуемости не будет.

#### 2. Консенсусные алгоритмы

Линеаризуемы. Отдельные алгоритмы имеют сходство с репликацией с одним ведущим узлом и содержат меры по предотвращению [[Распределенные системы/Согласованность и консенсус/Определения#^2|split-brain]] и использованию устаревших реплик, поэтому дают возможность безопасно реализовать линеаризуемые хранилища.

Так работают `ZooKeeper` и `etcd`.

#### 3. Репликация с несколькими ведущими узлами

Нелинеаризуема. Конкуретно обрабатывают операции записи на разных узлах и асинхронно реплицируют их на другие узлы. По этой причине в них могут появляться конфликты записи, чего не может быть в системе, эмулирующей "единственную копию данных".

#### 4. Репликация без ведущего узла

Можно получить линеаризуемость, но это сильно зависит от точной конфигурации кворумов и от того, как именно определяется сильная согласованность.

## Линеаризуемость и кворумы

Само условие строгого кворума  `w + r > n`  **не гарантирует линеаризуемость**.

Во время незавершённой записи разные реплики могут временно содержать разные версии:

```
R1 = 1
R2 = 0
R3 = 0
```

Первое чтение из кворума `{R1, R2}` может увидеть `1`, а более позднее чтение из `{R2, R3}` — вернуть `0`. Получается:

```
read A → 1
read B → 0
```

что нарушает линеаризуемость.

### Линеаризуемое чтение

Чтение должно не просто выбрать наиболее новую версию, а **синхронно распространить её на кворум перед возвратом результата**:

```
READ:
1. прочитать r реплик
2. определить наиболее новую версию
3. записать её обратно на кворум
4. только после этого вернуть значение
```

Например:

```
R1 = 1
R2 = 0

READ → latest = 1
write-back → R1 = 1, R2 = 1
return 1
```

Теперь любое последующее чтение кворума обязательно пересечётся с репликами, содержащими `1`, и не сможет вернуться к старому значению.

### Линеаризуемая запись

Перед записью необходимо сначала узнать последнее состояние кворума:

```
WRITE:
1. прочитать кворум
2. определить последнюю версию
3. создать более новую версию
4. записать её на кворум
5. вернуть подтверждение
```

То есть запись должна гарантированно продолжать уже существующий порядок версий, а не независимо создавать значение, которое потом может конфликтовать с другой записью.

При этом **линеаризуемый CAS (`compare-and-set`) таким способом уже не реализуется** — для атомарного выбора между конкурентными изменениями требуется консенсусный алгоритм.
