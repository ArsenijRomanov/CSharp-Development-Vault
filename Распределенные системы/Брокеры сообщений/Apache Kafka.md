# Роли нод в Kafka

Kafka-кластер состоит из нод, на которых запущены Kafka-процессы

Kafka-нода может выполнять одну или несколько ролей:

- **Broker** — хранит пользовательские данные и обслуживает producers и consumers
- **Controller** — управляет метаданными и состоянием кластера
- **Broker + Controller** — совмещает обе роли в одном процессе

---

# 1. Broker

**Брокер** — нода Kafka-кластера, которая принимает сообщения от продюсеров, хранит реплики партиций и отдаёт сообщения консьюмерам

### Функции брокера:

- ﻿﻿Приём сообщений продюсеров
- ﻿﻿Хранение сообщения для передачи консьюмерам
- ﻿﻿Выдача сообщений
- ﻿﻿Масштабирование
- Репликация
- Горизонтальное масштабирование хранения и обработки данных

---

# 2. Controller

**Контроллер** — управляющая нода Kafka-кластера, которая хранит метаданные кластера и координирует работу брокеров, партиций и реплик. Основная задача - поддержка консистентности.

### Функции контроллера:

- Регистрация брокеров в кластере
- Отслеживание доступности брокеров
- Создание и удаление топиков
- Создание партиций
- Распределение реплик партиций между брокерами
- Выбор лидеров партиций
- Перевыбор лидера при отказе брокера
- Управление составом ISR
- Перераспределение реплик между брокерами
- Управление конфигурацией кластера
- Координация штатного выключения брокеров
- Хранение и репликация метаданных кластера

В кластере работает несколько controller-нод, образующих KRaft-кворум

```
Controller 1 — active controller
Controller 2 — standby controller
Controller 3 — standby controller
```

### KRaft-кворум

**KRaft-кворум** — группа controller-нод, которая совместно хранит метаданные Kafka-кластера и выбирает активный контроллер

- Один контроллер является активным и принимает управляющие решения
- Остальные копируют журнал метаданных и готовы заменить активный контроллер
- Решение считается подтверждённым после согласия большинства контроллеров
- Для работы кворума должно быть доступно большинство его участников

# 3. Topic / Partition

**Топик** — логический канал в Kafka, в который продюсеры записывают сообщения и из которого консьюмеры их читают

Топик состоит из одной или нескольких партиций, распределённых между брокерами


**Партиция** — часть топика, представляющая собой упорядоченный append-only журнал сообщений, в котором каждое сообщение имеет уникальное смещение `offset`. По сути, это шард топика.

![[Pasted image 20260718030514.png]]

Партиции позволяют распределять данные топика между брокерами и обрабатывать сообщения параллельно.

Kafka гарантирует FIFO внутри одной партиции, но не топика.

### Встроенные стратегии партиционирования в `Confluent.Kafka`

Стратегия применяется продюсером, когда партиция не указана явно

```cs
public enum Partitioner
{
    Random,
    Consistent,
    ConsistentRandom,
    Murmur2,
    Murmur2Random
}
```

- `Random` — выбирает случайную партицию независимо от ключа
	
- `Consistent` — вычисляет `CRC32` от ключа, одинаковые ключи попадают в одну партицию, `null` и пустые ключи направляются в одну фиксированную партицию
	  
- `ConsistentRandom` — для ключа использует `CRC32`, а `null` и пустые ключи распределяет случайно
	  
- `Murmur2` — использует совместимый с Java Producer алгоритм `Murmur2`, одинаковые ключи попадают в одну партицию, `null` направляется в одну фиксированную партицию
	  
- `Murmur2Random` — для ключа использует `Murmur2`, а сообщения с `null`-ключом распределяет случайно

### Как Kafka хранит сообщение

Для каждого сообщения Kafka хранит:

- `Value` — полезная нагрузка сообщения
- `Key` — необязательный ключ для выбора партиции
- `Headers` — необязательные метаданные
- `Timestamp` — время создания или записи сообщения
- `Offset` — порядковая позиция сообщения внутри партиции

# 4. Репликация

**Репликация** — хранение нескольких копий каждой партиции на разных брокерах для защиты данных и продолжения работы при отказах

![[Pasted image 20260718035643.png]]


## 4.1. Replication factor

**Replication factor** — количество реплик каждой партиции, включая leader

Replication factor задаётся для топика, но применяется отдельно к каждой его партиции. При `replication.factor = 3` каждая партиция имеет три копии, обычно размещённые на разных брокерах.


## 4.2. Роли реплик

#### 1. Leader 

Основная реплика партиции

- Принимает сообщения от продюсеров
- Назначает сообщениям offset
- Обслуживает чтение консьюмеров
- Отслеживает состояние follower-реплик
- Управляет составом ISR

Для каждой партиции существует только один leader

#### 2. Follower

Резервная копия партиции, которая pull-ит данные от leader и копирует его журнал

Follower обычно не принимает записи непосредственно от продюсеров. При отказе leader одна из подходящих реплик может быть назначена новым leader.


## 4.3. ISR

**ISR — In-Sync Replicas** — набор актуальных реплик партиции, включая лидера, которые успевают копировать его данные. В случае падения лидера, любая из них может занять его место.

Если follower перестаёт регулярно получать данные или слишком долго не догоняет конец журнала leader, он удаляется из ISR. После синхронизации он может снова войти в ISR.


## 4.4. Out-of-sync replica

**Out-of-sync replica** — назначенная реплика, которая отстала от leader и в данный момент не входит в ISR

Out-of-sync replica продолжает пытаться догнать leader, но обычно не считается безопасным кандидатом на роль нового leader, поскольку может не содержать последние подтверждённые сообщения


## 4.5. Acknowledgements

**`acks`** — настройка продюсера, определяющая, сколько подтверждений должна получить запись перед тем, как отправка считается успешной

#### 1. `acks = 0` (None)

Продюсер не ждёт подтверждения от Kafka.

#### 2. `acks = 1` (Leader)

Leader сохраняет сообщение в собственный журнал и сразу отвечает продюсеру.

#### 3. `acks = -1` (All)

Leader ждёт подтверждения от всех реплик, которые в данный момент входят в ISR.

### min.insync.replicas

**`min.insync.replicas`** — минимальное количество реплик в ISR, необходимое для успешной записи при `acks=all`

Практическая надёжная конфигурация:

```
replication.factor = 3
min.insync.replicas = 2
acks = all
```

Она позволяет продолжать запись при потере одной реплики, но прекращает запись при потере двух, чтобы не подтверждать сообщения, существующие только в одной копии.

# 5. Producer

**Продюсер** — клиентское приложение или компонент, который формирует сообщения и отправляет их в выбранные топики Kafka. 

В ASP.NET Core `IProducer` регистрируется как `Singleton`

Продюсер не является частью Kafka-кластера и не обращается напрямую к контроллерам

Один экземпляр продюсера может отправлять сообщения в разные топики одного кластера, поскольку имя топика передаётся при каждой отправке

```cs
await producer.ProduceAsync(
    "orders.events",
    new Message<string, string>
    {
        Key = orderId,
        Value = payload
    });
```

## Путь сообщения через продюсер

~~~mermaid
%%{init: {"flowchart": {"nodeSpacing": 8, "rankSpacing": 14}, "themeVariables": {"fontSize": "11px"}}}%%

    A[Создание сообщения] --> B[Метаданные топика]

    D --> E[Локальный batch]
    E --> F[Сжатие batch]
    F --> G[Отправка leader-брокеру]
    G --> H[Ожидание ack]
    H --> I[Delivery report]
~~~

### 1. Получение метаданных

Продюсер получает у любого доступного брокера информацию:

- какие партиции существуют у топика
- какой брокер является leader каждой партиции
- какие брокеры сейчас доступны

Полученные метаданные кешируются и периодически обновляются.

### 2. Сериализация

Ключ и значение преобразуются в массивы байтов с помощью настроенных сериализаторов.

### 3. Выбор партиции

Партиция определяется [[#Встроенные стратегии партиционирования в `Confluent.Kafka`|стратегией партиционирования]].
### 4. Формирование batch

Сообщение добавляется во внутреннюю очередь выбранной партиции.

Batch формируется отдельно для каждой пары `топик + партиция`.

Продюсер отправляет batch, когда:

- достигнут максимальный размер batch
- истёк интервал `linger.ms`
- отправка была вызвана другими внутренними условиями

Объединение сообщений в batch уменьшает количество сетевых запросов и повышает пропускную способность.

### 5. Сжатие

При включённой компрессии сжимается сформированный batch.

Большие batch обычно обеспечивают более эффективное сжатие.

### 6. Отправка

Продюсер отправляет `ProduceRequest` напрямую брокеру, который является leader выбранной партиции.

### 7. Подтверждение

Leader записывает сообщения, выполняется репликация, после чего ответ зависит от настройки `acks`.

После успешной или неуспешной отправки продюсер формирует `DeliveryReport`, содержащий результат, партицию и offset сообщения.

# 6. Consumer

**Консьюмер** — клиентское приложение или компонент, который читает сообщения из партиций Kafka и выполняет над ними бизнес-обработку

Kafka использует **pull-модель** консьюмер сам запрашивает доступные данные

![[Pasted image 20260718064151.png]]

---

## 6.1. Создание консьюмера

```cs
var config = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",
    GroupId = "orders-handler",
    AutoOffsetReset = AutoOffsetReset.Earliest
};

using var consumer =
    new ConsumerBuilder<string, string>(config).Build();
```

Основные параметры:

- `BootstrapServers` — брокеры для первоначального подключения
- `GroupId` — идентификатор consumer group
- `AutoOffsetReset` — стартовая позиция при отсутствии корректного committed offset
- десериализаторы ключа и значения
- настройки offset commit
- настройки heartbeat и rebalance

`GroupId` определяет, к какой группе относится консьюмер, а `AutoOffsetReset` применяется только тогда, когда для партиции нет действительного сохранённого offset

### Подписка на топики

```cs
consumer.Subscribe("orders.events");
```

Можно подписаться на несколько топиков.

---

## 6.2. Consumer group

**Consumer group** — группа консьюмеров с одинаковым `GroupId`, совместно читающих топики и разделяющих между собой их партиции.

Консьюмер всегда принадлежит какой то группе.

Внутри одной группы одна партиция назначается не более чем одному консьюмеру одновременно.

Таким образом максимальный полезный параллелизм ограничен количеством партиций

При этом разные consumer groups читают топик независимо друг от друга, консьюмеры из разных групп могут читать одну и ту же партицию.

---

## 6.3. Group coordinator

Для каждой consumer group Kafka выбирает брокер, выполняющий роль **group coordinator**

Group coordinator:

- регистрирует участников группы
- отслеживает их состояние
- координирует распределение партиций
- инициирует rebalance
- принимает offset commits
- возвращает сохранённые offsets

---

## 6.4. Rebalance

**Rebalance** — перераспределение партиций между участниками consumer group

Rebalance может произойти, когда:

- новый консьюмер входит в группу
- консьюмер штатно выходит из группы
- консьюмер падает
- coordinator перестаёт получать heartbeat
- изменяется количество партиций
- изменяется подписка
- превышается допустимый интервал между вызовами `Consume`

### Подходы к ребалансировке

#### 1. Eager Rebalancing

Все консьюмеры временно отзывают все назначенные партиции, после чего Kafka полностью распределяет их заново

- отозвать все партиции
- остановить обработку группы
- выполнить новое назначение
- продолжить обработку

Плюсы:

- простая модель
- полное и однозначное перераспределение

Минусы:

- вся группа временно прекращает обработку
- даже неизменившиеся партиции отзываются и назначаются повторно


#### 2. Cooperative Incremental Rebalancing

Kafka отзыва﻿ет только те партиции, которые должны перейти другому консьюмеру

1. определить изменившиеся назначения
2. отозвать только перемещаемые партиции
3. передать их новым владельцам
4. остальные партиции продолжают обрабатываться

Плюсы:

- нет полной остановки группы
- меньше перемещений партиций
- короче пауза обработки

Минусы:

- перераспределение может происходить в несколько этапов
- модель сложнее eager-подхода


#### 3. Современный Consumer Protocol

Новый протокол consumer groups использует полностью инкрементальную ребалансировку и рассчитывает назначения на стороне брокера

- назначения рассчитывает брокер
- полностью incremental rebalancing

Новый Consumer Protocol доступен с Kafka 4.0, но пока включается явно через `group.protocol=consumer`

## 6.5. Heartbeat и контроль живости

Консьюмер поддерживает членство в группе с помощью heartbeat

Если heartbeat прекращаются, coordinator считает участника недоступным и передаёт его партиции другим консьюмерам

---

## 6.6. Получение сообщений

После назначения партиций librdkafka начинает отправлять запросы leader-брокерам этих партиций.

Брокеры возвращают сообщения батчами.

librdkafka получает данные в фоновых потоках и помещает их в локальную prefetch-очередь

## 6.7. Consume loop

Типичный консьюмер работает как долгоживущий цикл:

```cs
consumer.Subscribe("orders.events");

try
{
    while (!stoppingToken.IsCancellationRequested)
    {
        var result = consumer.Consume(stoppingToken);

        await ProcessAsync(result.Message, stoppingToken);
    }
}
finally
{
    consumer.Close();  // штатный выход из группы
}
```

`Consume`:

- получает следующую запись из локальной очереди
- выполняет десериализацию ключа и значения
- возвращает `ConsumeResult`
- может обработать rebalance-событие как побочный эффект вызова

`ConsumeResult` содержит:

- `Topic`
- `Partition`
- `Offset`
- `Key`
- `Value`
- `Headers`
- `Timestamp`

---

## 6.8. Consumer lag

**Consumer lag** — количество сообщений, находящихся между концом партиции и сохранённой позицией группы

Большой lag может означать:

- обработка медленнее поступления сообщений
- недостаточно консьюмеров
- недостаточно партиций
- медленная внешняя БД
- poison message (плохое сообщение без кейса обработки)
- частые rebalance
- зависший обработчик
- слишком крупные batch или длительная обработка

---

## 6.9. Гарантия доставки

- ﻿﻿At most once — сообщение может быть доставлено 0 или 1 раз
- ﻿﻿At least once - сообщение может быть доставлено 1 и более ра:
- ﻿﻿Exactly once — гарантирована доставка сообщения строго 1 (недостижимо)

---

## 6.10. Виды коммитов

- ﻿﻿Auto commit (At most once) - коммитит сразу после получения сообщений
	
- ﻿﻿Manual commit (At least once) - коммитим сами после обработки сообщения
	  
- ﻿﻿Custom offset management (Exactly once)  - своя реализация хранилища offset
