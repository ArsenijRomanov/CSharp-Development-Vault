# 1. Синхронное взаимодействие

Один сервис отправляет запрос другому и ожидает ответ в рамках текущей операции

~~~mermaid
sequenceDiagram
    participant A as Service A
    participant B as Service B

    A->>B: request
    B-->>A: response
~~~

Типичные технологии:

- HTTP REST
- gRPC
- синхронные вызовы RPC

---
## 1.1. Плюсы

- вызывающая сторона сразу получает результат
- ошибки возвращаются непосредственно вызывающему коду
- проще реализовать последовательный бизнес-сценарий
- проще поддерживать строгую согласованность в рамках короткой операции
- не требуется брокер сообщений

---

## 1.2. Минусы


### 1. Временная связанность

Оба сервиса должны быть доступны одновременно

### 2. Каскадные сбои

Если один сервис работает медленно, задержка распространяется вверх по цепочке

Проблема на последнем участке влияет на весь запрос

### 3. Рост задержки

Последовательные вызовы суммируют latency:

```
Общая задержка ≈ вызов A + вызов B + вызов C
```

### 4. High coupling

Вызывающий сервис должен знать:

- адрес вызываемого сервиса
- контракт запроса
- контракт ответа
- возможные ошибки
- требования к timeout и retry

### 5. Риск повторного выполнения

Если запрос завершился timeout, вызывающая сторона не всегда знает, была ли операция выполнена

---

# 2. Асинхронное взаимодействие

Продюсер публикует сообщение и не ожидает завершения обработки консьюмером

~~~mermaid
flowchart LR
    P[Producer] --> B[Message Broker]
    B --> C[Consumer]
~~~

Типичные технологии:

- Kafka
- RabbitMQ
- Azure Service Bus
- Amazon SQS
- NATS

---

## 2.1. Какие задачи решает


### 1. Устраняет временную связанность

Producer и consumer не обязаны быть доступны одновременно

### 2. Сглаживает пики нагрузки

Брокер выполняет роль буфера:

```
Producer создаёт 10 000 сообщений в секунду
Consumer обрабатывает 3 000 сообщений в секунду
Остальные сообщения накапливаются в очереди
```

Это не устраняет нехватку производительности, но позволяет пережить кратковременный пик

### 3. Обеспечивает low coupling

Producer знает контракт сообщения, но не обязан знать всех получателей

### 4. Позволяет выполнять долгие операции

Операция не удерживает пользовательский HTTP-запрос

### 5. Повышает устойчивость к временным сбоям

Consumer может повторить обработку после восстановления зависимости

---

## 2.2. Плюсы

- producer и consumer не обязаны работать одновременно
- меньше каскадных отказов
- брокер сглаживает кратковременные пики
- проще горизонтально масштабировать consumers
- одно событие может иметь несколько независимых обработчиков
- удобно выполнять долгие и фоновые операции
- временная недоступность consumer не обязательно приводит к потере операции

---

## 2.3. Минусы

### 1. Eventual consistency

В течение доставки сообщения части системы находятся в разных состояниях

### 2. Сложная обработка ошибок

Producer уже не может просто получить ошибку consumer в рамках исходного вызова

### 3. Повторная доставка

Большинство систем предоставляет `at least once delivery`

### 4. Проблема атомарной публикации

[[Определения#^Dual write|Dual write]]

### 5. Порядок сообщений

Порядок может нарушаться из-за:

- нескольких consumers
- нескольких партиций
- повторных попыток
- параллельной обработки

Если порядок важен, обычно используются:

- partition key по `AggregateId`
- версия агрегата
- sequence number
- один consumer на конкретную партицию

### 6. Сложнее наблюдаемость

Одна бизнес-операция может проходить через несколько сервисов и очередей в течение длительного времени

---

# 3. Сравнение

|Характеристика|Синхронное|Асинхронное|
|---|---|---|
|Получение результата|Сразу|Позже|
|Связанность по времени|Высокая|Низкая|
|Согласованность|Проще получить немедленную|Обычно eventual consistency|
|Поведение при недоступности consumer|Запрос завершается ошибкой|Сообщение может дождаться восстановления|
|Каскадные сбои|Более вероятны|Лучше изолированы|
|Работа с пиками|Ограничена пропускной способностью цепочки|Брокер временно буферизует нагрузку|
|Обработка ошибок|Ошибка возвращается вызывающему|Retry, DLQ, мониторинг|
|Дубликаты|Возможны при retry|Ожидаемы при at least once|
|Порядок|Проще контролировать в одном вызове|Требует отдельного проектирования|
|Сложность инфраструктуры|Ниже|Выше|
|Наблюдаемость|Проще|Сложнее|

---

# 4. Когда выбирать синхронное взаимодействие

- результат необходим для продолжения текущей операции
- пользователь должен получить немедленный ответ
- операция короткая
- зависимость обязательна для формирования результата
- устаревший результат недопустим
- ошибка должна быть сразу возвращена клиенту

Примеры:

```
получение карточки товара

проверка авторизации

расчёт стоимости доставки

получение текущего баланса
```

---

# 5. Когда выбирать асинхронное взаимодействие

- результат не требуется немедленно
- операция может выполняться долго
- нужно переживать временную недоступность consumer
- требуется сглаживание пиков
- событие обрабатывают несколько независимых сервисов
- допустима eventual consistency
- необходимо уменьшить каскадное влияние сбоев

Примеры:

```
отправка уведомления

индексация в поиске

обновление аналитики

генерация отчёта

обработка изображения

реакция других сервисов на доменное событие
```
