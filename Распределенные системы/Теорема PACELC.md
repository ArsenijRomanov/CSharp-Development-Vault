**PACELC** расширяет [[Теорема CAP|теорему CAP]] и описывает компромиссы распределённой системы не только во время сетевого разделения, но и при нормальной работе

```
If Partition:
    Availability ↔ Consistency

Else:
    Latency ↔ Consistency
```

---
## При наличии partition: `PA / PC`

Когда части системы не могут взаимодействовать, возникает выбор из CAP

## При отсутствии partition: `EL / EC`

Даже когда сеть работает, репликам необходимо обмениваться сообщениями

### 1. `EL` — Latency

Система отвечает с ближайшего узла, не ожидая согласования со всеми необходимыми репликами

```
Клиент → ближайшая реплика → быстрый ответ
```

Преимущества:

- низкая задержка
- меньше сетевых запросов
- лучше географическая масштабируемость

Недостаток — реплика может вернуть устаревшие данные

### 2. `EC` — Consistency

Перед подтверждением операции система координируется с лидером, кворумом или другими репликами

```
Клиент
    → координатор
    → реплики
    → подтверждения
    → ответ клиенту
```

Преимущество — более сильная консистентность

Недостаток — дополнительная задержка из-за сетевых обменов и ожидания реплик

## Почему возникает выбор между `L` и `C`

Допустим, клиент записал:

```
x = 1
```

После этого другой клиент обращается к удалённой реплике

Чтобы гарантированно вернуть последнее значение, реплика должна:

```
обратиться к лидеру или кворуму
    → проверить актуальную версию
    → дождаться ответа
```

Это сохраняет консистентность, но увеличивает latency

Если реплика сразу ответит локальным значением:

```
Read x → 0
```

ответ будет быстрее, но может оказаться устаревшим

```
Ждём координацию
    → выше C
    → выше latency

Отвечаем локально
    → ниже latency
    → слабее C
```

---

## Обозначения систем

PACELC-систему обычно описывают двумя решениями:

```
PA/EL
```

Во время partition выбирает доступность, а при нормальной работе — низкую задержку

```
PC/EC
```

Во время partition выбирает консистентность, а при нормальной работе также координирует реплики ради консистентности
