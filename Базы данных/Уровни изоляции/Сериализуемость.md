


Обычно считается самым сильным уровнем изоляции. Гарантирует, что даже при конкурентном выполнении транзакций результат останется таким же, как и в случае *последовательного* выполнения.

Большинство СУБД для реализации сериализуемости применяют один из трех методов:

- действительно последовательное выполнение
- двухфазная блокировка (2PL)
- методы оптимистичного управления конкурентным доступом (например **SSI**)

# 1. Последовательное выполнение

Одновременно выполняется только одна транзакция в одном потоке выполнения.

Хорошо работает при:

- расположении всех данных в RAM
- коротких OLTP транзакциях
- преобладающих транзакций чтения, которые можно выполнять вне цикла последовательного выполнения

> Подход реализован в таких СУБД, как **Redis**, Datomic, VoltDB

### Инкапсуляция транзакций в хранимых процедурах

При последовательном выполнении транзакций БД обрабатывает только одну транзакцию за раз. Поэтому особенно плохо работают **интерактивные транзакции**, в которых приложение выполняет несколько запросов к БД и принимает решения между ними:

```
BEGIN
→ SELECT
← результат

логика приложения

→ UPDATE
← результат

COMMIT
```

Пока результат запроса передаётся приложению, там выполняется логика и формируется следующий запрос, транзакция остаётся открытой, а БД при строго последовательном выполнении не может начать следующую транзакцию.

Чтобы убрать эти паузы, всю транзакционную логику можно перенести в **хранимую процедуру**:

```
Application
→ вызов процедуры

Database:
SELECT
→ проверки / ветвления
→ UPDATE / INSERT
→ завершение транзакции
```

Приложение передаёт параметры одним запросом, а вся последовательность чтений, проверок и изменений выполняется непосредственно внутри БД без сетевых round-trip между отдельными шагами. Это позволяет сделать короткие OLTP-транзакции достаточно быстрыми для последовательного выполнения.

#### Достоинства и недостатки хранимых процедур

Недостатки:
- У всех производителей СУБД свои языки написания хранимых процедур, не успевающие за новшествами неспециализированных языков. 
- Недостаток экосистемы и библиотек для языков
- Сложность отладки, контроля версий, развертывания, интеграции с системами сбора метрик
- Большая чувствительность к неэффективно написанным хранимых процедур

Достоинства:
- Современные реализации используют существующие универсальные языки (Redis — Lua)
- Значительное улучшение производительности при расположении данных в RAM

### Секционирование

При разбиении данных на секции появляется возможность отдельного потока обработки для каждой секции, однако многосекционные запросы работают значительно медленнее.

Можно ли сделать транзакцию односекционной — сильно зависит от структуры данных.

#  2. Двухфазная блокировка (2PL)

**Two-Phase Locking** — алгоритм управления конкурентным доступом, при котором транзакция захватывает блокировки на используемые объекты, а затем освобождает их в соответствии с правилами 2PL

В течение почти 30 лет только этот алгоритм использовался в СУБД.

При двухфазной блокировке:
- допускается конкурентное чтение несколькими транзакциями
- записывающие транзакции блокируют другие записывающие
- записывающие транзакции блокируют читающие
- читающие блокируют записывающие

Эти блокировки работают не для всей бд, а только для конкретных объектов.

> Подход реализован в MySQL (InnoDB) и SQL Server на уровне **Serializable**

### Реализация

Для объектов СУБД через `lock manager` отслеживает блокировки двух основных типов:

- shared mode (`S`, разделяемый режим)
- exclusive mode (`X`, монопольный режим)

Если объект в данный момент не используется транзакциями, блокировка на нём отсутствует. 

- перед чтением транзакция должна получить `Shared (S)` lock
    - если на объекте нет блокировки или уже есть только `S` — читать можно сразу
    - если есть `X` — нужно ждать
      
- перед записью транзакция должна получить `Exclusive (X)` lock
    - если объект свободен — писать можно сразу
    - если есть хотя бы один `S` или `X` — нужно ждать
      
- если транзакция сначала читала объект, а потом хочет его изменить, она повышает блокировку `S → X`, дожидаясь освобождения несовместимых блокировок
	  
- в 2PL захваченные блокировки удерживаются до `COMMIT` или `ROLLBACK`, после чего освобождаются

При таком подходе часто происходит `deadlock`. СУБД умеет автоматически их обнаруживать и прерывать одну из транзакций.

### Предикатные блокировки

Проблема обычных row-lock'ов — **фантомы**: транзакция может заблокировать все существующие строки, подходящие под условие, но другая транзакция всё ещё может вставить новую строку, которая тоже начнёт этому условию удовлетворять. Поэтому нам нужны предикатные блокировки.

Предикатная блокировка защищает не конкретные существующие строки, а **всё множество данных, удовлетворяющих условию запроса**, включая строки, которые могут появиться позже

Например:

```sql
SELECT *
FROM bookings
WHERE room_id = 123
  AND start_time < '13:00'
  AND end_time > '12:00';
```

Блокируется логический предикат:

```sql
room_id = 123 AND пересечение с интервалом 12:00 – 13:00
```

После этого конкурентная транзакция не сможет вставить или изменить запись так, чтобы она начала удовлетворять этому условию, пока блокировка не будет освобождена

Это предотвращает **phantom rows** и позволяет 2PL обеспечить `SERIALIZABLE`

### Блокировки по диапазону индекса

Полноценные предикатные блокировки дороги, поэтому на практике СУБД часто используют **range locks / next-key locks** по индексу

Вместо хранения произвольного условия:

```sql
room_id = 123 AND time overlaps 12:00 – 13:00
```

СУБД блокирует соответствующий диапазон ключей в индексе:

```
index range
[12:00 ........ 13:00]
```

Конкурентная транзакция не сможет вставить, удалить или изменить индексную запись внутри этого диапазона

Range lock может захватывать немного больше данных, чем строго необходимо, но реализуется значительно дешевле и также защищает от phantom-вставок.

### Производительность 2PL

Главный недостаток 2PL — снижение конкурентности: конфликтующие транзакции вынуждены ждать освобождения блокировок

Основные проблемы:

- **ожидание блокировок** — одна медленная транзакция может задержать множество других
- **очереди на горячих данных** — несколько транзакций, работающих с одним объектом, начинают выполняться почти последовательно
- **высокий tail latency** — медленная работа на верхних процентилях
- **deadlock** — транзакции могут циклически ждать друг друга, после чего одну приходится abort'ить и выполнять заново
- **lock overhead** — установка, учёт и освобождение большого количества блокировок сами по себе требуют ресурсов
- **нестабильность под нагрузкой** — одна длинная транзакция или запрос, захвативший много блокировок, может существенно замедлить весь участок системы

# 3. Сериализуемая изоляция снимков состояния (SSI)

**SSI (Serializable Snapshot Isolation)** — оптимистический механизм обеспечения `SERIALIZABLE`, построенный поверх snapshot isolation

В отличие от пессимистичных подходов вроде `2PL`, SSI **не пытается заранее блокировать потенциально конфликтующие операции**

СУБД отслеживает `read-write` зависимости между конкурентными транзакциями и при обнаружении потенциально несериализуемой истории завершает одну из них с `serialization failure`

Преимущества:

- чтения обычно не блокируют записи
- выше степень конкурентности
- нет длинных очередей на read-lock'ах
- при небольшой конфликтности обычно производительнее пессимистичных блокировок

Цена оптимистичного подхода — при высокой конфликтности возрастает число `abort` и повторных выполнений транзакций

> Подход реализован в PostgreSQL

База данных отслеживает два типа событий:
	
- операции чтения устаревших версий MVCC-объектов (перед чтением произошла незафиксированная операция записи)
- операции записи, влияющие на предшествующие операции чтения (операция чтения произошла после чтения)

### Выявление операций чтения устаревших версий MVCC объектов

Транзакция может прочитать старую версию строки из своего snapshot, хотя конкурентная транзакция уже создала новую версию:

```
T42:
Alice true → Alice false

T43:
snapshot всё ещё видит Alice = true
```

По MVCC-метаданным SSI замечает, что `T43` прочитала состояние, которое изменяет `T42`, и фиксирует зависимость:

```
T43 --rw--> T42
```

Но **T43 сразу не прерывается**, потому что одного такого события ещё недостаточно для нарушения сериализуемости:

- `T43` может вообще ничего не записать
- `T42` может откатиться
- одна `rw`-зависимость сама по себе ещё не образует опасную структуру

Поэтому SSI позволяет транзакциям продолжить работу и abort'ит одну из них только тогда, когда совокупность зависимостей действительно создаёт риск несериализуемой истории.

### Выявление записей, влияющих на предыдущие чтения

SSI запоминает, **какие данные или диапазоны читала транзакция**, через `SIREAD` / predicate locks

<div style="text-align: center;">

<img src="Pasted image 20260927185255.png" style="max-width: 600; width: 100%;">

</div>

Обе транзакции читали:

```sql
WHERE shift_id = 1234
```

СУБД фиксирует:

```
shift_id = 1234
→ read by T42
→ read by T43
```

Эти блокировки **ничего не запрещают**. Другая транзакция всё равно может выполнить `UPDATE`

Если затем `T42` изменяет данные, которые ранее читала `T43`, SSI фиксирует зависимость:

```
T43 --rw--> T42
```

И наоборот, если `T43` изменяет данные, прочитанные `T42`:

```
T42 --rw--> T43
```

После этого обе транзакции могут продолжить работу. При `COMMIT` SSI проверяет накопленные зависимости:

```
безопасная история
→ COMMIT

опасная комбинация зависимостей
→ одну транзакцию ABORT
→ retry
```

То есть `SIREAD` здесь работает как **ловушка на последующую запись**, а не как настоящая блокировка.

### Производительность SSI

SSI обычно даёт более высокую конкурентность, чем `2PL`, поскольку чтения и записи не блокируют друг друга, а конфликты разрешаются через `abort`

Основные особенности:

- **нет ожидания блокировок** — читающие и записывающие транзакции могут выполняться параллельно
- **хорошо подходит для read-heavy нагрузки** — чтения выполняются по snapshot без блокировки writers
- **нет ограничения одним потоком**, как при последовательном выполнении транзакций
- **цена — возможные abort и retry** при обнаружении опасных зависимостей
- чем дольше живёт read-write транзакция, тем выше вероятность пересечься с другими транзакциями и быть прерванной
- длинные read-only транзакции значительно менее проблемны, поскольку сами ничего не изменяют

Наиболее эффективен SSI при **коротких транзакциях и умеренной конфликтности**.
