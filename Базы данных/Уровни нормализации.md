# Термины


**Отношение** — математическое представление таблицы в реляционной модели

**Схема отношения** — название отношения и набор его атрибутов

**Кортеж** — одна строка отношения

**Атрибут** — именованное свойство отношения (колонка)

**Домен** — множество допустимых значений атрибута ^e69996

---

### Ключи

**Суперключ** — атрибут или набор атрибутов, который однозначно определяет строку

**Кандидатный ключ** — минимальный суперключ

- однозначно определяет строку
- перестаёт это делать после удаления любого входящего в него атрибута


**Первичный ключ** — один из кандидатных ключей, выбранный основным идентификатором строки

**Альтернативный ключ** — кандидатный ключ, который не был выбран первичным

**Составной ключ** — ключ, состоящий из нескольких атрибутов

**Естественный ключ** — ключ, имеющий предметный смысл

**Суррогатный ключ** — искусственно созданный идентификатор без самостоятельного предметного смысла (`id`, `UUID`)

---

### Атрибуты

**Ключевой атрибут** (**prime attribute**), — атрибут, входящий хотя бы в один кандидатный ключ

**Неключевой атрибут** (**non-prime attribute**), — атрибут, не входящий ни в один кандидатный ключ

---

### Функциональные зависимости


**Функциональная зависимость** — $X \rightarrow Y$: одинаковым значениям $X$ всегда соответствуют одинаковые значения $Y$

**Детерминант** — левая часть функциональной зависимости

**Зависимый атрибут** - правая часть функциональной зависимости

В зависимости $X \rightarrow Y$: 

- $X$ - детерминант
- $Y$ - зависимый атрибут

---

### Виды функциональных зависимостей


**Тривиальная функциональная зависимость** — `X` $\rightarrow$ `Y`,  где $Y \subseteq X$


**Нетривиальная функциональная зависимость** — `X` $\rightarrow$ `Y`, где $Y \nsubseteq X$


**Полная функциональная зависимость** — зависимость `X` $\rightarrow$ `Y`, при которой `Y` зависит от всего составного детерминанта `X` и не зависит ни от одного его собственного подмножества


**Частичная функциональная зависимость** — зависимость неключевого атрибута от собственного подмножества составного кандидатного ключа ^7ad953


**Транзитивная функциональная зависимость** — зависимость, при которой
$$X \to Y \; \land \; Y \to Z \; \Rightarrow \; X \to Z$$ ^7d780f

---

### Аномалии данных


##### 1. Аномалия обновления

^26d121

Один факт хранится в нескольких строках, поэтому его приходится изменять в нескольких местах

Например, название товара продублировано во всех позициях заказов:

|`OrderId`|`ProductId`|`ProductName`|`Quantity`|
|---|---|---|---|
|1|42|Keyboard|2|
|2|42|Keyboard|1|
|3|42|Keyboard|4|

Если товар переименовали, необходимо изменить каждую строку с `ProductId = 42`


##### 2. Аномалия вставки

^6127cd

Нельзя сохранить один факт, пока не появился другой, логически независимый факт

Например, таблица одновременно хранит сведения о товарах и их вхождении в заказы:

|`OrderId`|`ProductId`|`ProductName`|`Quantity`|
|---|---|---|---|
|1|42|Keyboard|2|
|1|73|Mouse|1|

Необходимо добавить новый товар (`ProductId`,`ProductName`), но он ещё не входит ни в один заказ, поэтому значения `OrderId` и `Quantity` для него отсутствуют


##### 3. Аномалия удаления

^7ee7bb

Удаление одного факта случайно уничтожает другой независимый факт

Допустим, товар `Mouse` встречается только в одном заказе:

|`OrderId`|`ProductId`|`ProductName`|`Quantity`|
|---|---|---|---|
|1|42|Keyboard|2|
|1|73|Mouse|1|
|2|42|Keyboard|1|

После удаления последней позиции с `ProductId = 73` из базы исчезает факт существования товара `Mouse`


##### 4. Избыточность

**Избыточность** — повторное хранение одного и того же самостоятельного факта

Например:

|`OrderId`|`ProductId`|`ProductName`|`Quantity`|
|---|---|---|---|
|1|42|Keyboard|2|
|2|42|Keyboard|1|
|3|42|Keyboard|4|

Значение `ProductId = 42` закономерно повторяется, поскольку один товар может входить в разные заказы

Избыточно повторяется факт: `ProductId` $\rightarrow$ `ProductName`

Избыточность является основной причиной аномалий обновления, вставки и удаления

---

**Декомпозиция** — разбиение одного отношения на несколько отношений

**Соединение** (`JOIN`) — восстановление связанных данных из нескольких отношений

**Декомпозиция без потерь** (lossless decomposition) — декомпозиция с возможностью соединить полученные отношения и восстановить исходные корректные данные без появления ложных комбинаций

**Сохранение зависимостей** — исходные ограничения можно проверять внутри отдельных полученных отношений без постоянного соединения всех таблиц


**Многозначная зависимость** — $X \twoheadrightarrow Y$: для одного значения $X$ может существовать несколько значений $Y$, причём выбор $Y$ не зависит от остальных атрибутов таблицы. ^85655c
Пример:

| `Student` | `Language` | `Hobby` |
| --------- | ---------- | ------- |
| Иван      | C#         | Шахматы |
| Иван      | C#         | Бег     |
| Иван      | Python     | Шахматы |
| Иван      | Python     | Бег     |
Здесь:
- `Student` $\twoheadrightarrow$ `Language`
- `Student` $\twoheadrightarrow$ `Hobby`


**Зависимость соединения** — ограничение, согласно которому отношение восстанавливается соединением нескольких его проекций

**Проекция** — выбор части атрибутов отношения

# 1НФ — Первая нормальная форма

**Отношение находится в 1НФ**, если:

- каждое поле содержит одно значение из своего [[#^e69996|домена]]
- в строках нет повторяющихся групп атрибутов
- каждая строка однозначно идентифицируется ключом

Атомарность зависит от модели: значение считается неделимым, если система не работает с его отдельными частями

### Проблемы

Общие:

- поиск, фильтрация, соединение и агрегация по `ProductId` усложняются
- сложно обеспечить внешний ключ для каждого отдельного товара
- сложно запретить дублирование одного товара внутри заказа
- нельзя удобно хранить атрибуты связи
- параллельные колонки или массивы могут рассогласоваться
- добавление, изменение и удаление отдельной позиции требуют специальной логики

Дополнительно для повторяющихся колонок:

- количество товаров ограничено числом колонок
- добавление новой позиции требует изменения схемы
- неиспользуемые колонки заполняются `NULL`
- одинаковая логика и ограничения дублируются для каждой позиции

- количество позиций не ограничено схемой
- отсутствуют повторяющиеся группы колонок
- к `ProductId` можно применить внешний ключ
- позиции удобно добавлять, удалять, фильтровать и обновлять

# 2НФ — Вторая нормальная форма

**Отношение находится во 2НФ**, если:

- оно находится в 1НФ
- каждый неключевой атрибут полностью зависит от каждого кандидатного ключа
- нет [[#^7ad953|частичных функциональных зависимостей]]

Формально для кандидатного ключа $K$ и неключевого атрибута $A$ не должно существовать собственного подмножества $X$:
$$X \subset K \quad\land\quad X \to A$$
---
### Нарушение 2НФ

<div style="text-align: center;">

<img src="Pasted image 20260801212159.png" style="max-width: 250px; width: 100%;">

</div>

Кандидатный ключ — (`OrderId`, `ProductId`)

Частичные зависимости:

- `OrderId` $\to$ `OrderDate`  
- `ProductId` $\to$ `ProductName`


### Проблемы

- дублирование данных (даты и названия товара)
- [[#^26d121|аномалия обновления]]
- нельзя сохранить заказ без товарной позиции или пока он не добавлен в заказ                ([[#^6127cd|аномалия вставки]])  
- удаление последней позиции может уничтожить информацию о заказе или товаре         ([[#^7ee7bb|аномалия удаления]])

---
### Приведение ко 2НФ

Атрибуты выносятся в отношения, ключи которых полностью их определяют:

<div style="text-align: center;">

<img src="Pasted image 20260801213314.png" style="max-width: 500px; width: 100%;">

</div>

Теперь зависимости распределены корректно:

- `OrderId` $\to$ `OrderDate`
- `ProductId` $\to$ `Name`
- (`OrderId`, `ProductId`) $\to$ `Quantity`


### Результат

- каждый самостоятельный факт хранится в одном месте
- устранены частичные зависимости
- исчезает дублирование данных заказа и товара
- заказ и товар можно создавать независимо от позиций
- обновление и удаление позиций не затрагивает сведения о заказе и товаре

> Если все кандидатные ключи отношения состоят из одного атрибута, то отношение в 1НФ автоматически находится и во 2НФ

# 3НФ — Третья нормальная форма

**Отношение находится в 3НФ**, если:

- оно находится во 2НФ
- ни один неключевой атрибут не находится в [[#^7d780f|транзитивной зависимости]] от кандидатного ключа

---
### Нарушение 3НФ

<div style="text-align: center;">

<img src="Pasted image 20260801214017.png" style="max-width: 300; width: 100%;">

</div>

Функциональные зависимости:

`Id` $\to$ `CustomerId`
`CustomerId`$\to$ `CustomerName`

Следовательно:

`Id` $\to$ `CustomerName`

### Проблемы

- имя клиента повторяется в каждом его заказе
- изменение имени требует обновления нескольких строк ([[#^26d121|аномалия обновления]])
- нельзя сохранить клиента без заказа ([[#^6127cd|аномалия вставки]])
- удаление последнего заказа может уничтожить сведения о клиенте ([[#^7ee7bb|аномалия удаления]])

- каждый неключевой атрибут описывает сущность своей таблицы

# BCNF — Нормальная форма Бойса — Кодда

**Отношение находится в BCNF**, если для каждой нетривиальной функциональной зависимости:  $X \to Y$ детерминант $X$ является суперключом

---

### Нарушение BCNF

<div style="text-align: center;">

<img src="Pasted image 20260801221123.png" style="max-width: 300; width: 100%;">

</div>

Предположим:

- каждый курс ведёт один преподаватель
- каждый преподаватель ведёт один курс
- на курсе может учиться несколько студентов

Кандидатные ключи:

- `(StudentId, CourseId)`
- `(StudentId, InstructorId)`

Функциональные зависимости:

- `CourseId` $\to$ `InstructorId`
- `InstructorId` $\to$ `CourseId`

Однако `CourseId` и `InstructorId` не являются суперключами, поскольку не определяют студента, поэтому BCNF нарушена


### Проблемы

|`StudentId`|`CourseId`|`InstructorId`|
|---|---|---|
|1|10|100|
|2|10|100|
|3|10|100|

- связь курса с преподавателем повторяется для каждого студента 
- смена преподавателя требует обновления нескольких строк ([[#^26d121|аномалия обновления]])
- одному курсу можно случайно назначить разных преподавателей (согласованность)
- нельзя назначить преподавателя до появления студента ([[#^6127cd|аномалия вставки]])
- удаление последнего студента уничтожает информацию о назначении ([[#^7ee7bb|аномалия удаления]])

---

### Приведение к BCNF

<div style="text-align: center;">

<img src="Pasted image 20260801222640.png" style="max-width: 500; width: 100%;">

</div>

Теперь:

- `CourseId` $\to$ `InstructorId`
- `InstructorId` $\to$ `CourseId`
- (`StudentId`, `CourseId`) $\to$ все атрибуты `StudentCourses`


### Результат

- связь курса с преподавателем хранится один раз
- устраняются аномалии обновления, вставки и удаления
- исключаются функциональные зависимости от детерминантов, не являющихся суперключами
- каждое полученное отношение находится в BCNF

# 4НФ — Четвёртая нормальная форма

**Отношение находится в 4НФ**, если для каждой нетривиальной [[#^85655c|многозначной зависимости]] $X \twoheadrightarrow Y$ детерминант $X$ является суперключом

4НФ устраняет несколько независимых отношений «один ко многим», смешанных в одной таблице

---

### Нарушение 4НФ

У сотрудника независимо существуют набор навыков и набор языков:

<div style="text-align: center;">

<img src="Pasted image 20260802005903.png" style="max-width: 300; width: 100%;">

</div>


Многозначные зависимости:

- `EmployeeId` $\twoheadrightarrow$ `SkillId`
- `EmployeeId` $\twoheadrightarrow$ `LanguageId`

`EmployeeId` не является суперключом, поэтому отношение нарушает 4НФ

|`EmployeeId`|`SkillId`|`LanguageId`|
|---|---|---|
|1|10|100|
|1|10|200|
|1|20|100|
|1|20|200|

Навыки и языки образуют декартово произведение


### Проблемы

- количество строк растёт как произведение размеров независимых наборов
- добавление навыка требует создать строку для каждого языка
- добавление языка требует создать строку для каждого навыка
- одни и те же факты многократно дублируются
- удаление отдельной комбинации нарушает полноту данных
- нельзя независимо хранить навыки и языки сотрудника

---

### Приведение к 4НФ

Независимые многозначные зависимости разделяются:

<div style="text-align: center;">

<img src="Pasted image 20260802010126.png" style="max-width: 500; width: 100%;">

</div>

Теперь:

- `EmployeeId` $\twoheadrightarrow$ `SkillId`        хранится в `EmployeeSkills`
- `EmployeeId` $\twoheadrightarrow$ `LanguageId`  хранится в `EmployeeLanguages`

### Результат

- независимые наборы хранятся отдельно
- исчезает их декартово произведение
- навыки и языки можно добавлять и удалять независимо
- устраняется избыточность многозначных зависимостей

---

# 5НФ — Пятая нормальная форма

**5НФ** требует разделять сложную связь между тремя и более сущностями, если она полностью складывается из нескольких более простых связей

Например, допустимость назначения переводчика определяется тем, что:

- переводчик знает язык
- переводчик работает с данным типом документа
- тип документа поддерживается на этом языке

Тогда вместо хранения всех троек:

```
TranslatorId, LanguageId, DocumentTypeId
```

можно отдельно хранить три связи:

```
TranslatorLanguages
TranslatorDocumentTypes
LanguageDocumentTypes
```

Это устраняет повторение одних и тех же парных фактов

### Когда применяется

5НФ нужна редко — обычно в сложных моделях, где одна таблица связывает три и более сущности в отношении "многие ко многим ко многим" и содержит много избыточных комбинаций, при этом тройка признаков (или больше) полностью определяется тремя парными связями 

---

# 6НФ — Шестая нормальная форма

**6НФ** требует разделять независимо изменяющиеся факты на отдельные отношения

Например, у сотрудника независимо меняются:

- должность
- зарплата
- подразделение

Вместо одной временной таблицы:

```sql
EmployeeId  -- работник
Position    -- должность
Salary      -- зарплата
Department  -- отдел
ValidFrom   -- начало периода действия записи
ValidTo     -- конец периода действия записи
```

можно хранить:

```
EmployeePositions
EmployeeSalaries
EmployeeDepartments
```

Каждая таблица содержит один факт и период его действия

### Зачем нужна

Такое разделение позволяет независимо изменять историю каждого атрибута и не создавать лишние комбинации периодов

### Когда применяется

6НФ используется редко, в основном:

- в темпоральных базах (когда хранится изменение данных во времени)
- при хранении полной истории изменений
- когда разные свойства сущности изменяются независимо

> Грубо говоря, 6НФ доводит декомпозицию почти до схемы «ключ + один факт + период его действия»
