**Секционирование** — общее понятие разделения набора данных на отдельные части

**Партиционирование** — разделение одной логической таблицы на несколько физических частей внутри одной СУБД

**Шардирование** — распределение частей данных между несколькими независимыми узлами или экземплярами базы данных

# 1. Шардирование и репликация

![[Pasted image 20260723211310.png]]

Данные разделяются на шарды, а каждый шард хранится в нескольких копиях на разных узлах

Для каждого шарда назначается собственный ведущий узел:

- `Leader` принимает запись
- `Followers` копируют изменения

Лидеры разных шардов распределяются между узлами, чтобы нагрузка на запись не концентрировалась в одном месте

**Шардирование**
- горизонтальное масштабирование

**Репликация**
- отказоустойчивость

# 2. Выбор нужной секции 

**Цель секционирования** - равномерно распределить данные и нагрузку между секциями

## 2.1. Секционирование по диапазонам ключей

Данные распределяются по секциям согласно значению ключа

```
1–100     → секция 1
101–200   → секция 2
201–300   → секция 3
```

Подходит для упорядоченных ключей:

- даты и время
- географические диапазоны
- ценовые категории

### Преимущества

- эффективные диапазонные запросы
- возможность исключить ненужные секции

### Недостатки

- возможность появления горячих секций
- горячая секция при последовательной записи
- необходимость заранее определять границы
- проблемы с масштабированием

---

## 2.2. Секционирование по хэшу ключа

для ключа вычисляется хеш, по которому выбирается секция

![[Pasted image 20260723213358.png]]

### Преимущества

- более равномерное распределение данных и записи
- легче масштабировать

### Недостатки

- диапазонные запросы затрагивают все секции
- изменение количества секций требует перераспределения данных
- популярные ключи могут создавать перекос нагрузки
- запросы без ключа секционирования обходят несколько секций

# 3. Перебалансировка

Требования:
- равномерность нагрузки
- отсутствие даунтайма
- минимальное количество перемещаемых данных

## 3.1. Хеширование по количеству секций

![[Pasted image 20260723231832.png]]

Номер физического шарда вычисляется напрямую из хеша ключа

- простая маршрутизация без таблицы соответствий
- равномерное распределение данных
- точечный запрос сразу направляется на нужный шард
- минимум метаданных

### Главный недостаток

Массовый перенос данных при изменении количества шардов

---

## 3.2. Фиксированное количество виртуальных секций

![[Pasted image 20260723224121.png]]

Сначала ключ отображается в одну из заранее созданных логических секций — `bucket`

Количество `buckets` фиксируется и обычно значительно превышает количество физических шардов

### Масштабирование

При добавлении нового шарда формула `key` $\rightarrow$ `bucket` не меняется. Новому шарду передаётся часть существующих buckets вместе с их данными

### Преимущества

- перемещается только часть данных
- ключ всегда остаётся в том же bucket
- можно явно управлять распределением нагрузки
- добавление шардов не требует изменения хеш-функции

---

## 3.3. Consistent hashing

![[Pasted image 20260724000504.png]]

Ключи и узлы отображаются хеш-функцией в общее кольцевое пространство

На схеме:
- белые точки - ключи данных
- цветные точки - виртуальные позиции физических узлов

Каждый ключ хранится на первом виртуальном узле, расположенном после него по часовой стрелке

Один физический узел размещается на кольце несколькими виртуальными точками

### Масштабирование

При добавлении или удалении узла перестраиваются только соседние участки кольца

- добавление узла $\rightarrow$ он забирает часть диапазонов у соседей
- удаление узла $\rightarrow$ его диапазоны переходят следующим узлам

---

## 3.4. Динамическое секционирование

Схема, в которой система сама изменяет количество и размещение секций по мере роста данных и нагрузки

Система отслеживает:

- размер секций
- объём чтения и записи
- загрузку узлов
- распределение данных

И решает: 

- рост секции $\rightarrow$ split
- уменьшение или простаивание $\rightarrow$ merge
- перегрузка узла $\rightarrow$ перенос секции

**Примеры**:

- MongoDB
- CockroachDB
- Google Spanner

# 4. Вторичные индексы 

Пусть ключ шардирования - `Name`

![[Pasted image 20260723234734.png]]

При поиске по другому полю определить нужный шард невозможно

```sql
SELECT * FROM cars
WHERE color = 'red';
```

Без дополнительного механизма запрос приходится отправлять на все шарды и объединять результаты

---

### 4.1. Локальный вторичный индекс

Каждый шард строит индекс только по своим данным.

Запись обновляет данные и индекс внутри одного шарда:

![[Pasted image 20260724000649.png]]

Но поиск по вторичному полю всё равно затрагивает все шарды:

![[Pasted image 20260723235830.png]]

`color = red`:
$\rightarrow$ запрос ко всем локальным индексам
$\rightarrow$ объединение результатов

---

### 4.2. Глобальный вторичный индекс

Здесь мы **отдельно шардируем сам вторичный индекс**. Данные распределяются по одному ключу, а записи индекса — по значению индексируемого поля. 
### Запись

![[Pasted image 20260723234616.png]]

Основная запись распределяется по shard key, а индексная запись — по вторичному ключу

- `car.id = 8 ` $\rightarrow$ `data shard` по `id`
- `car.color = red` $\rightarrow$ `index shard` по `color`

### Чтение

![[Pasted image 20260724000623.png]]

Запрос сначала направляется в секцию глобального индекса

`color = red`:
  $\rightarrow$ index shard
  $\rightarrow$ получение id записей
  $\rightarrow$ чтение записей с data shards

Можно реализовать что-то типа покрывающего глобального индекса, тогда второй этам можно пропустить.

### Проблема dual write

Возникают проблемы с ACID

Для строгой согласованности нужны распределённые транзакции, `2PC` или другой механизм атомарной фиксации

Альтернатива — обновлять индекс асинхронно через журнал, `CDC` или очередь

строгая согласованность:
- сложнее и медленнее запись

асинхронное обновление:
- проще масштабирование
- eventual consistency

# 5. Разница между партиционированием и шардированием

Оба подхода разделяют данные на части, но делают это на разных уровнях

### Партиционирование

Преимущества:

- изолированные `VACUUM`, `REINDEX`, backup и обслуживание
- быстрое удаление и архивирование секций
- меньшие индексы
- сравнительно простые `JOIN`, транзакции и ограничения

Ограничения:

- данные всё ещё находятся на одном сервере
- общая производительность ограничена ресурсами одного экземпляра
- большое количество партиций усложняет планирование
- запросы без фильтра по ключу могут обходить все партиции

### Шардирование

Преимущества:

- горизонтальное масштабирование хранения
- распределение нагрузки на чтение и запись
- изоляция отказов и нагрузки между шардами

Ограничения:

- сложнее `JOIN`, агрегации и транзакции между шардами
- сложнее поддерживать глобальные `UNIQUE`, внешние ключи и индексы
- появляются dual write, распределённая согласованность и перебалансировка

## Когда применять партиционирование

Партиционирование подходит, когда один экземпляр БД справляется с нагрузкой, но необходимо:

- упростить обслуживание больших таблиц
- быстро удалять или архивировать диапазоны данных
- ускорить запросы через partition pruning
- разделить горячие и холодные данные
- уменьшить размер обслуживаемых таблиц и индексов

## Когда применять шардирование

Шардирование необходимо, когда один узел становится физическим ограничением:

- данные не помещаются на одном сервере
- пропускной способности диска или сети недостаточно
- нагрузка на запись превышает возможности одного primary
- требуется распределение данных между регионами
- вертикальное масштабирование стало слишком дорогим или невозможным
