## 2.2. Snapshot

**Snapshot** — структура, описывающая состояние транзакций в определённый момент

Она содержит:

- `xmin` - самая старая транзакция, остававшаяся активной
- `xmax` - верхняя граница snapshot, еще не начавшаяся транзакция
- `xip`   - список активных транзакций $\in [xmin, xmax)$

Правила видимости:

- `XID` < `xmin`
	$\rightarrow$ транзакция уже не активна
	$\rightarrow$ её изменения видны, если она сделала COMMIT

- `xmin` <= `XID` < `xmax` и `XID` находится в `xip`
	$\rightarrow$ транзакция ещё выполнялась
	$\rightarrow$ её изменения не видны

- `xmin` <= `XID` < `xmax` и `XID` отсутствует в `xip`
	$\rightarrow$ транзакция уже завершилась
	$\rightarrow$ её изменения видны при COMMIT

- `XID` >= `xmax`
	$\rightarrow$ транзакция не началась к моменту snapshot
	$\rightarrow$ её изменения не видны

Собственные изменения транзакция видит по отдельным правилам.

## 2.3. Read Committed

В PostgreSQL новый snapshot создаётся для каждого SQL-запроса

```
T1: BEGIN

T1: SELECT balance
    snapshot S1
    результат = 100

T2: UPDATE balance = 200
T2: COMMIT

T1: SELECT balance
    snapshot S2
    результат = 200
```

Схема:

```
одна транзакция
├── запрос 1 → snapshot S1
├── запрос 2 → snapshot S2
└── запрос 3 → snapshot S3
```

Каждый запрос видит изменения, закоммиченные до начала этого запроса

`Read Uncommitted` в PostgreSQL реализован так же, как `Read Committed`.

---

## 2.4. Repeatable Read

Один snapshot создаётся при выполнении первой рабочей команды и используется до завершения транзакции

```
T1: BEGIN ISOLATION LEVEL REPEATABLE READ

T1: SELECT balance
    создаётся snapshot S1
    результат = 100

T2: UPDATE balance = 200
T2: COMMIT

T1: SELECT balance
    используется snapshot S1
    результат = 100
```

Схема:

```
одна транзакция
├── запрос 1 ─┐
├── запрос 2 ─┼─→ один snapshot
└── запрос 3 ─┘
```

При попытке изменить строку, которая была изменена конкурентной транзакцией после создания snapshot, операция может завершиться ошибкой:

```
could not serialize access due to concurrent update
```

Транзакцию необходимо выполнить заново. В PostgreSQL `Repeatable Read` также не допускает фантомных чтений.

---

## 2.5. Serializable

`Serializable` использует тот же стабильный snapshot, что и `Repeatable Read`, но добавляет **SSI — Serializable Snapshot Isolation**

```
Repeatable Read
+
отслеживание зависимостей чтение-запись
+
отмена опасных комбинаций транзакций
```

Пример:

```
T1 читает строки A и B
T2 читает строки A и B

T1 изменяет A
T2 изменяет B
```

Транзакции изменяют разные строки, поэтому обычного конфликта записи нет

PostgreSQL отслеживает зависимости:

```
T1 прочитала B → T2 изменила B
T2 прочитала A → T1 изменила A
```

Если успешный `COMMIT` обеих транзакций мог бы привести к несериализуемому результату, одна из них завершается ошибкой:

```
could not serialize access due to read/write dependencies
```

Приложение должно повторить отменённую транзакцию. Проверки SSI не превращают обычные чтения в блокирующие чтения.

# 3. WAL

**Write-Ahead Log** — журнал изменений PostgreSQL

> Сначала изменение записывается в WAL, и только потом страница данных может быть сохранена на диск

При изменении данных PostgreSQL:

1. изменяет страницу в оперативной памяти
2. создаёт WAL-запись
3. при `COMMIT` надёжно записывает WAL на диск
4. саму страницу таблицы может записать позже

После сбоя PostgreSQL берёт последний `checkpoint` и проигрывает WAL, восстанавливая подтверждённые изменения

WAL также используется для:

```
репликации
архивации
Point-in-Time Recovery
```

# 4. Хранение данных

## 4.1. Файлы и страницы

Каждая таблица и индекс PostgreSQL хранятся в отдельных файлах. Файл отношения разбит на страницы фиксированного размера, обычно `8 КБ`

---

## 4.2. Устройство страницы

Страница heap-таблицы состоит из нескольких областей:
### Page Header

Заголовок страницы занимает `24 байта` и содержит:

```
pd_lsn       позиция последнего изменения страницы в WAL
pd_checksum  контрольная сумма
pd_lower     начало свободного пространства
pd_upper     конец свободного пространства
pd_special   начало специальной области
```

### Item pointers

Для каждой строки создаётся указатель размером `4 байта`, содержащий:

```
offset   смещение строки внутри страницы
length   размер строки
flags    состояние указателя
```

Индекс указателя вместе с номером страницы образует `ctid` строки

### Запись строк

Указатели добавляются от начала страницы, а сами строки — с конца страницы

При вставке PostgreSQL:

1. ищет страницу со свободным местом через `FSM`
2. создаёт новый item pointer
3. записывает строку с конца свободной области
4. изменяет `pd_lower` и `pd_upper`

---

## 4.3. Устройство строки

Физическая строка PostgreSQL называется **heap tuple**, она содержит:

- `Tuple Header`
- `NULL bitmap`
- Выравнивание
- Данные столбцов

Заголовок строки занимает обычно `23 байта` и содержит:

```
t_xmin       XID транзакции, создавшей версию
t_xmax       XID транзакции, удалившей или заменившей версию
t_ctid       ссылка на эту или следующую версию строки
t_infomask   служебные флаги
t_hoff       смещение до пользовательских данных
```

`NULL` не хранится как значение столбца. При наличии nullable-полей используется bitmap, где каждому столбцу соответствует один бит

Данные столбцов записываются последовательно с учётом требований к выравниванию. Из-за выравнивания между значениями могут появляться пустые байты

Одна версия строки не может пересекать границу страницы. Если строка слишком большая, PostgreSQL использует TOAST.

---

## 4.4. TOAST

**TOAST — The Oversized-Attribute Storage Technique** — механизм хранения больших значений вне основной строки

PostgreSQL не позволяет одной строке занимать несколько страниц. Поэтому при превышении строкой порога примерно `2 КБ` он пытается:

1. сжать большие значения
2. вынести их в отдельную TOAST-таблицу
3. оставить в основной строке небольшой указатель

Указатель в основной строке занимает `18 байт` и содержит идентификаторы TOAST-таблицы и значения, размеры данных и информацию о сжатии.

### Типы, поддерживающие TOAST

TOAST применяется к типам переменной длины:

```
text
varchar
bytea
json
jsonb
массивы
```

---

## 4.5. Обновление и удаление

Из-за MVCC `UPDATE` не перезаписывает строку на месте.

`DELETE` записывает XID удаляющей транзакции в `t_xmax`, но физически строка остаётся на странице

Невидимые старые версии позднее очищаются `VACUUM`

---

## 4.6. Free Space Map

**FSM** хранит примерный объём свободного места на каждой странице

При `INSERT` или `UPDATE` PostgreSQL использует FSM, чтобы быстро найти страницу, куда поместится новая версия строки, не проверяя последовательно всю таблицу

FSM существует как для heap-таблиц, так и для большинства типов индексов. Для индекса она помогает находить и повторно использовать страницы со свободным местом вместо постоянного расширения файла. 

## 4.7. Visibility Map

**VM** хранит по два бита для каждой страницы heap-таблицы:

```
all-visible
→ все версии строк на странице видимы всем транзакциям

all-frozen
→ все версии строк заморожены и не требуют обработки XID
```

Биты устанавливаются `VACUUM` и сбрасываются при изменении страницы.


Visibility Map позволяет покрывающим индексам действительно работать без чтения таблицы.

Обычная индексная запись не содержит полной информации MVCC о видимости строки. 

При `Index Only Scan` PostgreSQL проверяет VM:

```
страница all-visible
→ результат можно получить только из индекса

страница не all-visible
→ необходимо прочитать heap-страницу
```

# 5. Очистка данных

## 5.1. VACUUM

После `UPDATE` и `DELETE` старые версии строк физически остаются в таблице как **dead tuples**

`VACUUM`:

- удаляет ссылки на недоступные версии строк
- освобождает место внутри страниц для повторного использования
- очищает мёртвые записи из индексов
- обновляет Visibility Map
- замораживает старые XID для защиты от transaction ID wraparound
- не блокирует обычные чтения и записи
- не выполняет дефрагментацию
- не возвращает освобожденное место операционной системе

В обычной работе очистку автоматически выполняет **autovacuum**

Долгие транзакции и состояния `idle in transaction` могут удерживать старый snapshot, из-за чего PostgreSQL не может удалить старые версии строк

---

## 5.2. Разрастание данных

**Bloat** — раздувание таблиц или индексов из-за накопления неиспользуемого пространства

Причины:

- большое количество `UPDATE` и `DELETE`
- autovacuum не успевает очищать данные
- долгие транзакции удерживают старые версии
- освободившееся место распределено по множеству страниц
- индексные страницы остаются частично заполненными

Последствия:

- больше чтений страниц
- хуже использование кеша
- медленнее последовательное сканирование
- больший размер резервных копий
- увеличенный размер индексов

---

## 5.3. VACUUM FULL

`VACUUM FULL` делает то же, что и `VACUUM`, но 

- получает `ACCESS EXCLUSIVE` lock и блокирует работу с таблицей
- выполняет дефрагментацию таблиц и индексов
- требует дополнительное место для новой копии
- возвращает свободное место операционной системе
- работает значительно дольше обычного `VACUUM`

`VACUUM FULL` практически неприменим без заранее выделенного окна обслуживания, поскольку на всё время выполнения он получает эксклюзивную блокировку таблицы и делает её недоступной для чтения и записи.

## 5.4. REINDEX

- полностью перестраивает индекс
- блокирует запись

### REINDEX CONCURRENTLY

- не блокирует запись
- работает дольше обычного `REINDEX`
- выполняет несколько проходов по таблице
- временно хранит старую и новую копии индекса
- допускает кратковременные блокировки 

---

## 5.5. pg_repack

`pg_repack` — стороннее расширение для онлайн-перестроения таблиц и индексов с минимальными блокировками

Упрощённая схема работы:

- копирует живые строки
- отслеживает изменения исходной таблицы через trigger
- применяет накопившиеся изменения
- кратковременно блокирует таблицу
- подменяет старую таблицу новой

Особенности:

- устраняет bloat таблицы и индексов
- записи могут продолжаться почти всё время операции
- `ACCESS EXCLUSIVE` lock нужен на короткое время в начале и конце
- для полного repack нужен Primary Key либо уникальный индекс по `NOT NULL`-полям
- требуется значительный запас свободного места

Полный repack может потребовать дополнительное место примерно вдвое больше суммарного размера таблицы и её индексов.

---

## 5.6. pgcompacttable

Это сторонняя Perl-утилита для уменьшения bloat таблиц и индексов без длительных тяжёлых блокировок

- работает преимущественно **на месте**:
- обновляет строки небольшими порциями
- новые версии перемещаются в свободные страницы ближе к началу файла
- VACUUM освобождает пустые страницы в конце
- файл таблицы усекается
- индексы перестраиваются по одному

Особенности:

- требует меньше временного дискового пространства, чем полное копирование таблицы
- регулирует скорость работы, снижая нагрузку на I/O и репликацию
- использует расширение `pgstattuple` для оценки bloat
- требует повышенных привилегий
- создаёт дополнительную нагрузку на WAL, autovacuum и репликацию

---

# 6. Методы доступа к данным

Выбранный способ можно увидеть через:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Планировщик выбирает метод на основании:

- селективности условия
- размера таблицы
- статистики
- стоимости чтения

## 6.1. Sequential Scan

**`Seq Scan`** — последовательное чтение всех страниц таблицы с проверкой условия для каждой строки

Эффективен, когда:

- таблица небольшая
- запрос возвращает значительную часть строк
- подходящего индекса нет

## 6.2. Index Scan

**Index Scan** сначала находит подходящие записи в индексе, а затем по `ctid` читает соответствующие строки из heap-таблицы

- эффективен при высокой селективности
- при плохой кэш-локальности может проигрывать `Seq Scan`

## 6.3. Index Only Scan

**Index Only Scan** получает необходимые значения непосредственно из индекса, не читая heap-таблицу

Для этого:

- все нужные столбцы должны находиться в индексе
- страница таблицы должна быть отмечена как `all-visible` в Visibility Map

## 6.4. Bitmap Scan

Bitmap-доступ обычно состоит из двух этапов:

- Bitmap Index Scan $\rightarrow$ собирает bitmap подходящих строк
- Bitmap Heap Scan $\rightarrow$ читает нужные страницы таблицы

Вместо отдельного случайного чтения для каждой строки PostgreSQL сначала группирует найденные `ctid` по страницам, а затем читает страницы более последовательно

Эффективен при средней селективности.

---

# 7. Стратегии `JOIN`

Выбранную стратегию можно увидеть через:

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders o
JOIN users u ON u.id = o.user_id;
```

Планировщик выбирает стратегию на основании:

- статистики
- размера таблиц 
- индексов
- условия соединения и ожидаемого количества строк

## 7.1. Nested Loop

Для каждой строки внешней таблицы PostgreSQL ищет подходящие строки во внутренней таблице

```
for each row in A
    find matching rows in B
```

Хорошо работает, когда:

- внешняя выборка небольшая
- во внутренней таблице есть индекс по полю соединения
- запрос возвращает мало строк

- Время $\rightarrow$ $O(n^2)$, без индекса на `B`
- Память $\rightarrow$ $O(1)$

## 7.2. Hash Join

PostgreSQL строит хеш-таблицу по меньшему набору данных, а затем проверяет строки второго набора по хешу

Хорошо работает, когда:

- соединяются большие неотсортированные наборы
- условие соединения основано на равенстве
- индекс не даёт существенного преимущества

- Время $\rightarrow$ $O(N + M)$
- Память $\rightarrow$ $O(min(N, M))$

## 7.3. Merge Join

Оба набора сортируются по ключу соединения, после чего PostgreSQL последовательно проходит их одновременно

Хорошо работает, когда:

- оба набора большие
- условие соединения поддерживает сортировку, обычно равенство
- данные уже отсортированы индексами
- результат также нужен в отсортированном виде

Если подходящей сортировки нет, PostgreSQL добавляет `Sort`, который требует памяти и может использовать временные файлы

- Время $\rightarrow$ $O(N + M)$, если есть индексы
- Память $\rightarrow$ $O(D)$, где $D$ — размер крупнейшей группы строк с одинаковым ключом

# 8. Обработка запроса

![[Pasted image 20260722131925.png]]

## 8.1. Parser

- выполняет синтаксический анализ
- передает построенное синтаксическое дерево (parse tree)

---

## 8.2. Analyzer

Выполняет семантический анализ запроса

Основные задачи:

- ищет таблицы и столбцы в системном каталоге
- разрешает имена объектов
- определяет типы выражений
- проверяет совместимость типов
- проверяет корректность функций и операторов
- проверяет права доступа
- формирует внутреннее дерево запроса (query tree)

---

## 8.3. Rewriter

Преобразует дерево запроса перед планированием

- раскрывает представления
- применяет правила PostgreSQL
- добавляет дополнительные запросы, созданные rules
- передает преобразованное дерево запроса (query tree)

---

## 8.4. Planner

Оптимизатор, строит возможные планы выполнения и выбирает план с минимальной ожидаемой стоимостью

Он определяет:

- порядок чтения таблиц
- способ доступа к данным
- порядок соединения таблиц
- необходимость сортировки
- возможность параллельного выполнения
- передает план запроса (query plan)

План выбирается на основании статистики, размера таблиц, индексов и настроек PostgreSQL

Стоимость является оценкой планировщика.

---

## 8.5. Executor

Выполняет выбранный план запроса

План состоит из узлов:

```
Seq Scan
Index Scan
Hash Join
Sort
Aggregate
Limit
```

Каждый узел получает строки от дочерних узлов, обрабатывает их и передаёт выше

```
Limit
└── Sort
    └── Seq Scan
```

Executor также:

- читает страницы таблиц и индексов
- проверяет видимость строк по MVCC
- применяет фильтры
- выполняет JOIN и агрегации
- изменяет данные при `INSERT`, `UPDATE`, `DELETE`
- передаёт результат клиенту

![[Pasted image 20260722160647.png]]

`Executor` работает внутри backend-процесса, обслуживающего подключение клиента

Основные элементы:

- **Backend process** выполняет узлы плана и возвращает результат клиенту
	
- **work_mem** — лимит рабочей оперативной памяти для одной операции внутри backend-процесса
	
- **Shared Memory** — внутренний кеш PostgreSQL для страниц таблиц и индексов, прочитанных с диска, общий для всех backend-процессов
	  
- **Temporary files** создаются, когда операции Executor не могут удержать промежуточные данные в `work_mem`
	  
- **Database files** содержат страницы таблиц и индексов
	  
- **Background processes** выполняют фоновые задачи: checkpoint, запись WAL, autovacuum и сброс грязных страниц

---

# 9. План выполнения запроса

План выполнения — дерево операций, которые PostgreSQL собирается выполнить для получения результата

```
Limit
└── Sort
    └── Seq Scan on users
```

Каждая строка плана — отдельный узел:

```
Seq Scan
Index Scan
Sort
Hash
Nested Loop
Hash Join
Aggregate
```

Дочерние узлы передают строки родительским узлам, поэтому план обычно читают **снизу вверх и от самых глубоких отступов к корню**

---

## 9.1. EXPLAIN

`EXPLAIN` показывает план, выбранный планировщиком. Не выполняет запрос.

```sql
EXPLAIN
SELECT *
FROM users
WHERE age > 30;
```

Пример:

```
Seq Scan on users
    (cost=0.00..184.00 rows=2500 width=48)
    Filter: (age > 30)
```

Здесь:

- `Seq Scan`  $\rightarrow$ способ чтения данных
- `cost`          $\rightarrow$ оценочная стоимость узла
- `rows`          $\rightarrow$ ожидаемое количество выходных строк, передаваемых вверх
- `width`        $\rightarrow$ средний размер одной выходной строки в байтах
- `Filter`      $\rightarrow$ условие, проверяемое после чтения строки

---

## 9.2. EXPLAIN ANALYZE

`EXPLAIN ANALYZE` выполняет запрос и добавляет фактические показатели

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE age > 30;
```

```
Seq Scan on users
    (cost=0.00..184.00 rows=2500 width=48)
    (actual time=0.020..2.340 rows=2700 loops=1)
```

Расшифровка:

- actual time=0.020..2.340  $\rightarrow$ время до первой строки и до завершения узла
- rows=2700                          $\rightarrow$ фактически возвращённые строки за один запуск
- loops=1                                $\rightarrow$ сколько раз выполнялся узел

Время указывается в миллисекундах. Значения `actual time` и `rows` показываются в среднем на один `loop`

Время родительского узла уже включает работу дочерних узлов. `EXPLAIN ANALYZE` добавляет некоторую измерительную нагрузку и не учитывает передачу результата клиенту.

---

## 9.3. Основные параметры EXPLAIN

#### 1. `ANALYZE`

Выполняет запрос и показывает:

```
actual time
actual rows
loops
Planning Time
Execution Time
```

#### 2. `BUFFERS`

Показывает работу с блоками памяти и диска:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM users
WHERE id = 100;
```

```
Buffers: shared hit=3 read=2
```

- shared hit                  $\rightarrow$ блок найден в shared_buffers
- shared read              $\rightarrow$ блок пришлось прочитать из файла
- shared dirtied           $\rightarrow$ блок был изменён в памяти
- shared written          $\rightarrow$ блок был записан на диск
- temp read / written  $\rightarrow$ использовались временные файлы

`BUFFERS` особенно полезен, потому что запрос может быть медленным не из-за CPU, а из-за большого количества чтений страниц.

#### 3. `WAL`

Показывает объём WAL, созданный запросом:

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
UPDATE users
SET active = false
WHERE id = 100;
```

```
WAL: records=2 fpi=1 bytes=8420
```

Полезно при анализе массовых изменений и нагрузки на репликацию.

#### 4. `VERBOSE`

Добавляет более подробную информацию:

```sql
EXPLAIN (VERBOSE)
SELECT id, name
FROM users;
```

Показывает:

- полные имена объектов
- выходные столбцы каждого узла
- дополнительные внутренние выражения

#### 5. `SETTINGS`

Показывает настройки планировщика, отличающиеся от стандартных:

```sql
EXPLAIN (ANALYZE, SETTINGS)
SELECT *
FROM users;
```

Например:

```
Settings: work_mem = '128MB', random_page_cost = '1.1'
```

#### 6. `TIMING OFF`

Отключает измерение времени каждого узла, но оставляет фактические строки и общее время запроса

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT *
FROM users;
```

Это снижает измерительную нагрузку `EXPLAIN ANALYZE`

#### 7. `FORMAT`

Изменяет формат результата:

```sql
EXPLAIN (ANALYZE, FORMAT JSON)
SELECT *
FROM users;
```

Доступные форматы:

```
TEXT
JSON
YAML
XML
```

`JSON` и `YAML` удобны для программного анализа и визуализаторов планов.

На практике часто используется:

```sql
EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL,
    SETTINGS
)
SELECT ...;
```

# 10. Архитектура PostgreSQL

![[Pasted image 20260722171733.png]]

## 10.1. Клиенты и Pooler

Клиенты подключаются к PostgreSQL напрямую или через пул соединений

**Pooler** сокращает количество серверных соединений и распределяет клиентские запросы между существующими подключениями к PostgreSQL

## 10.2. Postmaster и Backend

**Postmaster** — главный процесс PostgreSQL, который принимает подключения и запускает backend-процессы

**Backend process** обслуживает конкретное серверное соединение в одном потоке:

- принимает SQL-запросы
- строит и выполняет планы
- управляет транзакцией
- возвращает результат клиенту

Операции `Sort`, `Hash Join`, `HashAggregate` и другие используют локальную память backend-процесса, ограниченную параметром `work_mem`

## 10.3. Shared Memory

**Shared Memory** — общая оперативная память экземпляра PostgreSQL, доступная backend-процессам и фоновым процессам

Основные области:

- `shared_buffers`                         $\rightarrow$ кеш страниц таблиц и индексов
- `wal_buffers`                               $\rightarrow$ WAL-записи перед записью в WAL-файлы
- `transaction status buffers` $\rightarrow$ информация о состояниях транзакций
- `other buffers`                           $\rightarrow$ блокировки и служебные структуры

`shared_buffers` содержит копии страниц файлов базы данных, а изменённые страницы остаются dirty до последующей записи на диск. `wal_buffers` хранит WAL-данные, которые ещё не были записаны в WAL-файлы.

## 10.4. Фоновые процессы

- `Archiver`                     $\rightarrow$ копирует WAL-сегменты в архив
- `Autovacuum`                 $\rightarrow$ очищает старые версии строк и обновляет статистику
- `WAL writer`                 $\rightarrow$ записывает WAL buffers в WAL-файлы
- `Checkpointer`             $\rightarrow$ выполняет checkpoint
- `Background writer`   $\rightarrow$ постепенно записывает dirty pages
- `Logging collector`   $\rightarrow$ записывает серверные логи

Фоновые процессы работают независимо от клиентских backend-процессов и используют общую память экземпляра.

## 10.5. Данные на диске

- data files      $\rightarrow$ страницы таблиц и индексов
- WAL files      $\rightarrow$ журнал изменений
- archive logs $\rightarrow$ архивные WAL-сегменты
- log files        $\rightarrow$ серверные логи
