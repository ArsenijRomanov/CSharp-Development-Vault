# 1. Определение

**Оптимистическая блокировка** — это механизм контроля конкурентных изменений, при котором данные заранее не блокируются, а конфликт обнаруживается в момент записи

Более точное название — **оптимистический контроль конкурентности**, потому что физическая блокировка строки обычно не устанавливается

Основная идея:

# 2. Проблема конкурентного обновления

Допустим, в базе находится товар:

```
id = 42
name = "Keyboard"
version = 5
```

Два клиента одновременно читают одну версию:

```
Клиент A:
name = "Keyboard"
version = 5

Клиент B:
name = "Keyboard"
version = 5
```

Клиент A сохраняет новое название:

```sql
UPDATE products
SET name = 'Gaming Keyboard',
    version = version + 1
WHERE id = 42
  AND version = 5;
```

После этого в базе:

```
name = "Gaming Keyboard"
version = 6
```

Клиент B пытается сохранить изменение, основанное на старой версии:

```sql
UPDATE products
SET name = 'Wireless Keyboard',
    version = version + 1
WHERE id = 42
  AND version = 5;
```

Но в базе уже находится:

```
version = 6
```

Поэтому условию `version = 5` не соответствует ни одна строка:

```
affected rows = 0
```

Это означает:

> Строка была изменена после того, как клиент её прочитал

Результат первого обновления не перезаписывается устаревшим вторым обновлением

# 3. Основной алгоритм

Оптимистическая конкурентность состоит из четырёх шагов:

```
1. Прочитать данные и concurrency token
2. Сохранить токен вместе с операцией или передать его клиенту
3. Выполнить UPDATE с условием token = expectedToken
4. Проверить количество изменённых строк
```

Пример:

```sql
UPDATE products
SET name = @name,
    version = version + 1
WHERE id = @id
  AND version = @expected_version;
```

Обработка результата:

```
Изменена одна строка
→ версия совпадала
→ обновление успешно

Изменено ноль строк
→ строка удалена или версия изменилась
→ конкурентный конфликт
```

---

# 4. Concurrency token

**Concurrency token** — значение, по которому определяется, изменилась ли строка после её чтения

В качестве токена могут использоваться:

- числовая версия
- `Guid`
- системная версия строки, управляемая базой
- отдельные значимые поля сущности

Главные требования к токену:

- приложение должно запомнить значение, прочитанное вместе с данными
- значение должно изменяться при каждом конкурентно значимом обновлении
- старое значение должно участвовать в условии `UPDATE` или `DELETE`
- конфликт должен обрабатываться приложением

# 5. Явная колонка `version`

Наиболее понятный вариант — собственная числовая версия:

```sql
CREATE TABLE products
(
    id      bigint PRIMARY KEY,
    name    text NOT NULL,
    version bigint NOT NULL DEFAULT 1   -- версия
);
```

Чтение:

```sql
SELECT id, name, version
FROM products
WHERE id = 42;
```

Обновление:

```sql
UPDATE products
SET name = @new_name,
    version = version + 1
WHERE id = @id
  AND version = @expected_version
RETURNING version;
```

Если запрос ничего не вернул, произошёл конфликт или строка была удалена

Версия должна измениться атомарно вместе с бизнес-данными

# 6. Оптимистическая конкурентность в EF Core

EF Core позволяет пометить свойство сущности как concurrency token

```sql
public sealed class Product
{
    public long Id { get; set; }

    public string Name { get; set; } = null!;

    public long Version { get; set; }
}
```

Настройка:

```sql
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>()
        .Property(product => product.Version)
        .IsConcurrencyToken();
}
```

При загрузке сущности EF Core запоминает два набора значений:

```
OriginalValues → значения, прочитанные из базы

CurrentValues  → текущие значения сущности в приложении
```

Например:

```
Original Version = 5
Current Version  = 5
```

После изменения:

```cs
product.Name = "Gaming Keyboard";
product.Version++;
```

EF Core формирует SQL приблизительно такого вида:

```sql
UPDATE products
SET name = @newName,
    version = @newVersion
WHERE id = @id
  AND version = @originalVersion;
```

Если база сообщает, что изменено ноль строк, `SaveChanges` выбрасывает `DbUpdateConcurrencyException`. Такой же механизм применяется при конкурентном удалении или при попытке удалить уже изменённую строку. Для вставки сущности конфликт уникальности обычно приводит не к `DbUpdateConcurrencyException`, а к исключению конкретного провайдера базы данных.

# 7. Использование `xmin` в PostgreSQL

PostgreSQL создаёт несколько системных колонок для каждой таблицы. Системная колонка `xmin` содержит идентификатор транзакции, создавшей текущую версию строки. Каждый `UPDATE` создаёт новую версию строки, поэтому её `xmin` изменяется.

Npgsql позволяет сопоставить свойство типа `uint` с `xmin` и использовать его как автоматически обновляемый concurrency token:

## `xmin`

Преимущества:

- не нужна дополнительная колонка
- обновляется PostgreSQL автоматически
- изменение любой части строки меняет токен
- удобно интегрируется с EF Core через Npgsql

Ограничения:

- привязка к PostgreSQL
- токен имеет техническую семантику
- любое обновление строки создаёт новый конфликт
- нельзя самостоятельно выбирать, какие изменения должны менять версию

## Собственная колонка `version`

Преимущества:

- понятная модель
- независимость от конкретной СУБД
- можно управлять моментом увеличения версии
- удобно использовать в API и предметной модели

Ограничения:

- приложение должно гарантированно обновлять токен
- все способы изменения данных должны соблюдать один протокол
- прямой SQL, забывающий увеличить версию, может нарушить механизм

EF Core также поддерживает токены, которыми управляет само приложение, например `Guid` или числовое свойство, настроенное через `IsConcurrencyToken()`. В этом случае приложение самостоятельно решает, когда создавать новое значение токена.

# 8. Когда применять

Оптимистическая конкурентность особенно подходит, когда:

- конфликты относительно редки
- чтение и запись находятся в разных HTTP-запросах
- данные редактируются пользователями
- нельзя долго удерживать открытую транзакцию
- важна высокая параллельность
- конфликт можно отклонить, объединить или безопасно повторить

Типичные сценарии:

- редактирование документа
- изменение пользовательского профиля
- административный CRUD
- изменение настроек
- редактирование карточки товара
- обновление редко конфликтующего агрегата
- API с `ETag` и `If-Match`
