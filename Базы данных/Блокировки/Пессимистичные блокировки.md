# 1. Определение

**Пессимистическая блокировка** — это подход к конкурентному доступу, при котором транзакция заранее блокирует данные для конфликтующих изменений и для получения несовместимых строчных блокировок

Основная идея:

~~~mermaid
%%{init: {"flowchart": {"useMaxWidth": true, "nodeSpacing": 12, "rankSpacing": 20}, "themeVariables": {"fontSize": "11px"}}}%%
flowchart LR
    A[Прочитать данные] --> B[Заблокировать их]
    B --> C[Проверить<br/>бизнес-условия]
    C --> D[Изменить данные]
    D --> E[Завершить<br/>транзакцию]
    E --> F[Освободить<br/>блокировку]
~~~

В PostgreSQL пессимистические блокировки строк обычно устанавливаются через locking clauses:

```sql
SELECT ...
FOR UPDATE;
```

Блокировка запрашивается конкретной SQL-командой внутри конкретной транзакции

---

# 2. Основной сценарий

Допустим, приложение должно уменьшить остаток товара

```sql
BEGIN;

SELECT id, available_count
FROM products
WHERE id = 100
FOR UPDATE;

-- проверка значения и бизнес-логика

UPDATE products
SET available_count = available_count - 1
WHERE id = 100;

COMMIT;
```

После выполнения `SELECT ... FOR UPDATE` найденная строка блокируется до завершения транзакции

В этот момент приложение может получить результат запроса и выполнить обычную проверку в C#:

```sql
if (product.AvailableCount <= 0)
{
    throw new OutOfStockException();
}
```

Хотя проверка выполняется в процессе приложения, транзакция PostgreSQL всё ещё открыта, поэтому блокировка строки продолжает удерживаться

~~~mermaid
%%{init: {"flowchart": {"useMaxWidth": true, "nodeSpacing": 8, "rankSpacing": 14}, "themeVariables": {"fontSize": "11px"}}}%%
flowchart TD
    A[Приложение<br/>открывает транзакцию]
    A --> B[Отправляет<br/>SELECT FOR UPDATE]
    B --> C[PostgreSQL возвращает строку<br/>и блокирует её]
    C --> D[Приложение<br/>выполняет проверку]
    D --> E[Приложение<br/>отправляет UPDATE]
    E --> F[Приложение<br/>выполняет COMMIT]
    F --> G[PostgreSQL<br/>освобождает блокировку]
~~~

# 3. Что происходит с конкурентными транзакциями

Транзакция A:

```sql
BEGIN;

SELECT *
FROM products
WHERE id = 100
FOR UPDATE;
```

Транзакция B одновременно выполняет:

```sql
BEGIN;

SELECT *
FROM products
WHERE id = 100
FOR UPDATE;
```

Вторая транзакция будет ждать

1. транзакция `A` получила блокировку
2. транзакция `B` пытается получить несовместимую блокировку
3. транзакция `B` останавливается
4. `A` выполняет `COMMIT` или `ROLLBACK`
5. `B` получает блокировку и продолжает


После освобождения блокировки вторая транзакция работает уже с результатом изменений первой транзакции

## Обычное чтение не блокируется

Обычный `SELECT` обычно не ждёт освобождения строчной блокировки

Транзакция A:

```sql
BEGIN;

SELECT *
FROM products
WHERE id = 100
FOR UPDATE;
```

Транзакция B:

```sql
SELECT *
FROM products
WHERE id = 100;
```

Упрощённо:

- Обычный `SELECT`                        $\rightarrow$ разрешён
- Конкурентный `UPDATE`              $\rightarrow$ ждёт
- Конкурентный `DELETE`              $\rightarrow$ ждёт
- Другой `SELECT FOR UPDATE`     $\rightarrow$ ждёт

# 4. Режимы строчных блокировок

PostgreSQL предоставляет четыре основных режима

## 4.1. `FOR UPDATE`

Самая сильная обычная строчная блокировка

```sql
SELECT *
FROM orders
WHERE id = 42
FOR UPDATE;
```

Она конфликтует с другими locking clauses этой строки и с конкурентными изменениями

Обычный `SELECT` при этом остаётся разрешён

---

## 4.2. `FOR NO KEY UPDATE`

Более слабый вариант `FOR UPDATE`

```sql
SELECT *
FROM orders
WHERE id = 42
FOR NO KEY UPDATE;
```

Используется, когда строку нужно изменить, но её ключевые значения не будут меняться

Она позволяет другой транзакции получить `FOR KEY SHARE`, но блокирует конкурентное изменение строки

---

## 4.3. `FOR SHARE`

Разделяемая блокировка

```sql
SELECT *
FROM documents
WHERE id = 42
FOR SHARE;
```

Она означает:

> Другие транзакции могут читать строку и также получать `FOR SHARE`, но не могут изменить или удалить её

Несколько транзакций могут одновременно держать `FOR SHARE`

```
Транзакция A → FOR SHARE
Транзакция B → FOR SHARE
Обе продолжают работу
```

Но конкурентный `UPDATE` будет ждать

---

## 4.4. `FOR KEY SHARE`

Самая слабая строчная блокировка

```sql
SELECT *
FROM customers
WHERE id = 42
FOR KEY SHARE;
```

Она защищает строку от:

- удаления
- изменения ключевых значений

При этом обычные изменения неключевых полей могут оставаться разрешёнными

Такой тип блокировки используется PostgreSQL, в частности, при обеспечении ссылочной целостности внешних ключей

---

## Сравнение

|Режим|Что защищает|
|---|---|
|`FOR UPDATE`|Строку от любых конкурентных изменений и locking clauses|
|`FOR NO KEY UPDATE`|Строку от конкурентных изменений, кроме совместимого `FOR KEY SHARE`|
|`FOR SHARE`|Строку от изменения и удаления, разрешая другие `FOR SHARE`|
|`FOR KEY SHARE`|Строку от удаления и изменения ключевых значений|

На практике прикладной код чаще всего явно использует:

```
FOR UPDATE
```

# 5. `NOWAIT`

По умолчанию PostgreSQL ждёт освобождения блокировки

```sql
SELECT *
FROM orders
WHERE id = 42
FOR UPDATE;
```

Чтобы сразу получить ошибку вместо ожидания:

```sql
SELECT *
FROM orders
WHERE id = 42
FOR UPDATE NOWAIT;
```

---

# 6. `SKIP LOCKED`

`SKIP LOCKED` не ждёт заблокированные строки, а пропускает их

```sql
SELECT id
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

# 7. Тайм-аут ожидания блокировки

Чтобы запрос не ждал блокировку бесконечно, можно установить `lock_timeout`

```sql
BEGIN;

SET LOCAL lock_timeout = '2s';

SELECT *
FROM orders
WHERE id = 42
FOR UPDATE;

COMMIT;
```

Если блокировка не будет получена за две секунды, PostgreSQL завершит запрос ошибкой

`SET LOCAL` действует только внутри текущей транзакции

Дополнительно могут использоваться:

```sql
SET LOCAL statement_timeout = '5s';
```

Ограничивает общее время выполнения команды

```sql
SET LOCAL idle_in_transaction_session_timeout = '30s';
```

Ограничивает время, в течение которого соединение может бездействовать с открытой транзакцией

Это особенно важно для пессимистических блокировок: зависшее приложение может оставить транзакцию открытой и удерживать блокировки

---

# 8. `deadlock_timeout`

Определяет, через какое время PostgreSQL начнёт проверять, не возникла ли взаимная блокировка

```sql
lock_timeout
→ сколько ждать блокировку

statement_timeout
→ сколько может выполняться команда целиком

deadlock_timeout
→ когда начать проверку на deadlock
```

---

# 9. Deadlock

Deadlock возникает, когда транзакции циклически ждут друг друга

Пример:

```sql
-- Транзакция A
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

SELECT *
FROM accounts
WHERE id = 2
FOR UPDATE;
```

```sql
-- Транзакция B
SELECT *
FROM accounts
WHERE id = 2
FOR UPDATE;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

PostgreSQL обнаружит deadlock и отменит одну из транзакций

---

# 10. Блокировки и write skew

Пессимистическая блокировка хорошо защищает конкретную известную строку, но не всегда защищает инварианты, зависящие от нескольких разных строк

Если две транзакции читают общий набор данных, но изменяют разные строки, их строчные блокировки могут не конфликтовать

Так может возникнуть аномалия **write skew**

---

# 11. Табличные блокировки

PostgreSQL позволяет явно блокировать таблицу:

```sql
BEGIN;

LOCK TABLE orders IN SHARE MODE;

-- работа с таблицей

COMMIT;
```

Наиболее сильный режим:

```sql
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
```

`ACCESS EXCLUSIVE` блокирует даже обычные `SELECT`

---

# 12. Когда использовать пессимистическую блокировку

Подходит, когда:

- есть конкретная существующая строка или понятный логический ресурс
- конфликтующие операции происходят достаточно часто
- операция короткая
- дешевле подождать, чем повторять всю транзакцию
- нужно последовательно изменять состояние агрегата
- требуется распределить задания между worker-процессами

Типичные примеры:

- изменение состояния заказа
- обработка конкретного платежа
- резервирование конкретного ресурса
- изменение баланса конкретного счёта
- выдача задач через `SKIP LOCKED`
- предотвращение параллельного запуска операции
