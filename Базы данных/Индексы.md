# 1. B-tree индекс

В PostgreSQL основной универсальный индекс — **B-tree**. По устройству он близок к классическому B+tree: внутренние узлы используются для навигации, а индексные записи находятся на листовых страницах, которые связаны между собой для эффективного последовательного обхода.

</div>

**Степень ветвления (`fan-out`)** — количество дочерних страниц, на которые может ссылаться один внутренний узел B-tree

В PostgreSQL она **не фиксирована** и зависит прежде всего от размера ключей: внутренняя страница обычно имеет размер `8 KB`, и в неё помещается столько ключей-разделителей и ссылок, сколько позволяет их размер. Для компактных ключей fan-out обычно составляет **сотни дочерних страниц**, грубо порядка `200–500`.

Таким образом дерево получается очень неглубоким. В реальных больших индексах обычно **2–4 уровня от корня до листьев**. Даже 4–5 уровней уже способны адресовать колоссальное количество записей

### Индексная запись

Для обычного индекса лист содержит примерно:

```
indexed value → TID
```

`TID` указывает на физическую версию строки в heap:

```
(block number, tuple offset)
```

Поэтому обычный поиск выглядит так:

```
B-tree
→ найти значение
→ получить TID
→ перейти в heap
→ прочитать tuple
```

Сам индекс полную строку обычно не хранит.

### Поиск

Ключи внутри дерева отсортированы. Поиск начинается с корня и на каждом уровне выбирает нужного потомка:

Высота дерева поддерживается небольшой и все листья находятся примерно на одной глубине, поэтому поиск имеет сложность:

```
O(log N)
```

На практике из за большой степени ветвления, даже для очень больших таблиц обычно требуется всего несколько переходов между страницами.

### Диапазонный поиск

После нахождения начала диапазона PostgreSQL может последовательно двигаться по связанным leaf pages.

Поэтому B-tree хорошо подходит для:

```sql
=
<
<=
>
>=
BETWEEN
ORDER BY
MIN / MAX
```

а также для поиска по префиксу некоторых типов данных, если условие может быть выражено через порядок индекса.

### Сортировка

Индекс физически хранит ключи в отсортированном порядке, поэтому PostgreSQL иногда может использовать его вместо отдельного `Sort`.

Можно задавать направление и порядок `NULL`:

```sql
CREATE INDEX idx
ON users(created_at DESC NULLS LAST);
```

### Изменения данных

`INSERT` 
- в индекс добавляется новая сущность

`UPDATE` в индексируемом столбце
- добавляется новая сущность
- старая останется до VACUUM

`UPDATE` без изменения индексируемого столбца
- HOT (если возможно): индекс не меняется
- non-HOT: новая index entry всё равно создаётся

`DELETE`
- сразу индекс обычно не меняется

`VACUUM`
- удаляет мёртвые index entries

### Составной B-tree

Для:

```sql
CREATE INDEX ON users(country, city, age);
```

ключи упорядочены лексикографически:

```
country
→ внутри country по city
→ внутри (country, city) по age
```

Поэтому особенно хорошо работают условия, начинающиеся с левых колонок индекса:

```
(country)
(country, city)
(country, city, age)
```

Наиболее эффективно составной B-tree используется начиная с левого столбца индекса. Если условие не содержит `country`, индекс обычно значительно менее полезен, поскольку значения `city` разбросаны между группами разных `country`. PostgreSQL иногда всё же может использовать такой индекс, например через skip scan или полный/bitmap scan индекса, если planner считает это выгодным

# 2. Hash индекс

`Hash`-индекс в PostgreSQL предназначен для **точного поиска по равенству**

```sql
CREATE INDEX idx_users_email_hash
ON users USING hash(email);
```

Для диапазонов и сортировки бесполезен

### Организация Hash-индекса

Hash-индекс организован как хеш-таблица с чейнингом, каждому значению остатка соответствует бакет.

Каждому бакету соответствует как минимум одна страница. Если она переполняется, добавляются overflow-страницы, все страницы одного бакета связаны как списочек. 

Внутри страницы хранятся записи:

```text
hash + TID
```

Сами tuple-байты могут физически лежать в произвольных местах страницы, а логический порядок поддерживается через отсортированный массив `line pointer`-ов:

```text
line pointers:
hash 10
hash 15
hash 20
hash 25
```

Поэтому внутри страницы поиск нужного hash выполняется по этому упорядоченному массиву, а при вставке новый slot добавляется в нужную позицию

При росте индекса PostgreSQL постепенно добавляет новые buckets и перераспределяет между ними часть записей — используется динамическая схема хеширования, а не полная перестройка всей таблицы сразу

### Поиск

```text
key
→ вычислить hash
→ определить bucket
→ найти записи с нужным hash
→ получить TID
→ проверить tuple в heap
```

### Операции записи

#### `INSERT`

Всегда создаётся новая индексная запись.

#### `UPDATE`

Если изменилось индексируемое значение:

```text
old value → old hash
new value → new hash
```

создаётся новая индексная запись для новой версии tuple

Если индексируемое значение не изменилось, но `UPDATE` не является HOT, новая версия всё равно имеет новый `TID`, поэтому нужна новая index entry

При `HOT Update` hash-индекс не изменяется.

#### `DELETE`

Сам `DELETE` обычно не удаляет запись из индекса:

# 3. GIN индекс

`GIN` (**Generalized Inverted Index**) — инвертированный индекс для значений, которые можно разложить на множество элементов

Идея:

- из объекта извлекаются элементы
- для каждого элемента хранится список строк, где он встречается
t
Например массив:

```
row 1 → [red, green]
row 2 → [green, blue]
```

GIN хранит наоборот:

```
red   → TID 1
green → TID 1, TID 2
blue  → TID 2
```

### Организация

В основе GIN есть **B-tree по индексируемым элементам**:

<div style="text-align: center;">

<img src="Pasted image 20260924151428.png" style="max-width: 300; width: 100%;">

</div>

В leaf entry хранится:

```
key → posting list
```

Если строк с таким значением мало, `posting list` хранится прямо в leaf tuple:

Если TID становится слишком много, список выносится в отдельную структуру — **posting tree**, которая тоже является B-tree.

### Как строится

Для каждой строки operator class определяет, какие элементы нужно извлечь (для `jsonb` это могут быть и ключи, и значения отдельно или пары совместно)

Например:

```
{"name":"Alice","role":"admin"}
```

GIN для `jsonb` извлекает индексируемые компоненты и строит связи:

```
element A → TID
element B → TID
element C → TID
```

### С какими данными используется

GIN сам по себе не привязан к конкретному типу

Типичные применения:

- `ARRAY`        — поиск элементов массива
- `jsonb`        — поиск ключей и значений
- `tsvector`  — полнотекстовый поиск
- `pg_trgm`    — поиск по триграммам строк
- `hstore`      — ключи и значения

Особенно полезен там, где **одно значение столбца содержит множество независимо индексируемых элементов**

### Важная особенность записи

Вставка в GIN потенциально дорогая, потому что одна строка может породить много index entries

Поэтому при включённом `fastupdate` новые записи сначала могут попадать в **pending list**, а позже пачкой переноситься в основное дерево

```
INSERT
→ pending list
→ batch merge
→ GIN tree
```

Это уменьшает стоимость частых мелких вставок, но требует периодической очистки pending list

# 4. BRIN

`BRIN` (**Block Range Index**) — компактный индекс, который хранит не ссылки на отдельные строки, а **summary-информацию по диапазонам heap-страниц**

### Организация

Heap делится на диапазоны страниц:

```
pages 0–127
pages 128–255
pages 256–383
```

Для каждого диапазона BRIN хранит summary, например для `created_at`:

```
0–127     → min=2026-01-01, max=2026-01-03
128–255   → min=2026-01-04, max=2026-01-06
256–383   → min=2026-01-07, max=2026-01-09
```

Запрос:

```
WHERE created_at BETWEEN '2026-01-07' AND '2026-01-08'
```

позволяет сразу отбросить диапазоны, которые точно не подходят

```
0–127     → skip
128–255   → skip
256–383   → возможно подходит
```

После этого PostgreSQL читает подходящие heap pages и проверяет реальные строки

### Структура

BRIN не использует дерево, он хранит:

- `metapage`           — служебная информация об индексе 
- `revmap`               — таблица соответствий: heap range $\longrightarrow$ где лежит его summary 
- `summary pages` — сами summary-записи диапазонов

### Когда эффективен

BRIN особенно хорош, когда значение колонки коррелирует с физическим порядком строк:

`created_at` $\nearrow$  $\Longrightarrow$  `physical position` $\nearrow$

Типичные случаи:

- логи
- события
- метрики
- append-only таблицы
- монотонные id

Если значения разбросаны случайно, summary становятся слишком широкими и индекс почти не помогает

### Размер

BRIN очень маленький, потому что одна запись описывает сразу множество heap pages

Поэтому он особенно полезен на очень больших таблицах

### `pages_per_range`

Определяет размер одного диапазона:

меньше `range`:
- точнее
- индекс больше

больше `range`:
- компактнее
- больше false positives

# 5. GiST

`GiST` (**Generalized Search Tree**) — обобщённый индексный механизм для данных, для которых обычный линейный порядок B-tree плохо подходит

GiST сам по себе не задаёт конкретную структуру поиска. Конкретный оператор для каждого типа определяет:

- как представлять данные
- как описывать поддеревья
- как проверять, может ли нужное значение находиться в ветви

Для пространственных данных GiST часто реализует **R-tree-подобную организацию**, где внутренние узлы хранят компактное описание содержимого поддерева

### Когда полезен

GiST хорошо подходит для запросов, связанных не только с равенством или порядком, а с более сложными отношениями:

- пересечение
- включение
- содержит / содержится
- близость
- поиск ближайших объектов (KNN)

Типичные данные:

- геометрия
- география / PostGIS
- range types (интервалы: временные, числовые)
- триграммы
- некоторые полнотекстовые сценарии

Примеры операций:

- объекты, пересекающие область
- объекты внутри области
- диапазоны, пересекающиеся с другим диапазоном
- $N$ ближайших точек

# 6. Варианты построения индексов

### 6.1. Составной индекс

Индекс сразу по нескольким колонкам:

```sql
CREATE INDEX ON users(country, city, age);
```

Для B-tree ключи упорядочены лексикографически.

Наиболее эффективно работает поиск, начинающийся с левых колонок индекса

---

### 6.2. Покрывающий индекс

Содержит все данные, необходимые запросу, что позволяет потенциально выполнить `Index Only Scan`

Дополнительные колонки можно добавить через `INCLUDE`:

```sql
CREATE INDEX ON users(email)
INCLUDE (name, age);
```

В PostgreSQL возможность не обращаться к heap также зависит от `Visibility Map`

---

### 6.3. Частичный индекс

Индексирует только часть строк таблицы:

```sql
CREATE INDEX ON users(email)
WHERE deleted_at IS NULL;
```

Полезен, когда запросы регулярно работают с небольшим подмножеством данных

- меньше индекс
- дешевле чтение
- дешевле обслуживание

---

### 6.4. Индекс по выражению

Индексируется результат выражения:

```sql
CREATE INDEX ON users(lower(email));
```

Позволяет эффективно выполнять запросы с тем же выражением:

```sql
WHERE lower(email) = 'user@example.com'
```

---

### 6.5. Уникальный индекс

Гарантирует уникальность индексируемого значения:

```sql
CREATE UNIQUE INDEX ON users(email);
```

В PostgreSQL уникальность поддерживается B-tree индексами

---

### 6.6. Порядок индекса

Для B-tree можно явно задать порядок:

```sql
CREATE INDEX ON events(created_at DESC NULLS LAST);
```

Полезно, если индекс должен одновременно использоваться для поиска и `ORDER BY`

---

### 6.7. Operator class

Определяет, как конкретный тип данных индексируется и какие операции поддерживаются

Например для `jsonb` + GIN:

```sql
USING gin(data jsonb_ops)

USING gin(data jsonb_path_ops)
```

Один и тот же тип индекса может работать с данными по разным правилам

---

### 6.8. Collation

Для строковых колонок можно задавать правила сравнения и сортировки:

```sql
CREATE INDEX ON users(name COLLATE "C");
```

`Collation` влияет на:

- порядок строк
- сравнение строк
- возможность использования индекса для конкретного запроса
