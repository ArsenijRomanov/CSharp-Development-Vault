# 1. dotnet-counters

**`dotnet-counters`** — CLI-инструмент .NET для мониторинга метрик работающего процесса в реальном времени и первичной диагностики производительности. Он читает метрики, опубликованные через `System.Diagnostics.Metrics` (`Meter API`) и более старый `EventCounter API`.

Подходит для быстрого ответа на вопрос **«что сейчас происходит с процессом?»** перед более глубоким анализом через dump, trace или profiler.

Например, можно посмотреть:

- CPU usage
- allocation rate
- размер GC Heap
- количество и частоту GC по поколениям
- размеры Gen 0 / Gen 1 / Gen 2, LOH и POH
- GC fragmentation
- exception rate
- ThreadPool thread count и queue length
- количество загруженных assembly
- JIT activity
- working set процесса

# 2. dotnet-dump

**`dotnet-dump`** — CLI-инструмент .NET для **снятия и анализа дампа памяти работающего процесса** без использования нативного debugger'а. Дамп фиксирует состояние процесса в конкретный момент времени и позволяет потом исследовать его отдельно.

Основные сценарии использования:

- поиск утечек памяти
- анализ содержимого managed heap
- поиск объектов, занимающих больше всего памяти
- анализ GC roots и причин, почему объект остаётся достижимым
- анализ потоков и stack trace
- поиск deadlock'ов
- анализ состояния процесса после crash

Сначала снимается dump:

```sh
dotnet-dump collect --process-id 1234
```

Затем он анализируется:

```sh
dotnet-dump analyze <dump-file>
```

Внутри доступны SOS-команды, например:

```sh
dumpheap -stat   # статистика объектов в heap
dumpobj          # содержимое конкретного объекта
gcroot           # кто удерживает объект
clrstack         # managed stack текущего потока
threads          # список потоков
syncblk          # locks и возможные deadlock'и
```

Для поиска утечки часто снимают несколько dumps в разные моменты времени и сравнивают, какие типы объектов продолжают расти по количеству или занимаемой памяти.

# 3. dotMemory

**dotMemory** — memory profiler от JetBrains для анализа использования памяти .NET-приложением. Он подключается к процессу, собирает данные о managed memory и позволяет снимать **memory snapshots** для последующего анализа через GUI.

Основные сценарии использования:

- поиск утечек памяти
- анализ объектов в managed heap
- поиск типов, занимающих больше всего памяти
- анализ **GC roots** и цепочек удержания объектов
- анализ allocation rate и memory traffic
- поиск избыточных аллокаций
- анализ Gen 0 / Gen 1 / Gen 2, LOH и POH
- сравнение нескольких snapshots и поиск объектов, количество которых со временем растёт

Типичный сценарий поиска утечки:

```
Snapshot 1
    ↓
воспроизведение нагрузки
    ↓
Snapshot 2
    ↓
Compare
    ↓
New / Survived objects
    ↓
GC Roots / retention paths
```

При сравнении snapshots dotMemory показывает количество и размер **новых, удалённых и переживших GC объектов**, что позволяет находить типы, экземпляры которых продолжают накапливаться.

# 4. Как измерять производительность

## 4.1. Stopwatch

**`Stopwatch`** — стандартный инструмент .NET для точечного измерения времени выполнения участка кода. Он подходит для быстрых локальных замеров и простой instrumentation внутри приложения.

```cs
var started = Stopwatch.GetTimestamp();

await service.DoWorkAsync();

var elapsed = Stopwatch.GetElapsedTime(started);
```

Измеренное время записывают в метрики или tracing.

## 4.2. BenchmarkDotNet

**BenchmarkDotNet** — библиотека для проведения воспроизводимых microbenchmarks .NET-кода. Она многократно запускает измеряемый код в отдельном benchmark-процессе, выполняет warmup-итерации, учитывает служебный overhead и затем собирает статистику по реальным измерениям.

Warmup нужен прежде всего для того, чтобы измерять уже **прогретое состояние runtime**: прошедший JIT и стабилизировавшееся выполнение. При многократных запусках естественным образом прогреваются и CPU/data caches.

Также можно измерять allocations и GC через `MemoryDiagnoser`.

```cs
[MemoryDiagnoser]
public class Benchmarks
{
    [Benchmark]
    public void Test()
    {
        // измеряемый код
    }
}
```

BenchmarkDotNet лучше всего подходит для **локальных вычислений и небольших изолированных участков кода**:

- алгоритмы
- serialization
- LINQ
- парсинг
- коллекции
- аллокации

Для полноценного измерения операций с БД, Redis, Kafka и другими внешними системами microbenchmark уже плохо отражает production-поведение:

```
application
   ↓
network
   ↓
connection pool
   ↓
DB
├── buffer/cache
├── query plan cache
├── disk / OS page cache
├── locks
└── concurrent load
```

Повторные benchmark-итерации сами изменяют состояние этих кешей и внешней системы, поэтому результат становится сильно зависим от окружения. Для таких сценариев обычно используют **integration/performance/load tests и production metrics**, а BenchmarkDotNet оставляют для изолированного кода.

# 6. Долгие транзакции в БД

**Долгая транзакция** — транзакция, которая остаётся открытой существенно дольше, чем требуется для выполнения непосредственно связанных с БД операций.

Типичный антипаттерн:

```sql
BEGIN TRANSACTION
        ↓
UPDATE / SELECT FOR UPDATE
        ↓
HTTP-запрос во внешний сервис
        ↓
ожидание ответа 500 мс
        ↓
ещё один запрос в БД
        ↓
     COMMIT
```

Проблема здесь не обязательно в медленном SQL. Транзакция может выполнить запрос за несколько миллисекунд, а затем сотни миллисекунд или секунд просто ждать сеть, файловую систему, очередь или другой внешний ресурс.

С учётом порядков задержек из таблицы это особенно опасно: операции с памятью и CPU занимают наносекунды, а сетевые вызовы — уже сотни микросекунд или миллисекунды. Поэтому включение внешнего I/O внутрь транзакции способно увеличить время её жизни на несколько порядков.

## Почему это плохо

Пока транзакция открыта, PostgreSQL может продолжать удерживать взятые ей блокировки до завершения транзакции. Другие транзакции, которым нужны конфликтующие блокировки, будут ждать.

Кроме этого:

- дольше удерживаются DB connection и ресурсы connection pool; Npgsql рекомендует держать соединения открытыми как можно меньше, поскольку это ограниченный ресурс
- растёт вероятность lock contention и цепочек ожидающих транзакций
- долгоживущие открытые транзакции могут мешать `VACUUM` удалять старые версии строк и способствовать table bloat
- при росте конкуренции увеличиваются latency и вероятность timeout/deadlock

Поэтому транзакцию желательно ограничивать только операциями, которым действительно нужна единая ACID-граница:

```
HTTP / вычисление
  ↓
BEGIN
DB
DB
COMMIT
```

Разумеется, вынести внешний вызов из транзакции можно не всегда — иногда бизнес-инвариант требует более сложной координации, например через Outbox/Saga.

## Как возникают

Причиной могут быть:

- ожидание HTTP/RPC
- отправка сообщения в брокер
- работа с файловой системой
- тяжёлые вычисления
- забытый `Commit` / `Rollback`
- приложение открыло транзакцию и осталось в состоянии `idle in transaction`

## Как отслеживать в PostgreSQL

Текущие транзакции можно найти через `pg_stat_activity`: в нём доступны состояние сессии, `xact_start`, выполняемый запрос и информация об ожиданиях.

Например:

```sql
SELECT
    pid,
    state,
    now() - xact_start AS transaction_duration,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Особенно подозрительно состояние:

```
idle in transaction
```

То есть клиент открыл транзакцию, выполнил запрос и затем перестал отправлять команды, не сделав `COMMIT` или `ROLLBACK`.

Для защиты PostgreSQL также предоставляет:

```
transaction_timeout
idle_in_transaction_session_timeout
lock_timeout
statement_timeout
```

Например `idle_in_transaction_session_timeout` принудительно завершает сессию, слишком долго простаивающую внутри открытой транзакции. PostgreSQL отдельно отмечает, что такие сессии могут долго удерживать блокировки и мешать очистке старых версий строк.

Для анализа блокировок используются `pg_locks`, `pg_stat_activity` и связанные с ними средства мониторинга PostgreSQL.
