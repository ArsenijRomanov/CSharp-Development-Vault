**Мониторинг** — процесс постоянного сбора, хранения и анализа метрик системы, чтобы понимать её текущее состояние, отслеживать отклонения и обнаруживать проблемы

### Примеры метрик

- **RPS** - количество запросов за секунду
- **Request count** — общее количество обработанных запросов
- **Latency / Response time** — время обработки одного запроса
- **Error rate** — доля запросов, завершившихся ошибкой
- **4xx / 5xx count** — количество клиентских и серверных HTTP-ошибок
- **CPU usage** — процент загрузки процессора
- **Memory usage** — объём используемой памяти
- **DB query rate** — количество запросов к БД за единицу времени
- **DB latency** — время выполнения запросов к БД
- **Active connections** — количество текущих сетевых или DB-соединений
- **Connection pool usage** — насколько заполнен пул соединений
- **DB query rate** — количество запросов к БД за единицу времени
- **DB latency** — время выполнения запросов к БД
- **Cache hit rate** — доля запросов, которые удалось обслужить из кеша
- **Cache miss rate** — доля запросов, для которых данных в кеше не оказалось
- **Queue length** — количество сообщений, ожидающих обработки в очереди
- **Message processing rate** — скорость обработки сообщений
- **Network throughput** — объём передаваемых по сети данных за единицу времени
- **Disk usage** — объём занятого дискового пространства

# 1. Push и Pull модели сбора метрик

### Pull

**Система мониторинга сама периодически запрашивает метрики у источников**

Основные проблемы:

- **Дискретность сбора** — между двумя scrape может произойти кратковременный скачок, который мониторинг не увидит
	  
- **Короткоживущие процессы** — job может запуститься и завершиться между scrape, поэтому мониторинг вообще не успеет его опросить
	  
- **Сетевая доступность targets** — monitoring-система должна иметь возможность подключиться ко всем источникам

Пример:
	
- Prometheus

### Push

**Источник сам периодически отправляет метрики в collector/backend**

Основные проблемы:

- **Недоступность системы сбора** — если Collector/backend упал, нужно решить, что делать с новыми метриками: потерять, буферизовать, retry
	
- **Retry усложняет pipeline** — нужны очереди, backoff, ограничения памяти, обработка перегрузки
	  
- **Backpressure** — медленный backend может начать тормозить exporter; важно не допустить, чтобы monitoring начал влиять на работу самого приложения
	  
- **Точка приёма может стать bottleneck** — тысячи приложений одновременно пушат telemetry в Collector/backend
	  
- **Сложнее определить смерть источника** — отсутствие новых данных может означать как падение приложения, так и сетевую проблему или неисправность exporter'а

Пример:
	
- OpenTelemetry

# 2. Виды метрик

Основные типы метрик — это не графики, а **способы накопления и представления измерений**

### 1. Counter — счётчик

Значение только увеличивается

Примеры: количество HTTP-запросов, ошибок, обработанных сообщений

Из Counter часто вычисляют **rate** (скорость изменения за временное окно), например RPS

### 3. UpDownCounter — изменяемый счётчик

Значение изменяется явными операциями прибавления и вычитания

Подходит, например, для количества выполняющихся сейчас операций

Собирает **распределение множества измерений по диапазонам**

## Производные метрики

RPS, error rate и p99 часто являются **не исходными типами метрик, а вычисляемыми значениями**

## Визуализация

`Line chart`, `bar chart`, `heatmap`, `gauge panel` и другие графики — это **не виды метрик**, а способы их визуализации

Для .NET через `System.Diagnostics.Metrics` основные инструменты выглядят так:

```cs

UpDownCounter<T>
Histogram<T>
ObservableGauge<T>
ObservableCounter<T>
ObservableUpDownCounter<T>
```

# 3. Prometheus

**Prometheus** — система мониторинга и хранения метрик в виде **time series**. Она периодически собирает метрики из приложений и инфраструктуры, хранит их и позволяет выполнять запросы через **PromQL**.

### Как получает метрики

Основная модель Prometheus — **Pull**

Источник публикует HTTP endpoint с метриками

Prometheus через заданный `scrape_interval` опрашивает этот endpoint и сохраняет полученные значения.

Например:

```
ASP.NET Core
→ /metrics
→ Prometheus

node_exporter
→ /metrics
→ Prometheus

PostgreSQL exporter
→ /metrics
→ Prometheus
```

### Exporter

**Exporter** — адаптер, который получает данные из системы, не умеющей сама отдавать Prometheus-метрики, и предоставляет их в понятном Prometheus формате

То есть Prometheus не ходит напрямую разбираться во внутренностях каждой БД или ОС — этим обычно занимается соответствующий exporter.

### Targets и Service Discovery

**Target** — конкретный endpoint, с которого Prometheus собирает метрики

Targets можно задать вручную или получать динамически через **service discovery**, что особенно важно в Kubernetes, где pod'ы постоянно появляются и исчезают.

### Как хранятся данные

Prometheus хранит данные как временные ряды:

```
metric name
+ labels
+ timestamp
+ value
```

Например:

```
http_requests_total{
    service="orders",
    method="POST",
    status="200"
}
→ 15230
```

Разный набор labels образует отдельную time series.

### PromQL

**PromQL** — язык запросов Prometheus

Например RPS:

```
rate(http_requests_total[5m])
```

Prometheus хранит исходные time series, а различные `rate`, агрегаты, проценты и другие показатели можно вычислять запросами.

### Общий pipeline

```
Application / OS / DB / Kafka
        ↓
instrumentation / exporter
        ↓
      /metrics
        ↑
        │ scrape
        │
    Prometheus
        ↓
      PromQL
        ↓
      Grafana
```

Prometheus также умеет вычислять **recording rules** и **alerting rules**, а уведомления обычно передаются в **Alertmanager**.

# 4. Grafana

**Grafana** — система визуализации и анализа telemetry-данных. Она подключается к внешним **data sources**, выполняет к ним запросы и отображает полученные данные в виде графиков, панелей и dashboards. Grafana умеет работать не только с метриками, но также с логами и трейcами.

Grafana обычно **не собирает и не хранит сами метрики**. В случае Prometheus pipeline выглядит так:

```
Application / exporter
        ↓
    Prometheus
        ↓
      PromQL
        ↓
      Grafana
```

То есть Prometheus отвечает за сбор и хранение time series, а Grafana использует его как источник данных и визуализирует результаты запросов.

### Data sources

Grafana может получать данные из разных backend-систем, например:

```
Prometheus → metrics
Loki       → logs
Tempo      → traces
PostgreSQL → SQL data
CloudWatch → cloud telemetry
```

Один dashboard может использовать несколько различных data sources.

### Основные возможности

- построение dashboards и различных визуализаций
- выполнение запросов к data sources
- исследование telemetry через Explore
- использование переменных и фильтров в dashboards
- сопоставление данных из разных источников
- создание **alert rules** и отправка уведомлений при выполнении заданных условий

# 5. Алерты

**Алерт** — сигнал о том, что заданное условие состояния системы выполняется и потенциально требует реакции.

Обычно алерт строится поверх метрик:

```
Metric
  ↓
Alert rule
  ↓
Condition выполняется
  ↓
Firing alert
  ↓
Notification / incident
```

Alert rule обычно содержит условие срабатывания, длительность (`for`), severity, labels для маршрутизации и описание проблемы.

С алертами обычно выполняют следующие действия:

- **Silence** — временно подавить уведомления, не прекращая вычисление самого алерта
- **Mute** — подавлять уведомления по расписанию
- **Disable** — отключить вычисление alert rule
- **Resolve** — состояние, в которое алерт переходит, когда условие больше не выполняется

В incident-management системах также используется **ACK (acknowledge)** — подтверждение, что инженер увидел инцидент и взял его в работу. 

Типичный pipeline:

```
Prometheus / Grafana
        ↓
    Alert rule
        ↓
Alertmanager / Grafana Alerting
        ↓
PagerDuty / Grafana IRM / Slack
        ↓
    On-call engineer
```
