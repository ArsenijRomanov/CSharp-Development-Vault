# 1. Что такое Onion Architecture

**Onion Architecture** — архитектурный подход, предложенный **Джеффри Палермо в 2008 году**, в котором **Domain Model помещается в центр системы, а остальные компоненты располагаются вокруг неё слоями с зависимостями, направленными внутрь**

Луковая архитектура разделяет основные идеи гексагональной:

- бизнес-логика должна быть независима от инфраструктуры
- технические детали располагаются снаружи
- внешние зависимости подключаются через абстракции

Главное развитие этой идеи — луковая **явно структурирует само Application Core**, выделяя внутри него несколько уровней и помещая Domain Model в самый центр

DDD хорошо сочетается с луковой архитектурой, но **не является обязательным условием её использования**

На приведённой схеме:

**Application Core** включает:
- Domain Model
- Domain Services
- Application Services

Снаружи находятся:

- User Interface
- Infrastructure
- Tests

---

# 2. Главное правило зависимостей

Главный принцип Onion Architecture:

> **Зависимости направлены только внутрь, к более центральным слоям**

Чем ближе слой к центру, тем меньше он знает о внешнем мире

Например:

- Domain Model не знает об Application Services, EF Core, HTTP или PostgreSQL
- Domain Services могут использовать Domain Model
- Application Services могут использовать Domain Model и Domain Services
- Infrastructure может зависеть от внутренних абстракций
- User Interface может вызывать Application Services

Это применение **Dependency Inversion Principle** на архитектурном уровне

# 3. Слои Onion Architecture

### 1. Domain Model

**Domain Model** — самый внутренний и независимый слой системы

Если используется DDD, здесь находятся:

- Entities
- Value Objects
- Aggregates
- Aggregate Roots
- бизнес-поведение
- invariants

Например:

```csharp
public class Order
{
    public OrderStatus Status { get; private set; }

    public void Confirm()
    {
        if (Status != OrderStatus.Created)
            throw new DomainException();

        Status = OrderStatus.Confirmed;
    }
}
```

Domain Model описывает **бизнес** и не должна знать, как вызывается или сохраняется приложение

---

### 2. Domain Services

**Domain Services** содержат бизнес-логику, которая относится к Domain, но естественно не принадлежит одной Entity или Value Object

```csharp
public class TransferService
{
    public void Transfer(Account from, Account to, Money amount)
    {
        from.Withdraw(amount);
        to.Deposit(amount);
    }
}
```

Domain Services:

- работают в терминах Domain Model
- содержат именно бизнес-правила
- не должны зависеть от технической инфраструктуры

Если правило естественно принадлежит Entity или Aggregate, его не нужно искусственно выносить в Domain Service

---

### 3. Application Services

**Application Services** реализуют use cases приложения и организуют взаимодействие Domain Model с необходимыми внешними возможностями

Например:

```csharp
public class ConfirmOrderUseCase(
    IOrderRepository orders,
    IUnitOfWork unitOfWork)
{
    public async Task ExecuteAsync(OrderId id)
    {
        var order = await orders.GetAsync(id);

        order!.Confirm();

        await unitOfWork.CommitAsync();
    }
}
```

Application Service отвечает за оркестрацию:

- загрузить необходимые данные
- вызвать Domain Model или Domain Service
- вызвать внешние зависимости через абстракции
- сохранить результат
- организовать последовательность действий use case

При этом само бизнес-правило `можно ли подтвердить заказ` остаётся в Domain Model

---

### 4.1. Infrastructure

**Infrastructure** — внешний слой, содержащий конкретные технические реализации

Например:

- EF Core
- Dapper
- PostgreSQL
- MongoDB
- Kafka
- RabbitMQ
- HTTP clients
- SMTP
- файловая система

Infrastructure знает о внутренних контрактах и реализует их

```csharp
public class EfOrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
}
```

Но Application Core не должен знать о `EfOrderRepository` или `DbContext`


### 4.2. User Interface

**User Interface** — внешний способ инициировать use cases приложения

Это не обязательно графический интерфейс

Например:

- ASP.NET Core API
- MVC
- Minimal API
- gRPC
- CLI
- desktop UI

HTTP endpoint может просто преобразовать внешний запрос во вызов Application Service:

```csharp
app.MapPost("/orders/{id}/confirm",
    (Guid id, ConfirmOrderUseCase useCase) =>
        useCase.ExecuteAsync(new OrderId(id)));
```

HTTP здесь является внешней деталью, а use case ничего не знает о маршрутах, JSON или HTTP status codes


### 4.3. Tests

**Tests** располагаются снаружи Application Core, потому что они являются одним из его потребителей

# Отличие от Hexagonal Architecture

**Hexagonal Architecture — Alistair Cockburn, 2005**

**Onion Architecture — Jeffrey Palermo, 2008**

Обе архитектуры разделяют фундаментальную идею:

> ядро приложения должно быть независимо от инфраструктуры

Но основной акцент различается

**Hexagonal Architecture** в первую очередь описывает **границу между Application Core и внешним миром** через ports и adapters, почти не регламентируя внутреннее устройство ядра

**Onion Architecture** дополнительно **структурирует Application Core концентрическими слоями и явно помещает Domain Model в самый центр**
