# 1. Гексагональная архитектура

**Гексагональная архитектура — архитектурный подход Алистера Кокберна (2005 год), в котором **логика приложения находится в независимом ядре, а взаимодействие с внешним миром происходит через явно определённые порты и подключаемые к ним адаптеры**.

<div style="text-align: center;">

</div>

Главная цель — не позволять способу доставки запросов, хранения данных и другим техническим деталям определять бизнес-логику приложения.

Ядро может содержать:

- Domain Model
- Use Cases / Application Services
- необходимые ядру абстракции внешних возможностей

Снаружи находятся:

- HTTP
- UI
- БД
- брокеры сообщений
- внешние API
- файловая система
- email и другие технические механизмы

Сам шестиугольник — только способ визуализации границы приложения. Шесть граней не означают шесть слоёв или шесть обязательных компонентов, в общем случае архитектура может быть сколь угодно-гексагональной

---

# 2. Основная структура

Гексагональная архитектура разделяет систему на три основные части:

**Application Core** — само приложение и его бизнес-логика

**Port** — контракт на границе ядра, определяющий способ взаимодействия с приложением

**Adapter** — конкретная техническая реализация взаимодействия через этот port

У приложения может быть сколько угодно входов и выходов. Например один и тот же use case может запускаться через HTTP, message consumer или CLI, не меняясь внутри

---

# 3. Ports

**Port** — интерфейс на границе Application Core, через который внешний мир взаимодействует с приложением или приложение взаимодействует с внешним миром.

Выделяют два направления.

### Inbound Port

**Inbound Port** описывает, какие операции приложение предоставляет внешнему миру.

Например:

```csharp
public interface IConfirmOrderUseCase
{
    Task ConfirmAsync(OrderId orderId);
}
```

Он выражает возможность приложения:

```text
ConfirmOrder
CreatePayment
RegisterUser
```

Внешнему коду не важно, каким классом use case реализован внутри

### Outbound Port

**Outbound Port** описывает возможность внешнего мира, которая нужна самому приложению.

Например:

```csharp
public interface IOrderRepository
{
    Task<Order?> GetAsync(OrderId id);
    void Add(Order order);
}
```

Другие примеры:

```text
IPaymentGateway
IEmailSender
IClock
IFileStorage
```

То есть:

**Inbound Port** — что можно попросить сделать приложение

**Outbound Port** — что приложение должно уметь попросить у внешнего мира

---

# 4. Adapters

**Adapter** — технический компонент, который соединяет конкретную внешнюю технологию с port приложения.

### Inbound Adapter

**Inbound Adapter** принимает внешний запрос и вызывает Inbound Port.

Примеры:

- ASP.NET Controller
- Minimal API endpoint
- gRPC service
- Kafka / RabbitMQ consumer
- CLI command
- GUI controller

Например controller преобразует HTTP-запрос в вызов `IConfirmOrderUseCase`

### Outbound Adapter

**Outbound Adapter** реализует Outbound Port и связывает приложение с конкретной инфраструктурой.

Например:

```csharp
public class EfOrderRepository : IOrderRepository
{
    // EF Core
}
```

Примеры:

- EF Core repository
- Dapper repository
- HTTP client внешнего сервиса
- Kafka producer
- SMTP email sender
- S3 file storage

Поэтому один port может иметь разные адаптеры:

```text
IOrderRepository

EfOrderRepository
DapperOrderRepository
InMemoryOrderRepository
```

Ядро при этом не меняется

# 5. Направление зависимостей

**Application Core не должен зависеть от конкретных внешних технологий**

Например use case не должен напрямую зависеть от:

```text
DbContext
NpgsqlConnection
HttpClient конкретного сервиса
Kafka producer
SMTP client
```

Вместо этого ядро определяет необходимый ему контракт:

```csharp
public interface IPaymentGateway
{
    Task<PaymentResult> ChargeAsync(Money amount);
}
```

А Infrastructure предоставляет реализацию:

```csharp
public class StripePaymentGateway : IPaymentGateway
{
}
```

Получается применение **Dependency Inversion Principle**

Application знает только абстракцию, а конкретный технический компонент зависит от контракта приложения

При этом runtime-вызов естественно идёт наружу:

```text
Use Case
→ IPaymentGateway
→ StripePaymentGateway
→ Stripe API
```

То есть **направление выполнения и направление зависимостей кода — не одно и то же**

# 6. Пример

Допустим, получаем пользователя по `Id`

```cs
// Inbound Port
public interface IGetUser
{
    Task<User?> ExecuteAsync(Guid id);
}
```

```cs
// Application — реализация Inbound Port
public class GetUser(IUserRepository users) : IGetUser
{
    public Task<User?> ExecuteAsync(Guid id) => users.GetAsync(id);
}
```

```cs
// Outbound Port
public interface IUserRepository
{
    Task<User?> GetAsync(Guid id);
}
```

```cs
// Inbound Adapter
app.MapGet("/users/{id:guid}",
    (Guid id, IGetUser useCase) => useCase.ExecuteAsync(id));
```

```cs
// Outbound Adapter
public class EfUserRepository(AppDbContext db) : IUserRepository
{
    public Task<User?> GetAsync(Guid id) => db.Users.FindAsync(id).AsTask();
}
```

HTTP Endpoint можно заменить на Kafka consumer, а EF Core на Dapper

# 7. Что даёт гексагональная архитектура

Основные преимущества:

- бизнес-логика изолирована от инфраструктуры
- внешние технологии можно заменять без переписывания ядра
- один use case может использоваться через разные способы входа
- Domain и Application проще тестировать без настоящей БД, HTTP или брокера
- зависимости от фреймворков локализуются во внешних компонентах
- границы приложения становятся явными
- инфраструктура адаптируется к приложению, а не приложение к инфраструктуре

При этом гексагональная архитектура **не диктует жёсткое устройство самого Application Core**. Внутри него можно использовать DDD, Rich Domain Model и другие подходы
