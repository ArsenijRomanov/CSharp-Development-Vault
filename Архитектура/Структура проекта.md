
Это распространённый способ физически разложить backend-проект в духе чистой / луковой / гексагональной архитектуры. Верхний уровень отражает архитектурные границы, а внутри проектов уже можно использовать кричащую архитектуру и группировать код по бизнес-фичам и use cases.

### 1. Domain

Содержит **Domain Model и бизнес-правила**:

- Entities
- Value Objects
- Aggregates
- Domain Services
- Domain Events
- invariants

Не должен зависеть от БД, HTTP, брокеров и других технических деталей.

---

### 2. Application

Содержит **use cases приложения и orchestration**:

- Commands / Queries
- Handlers / Application Services
- интерфейсы необходимых внешних зависимостей
- DTO внутренних use cases при необходимости
- validation сценариев

Зависит от `Domain`, но не от конкретной инфраструктуры.

---

### 3. Infrastructure

Содержит **реализации внешних технических зависимостей**:

- EF Core / Dapper
- repositories
- PostgreSQL
- Redis
- Kafka producers
- HTTP clients
- файловое хранилище

Реализует интерфейсы, определённые во внутренних слоях.

---

### 4. Host

**Исполняемый проект и Composition Root**.

Отвечает за:

- запуск приложения
- DI-регистрацию
- конфигурацию
- middleware
- связывание `Application` с `Infrastructure`
- подключение входных адаптеров

Именно `Host` обычно знает почти обо всех остальных проектах, потому что должен собрать приложение во время запуска.

---

### 5. HTTP Contract / GRPC Proto

Отдельные **transport contracts** конкретных внешних протоколов.

Например:

- `request` / `response DTO`
- `protobuf contracts`

Они описывают внешний контракт системы.

---

### 6. Kafka Listener

**Входной адаптер** для сообщений из брокера.

- Kafka message
- десериализация
- mapping
- Application Use Case


По тому же принципу могут существовать отдельные HTTP, gRPC, background job или CLI adapters.

---

### 7. Common

Небольшой набор **технических компонентов без принадлежности к конкретному бизнес-домену или слою**.

Например:

- общие extension methods
- `Result<T>` / `Error`
- guards
- общие технические primitives
- универсальные attributes
- небольшие инфраструктурно-независимые utilities

`Common` стоит держать минимальным: если тип можно осмысленно отнести к `Domain`, `Application` или другому конкретному компоненту, туда его и следует положить.

---

Внутри `Domain` и `Application` уже удобно применять **кричащую архитектуру**:

```
Application
├── Orders
│   ├── CreateOrder
│   ├── ConfirmOrder
│   └── CancelOrder
├── Payments
└── Customers
```
