
**REST (Representational State Transfer)** — архитектурный стиль для построения распределённых гипермедийных систем, сформулированный **Роем Филдингом в 2000 году**

REST описывает взаимодействие клиента и сервера через **ресурсы и их представления**. Это не протокол и не формат данных, хотя чаще всего REST реализуют поверх HTTP

```text
Resource
→ /orders/42

Representation
→ JSON / XML / HTML
```

## Принципы REST

### 1. Client–Server

Клиент и сервер разделены и могут развиваться независимо

- Client — интерфейс и взаимодействие с пользователем
- Server — данные и бизнес-логика

### 2. Stateless

Каждый запрос содержит всю информацию, необходимую для его обработки

Сервер не хранит скрытое состояние клиентской сессии между запросами, но может хранить состояние ресурсов

### 3. Cacheable

Ответы явно определяют возможность кэширования

- `Cache-Control` — можно ли сохранять ответ и как долго
- `ETag` — идентификатор конкретной версии ресурса
- `Last-Modified` — дата последнего изменения ресурса

### 4. Uniform Interface

Клиенты взаимодействуют с системой через единообразный интерфейс

Он включает:

- идентификацию ресурсов через URI
- изменение ресурсов через их представления
- самодостаточные сообщения
- HATEOAS — ссылки на доступные дальнейшие действия

### 5. Layered System

Клиент не знает, взаимодействует ли он напрямую с сервером или через промежуточные слои

### 6. Code on Demand

Необязательный принцип, позволяющий серверу передавать клиенту исполняемый код, например JavaScript

## REST поверх HTTP

HTTP-методы используются согласно своей семантике

URI обычно описывает ресурс, а не действие, в них не должно быть глаголов

```http
GET /orders/42
```
```http
POST /orders
```
```http
DELETE /orders/42
```

Само использование HTTP, JSON и CRUD ещё не делает API полностью RESTful. Строгий REST требует соблюдения всех обязательных архитектурных ограничений, включая Uniform Interface и HATEOAS.
