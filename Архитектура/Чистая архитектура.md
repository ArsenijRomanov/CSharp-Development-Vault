Чистая архитектура во многом **обобщает и формализует идеи гексагональной и луковой архитектур**: бизнес-логика находится в центре, инфраструктура снаружи, зависимости направлены внутрь

Основное развитие по сравнению с луковой архитектурой — более чёткое разделение ответственности слоёв и формализация взаимодействия между ними

### Слои

**Entities — Enterprise Business Rules**

Самые фундаментальные бизнес-правила системы

Если используется DDD, сюда концептуально попадает Domain Model:

- Aggregates
- Entities
- Value Objects
- Domain Services
- invariants

> `Entities` у Мартина — это **не конкретно DDD Entity**, а бизнес-ядро в более широком смысле

---

**Use Cases — Application Business Rules**

Сценарии работы конкретного приложения

```
ConfirmOrder
CreatePayment
RegisterUser
```

Use Case организует выполнение сценария:

```
получить данные
→ вызвать Domain Model
→ использовать внешние зависимости
→ сформировать результат
```

То есть этот слой примерно соответствует **Application Services** луковой архитектуры

---

**Interface Adapters**

Преобразуют данные между внутренней моделью приложения и внешним миром

Сюда относятся:

- Controllers
- Presenters
- Gateways
- маппинг request / response моделей
- persistence adapters

---

**Frameworks & Drivers**

Самый внешний слой с конкретными техническими деталями:

- ASP.NET Core
- EF Core
- PostgreSQL
- RabbitMQ
- UI
- внешние API
- устройства

---

### Dependency Rule

Главное правило осталось тем же, что и в луковой архитектуре, но сформулировано максимально явно:

> **зависимости исходного кода могут быть направлены только внутрь**

Внутренний слой ничего не знает о внешнем

---

### Кричащая архитектура

**Кричащая архитектура (Screaming Architecture)** — идея Роберта Мартина, **2011 год**, которая также повлияла на чистую архитектуру

Смысл: структура приложения должна в первую очередь показывать **что делает система**, а не какие технологии она использует

Плохо:

```
Controllers
Services
Repositories
Models
```

По такой структуре невозможно понять назначение приложения

Лучше, когда архитектура отражает domain и use cases:

```
Orders
Payments
Inventory

или

CreateOrder
ConfirmOrder
CancelOrder
```

Отсюда и сильный акцент чистой архитектуры на **Use Cases**

---

### Что в итоге добавила чистая архитектура

Если рассматривать развитие идей последовательно:

**гексагональная архитектура**  
- отделила Application Core от внешнего мира

**луковая архитектура**  
- структурировала само ядро слоями вокруг Domain Model  
- сделала направление зависимостей внутрь центральной идеей

**кричащая архитектура**  
- потребовала, чтобы структура системы отражала domain и use cases

**чистая архитектура**  
- объединила и формализовала эти идеи  
- разделила фундаментальные бизнес-правила и application-specific use cases  
- явно выделила Interface Adapters  
- окончательно сформулировала Dependency Rule и отношение к frameworks как к внешним деталям

То есть чистая архитектура — **не революционно новая архитектурная идея, а достаточно строгая финализация и унификация уже существовавшего семейства подходов**.
