## 1. Origin — источник страницы

> [!info] Определение  
> **Origin** — сочетание схемы, имени хоста и порта, определяющее источник документа или ресурса.

Для адреса:

```http
​
https://shop.example.com/catalog?page=2
```

Origin содержит:

- Схему — `https`
- Хост — `shop.example.com`
- Порт — `443`, стандартный для HTTPS

Два адреса имеют одинаковый origin, только если совпадают все три составляющие. Стандартный порт учитывается даже тогда, когда явно не указан в URL.

## 2. Site и его отличие от origin

> [!info] Определение  
> **Site** — понятие, используемое браузером для определения принадлежности адресов к одному сайту. В современных правилах `SameSite` учитываются схема и регистрируемый домен.

**Регистрируемый домен** — доменное имя, которое можно закрепить за собой через компанию-регистратора и использовать как основу для создания поддоменов.

Например, организация оформляет право использовать `example.com`. После этого она может самостоятельно создать:

- `shop.example.com` — для магазина
- `api.example.com` — для API
- `mail.example.com` — для почты

Во всех трёх адресах **регистрируемый домен — `example.com`**. Части `shop`, `api` и `mail` добавлены его владельцем; отдельно регистрировать эти поддомены не требуется.

При сравнении site поддомены и порты не разделяют адреса, а схема учитывается. 

Сравнение с `https://shop.example.com`:

|Адрес|Тот же origin?|Тот же site?|
|---|---|---|
|`https://shop.example.com/orders`|Да|Да|
|`https://api.example.com/orders`|Нет|Да|
|`https://shop.example.com:8443`|Нет|Да|
|`http://shop.example.com`|Нет|Нет|
|`https://other.example.net`|Нет|Нет|

**Same-site не означает same-origin.** Это разные границы, используемые разными механизмами:

- SOP и CORS опираются на origin
- Атрибут cookie `SameSite` опирается на site

## 3. SOP — Same-Origin Policy

> [!info] Определение  
> **Same-Origin Policy, SOP** — политика браузера, ограничивающая взаимодействие страницы и её скриптов с ресурсами другого origin.

Она нужна, чтобы открытый чужой сайт не получил доступ к другим приложениям, где пользователь уже вошёл.

Например:

1. Пользователь вошёл на `{http}https://bank.example` — браузер сохранил cookie банка
2. Затем открыл `{http}https://evil.example`
3. JavaScript чужой страницы пытается запросить `{http}https://bank.example/balance` и прочитать баланс

Если правила cookies допускают их отправку, банк может получить запрос, узнать пользователя и вернуть баланс. **Но браузер видит, что ответ банка пытается прочитать код страницы `evil.example`, и не предоставляет ему ответ**, если банк явно не разрешил такой доступ через CORS.

Без SOP чужая страница могла бы прочитать баланс и отправить его злоумышленнику.

SOP ограничивает, в частности:

- **Чтение HTTP-ответов другого origin** — например, баланса или списка сообщений через `{js}fetch()`, если сервер не разрешил чтение через CORS
- **Чтение и изменение DOM другой страницы** — например, чужая страница не может прочитать поля формы банка или изменить её кнопки, даже если банк открыт в отдельном окне или iframe
- **Чтение и изменение хранилищ другого origin** — например, JavaScript чужого сайта не может получить значения из `localStorage` или IndexedDB банка

Возможность отправить запрос не означает возможность прочитать ответ: сервер может обработать запрос, но браузер не предоставит ответ вызывающему скрипту. **SOP защищает от чтения данных другого origin**.

## 4. Способы отправки HTTP-запросов в браузере

Браузер может отправлять запросы разными способами. Они отличаются тем, **как формируется запрос и кому доступен полученный ответ**.

#### 1. Переход по ссылке

HTML-элемент `{html}<a>` задаёт ссылку:

```html
<a href="https://api.example.com/products">
    Открыть товары
</a>
```

При обычном нажатии браузер:

1. Отправляет `GET` по адресу из `href`
2. Получает ответ
3. Открывает полученный ресурс, обычно вместо текущей страницы

Если сервер возвращает HTML, браузер отображает страницу. Если возвращает JSON, переход сам по себе не превращает его в интерфейс со списком товаров.

**Важные моменты:**

- Обычная ссылка отправляет `GET`; выбрать `POST` через атрибут ссылки нельзя
- Переход на другой origin разрешён без CORS
- Открытие ресурса пользователю не предоставляет JavaScript исходной страницы доступ к его содержимому (SOP)

JavaScript может перехватить нажатие и выполнить другое действие. Тогда запрос отправляется выбранным скриптом способом, а не обычным переходом по ссылке.

#### 2. Отправка HTML-формы

HTML-элемент `{html}<form>` объединяет поля, значения которых нужно отправить серверу:

```html
<form action="https://api.example.com/orders" method="post">
    <input name="productId" value="42">
    <input name="quantity" value="2">
    <button type="submit">Создать заказ</button>
</form>
```

При нажатии кнопки браузер:

1. Собирает отправляемые значения полей
2. Использует `name` как имя каждого параметра
3. Отправляет запрос по адресу из `action`, используя метод из `method`
4. Обычно открывает полученный ответ вместо текущей страницы

Для приведённой формы тело `POST` по умолчанию имеет формат `application/x-www-form-urlencoded`:

```http
productId=42&quantity=2
```

**Важные моменты:**

- JavaScript для обычной отправки формы не требуется
- Обычная HTML-форма поддерживает методы `GET` и `POST`
- При `GET` значения добавляются в URL, при `POST` — передаются в теле запроса
- Форму можно отправить на другой origin без разрешения CORS
- Ответ открывается браузером, но автоматически не передаётся JavaScript исходной страницы для чтения

#### 3. Запрос из JavaScript через fetch()

`{js}fetch()` позволяет коду страницы отправить запрос **без перехода на новую страницу** и затем обработать ответ:

```js
async function loadProducts() {
    const response = await fetch(
        "https://api.example.com/products"
    );

    const products = await response.json();

    console.log(products);
}
```

При вызове `{js}loadProducts()`:

1. JavaScript вызывает `{js}fetch()`
2. Браузер отправляет запрос; по умолчанию используется `GET`
3. При разрешённом доступе JavaScript получает объект ответа
4. `{js}response.json()` читает тело ответа и преобразует JSON в JavaScript-значение

`{js}await` ожидает завершения соответствующей асинхронной операции.

Дальше код может использовать данные: например, создать элементы товаров на текущей странице. **Сам `fetch()` интерфейс не изменяет**.

**Важные моменты:**

- Текущая страница остаётся открытой
- В параметрах можно задать метод, заголовки и тело запроса
- При same-origin запросе CORS не требуется
- При cross-origin запросе доступ JavaScript к ответу требует разрешения CORS
- Некоторые cross-origin запросы требуют предварительной проверки перед отправкой основного запроса

Например, если страница открыта на `{http}https://shop.example.com`, запрос к `{http}https://api.example.com/products` является cross-origin: API должен разрешить браузеру предоставить ответ коду этой страницы.

## 5. CORS — разрешение взаимодействия между origins

> [!info] Определение  
> **Cross-Origin Resource Sharing, CORS** — механизм HTTP-заголовков, через который сервер сообщает браузеру, каким origins разрешено получать доступ к его ресурсам.

Например:

- Фронтенд открыт на `https://shop.example.com`
- API находится на `https://api.example.com`
- Фронтенд вызывает API через `{js}fetch()`

Origins различаются, поэтому API должен разрешить браузеру предоставить ответ этому фронтенду. 

Браузер добавляет в cross-origin запрос заголовок `Origin`:

```http
GET /products HTTP/1.1
Host: api.example.com
Origin: https://shop.example.com
```

API возвращает разрешение в заголовке ответа:

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://shop.example.com
Vary: Origin
Content-Type: application/json

[{"id":42,"name":"Keyboard"}]
```

Браузер сравнивает разрешённый origin с origin вызывающей страницы. При совпадении предоставляет ответ JavaScript.

Если разрешение отсутствует или origin не подходит, код страницы получает ошибку CORS. **Сам запрос при этом мог уже выполниться на сервере.**

`Vary: Origin` сообщает кешам, что ответ может зависеть от заголовка `Origin`.

В `Access-Control-Allow-Origin` указывается один origin или `*`. Список нескольких origins через запятую не поддерживается: сервер выбирает подходящий origin из своей политики.

## 6. Preflight — предварительная проверка запроса

Для некоторых cross-origin запросов браузер сначала проверяет, разрешает ли сервер запрошенный способ взаимодействия.

Такая проверка называется **preflight** и выполняется запросом `OPTIONS`.

#### Запросы без preflight

Обычно предварительная проверка не требуется, если одновременно соблюдаются ограничения:

- Метод — `GET`, `HEAD` или `POST`
- Установленные кодом заголовки входят в разрешённый CORS список и удовлетворяют ограничениям
- Если задан `Content-Type`, его тип — `application/x-www-form-urlencoded`, `multipart/form-data` или `text/plain`

Это часто называют **простыми запросами**. Для них основной запрос отправляется сразу, а возможность прочитать ответ проверяется после его получения. 

#### Запросы с preflight

Предварительная проверка требуется, например, для:

- Методов `PUT`, `PATCH` и `DELETE`
- `Content-Type: application/json`
- Заголовка `Authorization`
- Пользовательского заголовка вроде `X-CSRF-Token`

Таким образом, **не каждый `POST` вызывает preflight**, но cross-origin `POST` с JSON обычно вызывает.

Пример основного запроса:

```js
async function createOrder() {
    return await fetch("https://api.example.com/orders", {
        method: "POST",
        headers: {
            "Content-Type": "application/json"
        },
        body: JSON.stringify({
            productId: 42,
            quantity: 2
        })
    });
}
```

Перед ним браузер отправляет:

```http
OPTIONS /orders HTTP/1.1
Host: api.example.com
Origin: https://shop.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

Сервер отвечает:

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: Content-Type
```

При успешной проверке браузер отправляет основной `POST`. Если проверка не проходит, основной запрос не отправляется.

Разрешение preflight может кешироваться, поэтому перед каждым последующим запросом новый `OPTIONS` необязательно появляется. Даже после успешного preflight основной ответ должен содержать необходимые CORS-заголовки.
