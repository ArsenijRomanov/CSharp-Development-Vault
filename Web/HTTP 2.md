Цель HTTP/2 — ускорить передачу множества ресурсов между клиентом и сервером без изменения семантики HTTP. Оптимизация достигается мультиплексированием запросов в одном TCP-соединении, бинарными фреймами и сжатием заголовков HPACK.

Семантика HTTP не изменилась: сохранились методы, URI, заголовки и статус-коды. Изменился способ кодирования и передачи сообщений по сети.

### 1. Бинарный фрейминг

В HTTP/1.1 стартовая строка и заголовки передаются как текст:

```
GET /users/42 HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 25
```

Чтобы разобрать сообщение, сервер должен искать пробелы, символы `:`, окончания строк `\r\n` и пустую строку, отделяющую заголовки от тела

В HTTP/2 сообщение разбивается на бинарные **фреймы** с заранее определённой структурой:

```
[Length][Type][Flags][StreamId][Payload]
```

Получатель сразу знает:

- сколько байтов занимает фрейм
- какой это тип данных
- к какому потоку относится фрейм
- где начинается и заканчивается его содержимое

Основные типы фреймов:

```
HEADERS — заголовки
DATA — тело сообщения
SETTINGS — настройки соединения
RST_STREAM — отмена потока
WINDOW_UPDATE — управление потоком данных
```

Текст тоже передаётся в виде байтов, поэтому бинарность сама по себе не является магическим ускорением. Разница в том, что в HTTP/1.1 структура сообщения определяется текстовыми разделителями, а в HTTP/2 — отдельными числовыми полями фиксированного формата

Это даёт HTTP/2:

- более однозначный и удобный для машины разбор сообщений
- явные границы и типы фреймов
- возможность указывать `StreamId` и чередовать фреймы разных запросов
- основу для мультиплексирования и управления отдельными потоками

```
HTTP/1.1:
текстовая последовательность
запрос → ответ → запрос → ответ

HTTP/2:
бинарные фреймы
A1 → B1 → C1 → A2 → B2
```

При этом тело сообщения не обязано становиться бинарным: внутри `DATA`-фреймов всё ещё может передаваться JSON, XML, изображение или Protobuf

### 2. Сжатие заголовков HPACK

В HTTP/1.1 заголовки передаются как обычный текст и повторяются в каждом запросе:

```
GET /users HTTP/1.1
Host: example.com
Authorization: Bearer ...
User-Agent: Mozilla/5.0
Accept: application/json
```

Следующий запрос к тому же серверу снова содержит почти те же данные:

```
GET /orders HTTP/1.1
Host: example.com
Authorization: Bearer ...
User-Agent: Mozilla/5.0
Accept: application/json
```

При большом количестве небольших запросов заголовки могут занимать значительную часть передаваемых данных

В HTTP/2 заголовки сжимаются алгоритмом **HPACK**. Клиент и сервер поддерживают таблицы заголовков и могут передавать повторяющиеся имена и значения как короткие числовые индексы:

```
Первый запрос:
Authorization: Bearer ...
User-Agent: Mozilla/5.0
Accept: application/json

Следующие запросы:
ссылки на ранее переданные заголовки
```

HPACK использует:

- статическую таблицу часто встречающихся заголовков
- динамическую таблицу заголовков текущего соединения
- кодирование повторяющихся значений через индексы
- кодирование строк для дополнительного уменьшения размера

В результате по сети передаются в основном новые или изменившиеся заголовки:

```
HTTP/1.1:
полный набор заголовков → полный набор заголовков → полный набор заголовков

HTTP/2:
полный набор → ссылки + изменения → ссылки + изменения
```

Это уменьшает объём служебных данных и особенно полезно при большом количестве запросов с одинаковыми `Cookie`, `Authorization`, `User-Agent` и другими повторяющимися заголовками

При этом HPACK сжимает только заголовки. Тело сообщения сжимается отдельно, например с помощью `gzip` или `br`.

### 3. Потоки и мультиплексирование

В HTTP/1.1 одно TCP-соединение обычно используется для последовательной передачи запросов и ответов:

```
запрос A → ответ A → запрос B → ответ B
```

Пока не завершён ответ `A`, следующий запрос по этому соединению обычно ожидает освобождения соединения

В HTTP/1.1 существовал механизм pipelining, позволявший отправить несколько запросов подряд, но сервер должен был возвращать ответы в том же порядке:

```
Запросы: A → B → C
Ответы:  A → B → C
```

Если обработка запроса `A` занимала много времени, ответы `B` и `C` не могли обогнать его, даже если уже были готовы. Такая проблема называется **head-of-line blocking на уровне HTTP**

Для параллельной загрузки ресурсов клиенты начали открывать несколько TCP-соединений к одному серверу:

```
Соединение 1: запрос A → ответ A
Соединение 2: запрос B → ответ B
Соединение 3: запрос C → ответ C
```

Это позволяло выполнять запросы параллельно, но каждое дополнительное соединение создавало накладные расходы:

- отдельный TCP-handshake
- для HTTPS — отдельный TLS-handshake
- отдельный сокет и сетевые буферы
- отдельное состояние соединения в операционной системе
- отдельный [[Определения#^2dfc36|TCP slow start]]

Большое количество соединений расходует ресурсы клиента, сервера, прокси и балансировщиков

HTTP/2 решает эту проблему с помощью **потоков и мультиплексирования**

Каждый запрос и соответствующий ответ передаются в отдельном логическом потоке внутри одного TCP-соединения:

```
Одно TCP-соединение
├── Stream 1: запрос A / ответ A
├── Stream 3: запрос B / ответ B
└── Stream 5: запрос C / ответ C
```

Данные каждого потока разбиваются на фреймы, а фреймы разных потоков могут чередоваться:

```
A1 → B1 → C1 → A2 → C2 → B2
```

Каждый фрейм содержит `StreamId`, поэтому получатель понимает, к какому запросу он относится, и собирает потоки независимо:

```
Stream 1: A1 + A2
Stream 3: B1 + B2
Stream 5: C1 + C2
```

Благодаря этому несколько запросов и ответов могут одновременно передаваться через одно TCP-соединение. Медленный ответ одного потока не мешает передавать фреймы других потоков

```
HTTP/1.1:
несколько параллельных запросов
→ обычно несколько TCP-соединений

HTTP/2:
несколько параллельных запросов
→ несколько потоков в одном TCP-соединении
```

Мультиплексирование уменьшает количество соединений и связанные с ними затраты на установление TCP и TLS, сокеты, буферы и разгон каждого нового соединения

### 4. Управление потоком данных

В HTTP/1.1 управление потоком выполнялось только на уровне TCP-соединения

TCP сообщает отправителю, сколько байтов ещё помещается в буфер получателя. Если приложение не успевает читать данные, TCP-окно уменьшается, и отправитель замедляет или останавливает передачу

```
Приложение медленно читает данные
→ заполняется TCP-буфер
→ уменьшается окно TCP
→ останавливается всё соединение
```

TCP при этом видит только единый поток байтов и не понимает, к какому HTTP-запросу или ответу относятся данные. Поэтому он не может ограничить передачу одного сообщения независимо от остальных

Для HTTP/1.1 это было естественно, поскольку через соединение запросы обычно передавались последовательно. Но в HTTP/2 через одно соединение одновременно идут данные множества потоков, поэтому управления только на уровне TCP недостаточно

HTTP/2 добавляет собственное управление потоком на двух уровнях:

- Окно соединения — ограничивает общий объём данных всех потоков
- Окно потока — ограничивает данные конкретного Stream


Например:

```
Connection window: 8000 байт

Stream 1 window: 0 байт
Stream 3 window: 5000 байт
```

В этом случае `Stream 1` временно останавливается, но `Stream 3` может продолжить передачу

Когда получатель обработал данные и освободил буфер, он отправляет фрейм `WINDOW_UPDATE`:

```
WINDOW_UPDATE Stream 1 — увеличить окно конкретного потока
WINDOW_UPDATE Stream 0 — увеличить окно всего соединения
```

Чтобы отправить `DATA`-фрейм, свободное место должно оставаться и в окне потока, и в общем окне соединения

```
HTTP/1.1:
TCP управляет всем соединением целиком

HTTP/2:
TCP управляет соединением
+
HTTP/2 отдельно управляет соединением и каждым Stream
```

Это позволяет приостановить поток, который получатель не успевает обрабатывать, не блокируя передачу данных остальных потоков

### 5. Приоритизация потоков

В HTTP/1.1 клиент практически не мог управлять порядком передачи нескольких параллельных ресурсов внутри одного соединения

Запросы обрабатывались последовательно, а при использовании нескольких соединений порядок зависел от того, какое соединение освободится раньше:

```
Соединение 1: большой файл изображения
Соединение 2: CSS
Соединение 3: JavaScript
```

При этом не было единого механизма, позволяющего сообщить серверу, что, например, CSS важнее фонового изображения

В HTTP/2 клиент может передать серверу **подсказку о приоритете потока**:

```
Высокий приоритет:
CSS, JavaScript, основной HTML

Низкий приоритет:
изображения, аналитика, фоновые запросы
```

Сервер может учитывать эти приоритеты при распределении пропускной способности между потоками:

```
Одно TCP-соединение
├── Stream 1 — CSS       → передавать раньше
├── Stream 3 — JavaScript → передавать раньше
└── Stream 5 — изображение → можно передать позже
```

Это особенно полезно, когда одновременно готовы данные нескольких потоков, но пропускной способности недостаточно для их полной передачи

Важно, что приоритет — это **рекомендация, а не гарантия**. Сервер может учитывать её вместе со своей загрузкой и внутренней логикой планирования

Первоначальная схема HTTP/2 с зависимостями и весами потоков оказалась слишком сложной и была объявлена устаревшей. Современная схема приоритизации описывает более простые параметры, например срочность ресурса, но её поддержка зависит от конкретного клиента и сервера.

### 6. Ограничения HTTP/2

#### TCP head-of-line blocking

HTTP/2 устранил блокировку на уровне HTTP: медленный ответ одного потока не мешает передавать фреймы других потоков

Однако все потоки по-прежнему работают поверх одного TCP-соединения. TCP представляет данные как единый упорядоченный поток байтов

Если один TCP-пакет теряется, получатель не может передать приложению последующие байты, пока потерянный пакет не будет повторно доставлен:

```
Stream 1: A1
Stream 3: B1
Stream 5: C1 — пакет потерян
Stream 1: A2
Stream 3: B2
```

Хотя `A2` и `B2` относятся к другим HTTP/2-потокам, TCP временно задержит их, пока не восстановит пропущенные данные

```
HTTP/1.1:
head-of-line blocking на уровне HTTP

HTTP/2:
HTTP-блокировка устранена
TCP head-of-line blocking остался
```

То есть потоки HTTP/2 логически независимы, но на транспортном уровне используют общий упорядоченный поток TCP

#### Зависимость от одного TCP-соединения

Главное преимущество HTTP/2 — передача множества запросов через одно соединение — одновременно создаёт общую точку отказа

```
Одно TCP-соединение
├── Stream 1
├── Stream 3
├── Stream 5
└── Stream 7
```

Если соединение разрывается, одновременно прерываются все активные потоки внутри него

Причиной может быть:

- потеря сети
- закрытие соединения сервером
- тайм-аут прокси или балансировщика
- сбой клиента или сервера
- TCP `RST`

После этого клиенту приходится устанавливать новое TCP-соединение, повторно выполнять TLS-handshake и при необходимости повторять незавершённые запросы
