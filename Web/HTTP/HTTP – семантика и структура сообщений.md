# 1. Что такое HTTP

**HTTP (Hypertext Transfer Protocol)** — прикладной протокол обмена сообщениями между клиентом и сервером по модели **запрос–ответ**.

Клиент отправляет **HTTP-запрос** к ресурсу, идентифицированному через **URI**, сервер обрабатывает запрос и возвращает **HTTP-ответ**.

HTTP определяет:

- структуру запросов и ответов
- методы работы с ресурсами
- коды состояния ответа
- заголовки и тело сообщения

HTTP имеет **stateless-семантику**: каждый запрос рассматривается независимо и не требует сохранения протокольного состояния предыдущих запросов клиента. Состояние приложения при необходимости хранится отдельно.

# 2. URI, URL и структура адреса

**URI (Uniform Resource Identifier)** — идентификатор ресурса.

**URL (Uniform Resource Locator)** — URI, который дополнительно указывает, где ресурс находится и как к нему обратиться.

URL является разновидностью URI.

Пример URL:

```http
​
https://api.example.com:8080/users/42/orders?status=active&limit=10#details
```

Структура:

```http
​
scheme://host:port/path?query#fragment
```

- `scheme` — схема обращения к ресурсу
- `host` — имя хоста или IP-адрес
- `port` — порт, необязательная часть
- `path` — путь к ресурсу
- `query` — дополнительные параметры запроса в формате `key=value`, начинается после `?`, разделяются через `&`
- `fragment` — идентификатор части представления ресурса

Для примера выше:

```
scheme   = https
host     = api.example.com
port     = 8080
path     = /users/42/orders
query    = status=active&limit=10
fragment = details
```

`fragment` не передаётся серверу в HTTP-запросе и обрабатывается на стороне клиента.

# 3. HTTP-сообщение

Обмен в HTTP происходит с помощью двух типов сообщений:

- **HTTP Request** — запрос клиента
- **HTTP Response** — ответ сервера

Логически:
- $Request=StartLine(method,\ target)+Headers+Body$
- $Response=StartLine(status)+Headers+Body$

`Body` является необязательной частью.

## HTTP Request

Запрос содержит:

1. **Метод** — определяет семантику операции
2. **Target URI** — указывает ресурс, к которому обращается клиент
3. **Headers** — передают метаданные запроса
4. **Body** — передаёт данные запроса, если они необходимы

Пример:

~~~http
POST /users?notify=true
Content-Type: application/json
Authorization: Bearer token

{
  "name": "Alice"
}
~~~

Здесь:

~~~
POST                  → method
/users?notify=true    → request target
Content-Type: ...     → header
Authorization: ...    → header

{ "name": "Alice" }   → body
~~~

## HTTP Response

Ответ содержит:

1. **Status Code** — результат обработки запроса
2. **Reason Phrase / описание статуса** — текстовое представление статуса, если используется
3. **Headers** — метаданные ответа
4. **Body** — представление результата, если оно есть

Пример:

~~~http
201 Created
Content-Type: application/json
Location: /users/42

{
  "id": 42,
  "name": "Alice"
}
~~~

Здесь:

~~~text
201 Created             → status
Content-Type: ...       → header
Location: ...           → header

{ ... }                 → body
~~~

## Headers

**HTTP-заголовок** — именованное поле с метаданными сообщения.

Общий вид:

~~~http
​
Name: Value
~~~

Например:

~~~http 
​
Content-Type: application/json
Accept: application/json
Authorization: Bearer token
~~~

## Body

**Body** — необязательная полезная нагрузка HTTP-сообщения.

В теле могут передаваться:

- `JSON`
- `HTML`
- `XML`
- текст
- изображение
- файл
- бинарные данные

Тип содержимого обычно описывается заголовком:

~~~http
​
Content-Type: application/json
~~~

# 4. Методы и их семантика

**HTTP-метод** определяет семантику операции, которую клиент просит выполнить над целевым ресурсом.

Для методов важны два свойства:

- **Safe** — клиент не запрашивает изменение состояния ресурса
- **Idempotent** — несколько одинаковых запросов имеют тот же ожидаемый эффект, что и один запрос

## 4.1. GET

Запрашивает текущее представление целевого ресурса.

~~~http
GET /users/42
~~~

Свойства:

- safe
- idempotent
- request body не имеет общей HTTP-семантики, использовать его не рекомендуется

Параметры выборки обычно передаются через `query`:

~~~http
GET /users?status=active&limit=10
~~~

## 4.2. HEAD

Имеет ту же семантику, что и `GET`, но сервер не передаёт response body.

~~~http
HEAD /users/42
~~~

Используется для получения метаданных ресурса без передачи самого представления.

Свойства:

- safe
- idempotent
- request body не имеет общей HTTP-семантики, использовать его не рекомендуется
- нет response body

## 4.3. POST

Просит целевой ресурс выполнить специфичную для него обработку переданных данных.

Частый случай — создание нового ресурса:

```http
POST /users

{
  "name": "Alice"
}
```

Сервер создаёт нового пользователя и может вернуть:

```http
201 Created
Location: /users/42
```

Но семантика `POST` шире простого `create`: это произвольная обработка данных целевым ресурсом.

Свойства:

- не safe
- не idempotent по умолчанию

## 4.4. PUT

Создаёт или полностью заменяет состояние ресурса по URI, указанному клиентом.

~~~http
PUT /users/42

{ ... }
~~~

Клиент заранее знает, состояние какого ресурса он устанавливает.

Свойства:

- не safe
- idempotent
- request body предстваляет желаемое состояние целевого ресурса

Повтор одного и того же `PUT` устанавливает то же самое состояние.

Главное различие:

- `POST` — передать данные ресурсу для обработки
- `PUT`   — установить указанное состояние конкретного ресурса

## 4.5. PATCH

Выполняет **частичное изменение** состояния ресурса.

~~~http
PATCH /users/42

{ ... }
~~~

В отличие от `PUT`, не требуется передавать полное новое представление ресурса.

Свойства:

- не safe
- idempotency не гарантируется

## 4.6. DELETE

Просит удалить целевой ресурс.

~~~http
DELETE /users/42
~~~

Свойства:

- не safe
- idempotent
- request body не имеет общей HTTP-семантики, использовать его не рекомендуется

## 4.7. OPTIONS

Запрашивает информацию о доступных возможностях взаимодействия с ресурсом.

~~~http
OPTIONS /users/42
~~~

Например сервер может сообщить поддерживаемые методы.

Свойства:

- safe
- idempotent

## 4.8. CONNECT

Просит установить туннель до указанного назначения.

Используется в основном инфраструктурными компонентами и прокси.

Свойства:

- не safe
- не idempotent
- нет request body

## 4.9. TRACE

Просит вернуть клиенту полученное сервером HTTP-сообщение и используется для диагностики прохождения запроса.

Свойства:

- safe
- idempotent
- нет request body

На практике часто отключается.

## 4.10. QUERY

`QUERY` предназначен для выполнения **запроса к данным**, описание которого передаётся в теле HTTP-запроса.

Например:

~~~http
QUERY /users
Content-Type: application/json

{
  "status": "active",
  "age": {
    "from": 18,
    "to": 30
  }
}
~~~

Метод имеет свойства:

- safe
- idempotent
- предполагает наличие тела с описанием запроса

`QUERY` был стандартизирован IETF в **июне 2026 года** как RFC 10008.

Предпосылкой было наличие неудобного промежутка между `GET` и `POST`.

`GET` хорошо выражает безопасную идемпотентную выборку:

~~~http
GET /users?status=active&ageFrom=18&ageTo=30&...
~~~

но сложный запрос может стать слишком большим для практического размещения в URI, а тело `GET` не имеет общей определённой семантики.

`POST` позволяет удобно передать сложное описание запроса в теле:

~~~http
POST /users/search

{ ...complex query... }
~~~

но из самого метода уже не следует, что операция **safe** и **idempotent**.

`QUERY` заполняет этот промежуток:

$$
\boxed{
QUERY\approx\text{safe + idempotent query + body}
}
$$

RFC также определяет ответы `QUERY` как кэшируемые с учётом содержимого запроса при формировании cache key.

# 5. Status Codes

**HTTP status code** — трёхзначный код в ответе сервера, описывающий результат обработки запроса.

Первая цифра определяет класс ответа:

- `1xx` — информационный ответ
- `2xx` — успешная обработка
- `3xx` — перенаправление / работа с сохранённым представлением
- `4xx` — запрос не может быть выполнен из-за проблемы со стороны клиента
- `5xx` — сервер не смог выполнить корректный запрос


## 1xx — Informational

Промежуточные ответы: запрос ещё не завершён, но сервер сообщает клиенту некоторую информацию о его обработке.

На практике встречаются значительно реже остальных классов.

## 2xx — Success

| Status Code | Reason Phrase     | Description                                                       |
| ----------: | ----------------- | ----------------------------------------------------------------- |
|       `200` | `OK`              | Запрос успешно обработан.                                         |
|       `201` | `Created`         | Запрос успешно выполнен и в результате создан новый ресурс.       |
|       `202` | `Accepted`        | Запрос принят сервером, но его обработка ещё не завершена.        |
|       `204` | `No Content`      | Запрос успешно выполнен, но сервер не возвращает тело ответа.     |
|       `206` | `Partial Content` | Сервер возвращает только запрошенную часть представления ресурса. |

## 3xx — Redirection

| Status Code | Reason Phrase      | Description                                                                                                                                            |
| ----------: | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
|       `301` | Moved Permanently  | Ресурс постоянно доступен по другому URI. Может превращать `POST` в `GET`                                                                              |
|       `302` | Found              | Ресурс временно доступен по другому URI. Может превращать `POST` в `GET`                                                                               |
|       `303` | See Other          | Предлагает получить результат операции через другой URI, используя `GET`.                                                                              |
|       `304` | Not Modified       | Используется при условных запросах и кэшировании, означает, что сохранённое клиентом представление всё ещё актуально и передавать его заново не нужно. |
|       `307` | Temporary Redirect | Выполняет временное перенаправление с сохранением исходного HTTP-метода.                                                                               |
|       `308` | Permanent Redirect | Выполняет постоянное перенаправление с сохранением HTTP-метода.                                                                                        |

## 4xx — Client Error

| Status Code | Reason Phrase          | Description                                                                                    |
| ----------: | ---------------------- | ---------------------------------------------------------------------------------------------- |
|       `400` | Bad Request            | Сервер не может обработать запрос из-за некорректного содержимого или структуры запроса.       |
|       `401` | Unauthorized           | У запроса отсутствуют корректные данные аутентификации.                                        |
|       `403` | Forbidden              | Сервер понял запрос, но отказывается его выполнять.                                            |
|       `404` | Not Found              | Целевой ресурс не найден либо сервер не желает раскрывать его существование.                   |
|       `405` | Method Not Allowed     | Ресурс существует, но указанный HTTP-метод для него не поддерживается.                         |
|       `409` | Conflict               | Запрос конфликтует с текущим состоянием ресурса.                                               |
|       `412` | Precondition Failed    | Не выполнено условие, заданное клиентом в запросе. Полезно для optimistic concurrency control. |
|       `415` | Unsupported Media Type | Сервер не поддерживает формат содержимого запроса.                                             |
|       `422` | Unprocessable Content  | Структура и формат запроса понятны серверу, но его содержимое невозможно обработать.           |
|       `429` | Too Many Requests      | Клиент отправил слишком много запросов за некоторый период.                                    |

## 5xx — Server Error

| Status Code | Reason Phrase | Description |
|---:|---|---|
| `500` | Internal Server Error | Сервер столкнулся с непредвиденной ошибкой при обработке запроса. Общий код для внутренних ошибок, для которых нет более подходящего статуса. |
| `501` | Not Implemented | Сервер не поддерживает функциональность, необходимую для выполнения запроса. |
| `502` | Bad Gateway | Сервер, выступающий посредником, получил некорректный ответ от следующего сервера. |
| `503` | Service Unavailable | Сервис временно не способен обработать запрос. |
| `504` | Gateway Timeout | Сервер-посредник не дождался ответа от следующего сервера вовремя. |

# 6. Headers

**HTTP header** — именованное поле HTTP-сообщения, передающее метаданные о запросе, ответе, представлении ресурса или правилах его обработки.

Имена заголовков регистронезависимы.

HTTP позволяет использовать **пользовательские заголовки**, если стандартных недостаточно.

Например:

```http
​
X-Correlation-Id: 12345
X-Client-Version: 2.1
```

Их семантика определяется самим приложением или договорённостью между системами.

## 6.1. Представление и тело сообщения

#### 1. `Content-Type`

Определяет тип содержимого тела сообщения.

```http
​
Content-Type: application/json
```

Например:

```
application/json
application/xml
text/html
text/plain
image/png
```

Для текстовых форматов здесь же может указываться кодировка символов через параметр `charset`:

```http
​
Content-Type: text/plain; charset=utf-8
```

#### 2. `Content-Length`

Указывает размер тела сообщения в байтах.

#### 3. `Content-Encoding`

Указывает преобразование, применённое к содержимому, например сжатие:

```http
​
Content-Encoding: gzip
```

---

## 6.2. Согласование представления

#### 1. `Accept`

Сообщает, какие типы представления клиент готов получить:

```http
​
Accept: application/json, application/xml
```

#### 2. `Accept-Encoding`

Указывает поддерживаемые способы кодирования содержимого:

```http
​
Accept-Encoding: gzip, br
```

#### 3. `Accept-Language`

Указывает предпочитаемые языки:

```http
​
Accept-Language: ru, en
```

---

## 6.3. Идентификация и маршрутизация

#### 1. `Host`

Указывает имя хоста, к которому адресован запрос:

```http
​
Host: api.example.com
```

Позволяет одному серверу обслуживать несколько доменных имён.

#### 2. `User-Agent`

Передаёт информацию о клиенте:

```http
​
User-Agent: MyClient/1.0
```

#### 3. `Referer`

Может указывать URI ресурса, с которого был инициирован текущий запрос:

```http
​
Referer: https://example.com/catalog
```

#### 4. `Origin`

Указывает origin, от которого был инициирован запрос:

```http
​
Origin: https://example.com
```

Особенно важен для CORS.

---

## 6.4. Аутентификация

#### 1. `Authorization`

Передаёт данные аутентификации клиента:

```http
​
Authorization: Bearer token
```

#### 2. `WWW-Authenticate`

Сервер сообщает, какой механизм аутентификации требуется:

```http
​
WWW-Authenticate: Bearer
```

---

## 6.5. Cookies

#### 1. `Set-Cookie`

Сервер просит клиента сохранить cookie:

```http
​
Set-Cookie: sessionId=abc123
```

#### 2. `Cookie`

Клиент отправляет сохранённые cookie обратно серверу:

```http
​
Cookie: sessionId=abc123
```

---

## 6.6. Кэширование и условные запросы

Основные заголовки:

```
Cache-Control
ETag
Last-Modified
If-None-Match
If-Match
If-Modified-Since
If-Unmodified-Since
```

---

## 6.7. Управление ответом

#### 1. `Location`

Указывает URI другого ресурса.

Например после создания:

```http
201 Created
Location: /users/42
```

или при перенаправлении:

```http
302 Found
Location: /login
```

#### 2. `Retry-After`

Сообщает, когда клиенту следует повторить запрос:

```http
​
Retry-After: 30
```

Например вместе с:

```http
429 Too Many Requests
503 Service Unavailable
```

---

## 6.8. Диапазоны данных

#### `Range`

Клиент запрашивает только часть представления:

```http
​
Range: bytes=0-999
```

Используется, например, при загрузке больших файлов и видео.

# 7. Кэширование

**HTTP-кэширование** — механизм повторного использования ранее полученного ответа без необходимости каждый раз заново получать данные с сервера.

Кэш может находиться у клиента, прокси или CDN.

Основные механизмы:

- `Cache-Control` — задаёт правила кэширования
- `max-age` — сколько времени ответ считается актуальным
- `no-store` — не сохранять ответ
- `no-cache` — можно сохранить, но перед повторным использованием нужно проверить актуальность
- `ETag` / `Last-Modified` — позволяют идентифицировать версию представления
- `If-None-Match` / `If-Modified-Since` — используются для проверки актуальности сохранённой копии
- `304 Not Modified` — представление не изменилось, можно использовать локальную копию

# 8. Cookies и состояние

HTTP имеет **stateless-семантику**, поэтому для связывания нескольких запросов одного клиента приложение может использовать **cookies**.

Cookie — небольшая пара `name=value`, которую сервер передаёт клиенту, клиент сохраняет и затем автоматически отправляет обратно в подходящих запросах.

## Установка cookie

Сервер устанавливает cookie заголовком `Set-Cookie`:

```http
​
Set-Cookie: name=value; attribute1; attribute2=value
```

Если сервер устанавливает несколько cookies, обычно используется несколько заголовков:

```http
​
Set-Cookie: sessionId=abc123; HttpOnly
Set-Cookie: language=ru; Max-Age=86400
```

## Отправка cookie клиентом

При следующих подходящих запросах клиент отправляет сохранённые cookies через заголовок `Cookie`:

```http
​
Cookie: sessionId=abc123; language=ru; theme=dark
```

В `Cookie` клиент отправляет только пары `name=value`. Атрибуты вроде `Secure`, `Path` и `SameSite` обратно серверу не передаются — они определяют, **когда клиент имеет право отправить cookie**.

## Основные атрибуты `Set-Cookie`

### `Expires`

Задаёт абсолютное время истечения cookie:

```http
​
Set-Cookie: token=abc; Expires=Wed, 21 Oct 2026 07:28:00 GMT
```

### `Max-Age`

Задаёт время жизни cookie в секундах:

```http
​
Set-Cookie: token=abc; Max-Age=3600
```

Если ни `Expires`, ни `Max-Age` не указаны, cookie обычно является **сессионной** и хранится до окончания клиентской сессии.

### `Domain`

Определяет домен, для которого cookie может отправляться:

```http
​
Set-Cookie: language=ru; Domain=example.com
```

### `Path`

Ограничивает cookie определённой частью URL:

```http
​
Set-Cookie: token=abc; Path=/api
```

Такая cookie будет подходить для:

```
/api/users
/api/orders
```

но не для:

```
/images
```

### `Secure`

```http
​
Set-Cookie: token=abc; Secure
```

Указывает, что cookie должна отправляться только по защищённому соединению.

### `HttpOnly`

```http
​
Set-Cookie: sessionId=abc; HttpOnly
```

Запрещает доступ к cookie через клиентский JavaScript. При этом браузер продолжает автоматически отправлять её в HTTP-запросах.

Особенно полезно для session cookies.

### `SameSite`

Ограничивает отправку cookie при межсайтовых запросах.


- `Strict` — наиболее строго ограничивает межсайтовую отправку
- `Lax` — допускает cookie в некоторых обычных переходах между сайтами
- `None` — разрешает межсайтовую отправку; обычно используется вместе с `Secure`

Это один из механизмов защиты от CSRF.

# 9. Authentication и Authorization

## Authentication в HTTP

Клиент может передавать данные аутентификации через заголовок `Authorization`:

~~~http
​
Authorization: <scheme> <credentials>
~~~

Например:

~~~http
​
Authorization: Basic dXNlcjpwYXNz
~~~

или:

~~~http
​
Authorization: Bearer eyJ...
~~~

### `Basic`

Передаёт имя пользователя и пароль в виде:

~~~text
Base64(username:password)
~~~

`Base64` не является шифрованием, поэтому такой механизм должен использоваться только поверх защищённого соединения.

### `Bearer`

Клиент передаёт некоторый токен:

~~~http
​
Authorization: Bearer token
~~~

Обладатель токена получает связанные с ним полномочия.

Сам HTTP не определяет внутренний формат такого токена — это может быть, например, JWT или другой тип access token.

## `WWW-Authenticate`

Если сервер требует аутентификацию, он может вернуть:

~~~http
401 Unauthorized
WWW-Authenticate: Bearer
~~~

`WWW-Authenticate` сообщает клиенту, какую схему аутентификации можно использовать.

## `401` и `403`

- `401 Unauthorized` — клиент не предоставил подходящие данные аутентификации или они недействительны.

- `403 Forbidden` — сервер понял, кто клиент, но у него недостаточно прав для выполнения операции.

## Cookies и Authentication

Данные аутентификации необязательно передавать через `Authorization`.

Например после входа сервер может создать session:

~~~http
​
Set-Cookie: sessionId=abc123; HttpOnly; Secure
~~~

После этого браузер автоматически отправляет:

~~~http
​
Cookie: sessionId=abc123
~~~

а сервер по `sessionId` определяет пользователя.

Также через Cookie можно передавать аутентификационные данные.
