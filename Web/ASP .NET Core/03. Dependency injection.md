# 1. Назначение DI и контейнер сервисов

**Dependency Injection (DI)** — паттерн проектирования, при котором зависимости объекта создаются или выбираются внешним кодом и передаются объекту для использования. Сам объект объявляет, какие зависимости ему необходимы, но не отвечает за их создание и выбор конкретных реализаций.

**Зависимость** — объект, который другой объект использует для своей работы.

DI позволяет отделить использование зависимости от выбора её реализации и создания экземпляра. Это упрощает замену реализаций, тестирование и настройку приложения. 

---

### Получение зависимостей

Обычно класс объявляет зависимости через параметры конструктора:

```cs
public class OrderService
{
    private readonly IOrderRepository _repository;

    public OrderService(IOrderRepository repository)
    {
        _repository = repository;
    }
}
```

Здесь `OrderService` получает готовый объект через интерфейс `IOrderRepository`. Ему не нужно знать, какая конкретная реализация используется и как она создаётся.

Для теста можно передать тестовую реализацию, а в приложении — репозиторий, работающий с базой данных.

> Интерфейс не является обязательным условием DI: зависимость можно получать и по типу конкретного класса. Кроме того, DI возможен без контейнера — например, при ручном создании объекта с передачей зависимости в конструктор.

---

### Контейнер сервисов

В ASP.NET Core встроен **DI-контейнер** (IoC-контейнер тоже говорят), который автоматизирует предоставление зависимостей.

В контейнере регистрируют **сервисы** — зависимости, доступные приложению. Сервисом здесь может быть репозиторий, логгер или другой объект.

Контейнер:

- Определяет, какую реализацию предоставить для запрошенного типа.
- Создаёт экземпляр или возвращает существующий согласно регистрации и времени жизни.
- Предоставляет зависимости, необходимые для создания объекта.
- Управляет освобождением принадлежащих ему экземпляров.

Если `OrderService` зависит от репозитория, а репозиторий — от другого сервиса, контейнер разрешает всю цепочку зависимостей. 

**Разрешение зависимости** (_resolution_) — получение подходящего экземпляра по запрошенному типу.

---

### Регистрация и получение сервисов

В работе с контейнером участвуют два основных интерфейса:

|Интерфейс|Назначение|
|---|---|
|`IServiceCollection`|Хранит регистрации сервисов: какие типы предоставлять и по каким правилам|
|`IServiceProvider`|Предоставляет экземпляры сервисов на основании регистраций|

В ASP.NET Core сервисы обычно регистрируют через `builder.Services` **до вызова `builder.Build()`**. После сборки приложения они доступны через провайдер и поддерживаемые механизмы внедрения.

**Объявление параметра само по себе не включает DI для любого метода или класса.** Автоматическое внедрение работает там, где объект создаёт контейнер или параметры заполняет инфраструктура ASP.NET Core. При самостоятельном вызове метода или конструктора аргументы передаёт вызывающий код.

# 2. `IServiceCollection`: регистрация зависимостей

**`IServiceCollection` — коллекция регистраций сервисов**, на основании которой строится DI-контейнер. Интерфейс наследует `IList<ServiceDescriptor>`:

```cs
public interface IServiceCollection : IList<ServiceDescriptor>
{
}
```

Каждый `ServiceDescriptor` описывает регистрацию:

|Сведения|Назначение|
|---|---|
|Тип сервиса|Тип, по которому запрашивают зависимость|
|Реализация|Тип реализации, фабрика или готовый экземпляр|
|Время жизни|Правило создания и повторного использования экземпляров|

Таким образом, коллекция хранит **описания регистраций**. Получение объектов выполняется через `IServiceProvider`.

В ASP.NET Core коллекция доступна через `builder.Services`:

```cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IOrderRepository, OrderRepository>();

var app = builder.Build();
```

Регистрации добавляют до `builder.Build()`. **Регистрация типа или фабрики сама по себе не создаёт экземпляр сервиса.**

---

### Основные методы регистрации

Для регистрации используются методы расширения из `ServiceCollectionServiceExtensions`:

|Метод|Время жизни|
|---|---|
|`AddTransient`|Новый экземпляр при каждом разрешении|
|`AddScoped`|Один экземпляр в пределах scope|
|`AddSingleton`|Один экземпляр на контейнер|

Эти методы возвращают тот же `IServiceCollection`, поэтому вызовы можно объединять в цепочку.

У них аналогичные формы регистрации. Ниже перегрузки разобраны преимущественно на примере `AddScoped`; время жизни рассматривается отдельно.

---

### Регистрация типа реализации

Основные сигнатуры:

```cs
public static IServiceCollection AddTransient<TService, TImplementation>(
    this IServiceCollection services)
    where TService : class
    where TImplementation : class, TService;

public static IServiceCollection AddScoped<TService, TImplementation>(
    this IServiceCollection services)
    where TService : class
    where TImplementation : class, TService;

public static IServiceCollection AddSingleton<TService, TImplementation>(
    this IServiceCollection services)
    where TService : class
    where TImplementation : class, TService;
```

- `TService` — тип, по которому запрашивают зависимость.
- `TImplementation` — конкретная реализация, которую предоставляет контейнер.

```cs
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
```

При запросе `IOrderRepository` контейнер предоставляет `OrderRepository`. Для создания объекта он получает необходимые зависимости его публичного конструктора. 

**Такая регистрация не регистрирует `OrderRepository` как отдельный тип сервиса.** Получение по `IOrderRepository` и получение по `OrderRepository` — разные запросы к контейнеру.

---

### Регистрация конкретного класса

Если отдельный интерфейс не требуется, класс можно зарегистрировать по его собственному типу:

```cs
public static IServiceCollection AddScoped<TService>(
    this IServiceCollection services)
    where TService : class;
```

```cs
builder.Services.AddScoped<OrderService>();
```

Здесь тип сервиса и тип реализации совпадают: зависимость запрашивают как `OrderService`.

Этот способ предназначен для классов, экземпляры которых контейнер может создать. Регистрация интерфейса без реализации или фабрики не указывает контейнеру, какой объект предоставить.

---

### Регистрация через фабрику

Фабрика позволяет явно определить способ создания объекта:

```cs
public static IServiceCollection AddScoped<TService>(
    this IServiceCollection services,
    Func<IServiceProvider, TService> implementationFactory)
    where TService : class;
```

Также можно явно указать тип реализации:

```cs
public static IServiceCollection AddScoped<TService, TImplementation>(
    this IServiceCollection services,
    Func<IServiceProvider, TImplementation> implementationFactory)
    where TService : class
    where TImplementation : class, TService;
```

Пример:

```cs
builder.Services.AddScoped<IOrderRepository>(provider =>
{
    var connectionFactory =
        provider.GetRequiredService<IConnectionFactory>();

    return new OrderRepository(connectionFactory);
});
```

Фабрика получает `IServiceProvider`, через который можно разрешить необходимые зависимости.

**Она вызывается, когда контейнеру требуется создать экземпляр**, с учётом выбранного времени жизни. При регистрации делегат сохраняется для последующего вызова. 

---

### Регистрация готового экземпляра

Для уже созданного объекта используется перегрузка `AddSingleton`:

```cs
public static IServiceCollection AddSingleton<TService>(
    this IServiceCollection services,
    TService implementationInstance)
    where TService : class;
```

```cs
var client = new ApiClient("https://example.com");

builder.Services.AddSingleton<ApiClient>(client);
```

При запросе `ApiClient` контейнер возвращает переданный экземпляр. Аналогичных перегрузок с готовым экземпляром у `AddScoped` и `AddTransient` нет. 

---

### Перегрузки с `Type`

Помимо generic-перегрузок доступны варианты, принимающие объекты `Type`:

```cs
public static IServiceCollection AddScoped(
    this IServiceCollection services,
    Type serviceType);

public static IServiceCollection AddScoped(
    this IServiceCollection services,
    Type serviceType,
    Type implementationType);

public static IServiceCollection AddScoped(
    this IServiceCollection services,
    Type serviceType,
    Func<IServiceProvider, object> implementationFactory);
```

Например:

```cs
builder.Services.AddScoped(
    typeof(IOrderRepository),
    typeof(OrderRepository));
```

Эти формы полезны, когда типы определяются во время выполнения. Они также позволяют регистрировать **открытые generic-типы**:

```cs
builder.Services.AddScoped(
    typeof(IRepository<>),
    typeof(Repository<>));
```

Такая регистрация позволяет разрешать, например, `IRepository<Order>` через `Repository<Order>`.

---

### Несколько регистраций одного типа

Методы `AddTransient`, `AddScoped` и `AddSingleton` **добавляют новую регистрацию**, даже если такой тип сервиса уже зарегистрирован:

```cs
builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();
```

Поведение зависит от запрашиваемого типа:

|Запрашиваемая зависимость|Результат|
|---|---|
|`INotifier`|Последняя регистрация — `SmsNotifier`|
|`IEnumerable<INotifier>`|Все зарегистрированные реализации в порядке регистрации|

Предыдущая регистрация не удаляется: она остаётся доступной при получении всех реализаций.

---

### Регистрация групп сервисов

Методы вроде:

```cs
builder.Services.AddControllers();
builder.Services.AddAuthentication();
builder.Services.AddAuthorization();
```

являются методами расширения, которые регистрируют сервисы соответствующего механизма, а также могут выполнять его настройку.

**Регистрация сервисов не добавляет middleware в конвейер.** Например, `AddAuthentication` регистрирует сервисы аутентификации, а `UseAuthentication` подключает middleware обработки запросов.

# 3. Время жизни: `Transient`, `Scoped`, `Singleton`

**Время жизни сервиса (lifetime)** определяет, когда DI-контейнер создаёт экземпляр и в каких пределах повторно использует его.

Встроенный контейнер поддерживает три варианта:

|Время жизни|Повторное получение в одном scope|Получение в другом scope|
|---|---|---|
|`Transient`|Новый экземпляр|Новый экземпляр|
|`Scoped`|Тот же экземпляр|Другой экземпляр|
|`Singleton`|Тот же экземпляр|Тот же экземпляр|

Эти правила относятся к разрешению сервиса через контейнер. Вызов метода уже полученного объекта не приводит к созданию новой зависимости. 

---

### `Transient`

**Новый экземпляр создаётся при каждом разрешении зависимости.**

```cs
builder.Services.AddTransient<IOrderRepository, OrderRepository>();
```

Если два сервиса получают `IOrderRepository` через свои конструкторы, каждому предоставляется отдельный экземпляр — даже в пределах одного HTTP-запроса.

Аналогично, два последовательных вызова:

```cs
var first = context.RequestServices.GetRequiredService<IOrderRepository>();

var second = context.RequestServices.GetRequiredService<IOrderRepository>();

bool same = ReferenceEquals(first, second); // false
```

создадут разные экземпляры при обычной регистрации типа реализации.

`Transient` подходит, когда экземпляр не требуется разделять между потребителями. При частом разрешении нужно учитывать стоимость создания объектов.

---

### `Scoped`

**Один экземпляр создаётся и повторно используется в пределах одного scope.**

**Scope** — область, внутри которой контейнер разделяет scoped-экземпляры между потребителями.

В ASP.NET Core для каждого HTTP-запроса предусмотрен отдельный scope. Провайдер этой области доступен через `HttpContext.RequestServices`.

```cs
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
```

Все компоненты, разрешающие `IOrderRepository` в scope одного запроса, получают один экземпляр:

```cs
var first = context.RequestServices.GetRequiredService<IOrderRepository>();

var second = context.RequestServices.GetRequiredService<IOrderRepository>();

bool same = ReferenceEquals(first, second); // true
```

Для другого HTTP-запроса будет создан другой экземпляр, даже если запросы проходят по одному соединению.

Экземпляр создаётся при первом разрешении в scope. Если сервис не запрашивали, создавать его не требуется.

`Scoped` подходит для состояния и ресурсов, которые должны быть общими в пределах запроса. Например, `AddDbContext` по умолчанию регистрирует `DbContext` как scoped-сервис. **Scoped не обеспечивает потокобезопасность:** один запрос тоже может выполнять параллельные операции.

---

### `Singleton`

**Контейнер предоставляет один экземпляр для данной регистрации всем потребителям**, независимо от scope и HTTP-запроса.

```cs
builder.Services.AddSingleton<IOrderRepository, OrderRepository>();
```

При регистрации типа или фабрики экземпляр обычно создаётся при первом разрешении и используется до освобождения контейнера. Для основного контейнера ASP.NET Core это обычно время работы приложения.

При регистрации готового экземпляра контейнер использует переданный объект:

```cs
builder.Services.AddSingleton<ApiClient>(client);
```

Singleton может одновременно использоваться разными запросами, поэтому **его реализация должна быть потокобезопасной**. Данные конкретного запроса нельзя хранить в его общих полях.

Такое время жизни подходит для сервисов, которые должны разделяться всем приложением, например общего кеша.

---

### Время жизни зависимостей

**Время жизни потребителя не изменяет регистрацию его зависимости**, но потребитель может удерживать полученный экземпляр.

#### Singleton и transient

Если singleton получает transient-зависимость через конструктор, она создаётся при создании singleton. Пока singleton хранит ссылку, он использует этот же экземпляр.

`Transient` означает «новый при каждом разрешении», а не «новый при каждом вызове метода singleton». Такая регистрация допустима, но удерживаемая зависимость должна подходить для длительного и потенциально одновременного использования.

#### Singleton и scoped

**Scoped-зависимость нельзя напрямую внедрять в singleton.** Она предназначена для определённого scope, тогда как singleton используется за его пределами.

При включённой проверке областей контейнер обнаруживает такую зависимость и выбрасывает исключение. Без проверки scoped-экземпляр, полученный из корневого провайдера, может удерживаться до освобождения контейнера.

Если singleton выполняет отдельную операцию со scoped-сервисами, для неё создают явный scope и используют зависимости внутри этой области.

---

### Время жизни и освобождение

Lifetime задаёт правила использования экземпляров, а не момент удаления объекта из памяти.

Для принадлежащих контейнеру сервисов, реализующих `IDisposable` или `IAsyncDisposable`:

- Transient и scoped освобождаются при завершении scope, в котором были получены.
- Singleton освобождается вместе с контейнером.

Удаление объектов из памяти выполняет сборщик мусора. Готовый экземпляр, переданный в `AddSingleton(instance)`, контейнер автоматически не освобождает. 

---

# 4. Типичные примеры выбора времени жизни

### `Transient`

Обычно это **небольшие сервисы, которым не требуется общий экземпляр между потребителями**.

|Пример|Почему подходит|
|---|---|
|Валидатор|Выполняет проверку входных данных, не накапливая общее состояние|
|Обработчик команды или запроса|Каждый создаваемый обработчик получает свои зависимости|
|Преобразователь данных, mapper|Преобразует объекты, не хранит состояние между вызовами|
|Стратегия расчёта|Например, расчёт скидки или стоимости доставки|
|Генератор документа|Может иметь собственное рабочее состояние для формирования документа|

Это возможные варианты проектирования, а не обязательное правило для всех таких классов. Например, простой потокобезопасный преобразователь без состояния может быть и singleton.

Конкретный пример — **валидаторы FluentValidation**: документация рекомендует transient как простой вариант, хотя автоматическая регистрация через сканирование сборки по умолчанию использует scoped.

>Валидаторы, mapper-ы и стратегии без состояния можно регистрировать как singleton, если они и их зависимости допускают совместное использование. Transient выбирают, когда нужны отдельные экземпляры или более гибкая работа с зависимостями. При частом разрешении transient-сервисов возникают дополнительные аллокации и нагрузка на GC.

---

### `Scoped`

Обычно это **сервисы, связанные с одной операцией или HTTP-запросом**, которым нужно разделять состояние и ресурсы внутри этой области.

|Пример|Почему подходит|
|---|---|
|`DbContext` EF Core|Хранит отслеживаемые сущности и изменения в рамках единицы работы|
|Репозиторий поверх `DbContext`|Использует контекст текущего scope|
|`UnitOfWork`|Координирует изменения нескольких репозиториев в рамках одной операции|
|Прикладной сервис, например `OrderService`|Работает с репозиториями и другими зависимостями текущего запроса|
|Сервис сведений о текущем пользователе или tenant|Может хранить сведения, относящиеся к текущему запросу|
|Кеш внутри запроса|Позволяет разным компонентам повторно использовать результат вычисления только в этом запросе|

`AddDbContext` регистрирует контекст как scoped по умолчанию. Несколько репозиториев внутри одного scope могут использовать один контекст и участвовать в одной единице работы.

**Репозиторий или прикладной сервис не обязан быть scoped только из-за своего названия.** Это распространённый выбор, когда он работает с ресурсами и состоянием текущей операции.

---

### `Singleton`

Обычно это **общие сервисы приложения** или **дорогие клиенты, рассчитанные на длительное и совместное использование**.

| Пример                                        | Почему подходит                                                                        |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| Общий кеш, например `IMemoryCache`            | Данные должны быть доступны разным запросам                                            |
| `ConnectionMultiplexer` `StackExchange.Redis` | Управляет соединениями, рассчитан на повторное и потокобезопасное использование        |
| Kafka producer                                | Позволяет переиспользовать клиент для публикации сообщений из разных компонентов       |
| Общая очередь фоновых задач                   | Производители и обработчики должны обращаться к одной очереди                          |
| Потокобезопасный сервис справочных данных     | Хранит общий справочник или подготовленные данные                                      |
| Фоновый сервис                                | Работает в течение жизни приложения; `AddHostedService` регистрирует его как singleton |

Для общего кеша и очереди singleton обеспечивает совместное использование одного объекта разными потребителями. Фоновые сервисы получают scoped-зависимости через отдельно создаваемые области.

#### Redis

В StackExchange.Redis разделяют именно **`ConnectionMultiplexer`**. Документация прямо рекомендует сохранять и переиспользовать его: создавать такой объект для каждой операции не следует.

При этом `RedisOrderCache`, использующий этот клиент, может быть scoped или transient, если его собственные зависимости и состояние этого требуют.

#### Kafka

Для обычной публикации сообщений через `Confluent.Kafka` общий producer — разумный вариант: клиент поддерживает параллельные операции публикации и объединяет сообщения в batches. Отсюда практический выбор — переиспользовать producer, например через singleton.

**Consumer обычно организуют как долгоживущий клиент отдельного цикла чтения**, например внутри фонового сервиса. Для обработки каждого сообщения можно создавать scope с `DbContext`, репозиториями и прикладными сервисами.

# 5. `IServiceProvider`: получение зависимостей

**`IServiceProvider` — интерфейс для получения сервисов по их типу.** В DI он предоставляет доступ к экземплярам на основании регистраций контейнера.

При разрешении зависимости контейнер создаёт объект либо возвращает существующий — согласно времени жизни сервиса.

Интерфейс содержит один метод:

```cs
public interface IServiceProvider
{
    object? GetService(Type serviceType);
}
```

Типизированное получение, получение обязательного сервиса и всех реализаций доступны через методы расширения из пространства имён `Microsoft.Extensions.DependencyInjection`.

---

### `GetService`: получение необязательного сервиса

Базовый метод принимает объект `Type`:

```cs
object? GetService(Type serviceType);
```

```cs
IServiceProvider provider = context.RequestServices;

var repository = (IOrderRepository?)
    provider.GetService(typeof(IOrderRepository));
```

Возвращаемый тип — `object?`, поэтому для использования интерфейса сервиса требуется приведение.

Generic-метод расширения позволяет сразу получить нужный тип:

```cs
public static T? GetService<T>(
    this IServiceProvider provider);
```

```cs
IOrderRepository? repository =
    provider.GetService<IOrderRepository>();
```

**Если сервис отсутствует, возвращается `null`.** Такой способ подходит, когда отсутствие зависимости допустимо и вызывающий код предусматривает этот случай.

> `GetService` не подавляет ошибки создания зарегистрированного сервиса. Например, если для его конструктора не удаётся получить обязательную зависимость, разрешение завершится исключением.

---

### `GetRequiredService`: получение обязательного сервиса

Методы расширения:

```cs
public static T GetRequiredService<T>(
    this IServiceProvider provider)
    where T : notnull;

public static object GetRequiredService(
    this IServiceProvider provider,
    Type serviceType);
```

```cs
IOrderRepository repository = provider.GetRequiredService<IOrderRepository>();
```

Вариант с `Type`:

```cs
var repository = (IOrderRepository)
    provider.GetRequiredService(typeof(IOrderRepository));
```

**Если сервис отсутствует, выбрасывается `InvalidOperationException`.**

Этот способ используют, когда зависимость необходима для выполнения операции: отсутствие регистрации является ошибкой настройки приложения.

---

### `GetServices`: получение всех реализаций

Методы расширения:

```cs
public static IEnumerable<T> GetServices<T>(this IServiceProvider provider);

public static IEnumerable<object?> GetServices(
    this IServiceProvider provider,
    Type serviceType);
```

Например, зарегистрированы две реализации:

```cs
builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();
```

Получение:

```cs
IEnumerable<INotifier> notifiers = provider.GetServices<INotifier>();
```

Для встроенного контейнера:

- `GetServices<INotifier>()` предоставляет обе реализации в порядке регистрации.
- `GetService<INotifier>()` и `GetRequiredService<INotifier>()` предоставляют последнюю — `SmsNotifier`.
- Если регистраций `INotifier` нет, `GetServices<INotifier>()` возвращает пустую коллекцию.

Получение всех реализаций также учитывает время жизни каждой регистрации.

---

### Провайдер приложения и провайдер запроса

В ASP.NET Core важно выбирать провайдер, соответствующий области использования зависимости:

|Источник|Какой провайдер предоставляет|
|---|---|
|`app.Services`|Корневой провайдер приложения|
|`IApplicationBuilder.ApplicationServices`|Провайдер сервисов приложения|
|`HttpContext.RequestServices`|Провайдер scope текущего HTTP-запроса|

Для зависимостей текущего запроса используют:

```cs
var repository =
    context.RequestServices.GetRequiredService<IOrderRepository>();
```

**Обращение к `app.Services` во время запроса не превращает его в провайдер этого запроса.** Он остаётся корневым.

Scoped-сервисы получают через провайдер соответствующего scope. При попытке получить их из корневого провайдера включённая проверка scope выбрасывает исключение. Без проверки экземпляр будет удерживаться корневой областью до её освобождения.

---

### Явное получение и внедрение зависимостей

Вызовы `GetService` и `GetRequiredService` — **явное разрешение зависимостей**: код сам обращается к провайдеру.

Это полезно, например, в middleware через делегат, где дополнительные параметры сервисов автоматически не заполняются:

```cs
app.Use(async (context, next) =>
{
    var logger = context.RequestServices
        .GetRequiredService<ILogger<Program>>();

    logger.LogInformation(
        "Request: {Path}",
        context.Request.Path);

    await next(context);
});
```

В классах, создаваемых через DI, обычно объявляют необходимые зависимости непосредственно в конструкторе. Так зависимости класса видны из его контракта, а их разрешение выполняет контейнер.

---

# 6. Внедрение зависимостей в компоненты ASP.NET Core

**Внедрение зависимостей выполняется в предусмотренных инфраструктурой местах:** через конструкторы создаваемых объектов или параметры вызываемых обработчиков.

Сервисы должны быть зарегистрированы в контейнере. Их получение учитывает время жизни и провайдер, через который выполняется разрешение.

---

### Сервисы приложения: конструктор

Когда контейнер создаёт зарегистрированный сервис, он получает зависимости для параметров его публичного конструктора:

```cs
public class OrderService
{
    private readonly IOrderRepository _repository;

    public OrderService(IOrderRepository repository)
    {
        _repository = repository;
    }
}
```

Регистрация:

```cs
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
builder.Services.AddScoped<OrderService>();
```

При разрешении `OrderService` контейнер получает `IOrderRepository` и передаёт его в конструктор.

Зависимости также могут иметь собственные зависимости — контейнер разрешает всю цепочку.

---

### Контроллеры: конструктор

ASP.NET Core получает зависимости конструктора контроллера из DI:

```cs
public class OrdersController : ControllerBase
{
    private readonly OrderService _orders;

    public OrdersController(OrderService orders)
    {
        _orders = orders;
    }
}
```

Такой способ подходит для зависимостей, используемых несколькими actions контроллера.

При обычной настройке MVC **сам контроллер не требуется отдельно регистрировать через `AddScoped` или другой метод регистрации**. Инфраструктура создаёт контроллер и получает его зависимости из провайдера текущего запроса.

---

### Actions контроллера: `[FromServices]`

Зависимость можно передать непосредственно в action. Атрибут `[FromServices]` явно указывает, что параметр следует получить из DI:

```cs
[HttpGet]
public IActionResult Get([FromServices] ILogger<OrdersController> logger)
{
    logger.LogInformation("Getting orders");

    return Ok();
}
```

Это удобно, когда сервис нужен только одному action: его не требуется сохранять в поле контроллера.

Атрибут относится к получению параметра инфраструктурой MVC. Если вызвать этот метод самостоятельно, аргумент придётся передать обычным способом. 

---

### Minimal API: параметры обработчика

В Minimal API зарегистрированный сервис можно объявить параметром обработчика:

```cs
app.MapGet("/orders", (OrderService orders) =>
{
    // Работа с сервисом

    return Results.Ok();
});
```

Инфраструктура определяет, что `OrderService` зарегистрирован в DI, и получает его через провайдер текущего запроса.

Источник можно указать явно:

```cs
app.MapGet("/orders", ([FromServices] OrderService orders) =>
{
    // Работа с сервисом

    return Results.Ok();
});
```

Остальные параметры обработчика могут поступать из маршрута, query string, тела запроса и других источников. **Не каждый параметр обработчика является DI-зависимостью.**

---

### Middleware

Способ внедрения зависит от формы middleware:

|Форма|Получение зависимостей|
|---|---|
|Делегат в `Use` или `Run`|Явно через `context.RequestServices`|
|Обычный класс через `UseMiddleware<T>`|Конструктор и дополнительные параметры `Invoke` / `InvokeAsync`|
|Класс, реализующий `IMiddleware`|Конструктор при разрешении экземпляра через DI|

#### Обычный класс middleware

**Зависимости конструктора** получают при создании middleware из провайдера приложения. Экземпляр middleware и сохранённые им зависимости используются разными запросами.

**Дополнительные параметры `Invoke` / `InvokeAsync`** разрешаются через `HttpContext.RequestServices` при каждом вызове:

```cs
public Task InvokeAsync(
    HttpContext context,
    OrderService orders)
{
    // Работа с сервисом текущего запроса

    return _next(context);
}
```

Поэтому scoped-зависимости и transient-зависимости, которые нужны заново для каждого вызова, получают через метод обработки.

#### `IMiddleware`

Экземпляр middleware разрешается из провайдера текущего запроса, поэтому зависимости передают через конструктор.

Его время жизни определяется регистрацией класса. Дополнительные параметры метода обработки не поддерживаются: используется фиксированная сигнатура интерфейса:

```cs
Task InvokeAsync(
    HttpContext context,
    RequestDelegate next);
```

---

### Получение нескольких реализаций

Вместо одного сервиса можно объявить зависимость типа `IEnumerable<T>`:

```cs
public class NotificationService
{
    private readonly IEnumerable<INotifier> _notifiers;

    public NotificationService(IEnumerable<INotifier> notifiers)
    {
        _notifiers = notifiers;
    }
}
```

Встроенный контейнер предоставляет все зарегистрированные реализации `INotifier` в порядке регистрации. Если реализаций нет, коллекция будет пустой.

# 7. Создание scope вручную: когда и зачем

**Scope создают вручную, когда для отдельной операции нужна собственная область DI.** Внутри неё scoped-сервисы создаются один раз, а при завершении области освобождаются принадлежащие ей ресурсы.

Для HTTP-запроса ASP.NET Core предоставляет scope автоматически. Вне обработки запросов область часто нужно создавать самостоятельно.

### Когда это требуется

Типичные случаи:

- **Фоновая задача:** обработка сообщения Kafka, задания из очереди или периодическая операция.
- **Операция при запуске приложения:** например, инициализация данных с использованием `DbContext`.
- **Отдельная единица работы:** операция должна использовать собственные scoped-экземпляры независимо от других операций.

В частности, scope позволяет singleton-сервису временно использовать scoped-зависимости, не сохраняя их на всё время работы приложения. 

---

### `IServiceScopeFactory` и `IServiceScope`

Для создания области используется `IServiceScopeFactory`:

```cs
public interface IServiceScopeFactory
{
    IServiceScope CreateScope();
}
```

Метод возвращает `IServiceScope` — объект, который предоставляет провайдер новой области и позволяет завершить её время жизни:

```cs
public interface IServiceScope : IDisposable
{
    IServiceProvider ServiceProvider { get; }
}
```

**Сервисы этой области получают через `scope.ServiceProvider`.** Вызов `Dispose()` завершает область и освобождает принадлежащие ей disposable-сервисы.

---

### Синхронное освобождение: `CreateScope`

Scope также можно создать через метод расширения для `IServiceProvider`:

```cs
public static IServiceScope CreateScope(
    this IServiceProvider provider);
```

Например, через провайдер приложения:

```cs
using (IServiceScope scope = app.Services.CreateScope())
{
    var repository = scope.ServiceProvider
        .GetRequiredService<IOrderRepository>();

    // Работа с repository
}
```

При выходе из блока `using` вызывается `scope.Dispose()`.

**Создание scope не переключает `app.Services` на новую область.** Чтобы получить её зависимости, нужно обращаться именно к `scope.ServiceProvider`.

---

### Асинхронное освобождение: `CreateAsyncScope`

Для поддержки асинхронного освобождения используются методы расширения:

```cs
public static AsyncServiceScope CreateAsyncScope(
    this IServiceProvider provider);

public static AsyncServiceScope CreateAsyncScope(
    this IServiceScopeFactory serviceScopeFactory);
```

Они возвращают `AsyncServiceScope`, который реализует `IServiceScope`, `IDisposable` и `IAsyncDisposable`.

```cs
await using (var scope = app.Services.CreateAsyncScope())
{
    var orders = scope.ServiceProvider
        .GetRequiredService<OrderService>();

    await orders.ProcessAsync(orderId, cancellationToken);
}
```

При выходе из блока `await using` ожидается завершение `DisposeAsync()` области.

**Само создание scope синхронное:** `CreateAsyncScope()` не возвращает `Task`. Асинхронность относится к освобождению ресурсов. В асинхронном коде этот вариант позволяет корректно работать и с сервисами, которым требуется асинхронное освобождение. 

---

### Использование scoped-сервисов из singleton

Singleton получает через конструктор **фабрику областей**, а зависимости конкретной операции разрешает внутри создаваемого scope:

```cs
public class OrderJobRunner
{
    private readonly IServiceScopeFactory _scopeFactory;

    public OrderJobRunner(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task RunAsync(
        int orderId,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();

        var orders = scope.ServiceProvider.GetRequiredService<OrderService>();

        await orders.ProcessAsync(orderId, cancellationToken);
    }
}
```

Регистрация:

```cs
builder.Services.AddScoped<OrderService>();
builder.Services.AddSingleton<OrderJobRunner>();
```

Здесь каждый вызов `RunAsync` создаёт отдельную область. `OrderService` и его scoped-зависимости относятся к этой операции, а не ко всему времени жизни `OrderJobRunner`.

Такой же подход применяется внутри фоновых сервисов: область обычно создают на отдельное задание или обрабатываемое сообщение.

---

### Границы области

Встроенный контейнер использует следующие правила:

- Разные scope имеют разные scoped-экземпляры.
- Singleton-сервисы остаются общими для всех областей.
- Области независимы: создание scope через провайдер другой области не образует иерархию и не наследует её scoped-экземпляры.

**Работа с зависимостями должна завершиться до освобождения scope.** Нельзя сохранить scoped-сервис для последующего использования или запустить работу с ним, которая продолжится после выхода из `using` / `await using`.

Освобождение области выполняет контейнер, поэтому отдельно вызывать `Dispose` у полученных из неё зависимостей обычно не нужно. 

---

# 8. Освобождение сервисов и типичные ошибки работы со временем жизни

**Освобождение сервиса — завершение работы с его ресурсами**, например соединениями или файловыми дескрипторами. Оно выполняется через:

```cs
// IDisposable
void Dispose();

// IAsyncDisposable
ValueTask DisposeAsync();
```

---

### Кто отвечает за освобождение

Ответственность зависит от того, как получен объект:

|Способ получения экземпляра|Кто отвечает за освобождение|
|---|---|
|Контейнер создаёт сервис по зарегистрированному типу|Контейнер|
|Контейнер получает сервис через зарегистрированную фабрику|Контейнер|
|Готовый экземпляр передан через `AddSingleton(instance)`|Код, предоставивший экземпляр|
|Объект создан вручную через `new` или прямой вызов `ActivatorUtilities.CreateInstance`|Вызывающий код|

**Создание объекта через `new` внутри зарегистрированной фабрики не исключает его из управления контейнера:** результат фабрики становится предоставляемым контейнером сервисом. 

Если класс получает disposable-зависимость через DI, он обычно **не должен освобождать её самостоятельно**. Она может использоваться другими потребителями и будет освобождена владельцем.

При этом ресурсы, которые класс создаёт и которыми владеет сам, он освобождает в собственной реализации `Dispose` / `DisposeAsync`. 

---

### Когда контейнер освобождает сервисы

Для принадлежащих контейнеру экземпляров, поддерживающих освобождение:

|Время жизни|Момент освобождения|
|---|---|
|`Transient`|При освобождении области, через которую получен экземпляр|
|`Scoped`|При освобождении его scope|
|`Singleton`|При освобождении основного контейнера, обычно при завершении приложения|

В HTTP-запросе область освобождает инфраструктура ASP.NET Core. Для вручную созданного scope это делает создающий его код через `using` или `await using`.

**Transient не освобождается сразу после использования.** Если disposable transient получен из корневого провайдера, контейнер удерживает его до своего освобождения. Частое получение таких объектов может привести к накоплению экземпляров и ресурсов. 

---

### Синхронное и асинхронное освобождение

- `using` вызывает `Dispose()`.
- `await using` ожидает `DisposeAsync()`.

При асинхронном освобождении scope встроенный контейнер использует `DisposeAsync` для сервисов, реализующих `IAsyncDisposable`, а для остальных disposable-сервисов — `Dispose`.

**Если сервис реализует только `IAsyncDisposable`, синхронное освобождение scope через `Dispose()` завершится исключением.** Для такой области используют `CreateAsyncScope()` и `await using`.

```cs
await using var scope = scopeFactory.CreateAsyncScope();

var service = scope.ServiceProvider
    .GetRequiredService<OrderService>();

await service.ProcessAsync(orderId, cancellationToken);
```

---

### Типичные ошибки

#### Ручное освобождение зависимости из DI

Например, самостоятельно вызывать `Dispose()` у `DbContext`, внедрённого в сервис.

Другие компоненты этого scope могут получить тот же контекст и попытаться продолжить работу с уже освобождённым объектом. **Освобождают область, а не отдельные принадлежащие ей зависимости.**

#### Получение scoped-сервиса из корневого провайдера

При включённой проверке scope возникает исключение. Без проверки экземпляр удерживается корневой областью до освобождения контейнера и фактически используется с продолжительностью жизни singleton.

#### Удержание scoped-зависимости в singleton

Общий сервис приложения сохраняет объект, предназначенный для отдельной области. Ограничение действует и при косвенной зависимости через другие сервисы.

Для отдельной операции singleton должен создать scope и использовать scoped-сервисы внутри него.

Удержание **transient** в singleton допустимо, но этот экземпляр также будет использоваться длительно: новая зависимость при каждом вызове метода автоматически не создаётся. 

#### Использование сервиса после завершения scope

Например, фоновая задача захватывает `DbContext` HTTP-запроса и продолжает работу после завершения запроса.

Контекст к этому моменту может быть освобождён. В фоновую обработку передают необходимые данные, а зависимости получают в собственной области. Аналогичная ошибка возникает, если выйти из `await using`, не дождавшись завершения операции с сервисом.

#### Предположение, что DI обеспечивает потокобезопасность

Контейнер может безопасно разрешать зависимости из разных потоков, но **это не делает полученные объекты потокобезопасными**.

Singleton используется разными запросами одновременно. Scoped-экземпляр тоже может использоваться параллельно внутри одной области. Совместимость с таким использованием определяется реализацией сервиса. 

#### Создание дополнительного контейнера при регистрации

Вызов `builder.Services.BuildServiceProvider()` создаёт отдельный провайдер. Это может привести к появлению дополнительных singleton-экземпляров и отдельной ответственности за освобождение контейнера.

Если при создании сервиса нужны другие зависимости, используют перегрузку регистрации с фабрикой, принимающей `IServiceProvider`, вместо сборки промежуточного контейнера.
