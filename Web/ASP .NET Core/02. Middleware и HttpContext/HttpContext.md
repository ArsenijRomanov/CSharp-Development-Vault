# 1. Назначение `HttpContext`

**`HttpContext`** — объект ASP.NET Core, объединяющий HTTP-данные, состояние и инфраструктурные возможности, связанные с обработкой **одного HTTP-запроса**.

Через него компоненты приложения получают доступ к:

- входящему запросу — `Request`
- формируемому ответу — `Response`
- пользователю текущего запроса — `User`
- сервисам текущего запроса — `RequestServices`
- дополнительным данным и возможностям обработки — `Items`, `Features`, `RequestAborted` и другим свойствам

Таким образом, `HttpContext` служит **общим контекстом обработки запроса**: через него можно прочитать входящие данные, сформировать ответ и получить состояние, необходимое для выполнения запроса.
## Место в обработке запроса

При поступлении HTTP-запроса инфраструктура ASP.NET Core инициализирует `HttpContext` и передаёт его в middleware pipeline.

Компоненты, участвующие в обработке запроса, работают с одним и тем же контекстом. Если обработка достигает endpoint, он также получает доступ к этому контексту.

По мере выполнения состояние контекста может изменяться: middleware может скорректировать данные запроса, установить сведения о пользователе или добавить информацию для следующих компонентов; endpoint может использовать эти данные и сформировать ответ.

# 2. Общая структура и реализация

## `HttpContext` как абстракция

`HttpContext` — **абстрактный класс** из пространства имён `Microsoft.AspNetCore.Http`.

Он определяет общий контракт контекста запроса: свойства для доступа к запросу, ответу, пользователю и инфраструктуре обработки, а также метод `Abort()`.

Прикладные компоненты обычно работают через тип `HttpContext`. Конкретная реализация определяет, как предоставляются данные и выполняются операции этого контракта.

## `DefaultHttpContext`

**`DefaultHttpContext`** — стандартная конкретная реализация `HttpContext`.

При обычной обработке запросов создание и инициализацию контекста выполняет инфраструктура ASP.NET Core. Прикладной код получает уже подготовленный объект.

`DefaultHttpContext` также можно создать самостоятельно, например для тестирования компонента, использующего контекст:

```cs
HttpContext context = new DefaultHttpContext();

context.Request.Method = "GET";
context.Request.Path = "/products";
context.Items["Source"] = "test";
```

У `DefaultHttpContext` есть два основных конструктора:

- `DefaultHttpContext()` — создаёт контекст с базовым набором features
- `DefaultHttpContext(IFeatureCollection features)` — создаёт контекст на основе переданной коллекции features

Это позволяет предоставить контексту конкретные реализации инфраструктурных возможностей.

## Основные свойства

|Свойство|Тип|Назначение|
|---|---|---|
|`Request`|`HttpRequest`|Входящий HTTP-запрос|
|`Response`|`HttpResponse`|Формируемый HTTP-ответ|
|`User`|`ClaimsPrincipal`|Пользователь текущего запроса|
|`RequestServices`|`IServiceProvider`|Доступ к сервисам текущего запроса|
|`Items`|`IDictionary<object, object?>`|Произвольные данные в пределах запроса|
|`Connection`|`ConnectionInfo`|Информация о соединении|
|`Features`|`IFeatureCollection`|Низкоуровневые возможности обработки запроса|
|`RequestAborted`|`CancellationToken`|Сигнал прерывания запроса|
|`TraceIdentifier`|`string`|Идентификатор запроса для диагностики|
|`Session`|`ISession`|Доступ к состоянию сессии|
|`WebSockets`|`WebSocketManager`|Возможности установления WebSocket-соединения|

## Связь с сервером и middleware

Под высокоуровневым API `HttpContext` находится слой **feature-интерфейсов**. Каждый такой интерфейс описывает отдельную часть функциональности: данные запроса, параметры ответа, информацию о соединении, поддержку сессии и другие возможности.

Сервер предоставляет базовые features, необходимые для обработки HTTP-запроса. Middleware может добавлять, заменять или оборачивать отдельные features по мере обработки.

Например:

- `IHttpRequestFeature` предоставляет основные данные входящего запроса
- `IHttpResponseFeature` предоставляет статус и заголовки ответа
- `IHttpResponseBodyFeature` предоставляет операции записи тела ответа
- `ISessionFeature` предоставляет доступ к сессии и добавляется session middleware

Такая структура позволяет расширять или изменять отдельные возможности обработки **без замены всей реализации `HttpContext`**.

Наличие свойства в контракте ещё не означает, что соответствующая возможность настроена в приложении. Например, использование `Session` требует подключённой session-инфраструктуры. Набор доступных возможностей зависит от сервера и компонентов обработки запроса.

# 3. `Request`

**`HttpContext.Request`** предоставляет объект `HttpRequest`, представляющий входящий HTTP-запрос.

```cs
HttpRequest request = context.Request;
```

Через него доступны метод, адрес, параметры, заголовки, cookies и тело запроса.

`HttpRequest` — абстрактный класс. Его свойства отражают текущее представление запроса внутри приложения: middleware может изменять некоторые значения, и следующие компоненты будут работать с изменёнными данными. Например, при обработке запроса могут корректироваться `Path`, `PathBase` или `Scheme`.

---

## Метод и адрес запроса

|Свойство|Тип|Назначение|
|---|---|---|
|`Method`|`string`|HTTP-метод, например `"GET"`|
|`Scheme`|`string`|Схема, например `"http"` или `"https"`|
|`IsHttps`|`bool`|Проверка, что `Scheme` соответствует HTTPS|
|`Host`|`HostString`|Имя хоста и указанный порт|
|`PathBase`|`PathString`|Базовый префикс пути приложения|
|`Path`|`PathString`|Путь запроса относительно `PathBase`|
|`Protocol`|`string`|Версия протокола, например `"HTTP/1.1"`|

### `Host`

`HostString` позволяет получить имя хоста и порт отдельно:

```cs
// Host: example.com:8443

string host = request.Host.Host; // "example.com"
int? port = request.Host.Port;   // 8443
```

Если порт явно не указан, `Host.Port` возвращает `null`.

### `PathBase` и `Path`

**`PathBase` задаёт префикс приложения, а `Path` — оставшийся путь, используемый при обработке запроса.**

Например, если приложение настроено на работу под префиксом `/shop`, запрос:

```http
​
https://example.com/shop/products/42?sort=price
```

может быть представлен так:

- `PathBase` — `/shop`
- `Path` — `/products/42`
 
Разделение зависит от конфигурации приложения. Первый сегмент пути сам по себе не становится `PathBase`.

---

## Параметры запроса

### `QueryString` и `Query`

|Свойство|Тип|Представление|
|---|---|---|
|`QueryString`|`QueryString`|Исходная строка параметров, включая `?` при её наличии|
|`Query`|`IQueryCollection`|Разобранная коллекция имён и значений|

Например:

```cs
// /products?page=2&tag=backend&tag=dotnet

string? rawQuery = request.QueryString.Value;
// "?page=2&tag=backend&tag=dotnet"

string page = request.Query["page"].ToString();
// "2"

var tags = request.Query["tag"];
// StringValues с двумя значениями: "backend", "dotnet"
```

**Значение одного query-параметра может содержать несколько элементов.** Поэтому индексатор `Query` возвращает `StringValues`, а не отдельную строку.

Для отсутствующего ключа возвращается `StringValues.Empty`. Проверить наличие параметра можно через `ContainsKey()` или `TryGetValue()`.

Получение значения из `Query` не преобразует его автоматически в прикладной тип: например, строку `"2"` необходимо отдельно разобрать как число либо использовать механизмы привязки параметров endpoint.

### `RouteValues`

`RouteValues` имеет тип `RouteValueDictionary` и содержит значения параметров маршрута.

Для маршрута `/products/{id}` и запроса `/products/42?category=books`:

```cs
object? id = request.RouteValues["id"];       // обычно "42"
string category = request.Query["category"].ToString(); // "books"
```

Query-параметры получаются из строки запроса, а route values — при сопоставлении запроса с маршрутом. Поэтому доступность `RouteValues` зависит от того, был ли уже выполнен соответствующий этап routing.

---

## Заголовки

`Headers` имеет тип `IHeaderDictionary` — коллекцию заголовков с ключами `string` и значениями `StringValues`.

Доступ возможен через имя заголовка или предусмотренное для него свойство:

```cs
var authorization = request.Headers.Authorization;
var correlationId = request.Headers["X-Correlation-Id"];
```

Имена заголовков сравниваются без учёта регистра. Если заголовок отсутствует, индексатор возвращает `StringValues.Empty`.

`StringValues` позволяет представить несколько значений. При вызове `.ToString()` несколько элементов объединяются через запятую; для поэлементной обработки следует работать с самой коллекцией.

---

## Cookies

`Cookies` имеет тип `IRequestCookieCollection` и предоставляет разобранные cookies, полученные в запросе.

```cs
request.Cookies.TryGetValue("theme", out string? theme);
```

Здесь доступны имена и значения входящих cookies. Установка cookies для клиента выполняется через `Response.Cookies`.

---

## Тип и длина тела

|Свойство|Тип|Назначение|
|---|---|---|
|`ContentType`|`string?`|Значение заголовка `Content-Type`|
|`ContentLength`|`long?`|Значение заголовка `Content-Length` в байтах|

Это удобные свойства для доступа к соответствующим заголовкам.

`ContentType` может включать параметры, например:

```cs
application/json; charset=utf-8
```

Для проверки поддерживаемого JSON-типа существует extension-метод `HasJsonContentType()`.

**`ContentLength == null` означает, что длина не указана, а не что тело пустое.** Тело может поступать без заранее известной длины. 

---

## Тело запроса: `Body` и `BodyReader`

`Body` имеет тип `Stream` и предоставляет байты тела запроса. Этот поток можно читать напрямую или передать библиотеке, выполняющей разбор данных.

`BodyReader` предоставляет то же тело через `PipeReader` из `System.IO.Pipelines`. Этот API предназначен для работы с буферами и последовательного разбора данных; его подробная механика рассматривается отдельно. 

В обычной серверной обработке тело читается последовательно по мере поступления данных. Получение объекта `HttpRequest` не означает, что всё тело уже загружено в память.

Чтение следует выполнять асинхронно. Синхронный I/O может блокировать поток и в стандартной конфигурации сервера ограничен.

---

## Чтение формы

**Форма** — это данные, которые клиент отправляет в теле HTTP-запроса как набор полей `имя → значение`. Например HTML-форма:

```html
<form method="post">
    <input name="name">
    <input name="avatar" type="file">
</form>
```

может отправить поле `name` и файл `avatar`.

В ASP.NET Core разобранная форма представлена интерфейсом:

```cs
IFormCollection
```

Для первоначального чтения лучше использовать асинхронный метод:

```cs
Task<IFormCollection> ReadFormAsync(CancellationToken ct = default);
```

Он работает с:

- `application/x-www-form-urlencoded`
- `multipart/form-data`

Пример:

```cs
if (request.HasFormContentType)
{
    var form = await request.ReadFormAsync(context.RequestAborted);

    string name = form["name"].ToString();
    var files = form.Files;
}
```

Обычные поля хранятся как `StringValues`, поэтому одно поле может содержать несколько значений:

```cs
var values = form["tag"];
```

Загруженные файлы доступны через:

```cs
form.Files
```

После первого разбора результат кешируется, поэтому к форме можно обращаться повторно через:

```cs
request.Form
```

Но для **первого чтения предпочтителен `ReadFormAsync()`**, так как прямое обращение к `Form` может привести к синхронному ожиданию асинхронного чтения тела запроса.

---

## Чтение JSON

Extension-метод `ReadFromJsonAsync<T>()` читает тело запроса и десериализует JSON в указанный тип.

Основная форма вызова:

```cs
ValueTask<T?> ReadFromJsonAsync<T>(CancellationToken ct = default);
```

Например:

```cs
var data = await request.ReadFromJsonAsync<Dictionary<string, string>>(
    cancellationToken: context.RequestAborted);
```

Метод проверяет, что `Content-Type` соответствует поддерживаемому JSON-типу. Другие перегрузки позволяют передать `JsonSerializerOptions` или метаданные сериализации `JsonTypeInfo<T>`.

Результат может быть `null`, например при JSON-значении `null`. Некорректный JSON приводит к ошибке десериализации. Проверка прикладных требований к полученному объекту выполняется отдельно.

---

## Повторное чтение тела: `EnableBuffering()`

После чтения обычного входящего потока уже прочитанные данные недоступны для повторного чтения без буферизации.

Это существенно, когда один компонент читает тело, а затем оно требуется следующему компоненту.

Extension-метод `EnableBuffering()` включает сохранение прочитанных данных и возможность перемотки:

```cs
using System.Text;

request.EnableBuffering(
    bufferThreshold: 64 * 1024,
    bufferLimit: 1024 * 1024);

using var reader = new StreamReader(
    request.Body,
    Encoding.UTF8,
    detectEncodingFromByteOrderMarks: false,
    bufferSize: 1024,
    leaveOpen: true);

string body = await reader.ReadToEndAsync(context.RequestAborted);

// Следующий компонент сможет прочитать тело с начала
request.Body.Position = 0;
```

`EnableBuffering()` вызывается **до чтения тела**. Он не восстанавливает данные, которые уже были прочитаны и не сохранены.

Параметры управляют стоимостью буферизации:

- `bufferThreshold` — порог хранения в памяти, после которого используется временный файл
- `bufferLimit` — максимальный объём буферизуемых данных; попытка чтения сверх лимита приводит к `IOException`

`leaveOpen: true` сохраняет поток запроса открытым после освобождения `StreamReader`.

Буферизация сохраняет байты по мере чтения. В примере `ReadToEndAsync()` дополнительно создаёт строку со всем телом, поэтому такой способ подходит для небольших текстовых запросов.

# 4. `Response`

**`HttpContext.Response`** предоставляет объект `HttpResponse`, через который формируется HTTP-ответ текущего запроса.

```cs
HttpResponse response = context.Response;
```

`HttpResponse` — абстрактный класс. Через его API задаются статус, заголовки, cookies и содержимое ответа, а также выполняются операции, связанные с началом и завершением отправки.

---

## Основные свойства

|Свойство|Тип|Назначение|
|---|---|---|
|`StatusCode`|`int`|HTTP-код ответа|
|`Headers`|`IHeaderDictionary`|Заголовки ответа|
|`ContentType`|`string?`|Значение заголовка `Content-Type`|
|`ContentLength`|`long?`|Значение заголовка `Content-Length`|
|`Cookies`|`IResponseCookies`|Установка и удаление cookies|
|`Body`|`Stream`|Поток для записи тела ответа|
|`BodyWriter`|`PipeWriter`|Запись тела через `System.IO.Pipelines`|
|`HasStarted`|`bool`|Признак начала отправки заголовков|

Ответ может формироваться несколькими компонентами: например, middleware добавляет заголовки, а endpoint задаёт статус и записывает тело.

---

## Статус и заголовки

### `StatusCode`

`StatusCode` определяет HTTP-код формируемого ответа. Начальное значение в стандартной реализации — `200`.

Для задания кодов можно использовать константы `StatusCodes`:

```cs
response.StatusCode = StatusCodes.Status404NotFound;
```

Присваивание статуса меняет параметры ответа. Оно само по себе не записывает тело и не прекращает выполнение обработчика.

### `Headers`

`Headers` предоставляет изменяемую коллекцию `IHeaderDictionary`.

```cs
response.Headers["X-Request-Id"] = context.TraceIdentifier;
response.Headers.CacheControl = "no-store";
```

Значения представлены через `StringValues`, что позволяет хранить несколько элементов для одного имени заголовка.

Присваивание через индексатор заменяет значение. Extension-метод `Append()` добавляет новые элементы к существующим:

```cs
response.Headers["X-Tag"] = "backend";
response.Headers.Append("X-Tag", "dotnet");
```

Изменение заголовков допустимо до начала их отправки.

---

## Тип и длина содержимого

`ContentType` и `ContentLength` предоставляют удобный доступ к соответствующим заголовкам:

```cs
response.ContentType = "text/plain; charset=utf-8";
response.ContentLength = 100;
```

**`ContentLength` задаётся в байтах**, поэтому длина строки в символах не обязательно совпадает с длиной тела после кодирования.

Если длина заранее неизвестна, свойство можно оставить равным `null`. Установленное значение должно соответствовать фактически отправляемому объёму тела; несоответствие может привести к ошибке при записи или завершении ответа.

---

## Запись тела ответа

### `Body` и `BodyWriter`

`Body` предоставляет тело ответа как `Stream`. Через него можно записывать байты напрямую или передавать поток библиотеке, формирующей содержимое.

`BodyWriter` предоставляет доступ к записи того же тела через `PipeWriter`. Этот API используется для работы с буферами и потоковой записи через `System.IO.Pipelines`.

Тело можно записывать постепенно, несколькими операциями. Завершение отдельной записи не означает завершение всего ответа.

### `WriteAsync()`

Extension-метод `WriteAsync()` записывает строку в тело ответа.

Основная форма вызова:

```cs
Task WriteAsync(string text, CancellationToken ct = default);
```

По умолчанию используется UTF-8. Другая перегрузка позволяет передать `Encoding`.

```cs
response.StatusCode = StatusCodes.Status200OK;
response.ContentType = "text/plain; charset=utf-8";

await response.WriteAsync("Hello", context.RequestAborted);
```

Тип содержимого задаётся отдельно: кодирование строки в байты и значение `Content-Type` — разные настройки.

### `WriteAsJsonAsync()`

Extension-метод `WriteAsJsonAsync<T>()` сериализует значение в JSON и записывает его в тело ответа.

Основная форма вызова:

```cs
Task WriteAsJsonAsync<T>(
    T value,
    CancellationToken cancellationToken = default);
```

```cs
await response.WriteAsJsonAsync(
    new { Id = 42, Name = "Keyboard" },
    cancellationToken: context.RequestAborted);
```

В этой перегрузке `Content-Type` устанавливается в:

```http
application/json; charset=utf-8
```

Другие перегрузки позволяют передать `JsonSerializerOptions`, `JsonTypeInfo<T>` и явно указать тип содержимого.

---

## Начало отправки: `HasStarted` и `StartAsync()`

До начала отправки приложение может изменять статус и заголовки.

**После начала отправки статус и обычные заголовки уже зафиксированы**, поскольку они переданы сервером для отправки клиенту. Запись тела при этом может продолжаться.

`HasStarted` позволяет проверить эту границу:

```cs
if (!response.HasStarted)
{
    response.Headers["X-Request-Id"] = context.TraceIdentifier;
}
```

Начало отправки обычно происходит при записи или сбросе данных тела. Подключённая буферизация может влиять на момент фактического начала ответа.

Метод `StartAsync()` позволяет явно начать ответ:

```cs
Task StartAsync(CancellationToken cancellationToken = default);
```

Он выполняет зарегистрированные `OnStarting` callbacks и переводит заголовки в состояние, запрещающее изменение.

```cs
response.ContentType = "text/plain; charset=utf-8";

await response.StartAsync(context.RequestAborted);

// Заголовки уже зафиксированы, но тело ещё можно записывать
await response.WriteAsync("First part\n", context.RequestAborted);
```

`HasStarted == true` означает начало отправки ответа, а не завершение отправки всего тела.

---

## Обратные вызовы: `OnStarting()` и `OnCompleted()`

### `OnStarting()`

`OnStarting()` регистрирует callback, выполняемый **непосредственно перед отправкой заголовков**.

Основные перегрузки:

```cs
void OnStarting(Func<Task> callback);

void OnStarting(Func<object, Task> callback, object state);
```

Это позволяет задать заголовки в момент, когда основные компоненты уже сформировали ответ, но отправка ещё не началась:

```cs
response.OnStarting(() =>
{
    response.Headers["X-Request-Id"] = context.TraceIdentifier;
    return Task.CompletedTask;
});
```

Регистрация callback выполняется заранее, до начала ответа.

**Callbacks вызываются в обратном порядке регистрации**: последний зарегистрированный выполняется первым. Такой порядок соответствует вложенности middleware, когда внутренние компоненты обрабатывают ответ раньше внешних.

### `OnCompleted()`

`OnCompleted()` регистрирует callback, выполняемый после завершения отправки ответа сервером.

Основные перегрузки:

```cs
void OnCompleted(Func<Task> callback);

void OnCompleted(Func<object, Task> callback, object state);
```

Он используется для завершающих действий, связанных с обработкой запроса. На этом этапе изменять уже отправленный ответ невозможно.

Различие заключается в моменте выполнения:

- `OnStarting()` — перед отправкой заголовков, когда параметры ответа ещё можно скорректировать
- `OnCompleted()` — после завершения ответа, для завершающих действий

---

## Завершение ответа: `CompleteAsync()`

`CompleteAsync()` явно завершает формирование ответа и сбрасывает оставшиеся заголовки, данные тела и trailers.

```cs
Task CompleteAsync();
```

```cs
await response.WriteAsync("Done", context.RequestAborted);
await response.CompleteAsync();
```

После завершения дальнейшую запись тела выполнять не следует.

Метод может выбросить исключение, если ответ находится в некорректном состоянии, например фактически записанная длина не соответствует `ContentLength`.

**Завершение ответа и завершение выполнения обработчика — разные операции.** После `await response.CompleteAsync()` вызывающий код продолжает выполняться. Чтобы выйти из обработчика, требуется обычный `return`.

В типичной обработке запроса инфраструктура завершает ответ после выполнения pipeline; вручную вызывать `CompleteAsync()` для каждого ответа не требуется.

---

## Cookies

`Cookies` имеет тип `IResponseCookies` и предоставляет операции формирования заголовков `Set-Cookie`.

Основные методы:

- `Append()` — добавление cookie в ответ
- `Delete()` — формирование cookie с истёкшим сроком действия

```cs
response.Cookies.Append("theme", "dark", new CookieOptions
{
    Path = "/",
    MaxAge = TimeSpan.FromDays(30)
});
```

`CookieOptions` позволяет настроить область действия, срок хранения и другие атрибуты cookie.

Удаление:

```cs
response.Cookies.Delete("theme", new CookieOptions
{
    Path = "/"
});
```

Для удаления конкретной cookie важны совпадающие `Path` и `Domain`, если они были заданы при её установке.

Операции с `Response.Cookies` формируют указания клиенту через заголовки ответа. Входящие cookies текущего запроса доступны отдельно через `Request.Cookies`.

---

## Перенаправление: `Redirect()`

`Redirect()` устанавливает код перенаправления и заголовок `Location`.

```cs
response.Redirect("/login");                        // 302
response.Redirect("/new-address", permanent: true); // 301
```

Extension-перегрузка с параметром `preserveMethod` позволяет выбрать код, сохраняющий метод и тело исходного запроса:

```cs
response.Redirect(
    "/new-address",
    permanent: false,
    preserveMethod: true); // 307
```

|`permanent`|`preserveMethod`|Код|
|---|---|---|
|`false`|`false`|`302`|
|`true`|`false`|`301`|
|`false`|`true`|`307`|
|`true`|`true`|`308`|

Вызов `Redirect()` задаёт параметры ответа; прекращение выполнения текущего обработчика выполняется отдельно.

---

## Освобождение ресурсов после обработки запроса

`HttpResponse` позволяет зарегистрировать объект для освобождения инфраструктурой после завершения обработки:

- `RegisterForDispose(IDisposable)` — синхронное освобождение
- `RegisterForDisposeAsync(IAsyncDisposable)` — асинхронное освобождение

Это применяется, когда ресурс должен оставаться доступным до завершения запроса и его нельзя освободить сразу после выхода из текущего компонента.

# 5. `User`

`HttpContext.User` представляет пользователя текущего запроса. Свойство имеет тип `ClaimsPrincipal` и доступно для чтения и присваивания:

```cs
public abstract ClaimsPrincipal User { get; set; }
```

Оно содержит сведения, используемые при аутентификации и авторизации: идентичность пользователя, его имя, роли и другие **claims** — утверждения о пользователе.

---

## Структура представления пользователя

|Тип|Назначение|
|---|---|
|`ClaimsPrincipal`|Представляет пользователя и объединяет его identities|
|`ClaimsIdentity`|Описывает одну идентичность: сведения об аутентификации и набор claims|
|`Claim`|Отдельное утверждение, например идентификатор пользователя или роль|

Обычно principal содержит одну identity, но их может быть несколько. Основная доступна через `User.Identity`, а `User.Claims` перечисляет claims всех identities.

У claim основные данные — `Type` и `Value`: тип определяет смысл утверждения, значение хранится как строка. Например, claim с типом `ClaimTypes.NameIdentifier` может содержать идентификатор `"42"`, а с типом `ClaimTypes.Role` — роль `"Admin"`. 

---

## Как заполняется `User`

Обычно `User` устанавливается инфраструктурой аутентификации после проверки данных запроса, например cookie или токена. Компоненты, которым нужен аутентифицированный пользователь, должны выполняться после этого этапа.

**Наличие объекта `User` не означает, что пользователь аутентифицирован:** в стандартной реализации он доступен и для анонимного запроса.

Приложение может самостоятельно присвоить `ClaimsPrincipal` свойству `User`. Это меняет представление пользователя текущего запроса; само присваивание не проверяет подлинность пользователя и не создаёт cookie или токен для следующих запросов.

---

## Основные операции

```cs
using System.Security.Claims;

ClaimsPrincipal user = context.User;

bool isAuthenticated = user.Identity?.IsAuthenticated == true;

string? name = user.Identity?.Name;

string? userId = user.FindFirst(ClaimTypes.NameIdentifier)?.Value;

bool isAdmin = user.IsInRole("Admin");
```

`IsAuthenticated` показывает состояние основной identity. Обращение к нему не запускает повторную проверку пароля или токена.

`FindFirst(type)` возвращает первый claim указанного типа или `null`. Если значений может быть несколько, используется `FindAll(type)`. Для проверки наличия конкретного утверждения доступен `HasClaim(type, value)`:

```cs
bool isDeveloper = user.HasClaim("department", "Development");
```

Состав claims зависит от настройки аутентификации: нужный идентификатор, имя или роль не обязательно присутствуют у каждого пользователя.

`Name` определяется claim, выбранным как имя identity, и может быть `null` даже у аутентифицированного пользователя. `IsInRole` проверяет claims, выбранные как роли. За это отвечают настройки `NameClaimType` и `RoleClaimType`; по умолчанию используются `ClaimTypes.Name` и `ClaimTypes.Role`.

---

## Связь с авторизацией

Аутентификация определяет пользователя, а авторизация — разрешено ли ему конкретное действие.

Чтение `User` и вызовы `FindFirst`, `HasClaim` или `IsInRole` только возвращают сведения. Ограничение доступа задаётся отдельно: например, через `[Authorize]`, `RequireAuthorization()` или явную проверку политики. **Аутентифицированный пользователь не получает автоматически доступ ко всем действиям.** 

---

# 6. `RequestServices`

`HttpContext.RequestServices` предоставляет доступ к DI-сервисам текущего запроса. Имеет тип `IServiceProvider`:

```cs
public abstract IServiceProvider RequestServices { get; set; }
```

Через него можно получить сервис, зарегистрированный в контейнере приложения:

```cs
var service = context.RequestServices.GetRequiredService<IOrderService>();
```

В отличие от корневого `app.Services`, `RequestServices` учитывает область текущего запроса. Это существенно для `Scoped`-сервисов: разные компоненты одного запроса получают один экземпляр соответствующего сервиса.

## Получение сервисов

Основные методы расширения из `Microsoft.Extensions.DependencyInjection`:

|Метод|Назначение|
|---|---|
|`GetService<T>()`|Получить сервис; для ссылочного типа при отсутствии возвращает `null`|
|`GetRequiredService<T>()`|Получить обязательный сервис; при отсутствии выбрасывает исключение|
|`GetServices<T>()`|Получить все сервисы, зарегистрированные под типом `T`|

`GetRequiredService` используется, когда зависимость необходима для работы кода. `GetService` — когда её отсутствие допустимо.

Обычно зависимости получают через конструктор или параметры обработчика. Прямой доступ через `RequestServices` полезен, когда сервис требуется получить из имеющегося `HttpContext`.

Временем жизни полученных сервисов управляет DI-контейнер. Самостоятельно освобождать их обычно не требуется; сервисы, связанные с запросом, нельзя сохранять для использования после его завершения.

---

# 7. `Items`

`HttpContext.Items` — коллекция для хранения данных **в рамках одного запроса**. Она позволяет передавать значения между middleware, фильтрами и обработчиком запроса.

Свойство имеет тип `IDictionary<object, object?>`:

```cs
public abstract IDictionary<object, object?> Items { get; set; }
```

Ключами могут быть строки или другие объекты, значениями — произвольные объекты, включая `null`.

---

## Запись и чтение

Запись выполняется через индексатор:

```cs
context.Items["Department"] = "Development";
```

Присваивание по существующему ключу заменяет значение.

При чтении удобно одновременно проверить наличие ключа и тип значения:

```cs
if (context.Items.TryGetValue("Department", out var value)
    && value is string department)
{
    // Использование department
}
```

Поскольку значение возвращается как `object?`, для работы с ним требуется приведение или проверка типа. Для удаления используется `Remove(key)`, для проверки наличия ключа — `ContainsKey(key)`.

Компонент, читающий значение, должен выполняться после компонента, который его записал. `Items` самостоятельно не вычисляет и не заполняет данные.

---

## Выбор ключей

Строковые ключи удобны, но разные компоненты могут случайно использовать одинаковое имя и перезаписать данные друг друга. Особенно это существенно для middleware из библиотек.

Для предотвращения таких конфликтов можно использовать уникальный объект, объявленный в общем доступном месте:

```cs
public static class RequestItemKeys
{
    public static readonly object Department = new();
}
```

Запись:

```cs
context.Items[RequestItemKeys.Department] = "Development";
```

Чтение:

```cs
if (context.Items.TryGetValue(
        RequestItemKeys.Department, out var value)
    && value is string department)
{
    // Использование department
}
```

Для записи и чтения используется **один и тот же экземпляр ключа**. Новый `new object()` будет другим ключом. Статический ключ общий, но значения по нему хранятся отдельно в `Items` каждого запроса.

---

# 8. `Connection`

`HttpContext.Connection` предоставляет сведения о соединении, через которое обрабатывается запрос. Свойство имеет тип `ConnectionInfo`:

```cs
public abstract ConnectionInfo Connection { get; }
```

```cs
ConnectionInfo connection = context.Connection;
```

Обычно используется для получения IP-адреса удалённой стороны, адреса сервера и идентификатора соединения. 

---

## Основные свойства

|Свойство|Тип|Назначение|
|---|---|---|
|`Id`|`string`|Идентификатор соединения|
|`RemoteIpAddress`|`IPAddress?`|IP-адрес удалённой стороны|
|`RemotePort`|`int`|Порт удалённой стороны|
|`LocalIpAddress`|`IPAddress?`|Локальный IP-адрес сервера|
|`LocalPort`|`int`|Локальный порт сервера|
|`ClientCertificate`|`X509Certificate2?`|Клиентский сертификат, если доступен|

`LocalIpAddress` и `LocalPort` относятся к соединению на сервере. Они могут отличаться от адреса и порта в `Request.Host`, особенно при работе через прокси.

---

## Адрес клиента и прокси

**`RemoteIpAddress` не всегда является адресом исходного клиента.** Если перед приложением находится reverse proxy или балансировщик, непосредственное соединение с сервером устанавливает он. Поэтому первоначально сервер видит адрес прокси.

Исходный адрес обычно передаётся в заголовке `X-Forwarded-For`. Настроенный **Forwarded Headers Middleware** обрабатывает этот заголовок и обновляет `Connection.RemoteIpAddress`.

Такую обработку настраивают с учётом доверенных прокси: произвольный входящий заголовок нельзя считать подтверждённым адресом клиента. Подробная настройка относится к размещению приложения за прокси.

---

## Идентификатор соединения

```cs
string connectionId = context.Connection.Id;
```

`Id` идентифицирует **соединение**, а `HttpContext.TraceIdentifier` — **конкретный запрос**.

Одно соединение может использоваться для нескольких HTTP-запросов, поэтому идентификатор соединения не заменяет идентификатор запроса. Он полезен для сопоставления записей журналов, относящихся к одному соединению.

---

## Клиентский сертификат

`ClientCertificate` предоставляет сертификат клиента, используемый в сценариях аутентификации по сертификату. Если сертификат отсутствует, значение равно `null`.

Для асинхронного получения доступен метод:

```cs
var certificate = await context.Connection
    .GetClientCertificateAsync(context.RequestAborted);
```

---

# 9. `RequestAborted` и `Abort()`

Эти члены связаны с прерыванием запроса:

|Член|Назначение|
|---|---|
|`RequestAborted`|Предоставляет токен, сигнализирующий об отмене запроса|
|`Abort()`|Позволяет серверному коду принудительно прервать запрос|

`RequestAborted` используется для реакции на отмену, а `Abort()` — для её инициирования со стороны приложения.

---

## `RequestAborted`

Свойство имеет тип `CancellationToken`:

```cs
public abstract CancellationToken RequestAborted { get; set; }
```

Токен сигнализирует, что запрос был прерван клиентом или сервером. Например, сервер обнаружил обрыв соединения либо приложение вызвало `Abort()`.

```cs
string data = await httpClient.GetStringAsync(
    "https://example.com/data",
    context.RequestAborted);
```

Если операция поддерживает отмену, она сможет прекратить работу после получения сигнала. Обычно отмена выражается через `OperationCanceledException` или производное от него исключение.

---

## Как код реагирует на отмену

**Отмена не останавливает произвольный код принудительно.** Операция должна поддерживать переданный токен или самостоятельно проверять его.

Проверка состояния:

```cs
bool isAborted = context.RequestAborted.IsCancellationRequested;
```

Проверка с выбрасыванием исключения:

```cs
context.RequestAborted.ThrowIfCancellationRequested();
```

Вторая форма удобна внутри длительных вычислений: проверки размещают в подходящих точках, чтобы прекратить дальнейшую работу при отмене. Если исключение не перехвачено, обычное выполнение метода прекращается.

---

## `Abort()`

Метод позволяет принудительно прервать запрос:

```cs
public abstract void Abort();
```

```cs
context.Abort();
return;
```

Вызов прерывает нормальную передачу ответа и приводит к сигналу отмены через `RequestAborted`. Клиент получает прерывание обмена, а не обычный HTTP-ответ с выбранным кодом ошибки.

**`Abort()` не завершает выполнение текущего метода.** Поэтому после него обычно требуется `return`, чтобы прикладной код не продолжал работу.

Для обычного отказа — например, некорректных входных данных или отсутствия доступа — формируют соответствующий HTTP-ответ. `Abort()` используется, когда обмен требуется именно принудительно прервать.

---
