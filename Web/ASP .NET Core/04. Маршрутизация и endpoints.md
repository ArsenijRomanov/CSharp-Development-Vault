# 1. Назначение маршрутизации и понятие endpoint

> [!info] Определение  
> **Маршрутизация (routing)** — механизм, который сопоставляет входящий HTTP-запрос с зарегистрированными endpoints и выбирает подходящий для обработки запроса.

При выборе учитываются шаблон пути, HTTP-метод и другие условия. Например:

- `{http}GET /products` — получение списка товаров.
- `{http}POST /products` — создание товара.
- `{http}GET /products/42` — получение конкретного товара.

Маршрутизация также позволяет извлекать значения параметров из пути и генерировать ссылки на endpoints. 

---

### 1.1. Что такое endpoint

> [!info] Определение  
> **Endpoint** — отдельная точка обработки запросов в приложении, объединяющая исполняемый обработчик и связанные с ним метаданные.

Для участия в маршрутизации endpoint также содержит сведения, позволяющие сопоставить его с запросом.

В ASP.NET Core endpoint представлен объектом класса `{cs}Endpoint`. Основные свойства:

|Свойство|Тип|Назначение|
|---|---|---|
|`RequestDelegate`|`RequestDelegate?`|Исполняемый обработчик запроса|
|`Metadata`|`EndpointMetadataCollection`|Метаданные endpoint|
|`DisplayName`|`string?`|Отображаемое имя для диагностики|

**Метаданные** — дополнительные сведения об endpoint: например, разрешённые HTTP-методы, требования авторизации и информация о формируемом ответе.

Они используются маршрутизацией, middleware и другими компонентами инфраструктуры. 

---

### 1.2. `RouteEndpoint`: endpoint с маршрутом

Для endpoints, выбираемых по маршруту, используется `{cs}RouteEndpoint`, наследующий `{cs}Endpoint`:

```cs
public sealed class RouteEndpoint : Endpoint
```

Он дополнительно содержит:

|Свойство|Тип|Назначение|
|---|---|---|
|`RoutePattern`|`RoutePattern`|Шаблон маршрута|
|`Order`|`int`|Значение, учитываемое при определении приоритета endpoint|

Например, `{cs}"/products/{id:int}"` — шаблон маршрута с параметром `id` и ограничением на целочисленное значение.

**Шаблон маршрута и обработчик — разные части endpoint:** шаблон участвует в выборе, обработчик выполняет работу с запросом. 

---

### 1.3. Пример регистрации endpoints

```cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/products", () => "Список товаров");

app.MapPost("/products", () => "Обработка создания товара");

app.MapGet("/products/{id:int}", (int id) => $"Товар {id}");

app.Run();
```

Здесь зарегистрированы три endpoint:

|Запрос|Обработчик|
|---|---|
|`GET /products`|Возвращает `"Список товаров"`|
|`POST /products`|Возвращает `"Обработка создания товара"`|
|`GET /products/42`|Получает `id = 42` и возвращает `"Товар 42"`|

Один путь может соответствовать разным endpoints в зависимости от HTTP-метода. Один endpoint с параметризованным маршрутом может обрабатывать множество конкретных путей.

---

### 1.4. Связь с конвейером middleware

Маршрутизация работает внутри конвейера middleware. **Выбор endpoint и его выполнение — отдельные этапы:**

1. Middleware маршрутизации выбирает endpoint.
2. Следующие middleware могут использовать сведения о выбранном endpoint и решить, продолжать ли обработку.
3. Middleware выполнения endpoints вызывает его обработчик.

Например, middleware авторизации проверяет требования выбранного endpoint **до вызова обработчика**. Если доступ запрещён, обработчик не выполняется.

Таким образом, endpoint не заменяет общий конвейер: запрос проходит через middleware, которые могут выполнять работу до и после его обработки или завершить запрос раньше. 

---

# 2. Этапы маршрутизации: `UseRouting` и `UseEndpoints`

Маршрутизация использует два этапа конвейера:

|Метод|Подключаемый этап|
|---|---|
|`UseRouting`|Сопоставление запроса с endpoints и выбор подходящего|
|`UseEndpoints`|Выполнение обработчика выбранного endpoint|

Оба метода являются расширениями для `{cs}IApplicationBuilder` из класса `{cs}EndpointRoutingApplicationBuilderExtensions`. Они добавляют middleware при настройке приложения; сами middleware выполняются при обработке запросов. 

---

### 2.1. `UseRouting`: выбор endpoint

Сигнатура:

```cs
public static IApplicationBuilder UseRouting(
    this IApplicationBuilder builder);
```

```cs
app.UseRouting();
```

Подключённый middleware сопоставляет запрос с зарегистрированными endpoints. При успешном выборе он связывает endpoint с текущим `{cs}HttpContext` и заполняет значения параметров маршрута в `{cs}Request.RouteValues`.

Например, для маршрута `{cs}"/products/{id:int}"` и запроса `/products/42` значение параметра `id` становится доступно следующим компонентам.

После выбора middleware продолжает конвейер. Если endpoint не найден, обработка также продолжается.

> [!note] Выбор и выполнение  
> `UseRouting` выбирает endpoint, но не вызывает его обработчик. Между выбором и выполнением могут работать другие middleware. 

#### Доступ к выбранному endpoint

Для получения endpoint используется метод расширения `{cs}GetEndpoint`:

```cs
public static Endpoint? GetEndpoint(this HttpContext context);
```

```cs
Endpoint? endpoint = context.GetEndpoint();

string? displayName = endpoint?.DisplayName;
```

Метод возвращает `null`, если endpoint не установлен — например, маршрутизация ещё не выполнялась или не нашла подходящий маршрут.

После `{cs}UseRouting` middleware может прочитать выбранный endpoint и его метаданные. 

---

### 2.2. `UseEndpoints`: выполнение endpoint

Сигнатура:

```cs
public static IApplicationBuilder UseEndpoints(
    this IApplicationBuilder builder,
    Action<IEndpointRouteBuilder> configure);
```

Параметр `configure` позволяет зарегистрировать endpoints:

```cs
app.UseEndpoints(endpoints =>
{
    endpoints.MapGet("/products", () => "Список товаров");
});
```

**Делегат `configure` вызывается при настройке приложения**. Он получает `{cs}IEndpointRouteBuilder`, через который регистрируются обработчики. `{cs}UseEndpoints` также добавляет middleware их выполнения. 

При обработке запроса это middleware:

- Если выбран исполняемый endpoint — вызывает его `{cs}RequestDelegate`, не передавая запрос следующим middleware.
- Если endpoint отсутствует — вызывает следующий компонент конвейера.

После завершения обработчика управление возвращается к предыдущим middleware, ожидающим `{cs}next`. **Отсутствие endpoint само по себе не означает, что `{cs}UseEndpoints` сразу формирует ответ `404`:** запрос может обработать следующий компонент. 

---

### 2.3. Middleware между выбором и выполнением

Между `{cs}UseRouting` и `{cs}UseEndpoints` размещают компоненты, которым нужно знать выбранный endpoint **до его выполнения**.

Например, авторизация использует требования доступа из метаданных endpoint. Собственное middleware может применять правила аудита или логировать выбранный обработчик.

Пример с явным расположением этапов:

```cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.UseRouting();

app.Use(async (context, next) =>
{
    Endpoint? endpoint = context.GetEndpoint();

    Console.WriteLine(
        $"Выбран endpoint: {endpoint?.DisplayName ?? "не выбран"}");

    await next(context);

    Console.WriteLine("Обработка завершена");
});

app.UseEndpoints(endpoints =>
{
    endpoints.MapGet("/products", () => "Список товаров");
});

app.Run(context =>
{
    context.Response.StatusCode = StatusCodes.Status404NotFound;

    return context.Response.WriteAsync("Маршрут не найден");
});

app.Run();
```

Для `{http}GET /products` выполняется зарегистрированный endpoint. Для пути, которому ничего не соответствует, запрос проходит через `{cs}UseEndpoints` к следующему терминальному обработчику.

Хотя регистрация внутри `{cs}UseEndpoints` записана ниже `{cs}UseRouting`, весь набор endpoints настраивается до начала обработки запросов. 

---

### 2.4. Автоматическое подключение в `WebApplication`

При использовании `{cs}WebApplication` обычная регистрация может выглядеть так:

```cs
app.MapGet("/products", () => "Список товаров");

app.Run();
```

Если endpoints зарегистрированы, инфраструктура автоматически добавляет:

- Middleware выбора endpoint, если `{cs}UseRouting` не вызван явно.
- Middleware выполнения endpoints в конце конвейера.

Поэтому явно вызывать оба метода для обычной регистрации endpoints не требуется.

**Явный `{cs}UseRouting` позволяет задать положение выбора endpoint.** Например, middleware, которому нужно изменить путь до сопоставления с маршрутами, размещают перед этим вызовом. `{cs}UseEndpoints` позволяет явно задать место выполнения обработчиков. 

> [!warning] Терминальный обработчик перед endpoints  
> `app.Run(handler)` не вызывает следующий компонент. Если он расположен перед этапом выполнения endpoints, запрос не дойдёт до выбранного обработчика.

Чтобы терминальный обработчик работал после endpoints, этап выполнения подключают явно:

```cs
app.UseRouting();

app.MapGet("/products", () => "Список товаров");

app.UseEndpoints(_ => { });

app.Run(context =>
{
    context.Response.StatusCode = StatusCodes.Status404NotFound;

    return context.Response.WriteAsync("Маршрут не найден");
});
```

Пустой делегат здесь ничего не регистрирует: endpoint уже зарегистрирован через `{cs}app.MapGet`. Вызов `{cs}UseEndpoints` задаёт место его выполнения перед последующим `Run`.

# 3. `IEndpointRouteBuilder`: регистрация endpoints

> [!info] Определение  
> **`IEndpointRouteBuilder`** — интерфейс, через который настраивают набор endpoints приложения.

`{cs}WebApplication` реализует этот интерфейс, поэтому методы регистрации доступны непосредственно через `app`:

```cs
app.MapGet("/products", () => "Список товаров");
```

Регистрация описывает, **каким запросам соответствует endpoint и какой обработчик нужно вызвать**. Она не добавляет обработчик в текущую позицию цепочки middleware и не выполняет его. 

---

### 3.1. Структура интерфейса

```cs
public interface IEndpointRouteBuilder
{
    IServiceProvider ServiceProvider { get; }

    ICollection<EndpointDataSource> DataSources { get; }

    IApplicationBuilder CreateApplicationBuilder();
}
```

|Член|Назначение|
|---|---|
|`ServiceProvider`|Провайдер сервисов, доступный при настройке endpoints|
|`DataSources`|Коллекция источников, предоставляющих endpoints|
|`CreateApplicationBuilder()`|Создание построителя конвейера middleware|

Методы `{cs}MapGet`, `{cs}MapPost` и другие **не являются членами самого интерфейса**. Это методы расширения, в частности из класса `{cs}EndpointRouteBuilderExtensions`. 

Endpoints можно регистрировать как непосредственно через `{cs}WebApplication`, так и через построитель, переданный в `{cs}UseEndpoints`:

```cs
app.MapGet("/products", () => "Список товаров");
```

```cs
app.UseEndpoints(endpoints =>
{
    endpoints.MapGet("/products", () => "Список товаров");
});
```

Это альтернативные формы регистрации. В обоих случаях получатель методов реализует `{cs}IEndpointRouteBuilder`.

---

### 3.2. Регистрация для определённого HTTP-метода

|Метод регистрации|HTTP-метод|
|---|---|
|`MapGet`|`GET`|
|`MapPost`|`POST`|
|`MapPut`|`PUT`|
|`MapDelete`|`DELETE`|
|`MapPatch`|`PATCH`|

Каждый метод принимает шаблон маршрута и обработчик. Для обработчика предусмотрены две формы: **`{cs}RequestDelegate`** и **`{cs}Delegate`**.

#### Перегрузки с `RequestDelegate`

```cs
public static IEndpointConventionBuilder MapGet(
    this IEndpointRouteBuilder endpoints,
    string pattern, RequestDelegate requestDelegate);

public static IEndpointConventionBuilder MapPost(
    this IEndpointRouteBuilder endpoints,
    string pattern, RequestDelegate requestDelegate);

public static IEndpointConventionBuilder MapPut(
    this IEndpointRouteBuilder endpoints,
    string pattern, RequestDelegate requestDelegate);

public static IEndpointConventionBuilder MapDelete(
    this IEndpointRouteBuilder endpoints,
    string pattern, RequestDelegate requestDelegate);

public static IEndpointConventionBuilder MapPatch(
    this IEndpointRouteBuilder endpoints,
    string pattern, RequestDelegate requestDelegate);
```

Обработчик имеет фиксированную сигнатуру:

```cs
public delegate Task RequestDelegate(HttpContext context);
```

Он работает непосредственно с `{cs}HttpContext`, в том числе самостоятельно записывает ответ:

```cs
RequestDelegate handler = async context =>
{
    await context.Response.WriteAsync("Список товаров");
};

app.MapGet("/products", handler);
```

Дополнительные параметры из маршрута или DI в такую сигнатуру добавить нельзя: необходимые данные получают через `{cs}HttpContext`.

#### Перегрузки с `Delegate`

```cs
public static RouteHandlerBuilder MapGet(
    this IEndpointRouteBuilder endpoints,
    string pattern, Delegate handler);

public static RouteHandlerBuilder MapPost(
    this IEndpointRouteBuilder endpoints,
    string pattern, Delegate handler);

public static RouteHandlerBuilder MapPut(
    this IEndpointRouteBuilder endpoints,
    string pattern, Delegate handler);

public static RouteHandlerBuilder MapDelete(
    this IEndpointRouteBuilder endpoints,
    string pattern, Delegate handler);

public static RouteHandlerBuilder MapPatch(
    this IEndpointRouteBuilder endpoints,
    string pattern, Delegate handler);
```

Эти перегрузки используются для обработчиков Minimal API. Обработчик может объявлять параметры запроса и сервисы, а также возвращать значение:

```cs
app.MapGet("/products/{id:int}", (int id) =>
{
    return new { Id = id };
});
```

Инфраструктура формирует исполняемый обработчик endpoint: получает аргументы, вызывает переданный делегат и обрабатывает его результат. В этом примере `id` берётся из маршрута, а возвращаемый объект записывается в ответ как JSON.

`{cs}Delegate` — базовый класс делегатов; допустимая сигнатура обработчика определяется правилами Minimal API. 

---

### 3.3. `MapMethods`: один endpoint для нескольких HTTP-методов

Сигнатуры:

```cs
public static IEndpointConventionBuilder MapMethods(
    this IEndpointRouteBuilder endpoints,
    string pattern,
    IEnumerable<string> httpMethods,
    RequestDelegate requestDelegate);

public static RouteHandlerBuilder MapMethods(
    this IEndpointRouteBuilder endpoints,
    string pattern,
    IEnumerable<string> httpMethods,
    Delegate handler);
```

Метод позволяет явно указать набор HTTP-методов:

```cs
app.MapMethods(
    "/status",
    new[] { HttpMethods.Get, HttpMethods.Head },
    () => "OK");
```

Здесь **один endpoint** соответствует запросам `{http}GET /status` и `{http}HEAD /status`.

`MapMethods` также используют для методов, у которых нет отдельного метода регистрации, например `OPTIONS`. 

> [!note]- `HttpMethods`: обозначения и проверка HTTP-методов  
> `HttpMethods` — статический класс из пространства имён `Microsoft.AspNetCore.Http`. Он содержит названия HTTP-методов в виде полей типа `string`, объявленных как `public static readonly`.
> 
> |Поле|Значение|
> |---|---|
> |`HttpMethods.Get`|`"GET"`|
> |`HttpMethods.Post`|`"POST"`|
> |`HttpMethods.Put`|`"PUT"`|
> |`HttpMethods.Delete`|`"DELETE"`|
> |`HttpMethods.Patch`|`"PATCH"`|
> |`HttpMethods.Head`|`"HEAD"`|
> |`HttpMethods.Options`|`"OPTIONS"`|
> |`HttpMethods.Trace`|`"TRACE"`|
> |`HttpMethods.Connect`|`"CONNECT"`|
> |`HttpMethods.Query`|`"QUERY"`|
> 
> Поле `Query` доступно начиная с ASP.NET Core 10.
> 
> Эти значения можно передавать в `MapMethods` вместо строковых литералов:
> 
> ```cs
> app.MapMethods(
>     "/status",
>     new[] { HttpMethods.Get, HttpMethods.Head },
>     () => Results.Ok());
> ```
> 
> Также класс предоставляет методы проверки: `IsGet`, `IsPost`, `IsPut` и аналогичные для остальных HTTP-методов. Например, сигнатура `IsGet`:
> 
> ```cs
> public static bool IsGet(string method);
> ```
> 
> Использование:
> 
> ```cs
> bool isGet = HttpMethods.IsGet(context.Request.Method);
> ```

---

### 3.4. `Map`: регистрация без ограничения HTTP-метода

Сигнатуры со строковым шаблоном:

```cs
public static IEndpointConventionBuilder Map(
    this IEndpointRouteBuilder endpoints,
    string pattern,
    RequestDelegate requestDelegate);

public static RouteHandlerBuilder Map(
    this IEndpointRouteBuilder endpoints,
    string pattern,
    Delegate handler);
```

Также доступны перегрузки с уже построенным `{cs}RoutePattern`:

```cs
public static IEndpointConventionBuilder Map(
    this IEndpointRouteBuilder endpoints,
    RoutePattern pattern,
    RequestDelegate requestDelegate);

public static RouteHandlerBuilder Map(
    this IEndpointRouteBuilder endpoints,
    RoutePattern pattern,
    Delegate handler);
```

Пример:

```cs
app.Map("/status", () => "OK");
```

**Сам `Map` не задаёт ограничение на HTTP-метод:** endpoint выбирается по шаблону маршрута независимо от метода запроса. Дополнительные ограничения могут быть заданы метаданными endpoint. 

#### Отличие от `Map` для ветвления middleware

У методов одинаковое имя, но разные получатели и параметры:

| Вариант                                                                    | Назначение                                 |
| -------------------------------------------------------------------------- | ------------------------------------------ |
| `Map` для `IEndpointRouteBuilder`, принимающий обработчик                  | Регистрация endpoint с шаблоном маршрута   |
| `Map` для `IApplicationBuilder`, принимающий `Action<IApplicationBuilder>` | Создание ветки middleware по префиксу пути |

```cs
// Endpoint
app.Map("/api", () => "API");
```

```cs
// Ветка middleware
app.Map("/api", branch =>
{
    branch.Run(context =>
        context.Response.WriteAsync("API"));
});
```

---

### 3.5. Возвращаемый построитель endpoint

Методы регистрации возвращают объект для **дальнейшей настройки endpoint**:

| Форма обработчика | Возвращаемый тип                                                |
| ----------------- | --------------------------------------------------------------- |
| `RequestDelegate` | `IEndpointConventionBuilder`                                    |
| `Delegate`        | `RouteHandlerBuilder`, реализующий `IEndpointConventionBuilder` |

Например, результат регистрации можно сохранить и затем настроить:

```cs
RouteHandlerBuilder endpointBuilder =
    app.MapGet("/products/{id:int}", (int id) => $"Товар {id}");

endpointBuilder.WithName("GetProduct");
```

Или объединить вызовы:

```cs
app.MapGet("/products/{id:int}", (int id) => $"Товар {id}")
    .WithName("GetProduct");
```

Возвращается **построитель для настройки**, а не результат обработки HTTP-запроса. Через него задают имя, метаданные, требования авторизации и другие характеристики endpoint.

# 4. Шаблоны маршрутов

> [!info] Определение  
> **Шаблон маршрута** — описание структуры пути запроса, используемое для сопоставления запроса с endpoint и извлечения значений параметров.

Шаблон передают при регистрации endpoint:

```cs
app.MapGet("/products/{id:int}", (int id) => $"Товар {id}");
```

Здесь `{cs}"/products/{id:int}"` описывает путь. Ограничение на HTTP-метод задаётся отдельно — методом `MapGet`.

---

### 4.1. Сегменты и литералы

Путь состоит из **сегментов**, разделённых `/`. Сегмент может содержать фиксированный текст — **литерал**, параметр или их сочетание.

Например, шаблон:

```cs
"/products/{id}/reviews"
```

Содержит три сегмента:

|Сегмент|Назначение|
|---|---|
|`products`|Фиксированный текст|
|`{id}`|Параметр|
|`reviews`|Фиксированный текст|

Ему соответствует `/products/42/reviews`, но не `/products/42` или `/products/42/reviews/15`.

Сопоставление литералов выполняется без учёта регистра: `/products` и `/Products` соответствуют одному шаблону. 

**[[HTTP – семантика и структура сообщений#^ljdm3b|Query string]] не является частью шаблона пути.**

---

### 4.2. Параметры маршрута

Параметр записывается в фигурных скобках:

```cs
/products/{id}
```

По умолчанию он обязателен и захватывает значение одного сегмента:

|Путь|Соответствие|Значение `id`|
|---|---|---|
|`/products/42`|Да|`"42"`|
|`/products/phone`|Да|`"phone"`|
|`/products`|Нет|—|
|`/products/42/details`|Нет|—|

В шаблоне можно объявить несколько параметров:

```cs
app.MapGet(
    "/users/{userId}/orders/{orderId}",
    (int userId, int orderId) =>
        $"Пользователь {userId}, заказ {orderId}");
```

Для `/users/3/orders/7` обработчик получит `{cs}userId = 3` и `{cs}orderId = 7`. Значения передаются аргументам обработчика по именам параметров. 

Извлечённые значения также доступны через `{cs}HttpContext.Request.RouteValues`:

```cs
string? id = context.Request.RouteValues["id"]?.ToString();
```

Эта коллекция заполняется при маршрутизации. 

---

### 4.3. Необязательные параметры

Символ `?` делает параметр необязательным:

```cs
"/products/{id?}"
```

Такому шаблону соответствуют и `/products/42`, и `/products`. Если сегмент отсутствует, значение `id` не добавляется в `RouteValues`. 

Обработчик также должен допускать отсутствие значения:

```cs
app.MapGet("/products/{id?}", (int? id) =>
    id.HasValue
        ? $"Товар {id.Value}"
        : "Список товаров");
```

Здесь `{cs}int?` позволяет получить `{cs}null`, когда `id` отсутствует. Необязательность в шаблоне и допустимость отсутствующего аргумента в обработчике задаются отдельно. 

> [!tip] Важно
> Необязательные сегменты размещают после обязательных.

---

### 4.4. Значения по умолчанию

Значение по умолчанию задаётся через `=`:

```cs
"/products/page/{page=1}"
```

|Путь|Значение `page`|
|---|---|
|`/products/page`|`"1"`|
|`/products/page/3`|`"3"`|

В отличие от необязательного параметра, **параметр со значением по умолчанию получает значение даже при отсутствии соответствующего сегмента**. 

```cs
app.MapGet("/products/page/{page=1}", (int page) =>
    $"Страница {page}");
```

Для `/products/page` обработчик получит `page = 1`.

---

### 4.5. Ограничения параметров

**Ограничение маршрута — route constraint — задаёт условие, которому должно соответствовать значение параметра для выбора endpoint.**

Оно записывается после имени параметра через `:`:

```cs
app.MapGet("/products/{id:int}", (int id) => $"Товар {id}");
```

Шаблону соответствуют `/products/42` и `/products/-5`, но не `/products/phone`. Само ограничение `int` допускает отрицательные значения. 

> [!note]- Встроенные ограничения ASP.NET Core
> 
> |Ограничение|Пример|Условие|
> |---|---|---|
> |`int`|`{id:int}`|Значение представимо как `int`|
> |`guid`|`{id:guid}`|Корректное значение `Guid`|
> |`long`|`{id:long}`|Значение представимо как `long`|
> |`min(n)`|`{id:min(1)}`|Целое число не меньше `n`|
> |`range(min,max)`|`{age:range(18,120)}`|Целое число в диапазоне включительно|
> |`max(n)`|`{count:max(100)}`|Целое число не больше `n`|
> |`bool`|`{active:bool}`|`true` или `false`, без учёта регистра|
> |`alpha`|`{name:alpha}`|Только латинские буквы `a–z`, без учёта регистра|
> |`length(n)`|`{code:length(6)}`|Строка указанной длины|
> |`length(min,max)`|`{code:length(3,6)}`|Длина строки в диапазоне включительно|
> |`minlength(n)`|`{name:minlength(3)}`|Длина строки не меньше `n`|
> |`maxlength(n)`|`{name:maxlength(20)}`|Длина строки не больше `n`|
> |`decimal`|`{price:decimal}`|Значение представимо как `decimal`|
> |`datetime`|`{date:datetime}`|Значение представимо как `DateTime`|
> |`regex(expression)`|`{code:regex(^abc$)}`|Значение соответствует регулярному выражению|
> |`double`|`{value:double}`|Значение представимо как `double`|
> |`float`|`{value:float}`|Значение представимо как `float`|
> |`file`|`{path:file}`|Последний сегмент содержит точку с последующими символами, среди которых есть отличный от точки|
> |`nonfile`|`{path:nonfile}`|Последний сегмент не соответствует условию `file`|
> |`required`|`{name:required}`|Наличие значения при генерации URL|
> 
> Числовые ограничения и `datetime` используют `InvariantCulture`. `file` и `nonfile` проверяют форму пути, а не существование файла на диске. 

Несколько ограничений объединяют через `:`:

```cs
"/products/{id:int:min(1)}"
```

Ограничения можно сочетать с необязательностью или значением по умолчанию:

```cs
"/products/{id:int?}"
"/products/page/{page:int=1}"
```

Сначала записываются ограничения, затем `?` или `=значение`. 

> [!warning] Ограничение маршрута и валидация  
> Ограничения участвуют в выборе endpoint. Если значение не подходит, этот endpoint не выбирается; при отсутствии другого подходящего endpoint обычно получится `404`. Для проверки корректности входных данных и возврата `400` используют валидацию.

**Ограничение не преобразует значение в `RouteValues`.** Например, при `{id:int}` извлечённое из пути значение остаётся строкой. Преобразование в аргумент `{cs}int id` выполняется отдельно при подготовке вызова обработчика. 

---

### 4.6. Захват остатка пути: catch-all

Обычный параметр захватывает один сегмент. **Catch-all параметр захватывает весь оставшийся путь**, включая `/` между сегментами:

```cs
app.MapGet("/files/{**path}", (string? path) =>
    $"Путь: {path}");
```

|Путь|Значение `path`|
|---|---|
|`/files/report.pdf`|`"report.pdf"`|
|`/files/docs/2026/report.pdf`|`"docs/2026/report.pdf"`|
|`/files`|Значение отсутствует|

Catch-all может соответствовать пустому остатку пути. Он должен находиться в конце шаблона и занимать отдельный сегмент. 

Поддерживаются две формы:

```cs
/files/{*path}
/files/{**path}
```

Обе захватывают остаток входящего пути. Различие проявляется **при генерации ссылки** для значения `{cs}path = "docs/report.pdf"`:

|Шаблон|Сгенерированный путь|
|---|---|
|`/files/{*path}`|`/files/docs%2Freport.pdf`|
|`/files/{**path}`|`/files/docs/report.pdf`|

У `*` разделитель `/` внутри значения кодируется, у `**` сохраняется. 

---

### 4.7. Несколько частей в одном сегменте

Один сегмент может объединять литералы и параметры:

```cs
"/files/{name}.{extension}"
```

Для `/files/report.pdf` будут извлечены:

- `{cs}name = "report"`;
- `{cs}extension = "pdf"`.

Параметры внутри одного сегмента должны разделяться литералом. Поэтому 
`{cs}{name}.{extension}` допустим, а `{cs}{name}{extension}` — нет.

Расширение можно сделать необязательным:

```cs
"/files/{name}.{extension?}"
```

Тогда подходят и `/files/report.pdf`, и `/files/report`. При отсутствии расширения точка также не требуется. 

---

# 5. Выбор endpoint

При обработке запроса маршрутизация определяет, **какие endpoints соответствуют запросу**, и выбирает среди них один с наибольшим приоритетом.

Наличие нескольких подходящих endpoints само по себе не является ошибкой: важно, можно ли однозначно определить лучший.

---

### 5.1. Что учитывается при выборе

Упрощённо выбор состоит из следующих этапов:

1. Находятся endpoints, шаблоны которых соответствуют пути запроса.
2. Исключаются кандидаты, не удовлетворяющие ограничениям маршрута.
3. Проверяются HTTP-метод и другие условия сопоставления.
4. Среди оставшихся кандидатов выбирается endpoint с наибольшим приоритетом.

Обработчики во время этого процесса **не вызываются**. Маршрутизация устанавливает выбранный endpoint в `{cs}HttpContext` и сохраняет его значения маршрута в `{cs}Request.RouteValues`. Выполнение обработчика происходит позднее. 

Например:

```cs
app.MapGet("/products", () => "Список товаров");

app.MapPost("/products", () => "Создание товара");
```

Путь одинаковый, но HTTP-методы различаются:

| Запрос           | Выбранный endpoint                 |
| ---------------- | ---------------------------------- |
| `GET /products ` | Зарегистрированный через `MapGet`  |
| `POST /products` | Зарегистрированный через `MapPost` |

> [!warning] Порядок регистрации  
> Для endpoints, зарегистрированных через `MapGet`, `MapPost` и аналогичные методы, порядок вызовов не задаёт приоритет. Правило «первый подходящий побеждает» здесь не применяется.

---

### 5.2. Приоритет: `Order`

Сначала сравнивается свойство `{cs}RouteEndpoint.Order`: **чем меньше значение, тем выше приоритет**. При одинаковом `Order` учитывается специфичность шаблона.

У обычных endpoints, зарегистрированных через `{cs}MapGet` и аналогичные методы, `{cs}Order` по умолчанию равен `0`. 

Значение можно изменить методом расширения `{cs}WithOrder`:

```cs
public static TBuilder WithOrder<TBuilder>(
    this TBuilder builder,
    int order)
    where TBuilder : IEndpointConventionBuilder;
```

Метод возвращает тот же builder, поэтому настройку можно продолжать цепочкой. 

```cs
app.MapGet("/products/{value}", (string value) => $"Значение: {value}")
    .WithOrder(-1);

app.MapGet("/products/new", () => "Новый товар");
```

Для `{http}GET /products/new` будет выбран **первый endpoint**: его `{cs}Order = -1` имеет преимущество перед `Order = 0`, несмотря на более специфичный шаблон второго.

Обычно `Order` оставляют стандартным: специфичности шаблонов достаточно для выбора. Явный порядок используют, когда необходимо намеренно изменить приоритет. 

---

### 5.3. Специфичность шаблона

При одинаковом `Order` более конкретный шаблон имеет преимущество.

При сравнении соответствующих сегментов действует следующий порядок:

|Приоритет|Вид сегмента|Пример|
|---|---|---|
|Выше|Литерал|`new`|
|↓|Параметр с ограничением или составной сегмент|`{id:int}`, `{name}.{extension}`|
|↓|Параметр без ограничения|`{value}`|
|↓|Catch-all с ограничением|`{**path:nonfile}`|
|Ниже|Catch-all без ограничения|`{**path}`|

Сегменты сравниваются слева направо: различие в более раннем сегменте определяет преимущество раньше различий в последующих. 

#### Литерал и параметр

```cs
app.MapGet("/products/{value}", (string value) => $"Значение: {value}");

app.MapGet("/products/new", () => "Новый товар");
```

Для `{http}GET /products/new` подходят оба шаблона, но выбирается `/products/new`: литерал `new` конкретнее параметра `{value}`.

Перестановка этих регистраций не изменит результат.

#### Параметр с ограничением и без него

```cs
app.MapGet("/products/{value}", (string value) => $"Значение: {value}");

app.MapGet("/products/{id:int}", (int id) => $"Товар {id}");
```

|Запрос|Выбранный шаблон|Причина|
|---|---|---|
|`GET /products/42`|`/products/{id:int}`|Оба подходят, но параметр с ограничением имеет преимущество|
|`GET /products/phone`|`/products/{value}`|Ограничение `int` исключает второй endpoint|

> [!note] Количество ограничений  
> Добавление ограничений не повышает приоритет за каждое из них. Например, `{id:int}` и `{id:int:min(1)}` имеют одинаковую специфичность: оба являются параметрами с ограничениями.

Ограничения определяют допустимость кандидата, а не ранжируются по строгости. 

---

### 5.4. Неоднозначность: `AmbiguousMatchException`

Если **несколько оставшихся кандидатов имеют одинаковый наивысший приоритет**, маршрутизация не может выбрать один и выбрасывает `AmbiguousMatchException`. Их обработчики не вызываются. 

```cs
app.MapGet("/products/{id}", (string id) => $"По id: {id}");

app.MapGet("/products/{name}", (string name) => $"По имени: {name}");
```

Для `GET /products/phone`:

- оба шаблона подходят;
- `Order` одинаковый;
- специфичность одинаковая;
- разные имена параметров не помогают различить endpoints.

**Порядок регистрации такую неоднозначность не разрешает.** Необходимо различить шаблоны, условия сопоставления либо явно задать приоритет.

Ошибку обнаруживают при запросе, для которого возникла неоднозначность. Одинаковая специфичность сама по себе допустима: например, `{value:int}` и `{value:alpha}` могут обслуживать разные значения без пересечения. 

---

### 5.5. Когда получаются `404` и `405`

Для приложения с единственным endpoint:

```cs
app.MapGet("/products/{id:int}", (int id) => $"Товар {id}");
```

Типичное поведение:

|Запрос|Результат|
|---|---|
|`GET /products/42`|Выполнение обработчика|
|`GET /orders/42`|`404 Not Found`: подходящего пути нет|
|`GET /products/phone`|`404 Not Found`: ограничение `int` не выполнено|
|`POST /products/42`|`405 Method Not Allowed`: HTTP-метод не разрешён|

При несовпадении HTTP-метода инфраструктура формирует ответ `405` с заголовком `Allow`, перечисляющим допустимые методы. В этом примере — `Allow: GET`. 

Если endpoint не выбран, запрос может обработать следующий middleware. `404` получается, когда обработка заканчивается без другого обработчика или явно заданного ответа.

---

# 6. Параметры обработчиков Minimal API

Обработчик Minimal API может принимать параметры, значения которых инфраструктура получает из запроса, DI или текущего `{cs}HttpContext`.

> [!info] Определение  
> **Привязка параметров — parameter binding** — получение значений из соответствующих источников и подготовка аргументов для вызова обработчика, включая необходимые преобразования типов.

Это относится к обработчикам, переданным как `{cs}Delegate`. Для них инфраструктура создаёт `{cs}RequestDelegate`, который подготавливает аргументы и вызывает обработчик. При передаче готового `{cs}RequestDelegate` его сигнатура остаётся фиксированной: он принимает только `{cs}HttpContext`. 

---

### 6.1. Автоматическое определение источника

Для обычных параметров источник определяется по типу и имени:

|Параметр|Источник|
|---|---|
|Простой тип, имя которого присутствует в шаблоне маршрута|Значения маршрута|
|Простой тип, имя которого отсутствует в шаблоне|Query string|
|Зарегистрированный сервисный тип|DI|
|Обычный DTO без специального способа привязки|JSON-тело запроса|

К простым типам здесь относятся, например, `{cs}string`, числовые типы, `{cs}bool`, `{cs}Guid`, перечисления и другие типы с поддерживаемым преобразованием из строки.

Специальные типы, такие как `{cs}HttpContext`, обрабатываются отдельно. Заголовки автоматически по имени параметра не определяются. 

Например:

```cs
app.MapGet(
    "/products/{id}",
    (int id, int page) => $"Товар {id}, страница {page}");
```

Для запроса `{http}GET /products/42?page=3`:

|Аргумент|Значение|Источник|
|---|---|---|
|`id`|`42`|Маршрут|
|`page`|`3`|Query string|

Если одновременно передать `?id=100`, аргумент `{cs}int id` всё равно получит значение из маршрута: его имя присутствует в шаблоне. Источники не перебираются в поисках подходящего значения. 

---

### 6.2. Явное указание источника

Источник можно задать атрибутом из пространства имён `{cs}Microsoft.AspNetCore.Mvc`:

|Атрибут|Источник|
|---|---|
|`[FromRoute]`|Значения маршрута|
|`[FromQuery]`|Query string|
|`[FromHeader]`|Заголовки|
|`[FromBody]`|JSON-тело запроса|
|`[FromForm]`|Данные формы|
|`[FromServices]`|DI|

Явно указанный источник имеет преимущество перед автоматическим определением.

Для маршрута, query string, заголовков и полей формы свойство `{cs}Name` позволяет задать имя входного значения, отличающееся от имени параметра. 

```cs
using Microsoft.AspNetCore.Mvc;

app.MapGet(
    "/products/{id}",
    (
        [FromRoute] int id,
        [FromQuery(Name = "q")] string? search,
        [FromHeader(Name = "X-Request-Id")] string? requestId
    ) => $"Товар {id}; поиск: {search}; запрос: {requestId}");
```

Здесь `{cs}search` получает значение параметра `q`, а `{cs}requestId` — заголовка `X-Request-Id`.

---

### 6.3. Привязка JSON-тела

Для обычного DTO в обработчике `{cs}MapPost` источник тела определяется автоматически:

```cs
app.MapPost("/products", (CreateProductRequest request) =>
    $"Создание товара {request.Name}, цена {request.Price}");

public record CreateProductRequest(string Name, decimal Price);
```

При запросе с заголовком `{http}Content-Type: application/json` тело десериализуется в `{cs}CreateProductRequest`:

```
{
  "name": "Keyboard",
  "price": 4990
}
```

Источник можно указать явно:

```cs
app.MapPost(
    "/products",
    ([FromBody] CreateProductRequest request) => request.Name);
```

В Minimal API `{cs}[FromBody]` означает чтение JSON. Атрибуты на свойствах такого DTO не заставляют инфраструктуру собирать его части из query string или заголовков. 

Для JSON-тела используют **один параметр**, объединяющий необходимые поля. Несколько отдельных параметров, каждый из которых привязывается к JSON-телу, не поддерживаются. 

> [!note] Автоматическая привязка тела  
> Для `GET`, `HEAD`, `OPTIONS` и `DELETE` JSON-тело автоматически не определяется. Если оно необходимо, источник указывают через `{cs}[FromBody]` или читают тело самостоятельно.

---

### 6.4. Данные формы и файлы

Атрибут `{cs}[FromForm]` привязывает параметры к полям формы. Он применяется к данным с типом содержимого `application/x-www-form-urlencoded` или `multipart/form-data`.

Для файлов и формы целиком поддерживаются специальные типы:

|Тип|Получаемые данные|
|---|---|
|`IFormFile`|Один файл; имя поля определяется по имени параметра|
|`IFormFileCollection`|Коллекция файлов запроса|
|`IFormCollection`|Данные формы целиком|

Файлы передаются через `multipart/form-data`. Для этих специальных типов источник формы может определяться без атрибута. 

> [!note] Antiforgery  
> В современных версиях ASP.NET Core endpoints с привязкой данных формы по умолчанию требуют проверки antiforgery-токена. Для их использования учитывают настройку сервисов и middleware antiforgery. 

---

### 6.5. Зависимости из DI

Зависимость объявляют обычным параметром обработчика. Если сервисный тип зарегистрирован в контейнере, инфраструктура получает его из провайдера текущего запроса:

```cs
app.MapGet(
    "/products/{id:int}",
    async (
        int id,
        IProductService service,
        CancellationToken cancellationToken
    ) => await service.GetAsync(id, cancellationToken));
```

Здесь `{cs}IProductService` должен быть зарегистрирован в DI. Его время жизни определяется регистрацией.

Атрибут `{cs}[FromServices]` позволяет явно обозначить этот источник:

```cs
app.MapGet(
    "/products/{id:int}",
    ([FromServices] IProductService service, int id) =>
        service.GetAsync(id, CancellationToken.None));
```

Параметры из DI можно свободно сочетать с параметрами запроса. 

---

### 6.6. Специальные типы

Некоторые параметры инфраструктура передаёт непосредственно из текущего контекста:

|Тип параметра|Значение|
|---|---|
|`HttpContext`|Текущий контекст|
|`HttpRequest`|`context.Request`|
|`HttpResponse`|`context.Response`|
|`ClaimsPrincipal`|`context.User`|
|`CancellationToken`|`context.RequestAborted`|
|`Stream`|`context.Request.Body`|
|`PipeReader`|`context.Request.BodyReader`|

Для них не нужны атрибуты или регистрация в DI. Параметры `{cs}Stream` и `{cs}PipeReader` дают доступ к телу для самостоятельного чтения, без десериализации в DTO. 

```cs
app.MapGet("/whoami", (ClaimsPrincipal user) =>
    user.Identity?.Name ?? "Анонимный пользователь");
```

---

### 6.7. Обязательные и необязательные параметры

Параметры данных запроса без nullable-типа или значения по умолчанию обычно обязательны:

```cs
app.MapGet("/products", (int page) => $"Страница {page}");
```

Для `{http}GET /products?page=3` аргумент получает `3`. При отсутствии `page` привязка завершается ошибкой.

Допустить отсутствие значения можно двумя способами:

```cs
app.MapGet("/products", (int? page) =>
    $"Страница {page ?? 1}");
```

```cs
app.MapGet("/products", (int page = 1) =>
    $"Страница {page}");
```

В первом случае отсутствующее значение становится `null`, во втором используется значение по умолчанию. Это также применимо к другим поддерживаемым источникам данных. 

> [!warning] Отсутствие и некорректное значение  
> Необязательность допускает отсутствие параметра. Она не допускает произвольное значение: `?page=abc` не преобразуется в `{cs}int?` и не заменяется значением по умолчанию.

---

### 6.8. Несколько значений одного параметра

Повторяющиеся query-параметры можно получить как массив:

```cs
app.MapGet("/products", ([FromQuery] int[] ids) =>
    $"Идентификаторы: {string.Join(", ", ids)}");
```

Для `{http}GET /products?ids=1&ids=2&ids=3` обработчик получит массив `{cs}new[] { 1, 2, 3 }`. Значения преобразуются по отдельности. 

---

### 6.9. Объединение параметров: `[AsParameters]`

Если параметров много, их можно объединить в отдельный тип и применить `{cs}[AsParameters]` из пространства имён `{cs}Microsoft.AspNetCore.Http`.

Его члены привязываются как отдельные параметры обработчика:

```cs
app.MapGet(
    "/products/{id:int}",
    ([AsParameters] GetProductParameters parameters) =>
        $"Товар {parameters.Id}, язык: {parameters.Language}");

public record struct GetProductParameters(
    [FromRoute] int Id,
    [FromQuery] string? Language);
```

Здесь объект собирается из маршрута и query string. **Он не десериализуется целиком из JSON-тела.** Атрибут предназначен для объединения списка параметров и не выполняет произвольную рекурсивную привязку вложенных объектов. 

---

### 6.10. Ошибки привязки

При ошибке подготовки входных параметров обработчик не вызывается.

Типичные ответы:

|Причина|Статус|
|---|---|
|Отсутствует обязательный параметр данных запроса|`400 Bad Request`|
|Значение нельзя преобразовать в требуемый тип|`400 Bad Request`|
|JSON некорректен или несовместим с типом DTO|`400 Bad Request`|
|При привязке JSON-тела указан неподдерживаемый `Content-Type`|`415 Unsupported Media Type`|

Привязка подготавливает значения, но проверку бизнес-правил — например, допустимость цены или существование товара — выполняют отдельно. 

---

# 7. Возвращаемые значения обработчиков

Возвращаемое значение обработчика Minimal API определяет, **как инфраструктура сформирует HTTP-ответ**.

Основные варианты:

|Возвращаемый тип|Обработка|
|---|---|
|`string`|Запись текста в тело ответа|
|DTO, коллекция, число и другие обычные значения|Сериализация в JSON|
|`IResult` или его реализация|Выполнение результата|
|`Task<T>`, `ValueTask<T>`|Ожидание завершения, затем обработка значения `T`|
|`void`, `Task`, `ValueTask`|Дополнительное содержимое из возвращаемого значения не формируется|

Статус обычного ответа по умолчанию — `200 OK`, если он не был изменён при обработке запроса. 

---

### 7.1. Строка: текстовый ответ

Возвращённая строка записывается непосредственно в тело ответа:

```cs
app.MapGet("/hello", () => "Hello!");
```

Обычный результат:

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8

Hello!
```

Строка не сериализуется в JSON и не получает окружающие кавычки.

Если вернуть строку с HTML-разметкой, она всё равно будет отправлена как текст. Для HTML необходимо явно задать соответствующий тип содержимого. 

```cs
app.MapGet("/page", () =>
    Results.Text("<h1>Hello!</h1>", contentType: "text/html"));
```

Метод `{cs}Results.Text()` позволяет настроить тип содержимого, кодировку и статус текстового ответа. 

---

### 7.2. Обычное значение: JSON

DTO, анонимные объекты, коллекции и другие обычные значения сериализуются в JSON:

```cs
app.MapGet("/products/{id:int}", (int id) =>
    new ProductDto(id, "Keyboard", 4990));

public record ProductDto(int Id, string Name, decimal Price);
```

Для `{http}GET /products/42` тело ответа будет выглядеть так:

```http
{
  "id": 42,
  "name": "Keyboard",
  "price": 4990
}
```

Используется `{cs}System.Text.Json`, а тип содержимого — `application/json`. При стандартных настройках имена свойств записываются в camelCase. 

> [!note] Значение и HTTP-статус  
> Возврат числа `{cs}404` означает JSON-значение `404` в теле ответа. Для установки HTTP-статуса используют `{cs}Results.NotFound()` или `{cs}Results.StatusCode(404)`.

---

### 7.3. `IResult`: управление ответом

> [!info] Определение  
> `{cs}IResult` — интерфейс результата HTTP-обработчика, который определяет способ формирования ответа при выполнении.

Интерфейс содержит один метод:

```cs
public interface IResult
{
    Task ExecuteAsync(HttpContext httpContext);
}
```

После получения результата инфраструктура вызывает `{cs}ExecuteAsync()`, передавая текущий контекст. Реализация результата устанавливает необходимые статус, заголовки и тело ответа. 

Например:

```cs
app.MapGet("/products/{id:int}", (int id) =>
{
    if (id != 1)
    {
        return Results.NotFound();
    }

    return Results.Ok(new ProductDto(1, "Keyboard", 4990));
});
```

Обработчик возвращает один из двух результатов:

- `{cs}Results.NotFound()` — ответ `404`.
- `{cs}Results.Ok(product)` — ответ `200` с JSON-представлением товара.

**Создание результата ещё не записывает ответ:** запись происходит при его выполнении инфраструктурой (она сама вызывает `{cs}ExecuteAsync`).

---

### 7.4. `Results`: фабрика результатов

Статический класс `{cs}Results` находится в пространстве имён `{cs}Microsoft.AspNetCore.Http`. Его методы создают готовые результаты и возвращают их через `{cs}IResult`. 

Сигнатуры основных методов:

```cs
public static IResult Ok(object? value = null);

public static IResult Ok<TValue>(TValue? value);

public static IResult NotFound(object? value = null);

public static IResult NotFound<TValue>(TValue? value);

public static IResult NoContent();

public static IResult StatusCode(int statusCode);
```

У `{cs}Ok()` и `{cs}NotFound()` можно передать данные для JSON-тела либо вызвать их без данных. 

Часто используемые результаты:

|Вызов|Ответ|
|---|---|
|`Results.Ok(value)`|`200`, данные в JSON|
|`Results.Created(uri, value)`|`201`, заголовок `Location`, данные в JSON|
|`Results.Accepted(uri, value)`|`202`, адрес проверки состояния и данные, если указаны|
|`Results.NoContent()`|`204`, без тела|
|`Results.BadRequest(value)`|`400`, данные в JSON, если указаны|
|`Results.Unauthorized()`|`401`, без тела|
|`Results.Forbid()`|Запуск механизма запрета доступа настроенной схемы аутентификации|
|`Results.NotFound(value)`|`404`, данные в JSON, если указаны|
|`Results.Conflict(value)`|`409`, данные в JSON, если указаны|
|`Results.StatusCode(code)`|Указанный статус, без тела|
|`Results.Json(value)`|JSON с возможностью настройки сериализации, типа содержимого и статуса|
|`Results.Text(text)`|Текстовый ответ|
|`Results.File(...)`|Содержимое файла|
|`Results.Stream(...)`|Содержимое потока|
|`Results.Redirect(url)`|Перенаправление; по умолчанию `302`|
|`Results.Problem(...)`|Структурированный ответ об ошибке в формате Problem Details|

Методы создания результатов не выполняют соответствующую бизнес-операцию: например, `{cs}Results.Created()` формирует ответ о создании ресурса, но сам ресурс не создаёт. 

#### Строка внутри результата

Строка, переданная в `{cs}Results.Ok()`, сериализуется как JSON-значение:

|Возвращаемое значение|Тип содержимого|Тело|
|---|---|---|
|`"Hello!"`|`text/plain`|`Hello!`|
|`Results.Ok("Hello!")`|`application/json`|`"Hello!"`|
|`Results.Text("Hello!")`|`text/plain`|`Hello!`|

Формат здесь определяется выбранным результатом. 

---

### 7.5. `TypedResults`: конкретные типы результатов

Статический класс `{cs}TypedResults` предоставляет аналогичные методы, но **возвращает конкретные типы результатов**.

Например, сигнатуры `{cs}TypedResults.Ok()`:

```cs
public static Ok Ok();

public static Ok<TValue> Ok<TValue>(TValue? value);
```

Типы `{cs}Ok`, `{cs}Ok<TValue>`, `{cs}NotFound` и другие находятся в пространстве имён `{cs}Microsoft.AspNetCore.Http.HttpResults`. 

Сравнение:

|Вызов|Объявленный возвращаемый тип|
|---|---|
|`Results.Ok(product)`|`IResult`|
|`TypedResults.Ok(product)`|`Ok<ProductDto>`|
|`Results.NotFound()`|`IResult`|
|`TypedResults.NotFound()`|`NotFound`|

Оба варианта создают HTTP-результаты. Разница заключается в информации, доступной через возвращаемый C#-тип.

Конкретный тип позволяет обращаться к свойствам результата без приведения и передавать инфраструктуре метаданные ответа: например, статус и тип JSON-данных для описания endpoint в OpenAPI. 

```cs
app.MapGet("/product", () =>
    TypedResults.Ok(new ProductDto(1, "Keyboard", 4990)));
```

---

### 7.6. Несколько типов результата: `Results<T1, T2>`

Если обработчик возвращает разные типизированные результаты, их можно объединить через `{cs}Results<T1, T2>`:

```cs
using Microsoft.AspNetCore.Http.HttpResults;

app.MapGet(
    "/products/{id:int}",
    Results<Ok<ProductDto>, NotFound> (int id) =>
    {
        if (id != 1)
        {
            return TypedResults.NotFound();
        }

        return TypedResults.Ok(new ProductDto(1, "Keyboard", 4990));
    });
```

Возвращаемый тип означает: результатом может быть **либо** `{cs}Ok<ProductDto>`, **либо** `{cs}NotFound`.

Для перечисленных типов предусмотрены неявные преобразования в объединяющий результат. Возврат другого типа, например `{cs}BadRequest`, потребует добавить его в список допустимых вариантов.

Такой тип сохраняет метаданные всех объявленных результатов и позволяет компилятору проверять возвращаемые варианты. Предусмотрены также формы с большим количеством типов. 

Можно явно объявить возвращаемый тип `{cs}IResult` и использовать `{cs}TypedResults` внутри обработчика. Однако сведения о возможных вариантах тогда не выражены в его возвращаемом типе.

---

### 7.7. Асинхронные обработчики

Асинхронность не меняет правила формирования ответа: инфраструктура ожидает завершения `{cs}Task<T>` или `{cs}ValueTask<T>`, после чего обрабатывает полученное значение.

|Возвращаемый тип|После завершения|
|---|---|
|`Task<string>`|Запись текста|
|`Task<ProductDto>`|Сериализация DTO в JSON|
|`Task<IResult>`|Выполнение результата|
|`Task<Results<Ok<ProductDto>, NotFound>>`|Выполнение одного из объявленных результатов|

Для `{cs}ValueTask<T>` правила аналогичны. 

```cs
app.MapGet(
    "/products/{id:int}",
    async Task<Results<Ok<ProductDto>, NotFound>> (
        int id,
        IProductService service,
        CancellationToken ct
    ) =>
    {
        ProductDto? product = await service.GetAsync(id, ct);

        if (product is null)
            return TypedResults.NotFound();

        return TypedResults.Ok(product);
    });
```

Здесь сервис выполняет асинхронную операцию, а обработчик возвращает результат, соответствующий найденным данным.

---

### 7.8. Самостоятельная запись в `Response`

Обработчик может непосредственно сформировать ответ через `{cs}HttpResponse`:

```cs
app.MapGet("/hello", async (HttpContext context) =>
{
    context.Response.ContentType = "text/plain; charset=utf-8";

    await context.Response.WriteAsync("Hello!");
});
```

Такой обработчик возвращает `{cs}Task` без значения. Инфраструктура ожидает его завершения и не добавляет тело из возвращаемого результата.

Отсутствие возвращаемого значения **само по себе не устанавливает статус `204`**. Для ответа без содержимого с этим статусом можно вернуть `{cs}Results.NoContent()`. 

> [!warning] Повторное формирование ответа  
> После самостоятельной записи тела не следует возвращать результат, который тоже записывает ответ: он попытается изменить уже начатый ответ или добавить к нему содержимое.

---

# 8. Настройка и метаданные endpoint

После регистрации endpoint можно настроить через возвращённый builder:

```cs
app.MapGet("/products/{id:int}", (int id) =>
        TypedResults.Ok(new { Id = id }))
    .WithName("GetProduct")
    .WithDisplayName("Получение товара")
    .WithTags("Products");
```

Эти методы выполняются при настройке приложения. Они задают сведения о будущем endpoint, а обработчик вызывается уже при поступлении подходящего запроса.

---

### 8.1. Метаданные и builder

> [!info] Определение  
> **Метаданные endpoint** — связанные с ним объекты, описывающие дополнительные условия и характеристики обработки: допустимые HTTP-методы, требования авторизации, типы ответов и другие сведения.

Они находятся в `{cs}Endpoint.Metadata`, имеющем тип `{cs}EndpointMetadataCollection`. Это коллекция объектов разных типов, которые соответствующие компоненты инфраструктуры могут читать и использовать.

Например:

|Метаданные|Кто использует|
|---|---|
|Допустимые HTTP-методы|Маршрутизация|
|Требования авторизации|Middleware авторизации|
|Имя endpoint|Генерация ссылок, OpenAPI|
|Теги и описание|Средства формирования документации API|
|Собственные метаданные|Код приложения|

Для настройки используется `{cs}IEndpointConventionBuilder`. В частности, его реализует `{cs}RouteHandlerBuilder`, возвращаемый методами регистрации обработчиков Minimal API.

Большинство методов настройки являются методами расширения и возвращают тот же builder, позволяя продолжать цепочку вызовов. В обобщённых сигнатурах параметр `{cs}TBuilder` сохраняет конкретный тип builder. 

---

### 8.2. Имя и отображаемое имя

#### Имя endpoint: `WithName`

```cs
public static TBuilder WithName<TBuilder>(
    this TBuilder builder,
    string endpointName)
    where TBuilder : IEndpointConventionBuilder;
```

Имя позволяет обращаться к endpoint независимо от его шаблона пути, например при генерации ссылки. В OpenAPI оно также используется как идентификатор операции — `operationId`. 

```cs
app.MapGet("/products/{id:int}", (int id) => $"Товар {id}")
    .WithName("GetProduct");
```

Имя `GetProduct`:

- должно быть уникальным среди endpoints приложения;
- сравнивается с учётом регистра;
- не меняет путь `/products/{id:int}`. 

#### Отображаемое имя: `WithDisplayName`

```cs
public static TBuilder WithDisplayName<TBuilder>(
    this TBuilder builder,
    string displayName)
    where TBuilder : IEndpointConventionBuilder;

public static TBuilder WithDisplayName<TBuilder>(
    this TBuilder builder,
    Func<EndpointBuilder, string> func)
    where TBuilder : IEndpointConventionBuilder;
```

Метод устанавливает `{cs}Endpoint.DisplayName` — имя для диагностики и журналирования. Перегрузка с делегатом позволяет вычислить его по данным builder при построении endpoint. 

```cs
app.MapGet("/products/{id:int}", (int id) => $"Товар {id}")
    .WithDisplayName("Получение товара по идентификатору");
```

|Настройка|Назначение|
|---|---|
|`WithName`|Идентификатор для обращения к endpoint|
|`WithDisplayName`|Отображаемое имя для диагностики|

Отображаемое имя хранится в отдельном свойстве endpoint, а имя для генерации ссылок — в его метаданных.

---

### 8.3. Теги и описание

Эти настройки используются при формировании документации API:

|Метод|Назначение|
|---|---|
|`WithTags`|Категории, по которым операции группируются в документации|
|`WithSummary`|Краткое описание операции|
|`WithDescription`|Подробное описание операции|

Сигнатуры:

```cs
public static RouteHandlerBuilder WithTags(
    this RouteHandlerBuilder builder,
    params string[] tags);

public static TBuilder WithTags<TBuilder>(
    this TBuilder builder,
    params string[] tags)
    where TBuilder : IEndpointConventionBuilder;

public static TBuilder WithSummary<TBuilder>(
    this TBuilder builder,
    string summary)
    where TBuilder : IEndpointConventionBuilder;

public static TBuilder WithDescription<TBuilder>(
    this TBuilder builder,
    string description)
    where TBuilder : IEndpointConventionBuilder;
```

Методы добавляют соответствующие объекты в метаданные endpoint. 

```cs
app.MapGet("/products/{id:int}", (int id) =>
        TypedResults.Ok(new { Id = id }))
    .WithTags("Products", "Catalog")
    .WithSummary("Получить товар")
    .WithDescription("Возвращает товар по его идентификатору.");
```

Добавление этих сведений само по себе не публикует документацию: её формирование требует настроенного механизма OpenAPI.

---

### 8.4. Требования авторизации

Основные способы настройки:

```cs
public static TBuilder RequireAuthorization<TBuilder>(
    this TBuilder builder)
    where TBuilder : IEndpointConventionBuilder;

public static TBuilder RequireAuthorization<TBuilder>(
    this TBuilder builder,
    params string[] policyNames)
    where TBuilder : IEndpointConventionBuilder;

public static TBuilder AllowAnonymous<TBuilder>(
    this TBuilder builder)
    where TBuilder : IEndpointConventionBuilder;
```

|Вызов|Назначение|
|---|---|
|`RequireAuthorization()`|Применить политику авторизации по умолчанию|
|`RequireAuthorization("PolicyName")`|Применить указанную именованную политику|
|`AllowAnonymous()`|Разрешить доступ без проверки требований авторизации|

У `{cs}RequireAuthorization()` также есть перегрузки для передачи `{cs}IAuthorizeData`, готовой `{cs}AuthorizationPolicy` и делегата настройки `{cs}AuthorizationPolicyBuilder`. 

```cs
app.MapGet("/profile", () => "Профиль")
    .RequireAuthorization();

app.MapDelete("/products/{id:int}", (int id) => Results.NoContent())
    .RequireAuthorization("ManageProducts");

app.MapGet("/health", () => "OK")
    .AllowAnonymous();
```

Политика `{cs}"ManageProducts"` должна быть зарегистрирована в приложении.

Методы добавляют требования в метаданные. **Проверку при запросе выполняет middleware авторизации**, использующий выбранный endpoint.

Настройка без аргументов означает политику по умолчанию, которая обычно требует аутентифицированного пользователя. Политику можно изменить, поэтому это не жёстко заданная проверка `{cs}IsAuthenticated`.

Метаданные `{cs}AllowAnonymous()` позволяют пропустить проверки авторизации endpoint, включая default и fallback policy. 

---

### 8.5. Описание возможных ответов: `Produces`

Метод `{cs}Produces()` добавляет сведения о статусе, типе данных и типе содержимого возможного ответа:

```cs
public static RouteHandlerBuilder Produces<TResponse>(
    this RouteHandlerBuilder builder,
    int statusCode = 200,
    string? contentType = null,
    params string[] additionalContentTypes);

public static RouteHandlerBuilder Produces(
    this RouteHandlerBuilder builder,
    int statusCode,
    Type? responseType = null,
    string? contentType = null,
    params string[] additionalContentTypes);
```

При указании типа данных без явного типа содержимого используется `application/json`. 

```cs
app.MapGet("/products/{id:int}", (int id) =>
    {
        if (id != 1)
        {
            return Results.NotFound();
        }

        return Results.Ok(new ProductDto(1, "Keyboard", 4990));
    })
    .Produces<ProductDto>(StatusCodes.Status200OK)
    .Produces(StatusCodes.Status404NotFound);

public record ProductDto(int Id, string Name, decimal Price);
```

Здесь описаны два возможных ответа:

- `200` с JSON-представлением `{cs}ProductDto`;
- `404` без данных.

> [!warning] Описание ответа  
> `{cs}Produces()` добавляет метаданные для документации. Он не устанавливает статус, не сериализует данные и не проверяет соответствие фактического ответа описанию.

Сведения об ответе могут определяться автоматически по возвращаемому типу обработчика. Например, `{cs}Ok<ProductDto>` и `{cs}Results<Ok<ProductDto>, NotFound>` передают метаданные соответствующих результатов. Поэтому при использовании типизированных результатов ручное описание часто не требуется. 

---

### 8.6. Собственные метаданные: `WithMetadata`

К endpoint можно прикрепить собственные объекты:

```cs
public static TBuilder WithMetadata<TBuilder>(
    this TBuilder builder,
    params object[] items)
    where TBuilder : IEndpointConventionBuilder;
```

Метод добавляет переданные объекты в коллекцию метаданных. Можно передать сразу несколько объектов; наследоваться от специального базового класса не требуется. 

```cs
app.MapGet("/report", () => "Отчёт")
    .WithMetadata(new AuditMetadata("ReadReport"));

public sealed record AuditMetadata(string Action);
```

Объект `{cs}AuditMetadata` содержит сведения, которые может использовать код приложения.

**Само добавление объекта не запускает аудит.** Необходим компонент, который прочитает эти метаданные и выполнит соответствующую работу.

Метаданные описывают endpoint и доступны при разных запросах к нему. Данные конкретного запроса следует хранить в контексте этого запроса.

---

### 8.7. Чтение метаданных

Во время обработки запроса выбранный endpoint получают через `{cs}context.GetEndpoint()`, затем обращаются к `{cs}endpoint.Metadata`.

Основные методы коллекции:

```cs
public T? GetMetadata<T>()
    where T : class;

public IReadOnlyList<T> GetOrderedMetadata<T>()
    where T : class;
```

|Метод|Результат|
|---|---|
|`GetMetadata<T>()`|Последний подходящий объект типа `T` или `null`|
|`GetOrderedMetadata<T>()`|Все подходящие объекты типа `T` в порядке возрастания приоритета|

Поиск учитывает совместимость типов: можно запрашивать и класс, и интерфейс, который реализует объект метаданных. 

Например, middleware после маршрутизации может прочитать сведения об аудите:

```cs
app.UseRouting();

app.Use(async (context, next) =>
{
    var audit = context.GetEndpoint()?
        .Metadata.GetMetadata<AuditMetadata>();

    if (audit is not null)
    {
        Console.WriteLine($"Аудит: {audit.Action}");
    }

    await next(context);
});
```

Для запроса к endpoint с `{cs}AuditMetadata` этот middleware выполнит дополнительную работу перед передачей управления дальше.

Способ использования нескольких объектов зависит от потребителя метаданных: один компонент может выбирать последний объект, другой — учитывать все найденные. Поэтому добавление новых метаданных не означает универсальное правило «всё предыдущее заменяется».

---

# 9. Группировка: `MapGroup`

> [!info] Определение  
> **Группа маршрутов** — объединение endpoints с общим префиксом пути и общими настройками.

Метод `{cs}MapGroup()` позволяет один раз задать префикс и настройки, а затем регистрировать endpoints внутри группы.

---

### 9.1. Сигнатуры и `RouteGroupBuilder`

`{cs}MapGroup()` — метод расширения для `{cs}IEndpointRouteBuilder`:

```cs
public static RouteGroupBuilder MapGroup(
    this IEndpointRouteBuilder endpoints,
    string prefix);

public static RouteGroupBuilder MapGroup(
    this IEndpointRouteBuilder endpoints,
    RoutePattern prefix);
```

Первая перегрузка принимает строковый шаблон префикса, вторая — объект `{cs}RoutePattern`. Обе возвращают `{cs}RouteGroupBuilder`. 

```cs
public sealed class RouteGroupBuilder :
    IEndpointRouteBuilder,
    IEndpointConventionBuilder;
```

Реализация двух интерфейсов позволяет:

|Интерфейс|Возможность|
|---|---|
|`IEndpointRouteBuilder`|Регистрировать endpoints и вложенные группы|
|`IEndpointConventionBuilder`|Задавать общие настройки endpoints группы|

Поэтому у группы доступны и методы регистрации вроде `{cs}MapGet()`, и методы настройки вроде `{cs}RequireAuthorization()`. 

---

### 9.2. Общий префикс

```cs
var products = app.MapGroup("/products");

products.MapGet("", () => "Список товаров");

products.MapGet("/{id:int}", (int id) => $"Товар {id}");

products.MapPost("", () => "Создание товара");
```

Шаблон каждого endpoint объединяется с префиксом группы:

|Регистрация внутри группы|Итоговый маршрут|
|---|---|
|`MapGet("")`|`GET /products`|
|`MapGet("/{id:int}")`|`GET /products/{id:int}`|
|`MapPost("")`|`POST /products`|

> [!note] Регистрация группы  
> Вызов `{cs}MapGroup("/products")` сам по себе не создаёт обработчик для `/products`. Для этого внутри группы нужно зарегистрировать endpoint, например через `{cs}MapGet("")`.

---

### 9.3. Общие настройки

Настройки, заданные на группе, применяются ко всем её endpoints, включая endpoints вложенных групп:

```cs
var products = app.MapGroup("/products")
    .WithTags("Products")
    .RequireAuthorization();

products.MapGet("", () => "Список товаров");

products.MapGet("/{id:int}", (int id) => $"Товар {id}");

products.MapPost("", () => "Создание товара");
```

Все три endpoint получают тег `Products` и требования политики авторизации по умолчанию. Для проверки доступа в приложении должен быть настроен механизм авторизации. 

На группе можно задавать, например:

|Метод|Общая настройка|
|---|---|
|`WithTags(...)`|Теги|
|`RequireAuthorization(...)`|Требования авторизации|
|`AllowAnonymous()`|Разрешение анонимного доступа|
|`WithMetadata(...)`|Собственные метаданные|
|`WithSummary(...)`|Краткое описание|
|`WithDescription(...)`|Подробное описание|
|`WithOrder(...)`|Приоритет маршрутов|

Принадлежность к группе определяется **регистрацией через её builder**. Один лишь общий префикс пути не связывает отдельно зарегистрированный endpoint с настройками группы.

Настройки можно задавать и после регистрации дочерних endpoints, пока приложение ещё настраивается: они будут применены при построении endpoints. 

#### Настройки отдельного endpoint

Каждый endpoint можно дополнительно настроить:

```cs
products.MapGet("/featured", () => "Популярные товары")
    .AllowAnonymous();

products.MapDelete("/{id:int}", (int id) => Results.NoContent())
    .RequireAuthorization("ManageProducts");
```

В первом случае `{cs}AllowAnonymous()` позволяет пропустить проверки авторизации для конкретного endpoint.

Во втором требования именованной политики добавляются к требованиям, полученным от группы. Дополнительный вызов `{cs}RequireAuthorization()` не отменяет групповые требования. 

В целом настройки применяются от внешней группы к внутренней, затем к конкретному endpoint. Но способ обработки метаданных зависит от их потребителя: некоторые учитываются совместно, для других выбирается наиболее приоритетное значение. 

---

### 9.4. Вложенные группы и параметры префикса

Группы можно вкладывать друг в друга:

```cs
var api = app.MapGroup("/api");

var products = api.MapGroup("/products")
    .WithTags("Products");

products.MapGet("/{id:int}", (int id) => $"Товар {id}");
```

Итоговый шаблон — `/api/products/{id:int}`. Префиксы всех уровней объединяются, а настройки внешних групп распространяются на дочерние endpoints. 

Префикс также может содержать параметры и ограничения:

```cs
var users = app.MapGroup("/users/{userId:int}");

var orders = users.MapGroup("/orders");

orders.MapGet(
    "/{orderId:int}",
    (int userId, int orderId) =>
        $"Заказ {orderId} пользователя {userId}");
```

Для `{http}GET /users/3/orders/7` обработчик получит:

|Аргумент|Значение|
|---|---|
|`userId`|`3`|
|`orderId`|`7`|

Параметры из префиксов доступны обработчику по тем же правилам привязки, что и параметры собственного шаблона endpoint. 

---

### 9.5. Группа без префикса

Пустой префикс позволяет объединить endpoints общими настройками, сохранив их пути:

```cs
var diagnostics = app.MapGroup("")
    .WithTags("Diagnostics");

diagnostics.MapGet("/health", () => "OK");

diagnostics.MapGet("/version", () => "1.0");
```

Пути останутся `/health` и `/version`, а оба endpoint получат тег `Diagnostics`. 

---

# 10. Генерация ссылок: `LinkGenerator`

> [!info] Определение  
> **Генерация ссылок** — построение пути или полного URL к endpoint на основе его маршрута и переданных значений параметров.

Например, для маршрута `/products/{id:int}` и значения `id = 42` можно получить `/products/42`.

Для этого используется `{cs}LinkGenerator` — сервис маршрутизации, доступный через DI. Его можно использовать в обработчиках, middleware и обычных сервисах, в том числе вне обработки HTTP-запроса. 

---

### 10.1. Генерация по имени endpoint

Чтобы обращаться к endpoint по имени, его задают через `{cs}WithName()`:

```cs
app.MapGet("/products/{id:int}", (int id) =>
    $"Товар {id}")
    .WithName("GetProduct");
```

Теперь для построения ссылки достаточно указать `"GetProduct"` и значения параметров. Сам шаблон пути в месте генерации ссылки повторять не требуется.

**Имя должно быть уникальным в приложении; регистр символов учитывается.** Если изменить маршрут, сохранив имя и параметры, ссылки будут строиться уже по новому шаблону. 

Получение сервиса и генерация пути в обработчике:

```cs
app.MapGet("/product-link/{id:int}",
    (int id, LinkGenerator links) =>
    {
        string? path = links.GetPathByName(
            endpointName: "GetProduct",
            values: new { id });

        return path is null
            ? Results.Problem("Не удалось построить ссылку.")
            : Results.Ok(new { path });
    });
```

Для `{http}GET /product-link/42` ответ будет содержать:

```
{
  "path": "/products/42"
}
```

### 10.2. `GetPathByName`: построение пути

`{cs}GetPathByName()` возвращает путь без схемы и адреса сервера. В результат также могут входить query string и фрагмент.

Основные перегрузки с передачей значений через объект — без контекста запроса и с ним: 

```cs
public static string? GetPathByName(
    this LinkGenerator generator,
    string endpointName,
    object? values,
    PathString pathBase = default,
    FragmentString fragment = default,
    LinkOptions? options = default);

public static string? GetPathByName(
    this LinkGenerator generator,
    HttpContext httpContext,
    string endpointName,
    object? values,
    PathString? pathBase = default,
    FragmentString fragment = default,
    LinkOptions? options = default);
```

|Параметр|Назначение|
|---|---|
|`endpointName`|Имя endpoint|
|`values`|Значения для построения маршрута|
|`pathBase`|Префикс, добавляемый перед сформированным путём|
|`fragment`|Фрагмент ссылки, например `#details`|
|`options`|Настройки генерации: например, завершающий `/` или нижний регистр|

Для обеих форм существуют перегрузки с `{cs}RouteValueDictionary? values = default` вместо `{cs}object? values`. Они позволяют передавать значения словарём:

```cs
var values = new RouteValueDictionary
{
    ["id"] = 42
};

string? path = links.GetPathByName("GetProduct", values);
// /products/42
```

Если маршрут не требует параметров, можно передать `{cs}null`:

```cs
string? path = links.GetPathByName("GetProducts", values: null);
```

---

### 10.3. Значения параметров и результат генерации

Имена свойств переданного объекта соответствуют именам параметров маршрута:

```cs
string? path = links.GetPathByName(
    "GetProduct",
    new { id = 42 });

// /products/42
```

**Значения, которые не используются параметрами маршрута, добавляются в query string.** Например: 

```cs
string? path = links.GetPathByName(
    "GetProduct",
    new { id = 42, mode = "full" });

// /products/42?mode=full
```

Фрагмент передают отдельно:

```cs
string? path = links.GetPathByName(
    "GetProduct",
    new { id = 42 },
    fragment: new FragmentString("#details"));

// /products/42#details
```

При построении учитываются обязательные и необязательные параметры, значения по умолчанию и ограничения маршрута.

Метод возвращает `{cs}null`, если подходящую ссылку построить не удалось. Для маршрута `/products/{id:int}`: 

|Вызов|Результат|
|---|---|
|`GetPathByName("GetProduct", new { id = 42 })`|`/products/42`|
|`GetPathByName("GetProduct", values: null)`|`null`: отсутствует обязательный `id`|
|`GetPathByName("GetProduct", new { id = "abc" })`|`null`: не выполнено ограничение `int`|
|`GetPathByName("UnknownEndpoint", new { id = 42 })`|`null`: endpoint с таким именем не найден|

---

### 10.4. Использование текущего `HttpContext`

Перегрузка с `{cs}HttpContext` по умолчанию учитывает `{cs}context.Request.PathBase`:

```cs
string? path = links.GetPathByName(
    context,
    "GetProduct",
    new { id = 42 });
```

Если `{cs}context.Request.PathBase` равен `/shop`, получится `/shop/products/42`.

Чтобы явно задать префикс или убрать его, используют параметр `{cs}pathBase`:

```cs
string? path = links.GetPathByName(
    context,
    "GetProduct",
    new { id = 42 },
    pathBase: PathString.Empty);

// /products/42
```

Без `{cs}HttpContext` префикс берётся только из явно переданного `{cs}pathBase`. 

> [!note] Параметры маршрута передаются явно  
> `{cs}GetPathByName()` не подставляет автоматически значения из `{cs}context.Request.RouteValues`. Даже при передаче контекста нужные параметры следует указать в `{cs}values`.

### 10.5. `GetUriByName`: построение полного URL

`{cs}GetUriByName()` добавляет к пути схему и адрес сервера:

```
https://example.com/products/42
```

Основные перегрузки с передачей значений через объект: 

```cs
public static string? GetUriByName(
    this LinkGenerator generator,
    string endpointName,
    object? values,
    string scheme,
    HostString host,
    PathString pathBase = default,
    FragmentString fragment = default,
    LinkOptions? options = default);

public static string? GetUriByName(
    this LinkGenerator generator,
    HttpContext httpContext,
    string endpointName,
    object? values,
    string? scheme = default,
    HostString? host = default,
    PathString? pathBase = default,
    FragmentString fragment = default,
    LinkOptions? options = default);
```

Также существуют соответствующие перегрузки с `{cs}RouteValueDictionary`. В форме с контекстом словарь необязателен: `{cs}RouteValueDictionary? values = default`; без контекста параметр имеет тип `{cs}RouteValueDictionary` и передаётся явно.

#### С текущим запросом

Если схема, адрес сервера и базовый путь не указаны, используются свойства запроса:

|Параметр|Источник|
|---|---|
|`scheme`|`context.Request.Scheme`|
|`host`|`context.Request.Host`|
|`pathBase`|`context.Request.PathBase`|

```cs
string? url = links.GetUriByName(
    context,
    "GetProduct",
    new { id = 42 });
```

При схеме `https`, адресе `example.com` и пустом базовом пути результат — `https://example.com/products/42`.

Любое из этих значений можно переопределить аргументом метода.

#### Без текущего запроса

Схему и адрес сервера требуется указать явно:

```cs
string? url = links.GetUriByName(
    "GetProduct",
    new { id = 42 },
    scheme: "https",
    host: new HostString("example.com"));

// https://example.com/products/42
```

Так можно строить ссылки, например, для писем или фоновых задач. Для публичных ссылок адрес сервера обычно берут из конфигурации приложения; при использовании адреса текущего запроса следует учитывать, что он поступает через заголовок `Host`.

### 10.6. Генерация ссылки в HTTP-результате

Некоторые результаты сами используют генерацию ссылок. Например, `{cs}Results.CreatedAtRoute()` позволяет сформировать ответ `201 Created` со ссылкой на созданный ресурс в заголовке `Location`.

После создания товара обработчик может вернуть:

```cs
return Results.CreatedAtRoute(
    routeName: "GetProduct",
    routeValues: new { id = product.Id },
    value: product);
```

Здесь:

- `"GetProduct"` — имя, заданное через `{cs}WithName()`.
- `{cs}routeValues` — значения для построения ссылки.
- `{cs}value` — объект для тела ответа.

Для товара с идентификатором `42` заголовок `Location` будет указывать на `/products/42`. Сам `{cs}CreatedAtRoute()` ресурс не создаёт: он формирует результат ответа после выполнения этой работы приложением.
