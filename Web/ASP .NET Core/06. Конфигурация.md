# 1. Модель конфигурации в ASP.NET Core

> [!info] Определение
> **Конфигурация приложения** — система доступа к настройкам, которая объединяет данные из разных источников и предоставляет их через общую модель ключей, значений и секций. Код приложения обращается к настройке по ключу независимо от того, получена она из файла, переменной окружения или другого источника. 

### 1.1. Назначение конфигурации

Конфигурация позволяет задавать параметры работы приложения отдельно от его исполняемого кода: адреса внешних сервисов, строки подключения, таймауты, ограничения и переключатели функций.

Источники читаются через **configuration providers**. Каждый provider предоставляет значения, а общая конфигурация объединяет их и определяет итоговое значение ключа.

Основные абстракции находятся в пространстве имён `{cs}Microsoft.Extensions.Configuration`:

| Тип | Роль |
|---|---|
| `IConfiguration` | Общий контракт доступа к значениям и секциям |
| `IConfigurationRoot` | Корень конфигурации с доступом к providers |
| `IConfigurationSection` | Секция внутри общей конфигурации |
| `IConfigurationBuilder` | Настройка источников и построение конфигурации |
| `ConfigurationManager` | Реализация, совмещающая настройку источников и доступ к текущей конфигурации |

На уровне `{cs}IConfiguration` значения представлены как `{cs}string?`. Преобразование в числа, enum или классы настроек выполняется дополнительными механизмами. 

### 1.2. `IConfiguration`

Основной контракт:

```cs
public interface IConfiguration
{
    string? this[string key] { get; set; }

    IConfigurationSection GetSection(string key);

    IEnumerable<IConfigurationSection> GetChildren();

    IChangeToken GetReloadToken();
}
```

| Член | Назначение |
|---|---|
| Индексатор | Получить или установить значение по ключу |
| `GetSection()` | Получить представление указанной секции |
| `GetChildren()` | Перечислить непосредственные дочерние секции |
| `GetReloadToken()` | Получить токен для наблюдения за обновлением конфигурации |

`{cs}IChangeToken` находится в пространстве имён `{cs}Microsoft.Extensions.Primitives`.

Для обычного потребителя настроек достаточно `{cs}IConfiguration`: ему не требуется знать, какие providers загрузили данные. Этот контракт реализуют и корень, и секции. 

### 1.3. Корень и секции

#### `IConfigurationRoot`

```cs
public interface IConfigurationRoot : IConfiguration
{
    IEnumerable<IConfigurationProvider> Providers { get; }

    void Reload();
}
```

Корень представляет общую конфигурацию. Помимо возможностей `{cs}IConfiguration`, он предоставляет:

- `{cs}Providers` — providers, участвующие в формировании конфигурации
- `{cs}Reload()` — принудительное повторное чтение значений из providers

Этот интерфейс нужен для управления конфигурацией и диагностики её источников. 

#### `IConfigurationSection`

```cs
public interface IConfigurationSection : IConfiguration
{
    string Key { get; }

    string Path { get; }

    string? Value { get; set; }
}
```

Секция представляет определённый участок общей конфигурации:

- `{cs}Key` — имя секции внутри родителя
- `{cs}Path` — полный путь от корня
- `{cs}Value` — собственное значение секции

Поскольку секция тоже реализует `{cs}IConfiguration`, через неё можно читать дочерние значения и получать вложенные секции.

Например, для секции с путём `ExternalApi:BaseUrl` её `{cs}Key` будет `"BaseUrl"`, а `{cs}Path` — `"ExternalApi:BaseUrl"`. 

### 1.4. `ConfigurationManager`

`{cs}ConfigurationManager` совмещает две роли:

- `{cs}IConfigurationBuilder` — подключение и настройка источников
- `{cs}IConfigurationRoot` — доступ к загруженным значениям и providers

При добавлении источника manager создаёт и загружает соответствующий provider, после чего его данные участвуют в чтении конфигурации.

У обычного `{cs}ConfigurationBuilder` источники сначала настраиваются, а конфигурация создаётся вызовом метода интерфейса `{cs}IConfigurationBuilder`:

```cs
IConfigurationRoot Build();
```

У `{cs}ConfigurationManager` текущая конфигурация доступна уже во время настройки. Его реализация `{cs}IConfigurationBuilder.Build()` возвращает сам manager. 

### 1.5. Конфигурация builder, приложения и DI

Свойства имеют разные объявленные типы:

```cs
// WebApplicationBuilder
public ConfigurationManager Configuration { get; }

// WebApplication
public IConfiguration Configuration { get; }
```

До построения приложения `{cs}builder.Configuration` позволяет подключать источники и читать настройки для регистрации сервисов. После построения `{cs}app.Configuration` предоставляет доступ к конфигурации работающего приложения. 

ASP.NET Core автоматически регистрирует конфигурацию в DI как `{cs}IConfiguration`. Её можно получить через конструктор сервиса, контроллера или параметр обработчика Minimal API:

```cs
var builder = WebApplication.CreateBuilder(args);

var nameAtStartup = builder.Configuration["Application:Name"];

var app = builder.Build();

app.MapGet("/application-name", (IConfiguration configuration) =>
{
    return Results.Ok(new
    {
        name = configuration["Application:Name"]
    });
});

app.Run();
```

В примере настройка читается при запуске и во время обработки запроса. В стандартной модели `{cs}WebApplicationBuilder` эти способы доступа используют общую конфигурацию приложения. 

### 1.6. Конфигурация приложения и host

Эти понятия различаются назначением:

| Конфигурация | Что определяет |
|---|---|
| Host configuration | Параметры инициализации host: имя приложения, окружение, content root |
| App configuration | Настройки приложения и подключаемых подсистем |

В стандартной модели `{cs}WebApplication.CreateBuilder()` host configuration используется также как источник значений по умолчанию для app configuration. Если ключ присутствует в обеих, значение app configuration имеет приоритет.

При этом некоторые параметры host фиксируются **на раннем этапе создания builder**: например, имя окружения и content root. Изменение соответствующего ключа позднее не переинициализирует host и не переключает уже выбранное окружение.

# 2. Ключи, значения и секции

### 2.1. Иерархические ключи

Конфигурация представляет вложенные настройки через **пути ключей**. Разделитель уровней — `:`.

#### Пример `appsettings.json`

```json
{
  "ExternalApi": {
    "BaseUrl": "https://api.example.com",
    "TimeoutSeconds": 30,
    "Endpoints": [
      "products",
      "orders"
    ]
  },
  "ConnectionStrings": {
    "Main": "Host=localhost;Database=catalog;Username=app"
  },
  "EmptyValue": ""
}
```

Для чтения отдельных значений используются следующие ключи:

|Ключ|Значение|
|---|---|
|`ExternalApi:BaseUrl`|`"https://api.example.com"`|
|`ExternalApi:TimeoutSeconds`|`"30"`|
|`ExternalApi:Endpoints:0`|`"products"`|
|`ExternalApi:Endpoints:1`|`"orders"`|
|`ConnectionStrings:Main`|`"Host=localhost;Database=catalog;Username=app"`|
|`EmptyValue`|`""`|

Вложенный объект задаёт общий префикс ключей, а индекс элемента массива становится дополнительным сегментом пути. Стандартные провайдеры сравнивают ключи без учёта регистра: `ExternalApi:BaseUrl` и `externalapi:baseurl` обозначают одну настройку. 

### 2.2. Чтение значения через индексатор

Индексатор — член интерфейса `{cs}IConfiguration`:

```cs
string? this[string key] { get; set; }
```

Параметр `{cs}key` задаёт путь настройки относительно текущего объекта конфигурации. Чтение возвращает строковое значение либо `{cs}null`, если значение отсутствует.

В примерах используется конфигурация из [[06. Конфигурация#Пример appsettings json|предыдущего]] JSON без переопределений другими источниками:

```cs
var builder = WebApplication.CreateBuilder(args);

IConfiguration configuration = builder.Configuration;

string? baseUrl = configuration["ExternalApi:BaseUrl"];
// "https://api.example.com"

string? timeout = configuration["ExternalApi:TimeoutSeconds"];
// "30"

string? missing = configuration["ExternalApi:ApiKey"];
// null
```

Число из JSON читается как строка `"30"`. Индексатор не преобразует значение в `{cs}int` и не собирает вложенные настройки в объект .NET. JSON-провайдер преобразует отдельные скалярные значения в строки при загрузке. 

Чтение ключа группы не возвращает её содержимое:

```cs
string? api = configuration["ExternalApi"];
// null
```

У `ExternalApi` есть дочерние настройки, но в этом примере нет собственного строкового значения.

### 2.3. Получение секции: `GetSection`

> [!info] Определение  
> **Секция конфигурации** — представление конфигурации относительно определённого пути. Она позволяет читать собственное значение и обращаться к дочерним настройкам.

Метод интерфейса `{cs}IConfiguration`:

```cs
IConfigurationSection GetSection(string key);
```

- `{cs}key` — относительный путь секции, который может содержать несколько уровней
- Возвращаемое значение — `{cs}IConfigurationSection`, представляющий указанный путь

[[06. Конфигурация#Пример appsettings json|примерчик]]
```cs
IConfigurationSection api =
    configuration.GetSection("ExternalApi");

string? baseUrl = api["BaseUrl"];
string? firstEndpoint = api["Endpoints:0"];
```

Обращения относительно секции эквивалентны обращениям по полному пути:

```cs
api["BaseUrl"];
configuration["ExternalApi:BaseUrl"];

api.GetSection("Endpoints");
configuration.GetSection("ExternalApi:Endpoints");
```

Секция использует ту же конфигурацию и добавляет свой путь к относительным ключам. Её получение не создаёт копию настроек. 

Свойства секции:

```cs
string Key { get; }
string Path { get; }
string? Value { get; set; }
```

|Секция|`Key`|`Path`|`Value`|
|---|---|---|---|
|`ExternalApi`|`"ExternalApi"`|`"ExternalApi"`|`null`|
|`ExternalApi:BaseUrl`|`"BaseUrl"`|`"ExternalApi:BaseUrl"`|`"https://api.example.com"`|
|`ExternalApi:Endpoints:0`|`"0"`|`"ExternalApi:Endpoints:0"`|`"products"`|

Таким образом, секцией может быть и группа настроек, и отдельное значение.

**`{cs}GetSection()` никогда не возвращает `{cs}null`**, даже если указанный путь отсутствует:

[[06. Конфигурация#Пример appsettings json|примерчик]]
```cs
var missing = configuration.GetSection("Missing");

Console.WriteLine(missing.Path);          // Missing
Console.WriteLine(missing.Value is null); // True
```

Проверка `{cs}missing is null` не определяет наличие настройки.

### 2.4. Проверка наличия: `Exists` и `GetRequiredSection`

Оба метода — расширения из `{cs}ConfigurationExtensions`, пространство имён `{cs}Microsoft.Extensions.Configuration`.

#### `Exists`

```cs
public static bool Exists(
    this IConfigurationSection? section);
```

Возвращает `{cs}true`, если секция имеет собственное значение, отличное от `{cs}null`, **или хотя бы одну дочернюю секцию**:

[[06. Конфигурация#Пример appsettings json|примерчик]]
```cs
configuration.GetSection("ExternalApi").Exists();
// true: есть дочерние секции

configuration.GetSection("ExternalApi:BaseUrl").Exists();
// true: есть собственное значение

configuration.GetSection("Missing").Exists();
// false

configuration.GetSection("EmptyValue").Exists();
// true: пустая строка отличается от null
```

Для аргумента `{cs}null` метод возвращает `{cs}false`.

#### `GetRequiredSection`

```cs
public static IConfigurationSection GetRequiredSection(
    this IConfiguration configuration,
    string key);
```

Получает секцию по `{cs}key` и проверяет её через `{cs}Exists()`. Если проверка возвращает `{cs}false`, выбрасывает `{cs}InvalidOperationException`:

[[06. Конфигурация#Пример appsettings json|примерчик]]
```cs
var api = configuration.GetRequiredSection("ExternalApi");
// Секция существует — возвращается IConfigurationSection

var missing = configuration.GetRequiredSection("Missing");
// InvalidOperationException
```

Метод проверяет наличие секции, но не обязательность её отдельных настроек и не корректность значений. 

> [!warning] Наличие не означает валидность  
> `{cs}GetRequiredSection("ExternalApi")` может успешно выполниться, даже если внутри отсутствует `BaseUrl`. Пустая строка также удовлетворяет проверке `{cs}Exists()`.

### 2.5. Перебор дочерних секций: `GetChildren`

Метод интерфейса `{cs}IConfiguration`:

```cs
IEnumerable<IConfigurationSection> GetChildren();
```

Возвращает **непосредственные дочерние секции** текущего уровня. Вложенные уровни автоматически не обходятся.

[[06. Конфигурация#Пример appsettings json|примерчик]]
```cs
var api = configuration.GetSection("ExternalApi");

foreach (IConfigurationSection child in api.GetChildren())
{
    Console.WriteLine($"{child.Path}: {child.Value}");
}
```

В перечисление попадут:

|`Key`|`Path`|`Value`|
|---|---|---|
|`BaseUrl`|`ExternalApi:BaseUrl`|`"https://api.example.com"`|
|`Endpoints`|`ExternalApi:Endpoints`|`null`|
|`TimeoutSeconds`|`ExternalApi:TimeoutSeconds`|`"30"`|

Элементы массива находятся на следующем уровне:

```cs
var endpoints = api.GetSection("Endpoints");

foreach (IConfigurationSection endpoint in endpoints.GetChildren())
{
    Console.WriteLine($"{endpoint.Key}: {endpoint.Value}");
}

// 0: products
// 1: orders
```

Здесь возвращаются секции с ключами `"0"` и `"1"`, а не готовый массив .NET. Для отсутствующей секции `{cs}GetChildren()` возвращает пустое перечисление. 

### 2.6. Чтение строки подключения: `GetConnectionString`

Метод расширения из `{cs}ConfigurationExtensions`:

```cs
public static string? GetConnectionString(
    this IConfiguration configuration,
    string name);
```

Параметр `{cs}name` — имя настройки внутри секции `ConnectionStrings`:

```cs
string? connectionString =
    configuration.GetConnectionString("Main");
```

Вызов эквивалентен:

```cs
configuration.GetSection("ConnectionStrings")["Main"];
```

При обращении к корневой конфигурации это также:

```cs
configuration["ConnectionStrings:Main"];
```

Если значение отсутствует, возвращается `{cs}null`. Метод только читает строку: он не открывает подключение и не проверяет её формат.

# 3. Источники и приоритеты настроек

### 3.1. Configuration providers

> [!info] Определение  
> **Configuration provider** — компонент, который загружает настройки из определённого источника и предоставляет их конфигурации как пары «ключ — значение».

JSON-файл, переменные окружения и аргументы командной строки имеют разные форматы. Провайдеры приводят их к общей модели, доступной через `{cs}IConfiguration`.

При подключении источника участвуют два объекта:

|Контракт|Назначение|
|---|---|
|`IConfigurationSource`|Хранит параметры подключения источника и создаёт провайдер|
|`IConfigurationProvider`|Загружает данные и предоставляет значения ключей|

Например, `{cs}JsonConfigurationSource` хранит путь к файлу и параметры загрузки, а `{cs}JsonConfigurationProvider` читает JSON.

У источника есть метод создания провайдера:

```cs
IConfigurationProvider Build(IConfigurationBuilder builder);
```

При построении конфигурации источники создают свои провайдеры. Корневая конфигурация использует их для чтения настроек. 

### 3.2. Стандартные источники ASP.NET Core

При обычном вызове:

```cs
var builder = WebApplication.CreateBuilder(args);
```

основные источники конфигурации приложения подключаются автоматически.

**Порядок от меньшего приоритета к большему:**

| Источник                         | Назначение                                                                |
| -------------------------------- | ------------------------------------------------------------------------- |
| `appsettings.json`               | Общие настройки приложения                                                |
| `appsettings.{Environment}.json` | Настройки конкретного окружения (`Development`, `Staging`, `Production` ) |
| User Secrets                     | Локальные настройки разработки, подключаемые в `Development`              |
| Переменные окружения             | Настройки процесса и среды запуска                                        |
| Аргументы командной строки       | Настройки, переданные при запуске                                         |

Например, в окружении `Production` используется `appsettings.Production.json`.

Конфигурация хоста также может предоставлять значения как источник с меньшим приоритетом. Приведённый порядок относится к стандартной конфигурации приложения и может измениться после подключения дополнительных источников. 

### 3.3. Правило приоритета

**Если один ключ присутствует в нескольких провайдерах, используется значение из провайдера, добавленного последним.**

При чтении корневая конфигурация проверяет провайдеры в обратном порядке и возвращает первое найденное значение:

```cs
bool TryGet(string key, out string? value);
```

Результат `{cs}TryGet()` показывает, содержит ли провайдер указанный ключ.

Провайдер с большим приоритетом влияет только на ключи, которые он предоставляет. Если ключа в нём нет, поиск продолжается в предыдущих провайдерах. 

Приоритет определяется **порядком подключения**, а не видом источника. JSON-файл, добавленный после аргументов командной строки, сможет переопределить их значения.

### 3.4. Переопределение отдельных ключей

`appsettings.json`:

```cs
{
  "ExternalApi": {
    "BaseUrl": "https://api.example.com",
    "TimeoutSeconds": 30
  }
}
```

`appsettings.Production.json`:

```cs
{
  "ExternalApi": {
    "TimeoutSeconds": 10
  }
}
```

Итоговая конфигурация:

|Ключ|Значение|Источник|
|---|---|---|
|`ExternalApi:BaseUrl`|`"https://api.example.com"`|`appsettings.json`|
|`ExternalApi:TimeoutSeconds`|`"10"`|`appsettings.Production.json`|

Если переменная окружения `ExternalApi__TimeoutSeconds` содержит `20`, итоговым значением станет `"20"`.

Если приложение запускается с аргументом:

```sh
dotnet run -- --ExternalApi:TimeoutSeconds=5
```

итоговым значением станет `"5"`.

> [!info] Объединение происходит по ключам  
> Более поздний источник не заменяет секцию целиком. Он переопределяет только совпадающие ключи, поэтому итоговая секция может содержать настройки из нескольких источников.

Это правило применяется и к массивам, поскольку их элементы представлены ключами с индексами. Например, переопределение `Endpoints:0` не удаляет `Endpoints:1`, полученный из предыдущего источника.

### 3.5. User Secrets

User Secrets хранит локальные настройки вне каталога проекта. Проект связывается с хранилищем через идентификатор `{cs}UserSecretsId`.

Инициализация и запись настройки:

```sh
dotnet user-secrets init
dotnet user-secrets set "ExternalApi:ApiKey" "development-key"
```

После загрузки значение читается обычным способом:

```cs
string? apiKey = builder.Configuration["ExternalApi:ApiKey"];
```

При стандартной настройке `{cs}WebApplication.CreateBuilder()` User Secrets подключается в окружении `Development`, если у приложения задан соответствующий идентификатор. Хранилище предназначено для разработки и не шифрует значения. 

### 3.6. Просмотр провайдеров

Загруженные провайдеры доступны через `{cs}IConfigurationRoot.Providers`:

```cs
IConfigurationRoot root = builder.Configuration;

foreach (IConfigurationProvider provider in root.Providers)
{
    Console.WriteLine(provider);
}
```

Провайдеры перечисляются в порядке подключения: более поздние имеют больший приоритет.

# 4. Подключение и настройка источников

### 4.1. `IConfigurationBuilder` и `Sources`

Контракт `{cs}IConfigurationBuilder`:

```cs
public interface IConfigurationBuilder
{
    IDictionary<string, object> Properties { get; }

    IList<IConfigurationSource> Sources { get; }

    IConfigurationBuilder Add(IConfigurationSource source);

    IConfigurationRoot Build();
}
```

|Член|Назначение|
|---|---|
|`Properties`|Служебные данные построителя, например параметры доступа к файлам|
|`Sources`|Упорядоченная коллекция подключённых источников|
|`Add()`|Добавляет источник в конец коллекции|
|`Build()`|Строит корневую конфигурацию|

`{cs}Sources` содержит описания источников, а `{cs}IConfigurationRoot.Providers` — провайдеры, работающие с данными. 

В ASP.NET Core `{cs}builder.Configuration` имеет тип `{cs}ConfigurationManager`, поэтому позволяет одновременно добавлять источники и читать настройки:

```cs
builder.Configuration.AddJsonFile(
    "external-api.json",
    optional: false,
    reloadOnChange: true);

string? baseUrl =
    builder.Configuration["ExternalApi:BaseUrl"];
```

Дополнительный вызов `{cs}Build()` для этой конфигурации не требуется.

Добавление источника сохраняет уже подключённые источники. Чтобы полностью задать собственный набор, коллекцию можно очистить:

```cs
builder.Configuration.Sources.Clear();
```

После очистки настройки из прежних источников больше не участвуют в чтении конфигурации.

### 4.2. `AddJsonFile`

Методы расширения из `{cs}JsonConfigurationExtensions`, пространство имён `{cs}Microsoft.Extensions.Configuration`.

Основные перегрузки:

```cs
public static IConfigurationBuilder AddJsonFile(
    this IConfigurationBuilder builder,
    string path);

public static IConfigurationBuilder AddJsonFile(
    this IConfigurationBuilder builder,
    string path,
    bool optional);

public static IConfigurationBuilder AddJsonFile(
    this IConfigurationBuilder builder,
    string path,
    bool optional,
    bool reloadOnChange);
```

Дополнительные формы:

```cs
public static IConfigurationBuilder AddJsonFile(
    this IConfigurationBuilder builder,
    IFileProvider? provider,
    string path,
    bool optional,
    bool reloadOnChange);

public static IConfigurationBuilder AddJsonFile(
    this IConfigurationBuilder builder,
    Action<JsonConfigurationSource>? configureSource);
```

|Параметр|Значение|
|---|---|
|`path`|Путь к JSON-файлу|
|`optional`|Допускается ли отсутствие файла|
|`reloadOnChange`|Нужно ли отслеживать изменения файла и перезагружать данные|
|`provider`|Способ доступа к файлу через `IFileProvider`|
|`configureSource`|Настройка объекта `JsonConfigurationSource`|

Для относительного пути используется базовый путь файловой конфигурации. В стандартном ASP.NET Core приложении он связан с content root.

Короткие перегрузки не включают отслеживание изменений:

```cs
configurationBuilder.AddJsonFile("settings.json");
// optional: false, reloadOnChange: false

configurationBuilder.AddJsonFile("settings.json", optional: true);
// reloadOnChange: false
```

Это отличается от стандартного подключения `appsettings.json` хостом, где отслеживание изменений обычно включено. 

Пример явной настройки:

```cs
builder.Configuration.AddJsonFile(
    "external-api.json",
    optional: true,
    reloadOnChange: true);
```

- `{cs}optional: true` позволяет запустить приложение без файла
- `{cs}reloadOnChange: true` включает перезагрузку данных при изменении файла

`{cs}optional` не означает игнорирование любых ошибок: существующий файл с некорректным JSON по умолчанию вызывает ошибку загрузки. 

### 4.3. `AddEnvironmentVariables`

Методы расширения из `{cs}EnvironmentVariablesExtensions`:

```cs
public static IConfigurationBuilder AddEnvironmentVariables(
    this IConfigurationBuilder configurationBuilder);

public static IConfigurationBuilder AddEnvironmentVariables(
    this IConfigurationBuilder configurationBuilder,
    string? prefix);
```

Без префикса провайдер читает переменные окружения процесса:

```cs
builder.Configuration.AddEnvironmentVariables();
```

С префиксом он отбирает только подходящие имена и удаляет префикс из итогового ключа:

```cs
builder.Configuration.AddEnvironmentVariables(prefix: "MYAPP_");
```

|Переменная окружения|Ключ конфигурации|
|---|---|
|`MYAPP_ExternalApi__BaseUrl`|`ExternalApi:BaseUrl`|
|`MYAPP_ExternalApi__TimeoutSeconds`|`ExternalApi:TimeoutSeconds`|
|`OTHER_ExternalApi__TimeoutSeconds`|Не загружается этим провайдером|

Разделитель `__` преобразуется в `:`. Одиночный `_` остаётся частью имени.

Например:

```cs
export MYAPP_ExternalApi__TimeoutSeconds=15
```

```cs
string? timeout =
    builder.Configuration["ExternalApi:TimeoutSeconds"];
// "15"
```

Сам префикс не становится отдельной секцией. 

### 4.4. `AddCommandLine`

Методы расширения из `{cs}CommandLineConfigurationExtensions`:

```cs
public static IConfigurationBuilder AddCommandLine(
    this IConfigurationBuilder configurationBuilder,
    string[] args);

public static IConfigurationBuilder AddCommandLine(
    this IConfigurationBuilder configurationBuilder,
    string[] args,
    IDictionary<string, string>? switchMappings);
```

- `{cs}args` — аргументы приложения
- `{cs}switchMappings` — соответствия между аргументами и ключами конфигурации

Прямое указание ключа:

```sh
dotnet run -- --ExternalApi:TimeoutSeconds=15
```

Поддерживается также отдельное значение:

```sh
dotnet run -- --ExternalApi:TimeoutSeconds 15
```

Короткий аргумент можно сопоставить с полным ключом:

```cs
var mappings = new Dictionary<string, string>
{
    ["-t"] = "ExternalApi:TimeoutSeconds",
    ["--api-timeout"] = "ExternalApi:TimeoutSeconds"
};

builder.Configuration.AddCommandLine(args, mappings);
```

```sh
dotnet run -- -t 15
```

После загрузки:

```cs
string? timeout =
    builder.Configuration["ExternalApi:TimeoutSeconds"];
// "15"
```

Аргументы с одним дефисом требуют соответствующего сопоставления. `{cs}AddCommandLine()` не превращает аргумент без значения в логический флаг автоматически. 

### 4.5. `AddInMemoryCollection`

Методы расширения из `{cs}MemoryConfigurationBuilderExtensions`:

```cs
public static IConfigurationBuilder AddInMemoryCollection(
    this IConfigurationBuilder configurationBuilder);

public static IConfigurationBuilder AddInMemoryCollection(
    this IConfigurationBuilder configurationBuilder,
    IEnumerable<KeyValuePair<string, string?>>? initialData);
```

Первая перегрузка добавляет пустой провайдер, вторая — провайдер с начальными данными.

```cs
builder.Configuration.AddInMemoryCollection(
    new Dictionary<string, string?>
    {
        ["ExternalApi:BaseUrl"] = "https://test.example.com",
        ["ExternalApi:TimeoutSeconds"] = "5"
    });
```

Значения задаются строками, а вложенность — путями ключей. Такой источник удобен для настроек, формируемых кодом, и для тестовых конфигураций. 

### 4.6. Собственный порядок источников

```cs
var builder = WebApplication.CreateBuilder(args);

builder.Configuration.Sources.Clear();

builder.Configuration
    .AddJsonFile(
        "appsettings.json",
        optional: false,
        reloadOnChange: true)
    .AddJsonFile(
        $"appsettings.{builder.Environment.EnvironmentName}.json",
        optional: true,
        reloadOnChange: true)
    .AddEnvironmentVariables(prefix: "MYAPP_")
    .AddCommandLine(args);
```

В этом наборе аргументы командной строки имеют наибольший приоритет. User Secrets не подключается, поскольку стандартные источники были удалены.

Все рассмотренные методы возвращают `{cs}IConfigurationBuilder`, позволяя последовательно добавлять источники в одной цепочке. 

# 5. Привязка конфигурации к .NET-типам

### 5.1. `ConfigurationBinder`

> [!info] Определение  
> **Привязка конфигурации** — преобразование значений и секций конфигурации в значения, объекты и коллекции .NET.

Методы `{cs}ConfigurationBinder` — расширения для `{cs}IConfiguration` из пространства имён `{cs}Microsoft.Extensions.Configuration`.

|Метод|Назначение|
|---|---|
|`GetValue<T>()`|Читает одно значение и преобразует его в `T`|
|`Get<T>()`|Получает новое значение или создаёт и заполняет объект `T`|
|`Bind()`|Заполняет переданный существующий объект|

### 5.2. `GetValue<T>`

Основные перегрузки:

```cs
public static T? GetValue<T>(
    this IConfiguration configuration,
    string key);

public static T? GetValue<T>(
    this IConfiguration configuration,
    string key,
    T defaultValue);
```

- `{cs}key` — путь отдельного значения
- `{cs}defaultValue` — результат, если строковое значение отсутствует
- Возвращаемое значение — результат преобразования в `{cs}T`

```cs
int timeout = configuration.GetValue<int>(
    "ExternalApi:TimeoutSeconds");

int attempts = configuration.GetValue<int>(
    "ExternalApi:MaxAttempts",
    defaultValue: 3);
```

Если `MaxAttempts` отсутствует, второй вызов возвращает `{cs}3`. Без явно заданного значения используется `{cs}default(T)`:

```cs
int missing = configuration.GetValue<int>("Missing");
// 0

int? nullableMissing = configuration.GetValue<int?>("Missing");
// null
```

Обозначение `{cs}T?` в обобщённой сигнатуре не превращает результат `{cs}GetValue<int>()` в `{cs}int?`.

Метод читает собственное значение секции. Он не собирает объект из дочерних ключей. 

> [!warning] Значение по умолчанию не исправляет ошибку преобразования  
> Если `TimeoutSeconds` содержит `"abc"`, `{cs}GetValue<int>()` выбрасывает `{cs}InvalidOperationException`. Аргумент `{cs}defaultValue` применяется при отсутствии значения, а не при невозможности его преобразовать.

Для типа, известного во время выполнения, существуют перегрузки с параметром `{cs}Type`:

```cs
public static object? GetValue(
    this IConfiguration configuration,
    Type type,
    string key);

public static object? GetValue(
    this IConfiguration configuration,
    Type type,
    string key,
    object? defaultValue);
```

### 5.3. `Get<T>`

Основные перегрузки:

```cs
public static T? Get<T>(
    this IConfiguration configuration);

public static T? Get<T>(
    this IConfiguration configuration,
    Action<BinderOptions>? configureOptions);
```

Метод рекурсивно сопоставляет ключи конфигурации со свойствами объекта.

Например:

```json
{
  "ExternalApi": {
    "BaseUrl": "https://api.example.com",
    "TimeoutSeconds": 15,
    "Retry": {
      "MaxAttempts": 3,
      "Delay": "00:00:02"
    },
    "Endpoints": [
      "products",
      "orders"
    ],
    "Headers": {
      "X-Client": "catalog"
    }
  }
}
```

Классы настроек:

```cs
public sealed class ExternalApiOptions
{
    public const string SectionName = "ExternalApi";

    public string BaseUrl { get; set; } = "";

    public int TimeoutSeconds { get; set; } = 30;

    public RetryOptions Retry { get; set; } = new();

    public string[] Endpoints { get; set; } = [];

    public Dictionary<string, string> Headers { get; set; } = new();
}

public sealed class RetryOptions
{
    public int MaxAttempts { get; set; } = 3;

    public TimeSpan Delay { get; set; } = TimeSpan.FromSeconds(1);
}
```

Привязка:

```cs
ExternalApiOptions? options = configuration
    .GetSection(ExternalApiOptions.SectionName)
    .Get<ExternalApiOptions>();
```

В полученном объекте:

```cs
options!.TimeoutSeconds;       // 15
options.Retry.MaxAttempts;     // 3
options.Retry.Delay;           // 00:00:02
options.Endpoints[0];          // "products"
options.Headers["X-Client"];   // "catalog"
```

Если для отсутствующей секции объект создать не из чего, `{cs}Get<ExternalApiOptions>()` возвращает `{cs}null`. Ошибки преобразования при этом не заменяются результатом `{cs}null`. 

Существуют также перегрузки:

```cs
public static object? Get(
    this IConfiguration configuration,
    Type type);

public static object? Get(
    this IConfiguration configuration,
    Type type,
    Action<BinderOptions>? configureOptions);
```

### 5.4. `Bind`

Основные перегрузки:

```cs
public static void Bind(
    this IConfiguration configuration,
    object? instance);

public static void Bind(
    this IConfiguration configuration,
    object? instance,
    Action<BinderOptions>? configureOptions);

public static void Bind(
    this IConfiguration configuration,
    string key,
    object? instance);
```

- `{cs}instance` — существующий объект для заполнения
- `{cs}configureOptions` — настройка поведения binder
- `{cs}key` — путь секции в перегрузке с явным ключом

```cs
var options = new ExternalApiOptions
{
    TimeoutSeconds = 60
};

configuration
    .GetSection("ExternalApi")
    .Bind(options);
```

Эквивалентная короткая форма:

```cs
configuration.Bind("ExternalApi", options);
```

`{cs}Bind()` возвращает `{cs}void` и изменяет переданный объект. Если отдельная настройка отсутствует, существующее значение свойства сохраняется. Например, при отсутствии `TimeoutSeconds` останется `{cs}60`. 

### 5.5. Свойства, вложенные объекты и коллекции

Для обычных классов настроек используются публичные свойства с `{cs}get` и `{cs}set`. Поля не участвуют в стандартном сопоставлении.

Имена ключей сопоставляются с именами свойств без учёта регистра. Вложенная секция привязывается к вложенному объекту.

Для создания простого объекта подходит публичный конструктор без параметров. `{cs}Get<T>()` также поддерживает определённые случаи привязки через единственный публичный параметризованный конструктор, параметры которого соответствуют свойствам. Это не означает автоматического создания произвольного типа.

Для коллекций:

- Числовые дочерние ключи используются при привязке массивов и списков
- Имена дочерних ключей используются как ключи словаря
- Пропуски в числовых ключах не создают автоматически пустые позиции массива
- Привязка в существующие коллекции может добавлять элементы к уже имеющимся

Например, ключи `Endpoints:0` и `Endpoints:2` со значениями `"products"` и `"orders"` могут дать массив из двух последовательных элементов.

Повторный `{cs}Bind()` в объект с заполненным списком нельзя считать операцией полной замены всех настроек: элементы могут накопиться. 

### 5.6. Отсутствующие значения, `null` и ошибки

|Ситуация|Поведение|
|---|---|
|Значение отсутствует при `GetValue<T>()`|Возвращается значение по умолчанию|
|Свойство отсутствует при привязке объекта|Сохраняется его начальное или существующее значение|
|Вся секция отсутствует при `Get<T>()` для обычного класса|Обычно возвращается `null`|
|Вся секция отсутствует при `Bind()`|Переданный объект остаётся без новых настроек|
|Строка не преобразуется в тип скалярного свойства|Возникает ошибка преобразования|
|Ключ не соответствует свойству|По умолчанию игнорируется|

Для поддерживаемых типов binder использует преобразование строк, в том числе для `{cs}int`, `{cs}bool`, `{cs}TimeSpan` и перечислений. Успешное преобразование не проверяет смысл значения: отрицательный тайм-аут может корректно преобразоваться в `{cs}int`.

> [!info] Поведение `null` зависит от версии  
> Начиная с .NET 10 JSON-провайдер сохраняет явные значения `null`, а привязка поддерживает их для свойств и элементов массивов. Пустые JSON-массивы также привязываются как пустые массивы. Для non-nullable value type явный `null` приводит к `{cs}default(T)`. 

Аннотация `{cs}string` вместо `{cs}string?` сама по себе не является проверкой значения во время выполнения.

При этом `{cs}GetValue<T>()` использует значение по умолчанию и для собственного значения секции, равного `{cs}null`.

### 5.7. `BinderOptions`

Основные свойства:

```cs
public bool BindNonPublicProperties { get; set; }

public bool ErrorOnUnknownConfiguration { get; set; }
```

Оба по умолчанию равны `{cs}false`.

|Свойство|Назначение|
|---|---|
|`BindNonPublicProperties`|Разрешает обычному binder обращаться к непубличным свойствам и setter|
|`ErrorOnUnknownConfiguration`|Включает ошибки для неизвестных ключей и дополнительных проблем привязки|

```cs
ExternalApiOptions? options = configuration
    .GetSection("ExternalApi")
    .Get<ExternalApiOptions>(binder =>
    {
        binder.ErrorOnUnknownConfiguration = true;
    });
```

Так можно обнаружить опечатку в ключе, например `TimeotSeconds`. 

Некорректные элементы коллекций при стандартном поведении могут быть пропущены. Начиная с .NET 8 `{cs}ErrorOnUnknownConfiguration = true` также требует сообщать об ошибках преобразования таких элементов.

Значение `{cs}false` не означает, что binder никогда не выбрасывает исключений: ошибка обычного скалярного свойства всё равно может прервать привязку. 

# 6. Options pattern и регистрация настроек

### 6.1. Назначение Options pattern

> [!info] Определение  
> **Options pattern** — механизм создания, настройки, проверки и предоставления типизированных настроек через DI.

Класс настроек объединяет параметры конкретного компонента. Сервис получает его через специализированный контракт, например `{cs}IOptions<ExternalApiOptions>`.

|Непосредственное чтение конфигурации|Options pattern|
|---|---|
|Сервис знает пути ключей|Сервис работает со свойствами класса|
|Преобразование выполняется при чтении|Привязка регистрируется отдельно|
|Момент чтения определяет сам сервис|Создание и кеширование задаются Options|
|Проверки нужно вызывать отдельно|Валидация включается в создание Options|

Сам `{cs}Get<T>()` также создаёт типизированный объект, но не подключает его автоматически к механизму Options, DI и уведомлениям об изменениях.

### 6.2. Требования к классу настроек

Для стандартной фабрики Options используется неабстрактный класс с публичным конструктором без параметров.

Класс `{cs}ExternalApiOptions` из предыдущего пункта подходит: у него есть неявный публичный конструктор без параметров и свойства для привязки.

```cs
public sealed class ExternalApiOptions
{
    public const string SectionName = "ExternalApi";

    public string BaseUrl { get; set; } = "";

    public int TimeoutSeconds { get; set; } = 30;

    public RetryOptions Retry { get; set; } = new();

    public string[] Endpoints { get; set; } = [];

    public Dictionary<string, string> Headers { get; set; } = new();
}
```

Возможности создания объектов через `{cs}ConfigurationBinder.Get<T>()` и через стандартную фабрику Options различаются: фабрика сначала создаёт пустой объект, а затем применяет к нему правила настройки.

### 6.3. `Configure<TOptions>`

Методы расширения для `{cs}IServiceCollection`, пространство имён `{cs}Microsoft.Extensions.DependencyInjection`.

Настройка через делегат:

```cs
public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    Action<TOptions> configureOptions)
    where TOptions : class;

public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    string? name,
    Action<TOptions> configureOptions)
    where TOptions : class;
```

```cs
builder.Services.Configure<ExternalApiOptions>(options =>
{
    options.BaseUrl = "https://api.example.com";
    options.TimeoutSeconds = 15;
});
```

Привязка к конфигурации:

```cs
public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    IConfiguration config)
    where TOptions : class;

public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    IConfiguration config,
    Action<BinderOptions>? configureBinder)
    where TOptions : class;

public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    string? name,
    IConfiguration config)
    where TOptions : class;

public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    string? name,
    IConfiguration config,
    Action<BinderOptions>? configureBinder)
    where TOptions : class;
```

```cs
builder.Services.Configure<ExternalApiOptions>(
    builder.Configuration.GetSection(
        ExternalApiOptions.SectionName));
```

Параметр `{cs}config` может представлять корневую конфигурацию или отдельную секцию. `{cs}configureBinder` задаёт параметры привязки, а `{cs}name` — имя набора Options.

Перегрузки с конфигурацией регистрируют привязку и источник уведомлений об изменениях. 

### 6.4. `AddOptions<TOptions>` и `OptionsBuilder<TOptions>`

Основные перегрузки:

```cs
public static IServiceCollection AddOptions(
    this IServiceCollection services);

public static OptionsBuilder<TOptions> AddOptions<TOptions>(
    this IServiceCollection services)
    where TOptions : class;

public static OptionsBuilder<TOptions> AddOptions<TOptions>(
    this IServiceCollection services,
    string? name)
    where TOptions : class;
```

Необобщённый метод подключает инфраструктуру Options. Обобщённые методы дополнительно возвращают построитель для определённого типа и имени.

У `{cs}OptionsBuilder<TOptions>` есть свойства:

```cs
public IServiceCollection Services { get; }

public string Name { get; }
```

И метод настройки через делегат:

```cs
public virtual OptionsBuilder<TOptions> Configure(
    Action<TOptions> configureOptions);
```

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .Configure(options =>
    {
        options.TimeoutSeconds = 15;
    });
```

Построитель объединяет регистрацию привязки, дополнительных правил и валидации в цепочку. Он не является объектом настроек.

Вызовы `{cs}Configure<TOptions>()` сами подключают необходимую инфраструктуру, поэтому отдельный `{cs}AddOptions()` перед ними обычно не требуется.

### 6.5. `Bind` и `BindConfiguration`

Это методы расширения для `{cs}OptionsBuilder<TOptions>`:

```cs
public static OptionsBuilder<TOptions> Bind<TOptions>(
    this OptionsBuilder<TOptions> optionsBuilder,
    IConfiguration config)
    where TOptions : class;

public static OptionsBuilder<TOptions> Bind<TOptions>(
    this OptionsBuilder<TOptions> optionsBuilder,
    IConfiguration config,
    Action<BinderOptions>? configureBinder)
    where TOptions : class;

public static OptionsBuilder<TOptions> BindConfiguration<TOptions>(
    this OptionsBuilder<TOptions> optionsBuilder,
    string configSectionPath,
    Action<BinderOptions>? configureBinder = null)
    where TOptions : class;
```

`{cs}Bind()` получает конкретный объект конфигурации:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .Bind(builder.Configuration.GetSection("ExternalApi"));
```

`{cs}BindConfiguration()` получает путь секции, а `{cs}IConfiguration` разрешает через DI:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .BindConfiguration("ExternalApi");
```

Пустой путь `{cs}""` означает привязку к корневой конфигурации.

Оба метода регистрируют привязку и поддержку уведомлений об изменениях. Они не требуют наличия секции автоматически: без настроек объект может сохранить значения из инициализаторов. 

> [!info] Два разных `Bind`  
> `{cs}configuration.Bind(instance)` выполняет привязку сразу.
> 
> `{cs}optionsBuilder.Bind(configuration)` регистрирует правило, которое будет выполнено при создании объекта Options.

### 6.6. Момент создания объекта

Регистрация:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .BindConfiguration("ExternalApi")
    .Configure(options =>
    {
        options.TimeoutSeconds += 5;
    });
```

не создаёт готовый `{cs}ExternalApiOptions` немедленно.

При запросе настроек стандартная фабрика:

1. Создаёт объект
2. Выполняет подходящие правила `{cs}Configure`
3. Выполняет правила `{cs}PostConfigure`
4. Запускает зарегистрированную валидацию

Созданный объект затем кешируется соответствующим механизмом Options. Правила выполняются при каждом новом создании объекта, а не при каждом обращении к уже кешированному значению. 

### 6.7. Получение настроек в сервисе

```cs
using Microsoft.Extensions.Options;

public sealed class ExternalApiClient
{
    private readonly ExternalApiOptions _options;

    public ExternalApiClient(
        IOptions<ExternalApiOptions> options)
    {
        _options = options.Value;
    }

    public string GetBaseUrl()
    {
        return _options.BaseUrl;
    }
}
```

```cs
builder.Services.AddScoped<ExternalApiClient>();
```

Options-регистрация предоставляет `{cs}IOptions<ExternalApiOptions>` и другие стандартные обёртки. Она не регистрирует сам `{cs}ExternalApiOptions` для непосредственного внедрения.

# 7. `IOptions<T>`, `IOptionsSnapshot<T>` и `IOptionsMonitor<T>`

### 7.1. Контракты

Все три интерфейса находятся в пространстве имён `{cs}Microsoft.Extensions.Options`.

```cs
public interface IOptions<out TOptions>
    where TOptions : class
{
    TOptions Value { get; }
}

public interface IOptionsSnapshot<out TOptions>
    : IOptions<TOptions>
    where TOptions : class
{
    TOptions Get(string? name);
}

public interface IOptionsMonitor<out TOptions>
    where TOptions : class
{
    TOptions CurrentValue { get; }

    TOptions Get(string? name);

    IDisposable? OnChange(
        Action<TOptions, string?> listener);
}
```

|Член|Назначение|
|---|---|
|`Value`|Объект с именем по умолчанию|
|`CurrentValue`|Текущий объект с именем по умолчанию|
|`Get(name)`|Объект с указанным именем|
|`OnChange(listener)`|Подписка на уведомления об обновлении|

`{cs}IOptionsSnapshot<T>` наследует `{cs}Value` от `{cs}IOptions<T>`. У `{cs}IOptionsMonitor<T>` вместо него используется `{cs}CurrentValue`. 

### 7.2. Время жизни и кеширование

Для стандартных реализаций:

|Контракт|Время жизни в DI|Кеширование|Обновление|
|---|---|---|---|
|`IOptions<T>`|Singleton|Один объект с именем по умолчанию|Уже созданный объект автоматически не обновляется|
|`IOptionsSnapshot<T>`|Scoped|Отдельный объект для каждого имени внутри scope|Новый scope может получить новые настройки|
|`IOptionsMonitor<T>`|Singleton|Отдельный объект для каждого имени|Уведомление сбрасывает соответствующий кеш и приводит к пересозданию|

Эти времена жизни регистрируются инфраструктурой Options. 

### 7.3. `IOptions<T>`

Объект создаётся при первом обращении к `{cs}Value` и сохраняется для последующих обращений:

```cs
ExternalApiOptions first = options.Value;
ExternalApiOptions second = options.Value;

bool same = ReferenceEquals(first, second);
// true
```

Это не обязательно настройки, прочитанные в момент запуска. Если первое обращение произошло позже, объект создаётся из доступных на тот момент данных.

После создания автоматическая перезагрузка конфигурации не заменяет этот объект. 

`{cs}IOptions<T>` подходит сервисам, которым достаточно одного набора настроек без получения последующих обновлений.

### 7.4. `IOptionsSnapshot<T>`

В каждом scope используется собственный кеш. Объект для конкретного имени создаётся при первом обращении к `{cs}Value` или `{cs}Get(name)`:

```cs
ExternalApiOptions first = snapshot.Value;
ExternalApiOptions second = snapshot.Value;

bool same = ReferenceEquals(first, second);
// true внутри одного scope
```

В обычном ASP.NET Core приложении scope связан с HTTP-запросом. Поэтому уже полученные настройки остаются стабильными в пределах запроса, а следующий запрос может получить обновлённые значения. 

> [!info] Snapshot создаётся лениво  
> Объект настроек фиксируется при первом обращении к нему внутри scope. Создание scope само по себе не читает все возможные наборы Options.

Разные имена также создаются лениво и кешируются отдельно.

### 7.5. `IOptionsMonitor<T>`

Monitor предоставляет текущий объект:

```cs
ExternalApiOptions current = monitor.CurrentValue;
```

Повторное чтение обычно возвращает кешированный экземпляр. При поступлении уведомления об изменениях стандартный Monitor удаляет объект соответствующего имени из кеша и создаёт новый.

Это отличается от создания объекта при каждом чтении `{cs}CurrentValue`. 

Monitor поддерживает именованные Options и подписки, поэтому подходит singleton-сервисам, которым нужны обновления.

### 7.6. Использование в scoped-сервисе

```cs
public sealed class RequestApiSettings
{
    private readonly ExternalApiOptions _options;

    public RequestApiSettings(
        IOptionsSnapshot<ExternalApiOptions> options)
    {
        _options = options.Value;
    }

    public int GetTimeoutSeconds()
    {
        return _options.TimeoutSeconds;
    }
}
```

```cs
builder.Services.AddScoped<RequestApiSettings>();
```

Сервис сохраняет объект, полученный в текущем scope. Следующий scope создаст новый экземпляр сервиса и получит свой объект настроек.

### 7.7. Использование в singleton-сервисе

```cs
public sealed class CurrentApiSettings
{
    private readonly IOptionsMonitor<ExternalApiOptions> _options;

    public CurrentApiSettings(
        IOptionsMonitor<ExternalApiOptions> options)
    {
        _options = options;
    }

    public int GetTimeoutSeconds()
    {
        ExternalApiOptions current = _options.CurrentValue;

        return current.TimeoutSeconds;
    }
}
```

```cs
builder.Services.AddSingleton<CurrentApiSettings>();
```

Singleton сохраняет Monitor и обращается к текущему объекту во время работы.

Если сохранить `{cs}monitor.CurrentValue` только в конструкторе, поле останется ссылкой на ранее полученный объект.

`{cs}IOptionsSnapshot<T>` является scoped-зависимостью, поэтому его нельзя напрямую внедрять в singleton. `{cs}IOptions<T>` и `{cs}IOptionsMonitor<T>` допускают такое внедрение. 

# 8. Именованные Options и последовательность настройки

### 8.1. Назначение именованных Options

Именованные Options позволяют использовать несколько наборов настроек одного типа.

```json
{
  "ExternalApis": {
    "Catalog": {
      "BaseUrl": "https://catalog.example.com",
      "TimeoutSeconds": 10
    },
    "Billing": {
      "BaseUrl": "https://billing.example.com",
      "TimeoutSeconds": 20
    }
  }
}
```

Регистрация:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>("Catalog")
    .BindConfiguration("ExternalApis:Catalog");

builder.Services
    .AddOptions<ExternalApiOptions>("Billing")
    .BindConfiguration("ExternalApis:Billing");
```

Имя Options и путь конфигурации независимы. Имя `"Catalog"` используется для получения объекта, а `ExternalApis:Catalog` определяет источник его настроек.

### 8.2. Получение по имени

```cs
ExternalApiOptions catalog = monitor.Get("Catalog");
ExternalApiOptions billing = monitor.Get("Billing");
```

Аналогично через Snapshot:

```cs
ExternalApiOptions catalog = snapshot.Get("Catalog");
```

Имена Options сравниваются с учётом регистра: `"Catalog"` и `"catalog"` — разные имена. Это отличается от сравнения ключей стандартной конфигурации. 

Имя по умолчанию:

```cs
Options.DefaultName
```

равно пустой строке `{cs}""`.

|Обращение|Имя|
|---|---|
|`IOptions<T>.Value`|`Options.DefaultName`|
|`IOptionsSnapshot<T>.Value`|`Options.DefaultName`|
|`IOptionsMonitor<T>.CurrentValue`|`Options.DefaultName`|
|`Get(null)`|Нормализуется к `Options.DefaultName`|
|`Get("Catalog")`|`"Catalog"`|

`{cs}IOptions<T>` не предоставляет метода получения именованных объектов.

Регистрация `"Catalog"` не делает этот набор набором по умолчанию. Правила для имени по умолчанию также не наследуются именованными наборами автоматически.

### 8.3. `Configure`, `ConfigureAll`, `PostConfigure` и `PostConfigureAll`

Основные методы расширения для `{cs}IServiceCollection`:

```cs
public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    Action<TOptions> configureOptions)
    where TOptions : class;

public static IServiceCollection Configure<TOptions>(
    this IServiceCollection services,
    string? name,
    Action<TOptions> configureOptions)
    where TOptions : class;

public static IServiceCollection ConfigureAll<TOptions>(
    this IServiceCollection services,
    Action<TOptions> configureOptions)
    where TOptions : class;

public static IServiceCollection PostConfigure<TOptions>(
    this IServiceCollection services,
    Action<TOptions> configureOptions)
    where TOptions : class;

public static IServiceCollection PostConfigure<TOptions>(
    this IServiceCollection services,
    string? name,
    Action<TOptions> configureOptions)
    where TOptions : class;

public static IServiceCollection PostConfigureAll<TOptions>(
    this IServiceCollection services,
    Action<TOptions> configureOptions)
    where TOptions : class;
```

|Метод|К каким объектам применяется|Этап|
|---|---|---|
|`Configure(action)`|Имя по умолчанию|Основная настройка|
|`Configure(name, action)`|Указанное имя|Основная настройка|
|`ConfigureAll(action)`|Все имена|Основная настройка|
|`PostConfigure(action)`|Имя по умолчанию|После основной настройки|
|`PostConfigure(name, action)`|Указанное имя|После основной настройки|
|`PostConfigureAll(action)`|Все имена|После основной настройки|

`{cs}ConfigureAll()` и `{cs}PostConfigureAll()` применяют правило при создании каждого подходящего объекта. Они не создают заранее все возможные наборы.

### 8.4. Порядок выполнения

При создании одного объекта:

1. Подходящие `{cs}Configure` и `{cs}ConfigureAll` выполняются в порядке регистрации
2. Подходящие `{cs}PostConfigure` и `{cs}PostConfigureAll` выполняются в порядке регистрации
3. Выполняется валидация

Все правила `{cs}PostConfigure` выполняются после всех правил `{cs}Configure`, даже если зарегистрированы раньше. 

```cs
builder.Services.PostConfigure<ExternalApiOptions>(
    options => options.TimeoutSeconds += 5);

builder.Services.Configure<ExternalApiOptions>(
    options => options.TimeoutSeconds = 10);

builder.Services.Configure<ExternalApiOptions>(
    options => options.TimeoutSeconds *= 2);
```

Результат для имени по умолчанию — `{cs}25`:

- Первый `{cs}Configure` устанавливает `{cs}10`
- Второй `{cs}Configure` получает `{cs}20`
- `{cs}PostConfigure` получает `{cs}25`

Несколько регистраций не заменяют друг друга: они добавляют последовательные правила.

### 8.5. Общие и отдельные настройки

```cs
builder.Services.ConfigureAll<ExternalApiOptions>(
    options => options.TimeoutSeconds = 30);

builder.Services.Configure<ExternalApiOptions>(
    "Catalog",
    options => options.TimeoutSeconds = 10);

builder.Services.PostConfigureAll<ExternalApiOptions>(
    options =>
    {
        options.BaseUrl = options.BaseUrl.TrimEnd('/');
    });
```

Общее правило задаёт тайм-аут `{cs}30`, а последующее правило для `"Catalog"` меняет его на `{cs}10`.

Если поменять порядок двух первых регистраций, общее правило снова установит `{cs}30`.

`{cs}PostConfigureAll()` удобно использовать для завершающей обработки значений после привязки и остальных правил.

### 8.6. Контракты настройки

```cs
public interface IConfigureOptions<in TOptions>
    where TOptions : class
{
    void Configure(TOptions options);
}

public interface IConfigureNamedOptions<in TOptions>
    : IConfigureOptions<TOptions>
    where TOptions : class
{
    void Configure(string? name, TOptions options);
}

public interface IPostConfigureOptions<in TOptions>
    where TOptions : class
{
    void PostConfigure(string? name, TOptions options);
}
```

|Контракт|Роль|
|---|---|
|`IConfigureOptions<T>`|Основная настройка без параметра имени|
|`IConfigureNamedOptions<T>`|Основная настройка с учётом имени|
|`IPostConfigureOptions<T>`|Завершающая настройка после основного этапа|

Стандартная фабрика применяет обычный `{cs}IConfigureOptions<T>` только к имени по умолчанию. Если объект настройки реализует `{cs}IConfigureNamedOptions<T>`, фабрика передаёт ему имя создаваемого набора.

Реализации именованной настройки регистрируются как `{cs}IConfigureOptions<T>`, поскольку фабрика получает коллекцию именно этого базового контракта. 

Для стандартных правил регистрации `{cs}name: null` означает применение ко всем именам. Это значение используется внутри `{cs}ConfigureAll()` и отличается от нормализации `{cs}Get(null)` к имени по умолчанию.

### 8.7. Получение незарегистрированного имени

Options не является словарём заранее зарегистрированных готовых объектов.

Вызов `{cs}Get("Unknown")` сам по себе не проверяет, встречалось ли это имя в `{cs}AddOptions()`. Фабрика может создать объект с начальными значениями, применить общие правила и выполнить валидацию.

Поэтому отсутствие отдельной регистрации имени не гарантирует исключения. Если существование определённого набора обязательно, это выражается правилами проверки.

# 9. Обновление настроек во время работы

### 9.1. Поддержка изменений со стороны provider

Обновление начинается на уровне источника конфигурации.

|Источник|Стандартное поведение|
|---|---|
|JSON с `reloadOnChange: true`|Отслеживает изменения файла|
|JSON с `reloadOnChange: false`|Автоматически не отслеживает файл|
|Переменные окружения|Читаются при загрузке, автоматического отслеживания нет|
|Аргументы командной строки|Читаются из переданного набора аргументов|
|In-memory provider|Изменение данных само по себе не означает уведомление Options|

Провайдер сообщает об обновлении через change token. Корневая конфигурация предоставляет общий токен через:

```cs
IChangeToken GetReloadToken();
```

Принудительная перезагрузка доступна через `{cs}IConfigurationRoot`:

```cs
void Reload();
```

```cs
((IConfigurationRoot)configuration).Reload();
```

Она вызывает загрузку провайдеров и уведомляет об обновлении конфигурации.

### 9.2. Связь конфигурации и Options

Регистрации `{cs}Configure<T>(configuration)`, `{cs}OptionsBuilder<T>.Bind()` и `{cs}BindConfiguration()` связывают Options с уведомлениями конфигурации.

Для Monitor обновление проходит следующие этапы:

1. Провайдер загружает новые данные и сигнализирует об изменении
2. Конфигурация передаёт уведомление
3. Monitor удаляет объект соответствующего имени из кеша
4. Фабрика создаёт, настраивает и проверяет новый объект
5. Monitor вызывает подписчиков `{cs}OnChange()`

Обновление не изменяет ранее выданный объект на месте.

Уведомление конфигурации может быть шире конкретной секции. Поэтому вызов `{cs}OnChange()` не гарантирует, что изменилось именно используемое сервисом свойство.

### 9.3. `IOptionsMonitor<T>.OnChange`

Метод интерфейса:

```cs
IDisposable? OnChange(
    Action<TOptions, string?> listener);
```

Параметры обработчика:

- `{cs}TOptions` — новый объект настроек
- `{cs}string?` — имя обновлённого набора

Возвращаемый `{cs}IDisposable` позволяет прекратить подписку.

```cs
public sealed class ApiSettingsObserver : IDisposable
{
    private readonly IDisposable? _subscription;

    public ApiSettingsObserver(
        IOptionsMonitor<ExternalApiOptions> monitor,
        ILogger<ApiSettingsObserver> logger)
    {
        _subscription = monitor.OnChange((options, name) =>
        {
            logger.LogInformation(
                "Options {Name}: timeout = {Timeout}",
                name,
                options.TimeoutSeconds);
        });
    }

    public void Dispose()
    {
        _subscription?.Dispose();
    }
}
```

Подписка действует после создания экземпляра сервиса и до освобождения возвращённого объекта. `{cs}OnChange()` не вызывает обработчик немедленно для передачи начального значения. 

### 9.4. Уже полученные объекты

```cs
ExternalApiOptions previous = monitor.CurrentValue;

// После успешной перезагрузки конфигурации:
ExternalApiOptions current = monitor.CurrentValue;
```

При стандартном механизме обновления `{cs}current` будет новым объектом. Переменная `{cs}previous` продолжит ссылаться на прежний.

То же относится к значению, сохранённому в поле сервиса:

```cs
_options = monitor.CurrentValue;
```

Последующие обновления Monitor не переприсваивают такое поле.

Для получения актуальных настроек сервис должен читать `{cs}CurrentValue` во время работы либо явно обрабатывать уведомления.

### 9.5. Почему сервисы не пересоздаются

Options и жизненный цикл DI-сервисов — разные механизмы.

Обновление настроек:

- Может пересоздать объект Options
- Не запускает повторно конструкторы уже созданных сервисов
- Не заменяет автоматически поля сервисов
- Не перенастраивает автоматически созданные ими ресурсы

Например, если singleton создал подключение или клиент с параметрами из Options, появление нового объекта настроек само по себе не изменит этот ресурс. Применение обновлений должно быть предусмотрено кодом компонента.

### 9.6. Изменение значений и запись в файл

```cs
configuration["ExternalApi:TimeoutSeconds"] = "20";
```

изменяет значения в провайдерах текущей конфигурации. Стандартные провайдеры не сохраняют это присваивание обратно в `appsettings.json`.

Стандартный setter провайдера также не вызывает уведомление о перезагрузке автоматически. Поэтому присваивание через индексатор не следует считать эквивалентом изменения файла с последующим `{cs}reloadOnChange`.

Аналогично:

```cs
monitor.CurrentValue.TimeoutSeconds = 20;
```

меняет полученный объект .NET, но не исходную конфигурацию. Последующее пересоздание Options снова применит зарегистрированные правила. 

> [!info] Options не является механизмом сохранения  
> Чтение, кеширование и обновление Options не обеспечивают запись настроек в исходный файл. Для сохранения нужен отдельный механизм работы с источником.

# 10. Валидация Options

### 10.1. Назначение валидации

Привязка проверяет возможность преобразовать данные в нужные типы. Валидация проверяет допустимость полученных значений.

Например, строка `"-10"` успешно преобразуется в `{cs}int`, но может быть недопустимым тайм-аутом.

В стандартном механизме Options проверки выполняются после `{cs}Configure` и `{cs}PostConfigure`, поэтому валидируется итоговый объект.

### 10.2. `Validate`

Методы класса `{cs}OptionsBuilder<TOptions>`:

```cs
public virtual OptionsBuilder<TOptions> Validate(
    Func<TOptions, bool> validation);

public virtual OptionsBuilder<TOptions> Validate(
    Func<TOptions, bool> validation,
    string failureMessage);
```

- `{cs}validation` — проверка объекта; `{cs}true` означает успех
- `{cs}failureMessage` — сообщение при результате `{cs}false`

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .BindConfiguration("ExternalApi")
    .Validate(
        options => options.TimeoutSeconds > 0,
        "TimeoutSeconds должен быть больше нуля")
    .Validate(
        options => Uri.TryCreate(
            options.BaseUrl,
            UriKind.Absolute,
            out _),
        "BaseUrl должен содержать абсолютный URI");
```

Каждый вызов добавляет отдельное правило. Метод регистрирует проверку, а не выполняет её немедленно. 

Если проверка требует собственных зависимостей или сложной логики, её можно вынести в `{cs}IValidateOptions<T>`.

### 10.3. `ValidateDataAnnotations`

Метод расширения для `{cs}OptionsBuilder<TOptions>`:

```cs
public static OptionsBuilder<TOptions>
    ValidateDataAnnotations<TOptions>(
        this OptionsBuilder<TOptions> optionsBuilder)
    where TOptions : class;
```

Находится в пространстве имён `{cs}Microsoft.Extensions.DependencyInjection`. Реализация предоставляется библиотекой `Microsoft.Extensions.Options.DataAnnotations`.

Например, к свойствам класса `{cs}ExternalApiOptions` добавляются атрибуты:

```cs
[Required]
[Url]
public string BaseUrl { get; set; } = "";

[Range(1, 300)]
public int TimeoutSeconds { get; set; } = 30;
```

Атрибуты находятся в `{cs}System.ComponentModel.DataAnnotations`.

Регистрация:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .BindConfiguration("ExternalApi")
    .ValidateDataAnnotations();
```

Наличие атрибутов само по себе не включает их проверку при обычном `{cs}Bind()` или `{cs}Get<T>()`. Для Options требуется регистрация валидатора. 

`{cs}[Required]` на числовом non-nullable свойстве не проверяет, присутствовал ли ключ в конфигурации: у свойства уже есть значение. Для допустимого диапазона используется, например, `{cs}[Range]`.

### 10.4. `IValidateOptions<T>` и `ValidateOptionsResult`

Контракт:

```cs
public interface IValidateOptions<TOptions>
    where TOptions : class
{
    ValidateOptionsResult Validate(
        string? name,
        TOptions options);
}
```

- `{cs}name` — имя проверяемого набора
- `{cs}options` — настроенный объект
- Результат сообщает об успехе, ошибке или пропуске проверки 

Основные результаты:

```cs
ValidateOptionsResult.Success;

ValidateOptionsResult.Skip;

ValidateOptionsResult.Fail("Описание ошибки");
```

Методы создания ошибки:

```cs
public static ValidateOptionsResult Fail(
    string failureMessage);

public static ValidateOptionsResult Fail(
    IEnumerable<string> failures);
```

|Результат|Значение|
|---|---|
|`Success`|Проверка успешно выполнена|
|`Fail(...)`|Настройки не прошли проверку|
|`Skip`|Валидатор не применяется к этому набору|

У результата есть свойства `{cs}Succeeded`, `{cs}Failed`, `{cs}Skipped`, `{cs}FailureMessage` и `{cs}Failures`. 

Пример проверки связи между настройками:

```cs
public sealed class ExternalApiOptionsValidator
    : IValidateOptions<ExternalApiOptions>
{
    public ValidateOptionsResult Validate(
        string? name,
        ExternalApiOptions options)
    {
        if (name != Options.DefaultName)
        {
            return ValidateOptionsResult.Skip;
        }

        if (options.Retry.Delay >=
            TimeSpan.FromSeconds(options.TimeoutSeconds))
        {
            return ValidateOptionsResult.Fail(
                "Retry.Delay должен быть меньше общего тайм-аута");
        }

        return ValidateOptionsResult.Success;
    }
}
```

Регистрация:

```cs
builder.Services.AddSingleton<
    IValidateOptions<ExternalApiOptions>,
    ExternalApiOptionsValidator>();
```

В примере валидатор применяется только к имени по умолчанию. Для проверки всех имён условие с `{cs}Skip` удаляется.

### 10.5. Когда выполняется проверка

По умолчанию настройки проверяются при создании объекта:

|Механизм|Момент проверки|
|---|---|
|`IOptions<T>`|Первое создание значения через `Value`|
|`IOptionsSnapshot<T>`|Первое создание объекта данного имени внутри scope|
|`IOptionsMonitor<T>`|Первое создание объекта и пересоздание после уведомления|
|Повторное чтение успешно кешированного объекта|Проверка заново не запускается|

Регистрация правил и обычный `{cs}builder.Build()` сами по себе не гарантируют, что все настройки уже проверены.

Если приложение не обращается к определённому набору, ошибка в нём может долго оставаться необнаруженной.

### 10.6. `ValidateOnStart`

Метод расширения:

```cs
public static OptionsBuilder<TOptions> ValidateOnStart<TOptions>(
    this OptionsBuilder<TOptions> optionsBuilder)
    where TOptions : class;
```

Он включает получение и проверку указанного типа и имени при запуске хоста:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>()
    .BindConfiguration("ExternalApi")
    .ValidateDataAnnotations()
    .Validate(
        options => options.TimeoutSeconds > 0,
        "TimeoutSeconds должен быть больше нуля")
    .ValidateOnStart();
```

Проверка запуска выполняется при старте хоста, например во время `{cs}app.Run()`, а не непосредственно при вызове `{cs}ValidateOnStart()`.

Для именованных Options проверяется имя текущего построителя:

```cs
builder.Services
    .AddOptions<ExternalApiOptions>("Catalog")
    .BindConfiguration("ExternalApis:Catalog")
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

Чтобы проверять при запуске несколько имён, регистрация выполняется для каждого из них.

`{cs}ValidateOnStart()` не добавляет содержательных правил проверки: он меняет момент их выполнения. 

### 10.7. `OptionsValidationException`

Если валидаторы возвращают ошибки, стандартная фабрика выбрасывает `{cs}OptionsValidationException`.

Основные свойства:

```cs
public string OptionsName { get; }

public Type OptionsType { get; }

public IEnumerable<string> Failures { get; }
```

|Свойство|Значение|
|---|---|
|`OptionsName`|Имя невалидного набора|
|`OptionsType`|Тип настроек|
|`Failures`|Сообщения об ошибках проверки|

```cs
try
{
    ExternalApiOptions options = monitor.CurrentValue;
}
catch (OptionsValidationException exception)
{
    foreach (string failure in exception.Failures)
    {
        Console.WriteLine(failure);
    }
}
```

С `{cs}ValidateOnStart()` такая ошибка препятствует успешному запуску хоста. Без него ошибка возникает при создании настроек во время работы. 

Ошибка привязки может возникнуть раньше проверки. Например, значение `"abc"` для `{cs}int` приводит к ошибке преобразования, а не к `{cs}OptionsValidationException`.

### 10.8. Повторная проверка обновлённых настроек

После уведомления об изменении Monitor создаёт новый объект через ту же фабрику. Поэтому повторно выполняются:

- Привязка конфигурации
- Правила `{cs}Configure`
- Правила `{cs}PostConfigure`
- Зарегистрированные валидаторы

Если новый объект не проходит проверку, обработчики `{cs}OnChange()` не получают его как успешно обновлённые настройки.

Стандартный Monitor не обеспечивает автоматического отката к последнему валидному объекту: прежняя запись уже удалена из кеша, а создание новой завершилось ошибкой. Ссылки на ранее полученный объект при этом продолжают существовать.

Для Snapshot обновлённые данные проверяются при создании объекта в новом scope. Уже созданный объект `{cs}IOptions<T>` повторную проверку после перезагрузки не проходит.

### 10.9. Совместная регистрация

```cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSingleton<
    IValidateOptions<ExternalApiOptions>,
    ExternalApiOptionsValidator>();

builder.Services
    .AddOptions<ExternalApiOptions>()
    .BindConfiguration(ExternalApiOptions.SectionName)
    .ValidateDataAnnotations()
    .Validate(
        options => options.Retry.MaxAttempts > 0,
        "Retry.MaxAttempts должен быть больше нуля")
    .ValidateOnStart();

var app = builder.Build();

app.MapGet(
    "/api-timeout",
    (IOptionsMonitor<ExternalApiOptions> options) =>
        options.CurrentValue.TimeoutSeconds);

app.Run();
```

Здесь секция привязывается к классу настроек, итоговый объект проверяется несколькими валидаторами, проверка выполняется при запуске, а endpoint получает текущий объект через Monitor.
