## 1. Protocol Buffers

**Protobuf (Protocol Buffers)** — независимый от языка и платформы механизм описания и сериализации структурированных данных

Он позволяет один раз описать структуру данных в `.proto`-файле, а затем сгенерировать типизированные классы для C#, Java, Go и других языков. Объекты этих классов можно сериализовать в компактный бинарный формат и восстановить обратно.

```protobuf
message User {
  int64 id = 1;
  string name = 2;
}
```

Из такого описания для C# генерируется класс, концептуально похожий на:

```cs
var user = new User
{
    Id = 42,
    Name = "Ivan"
};

byte[] data = user.ToByteArray();
```

### Из чего состоит Protobuf

Protobuf — это не только бинарный формат, а набор связанных компонентов:

- язык описания схем в `.proto`-файлах
- бинарный формат сериализации
- компилятор `protoc`
- генерируемые классы для выбранного языка
- runtime-библиотеки для чтения и записи сообщений

### Schema-first подход

Сначала определяется контракт:

```protobuf
message CreateUserRequest {
  string name = 1;
  string email = 2;
}
```

Затем из него генерируется код для разных приложений.

Это обеспечивает одинаковое представление данных между сервисами, написанными на разных языках

## 2. Бинарное представление данных

Protobuf сериализует сообщение как последовательность пар:

```
[tag][value][tag][value]...
```

Каждое поле содержит:

- числовой идентификатор поля
- способ кодирования значения — `wire type`
- само значение

Имена полей в бинарные данные не записываются. Это одна из причин, почему Protobuf обычно компактнее текстовых форматов. В JSON имя каждого поля передаётся вместе со значением, а Protobuf использует короткие числовые идентификаторы. Чтобы восстановить сообщение, получателю нужен соответствующий `.proto`-контракт. 

### Tag поля

Перед каждым значением записывается `tag`, объединяющий номер поля и `wire type`.

Номер определяет, **какое это поле**, а `wire type` — **как прочитать следующие байты**.

Номера полей являются частью бинарного контракта:

```Protobuf
int64 user_id = 1;
string user_name = 2;
```

Поэтому номер существующего поля нельзя произвольно менять: старый получатель будет интерпретировать его как другое или неизвестное поле

### Wire types

`Wire type` — не конкретный тип из `.proto`, а категория бинарного представления значения

Основные варианты:

|Wire type|Как хранится|Примеры типов|
|---|---|---|
|`Varint`|целое переменной длины|`int32`, `int64`, `uint32`, `bool`, `enum`|
|`I64`|ровно 8 байт|`fixed64`, `sfixed64`, `double`|
|`Length-delimited`|длина + содержимое|`string`, `bytes`, вложенные сообщения, packed-коллекции|
|`I32`|ровно 4 байта|`fixed32`, `sfixed32`, `float`|

Один `wire type` может использоваться несколькими типами Protobuf. Например, `string`, `bytes` и вложенное сообщение кодируются одинаково на уровне структуры:

```
[длина содержимого][содержимое]
```

Как именно интерпретировать содержимое, получатель узнаёт из `.proto`-схемы.

### Varint

**Varint** кодирует целые числа переменным количеством байтов

Небольшие значения занимают меньше места:

```
маленькое число → 1 байт
большее число   → несколько байтов
```

Каждый байт использует:

- 7 бит для значения
- старший бит как признак продолжения

```
0xxxxxxx — последний байт
1xxxxxxx — после него есть ещё байты
```

Таким образом, и номер поля, и небольшое числовое значение могут занимать совсем немного места.

### Length-delimited значения

Строки, массивы байтов и вложенные сообщения хранятся по схеме:

```
[tag][length][payload]
```

Например:

```
string user_name = 2;
```

Значение `"Ivan"` концептуально кодируется так:

```
tag поля №2
длина: 4 байта
UTF-8-байты строки "Ivan"
```

Получатель сначала читает длину, а затем ровно указанное количество байтов

Вложенное сообщение хранится аналогично:

```Protobuf
message Address {
  string city = 1;
}

message User {
  Address address = 1;
}
```

```
tag поля address
длина вложенного сообщения
бинарное содержимое Address
```

### Поля со значениями по умолчанию

При использовании неявного присутствия скалярные поля со значением по умолчанию обычно не записываются в бинарное сообщение:

```Protobuf
int32 count = 1;   // значение по умолчанию 0
bool enabled = 2;  // значение по умолчанию false
string name = 3;   // значение по умолчанию ""
```

Если поле отсутствует в данных, сгенерированный код возвращает соответствующее значение по умолчанию

Это дополнительно уменьшает размер сообщения, но означает, что без явного отслеживания присутствия нельзя различить:

- поле не передавалось
- поле явно установили в значение по умолчанию

## 3. Описание сообщений и типов в `.proto`

`.proto`-файл описывает структуру передаваемых данных независимо от конкретного языка программирования

Пример контракта, использующего основные возможности Protobuf:

```Protobuf
syntax = "proto3";

package users.v1;

option csharp_namespace = "Users.Contracts.V1";

enum UserStatus {
  USER_STATUS_UNSPECIFIED = 0;
  USER_STATUS_ACTIVE = 1;
  USER_STATUS_BLOCKED = 2;
}

message User {
  message Address {
    string city = 1;
    string street = 2;
  }

  int64 user_id = 1;
  string user_name = 2;
  optional int32 age = 3;
  UserStatus status = 4;
  repeated string roles = 5;
  map<string, string> metadata = 6;
  Address address = 7;

  oneof contact {
    string email = 8;
    string phone_number = 9;
  }
}
```

### 3.1. Структура файла

Обычно содержимое `.proto` располагается в таком порядке:

```Protobuf
syntax 
package
imports
options
message и enum
```

#### `syntax`

```
syntax = "proto3";
```

Указывает, что файл использует синтаксис `proto3`

Директива `syntax` должна быть первой непустой строкой файла, не считая комментариев. Если не указать ни `syntax`, ни `edition`, компилятор будет считать, что используется `proto2`.

#### `package`

```Protobuf
package users.v1;
```

`package` задаёт пространство имён типов внутри самого Protobuf-контракта и предотвращает конфликты одинаковых имён:

```Protobuf
users.v1.User
orders.v1.User
```

Имена пакетов пишутся строчными буквами и разделяются точками.

Пакет является частью полного имени Protobuf-типа, поэтому после публикации контракта его не следует менять без необходимости. Для C# пакет по умолчанию также используется как основа namespace.

#### `csharp_namespace`

```Protobuf
option csharp_namespace = "Users.Contracts.V1";
```

Определяет namespace сгенерированных C#-типов:

```Protobuf
namespace Users.Contracts.V1;
```

Без этой опции C#-генератор преобразует `package` в PascalCase:

`package` и `csharp_namespace` решают разные задачи:

- `package` $\rightarrow$ полное имя типа в Protobuf
- `csharp_namespace` $\rightarrow$ namespace сгенерированного C#-кода

#### Именование файлов

Имена `.proto`-файлов пишутся в `lower_snake_case`:

```
user.proto
user_profile.proto
create_user_request.proto
```

Внутри файла используются следующие соглашения:

```
message и enum  → PascalCase
поля            → snake_case
package         → lowercase_with_dots
значения enum   → UPPER_SNAKE_CASE
oneof           → snake_case
```

Генератор самостоятельно преобразует имена под стиль C#:

```
user_id       → UserId
phone_number  → PhoneNumber
```

### 3.2. Сообщения и поля

`message` описывает структуру сериализуемого объекта:

```Protobuf
message User {
  int64 user_id = 1;
  string user_name = 2;
}
```

Для него генерируется C#-класс примерно такого вида:

```cs
public sealed partial class User : IMessage<User>
{
    public long UserId { get; set; }

    public string UserName { get; set; }
}
```

Сгенерированный класс содержит не только свойства, но и логику сериализации, десериализации, вычисления размера, клонирования и сравнения сообщений.

Каждое поле описывается так:

```Protobuf
тип имя_поля = номер_поля;
```

Например:

```Protobuf
string user_name = 2;
```

#### Номера полей

В пределах одного `message` номер каждого поля должен быть уникальным:

```Protobuf
message User {
  int64 user_id = 1;
  string user_name = 2;
}
```

Допустимый диапазон номеров: 1 – 536 870 911

Номера `1–15` занимают в теге один байт, поэтому их желательно назначать наиболее часто передаваемым полям. Номера `16–2047` занимают уже два байта.

После публикации контракта нельзя:

- менять номер существующего поля
- использовать один номер для нескольких полей
- повторно использовать номер удалённого поля
- перенумеровывать поля ради красивого порядка

Изменение номера означает для Protobuf удаление старого поля и создание совершенно нового

### 3.3. Скалярные типы

Основные типы Protobuf и соответствующие им типы C#:

| Protobuf   | C#           | Описание                               |
| ---------- | ------------ | -------------------------------------- |
| `double`   | `double`     | 64-битное число с плавающей точкой     |
| `float`    | `float`      | 32-битное число с плавающей точкой     |
| `int32`    | `int`        | знаковое число, кодируется как Varint  |
| `int64`    | `long`       | знаковое число, кодируется как Varint  |
| `uint32`   | `uint`       | беззнаковое число                      |
| `uint64`   | `ulong`      | беззнаковое число                      |
| `sint32`   | `int`        | эффективнее для отрицательных значений |
| `sint64`   | `long`       | эффективнее для отрицательных значений |
| `fixed32`  | `uint`       | всегда занимает 4 байта                |
| `fixed64`  | `ulong`      | всегда занимает 8 байт                 |
| `sfixed32` | `int`        | знаковое число размером 4 байта        |
| `sfixed64` | `long`       | знаковое число размером 8 байт         |
| `bool`     | `bool`       | логическое значение                    |
| `string`   | `string`     | строка в UTF-8                         |
| `bytes`    | `ByteString` | произвольные бинарные данные           |

`int32` и `int64` хорошо подходят для небольших положительных значений, но отрицательные значения всегда занимают много байтов. Если поле часто содержит отрицательные числа, лучше использовать `sint32` или `sint64`, которые применяют ZigZag-кодирование.

Пример:

```Protobuf
message Product {
  int64 product_id = 1;
  string product_name = 2;
  double price = 3;
  bool available = 4;
  bytes image_hash = 5;
}
```

#### Значения по умолчанию

Если поле отсутствует в сообщении, сгенерированный код возвращает значение по умолчанию:

```
числа        → 0
bool         → false
string       → ""
bytes        → пустой ByteString
enum         → значение с номером 0
repeated     → пустая коллекция
map          → пустой словарь
message      → поле не установлено
```

Для обычного `string` нельзя присвоить `null`: C#-свойство возвращает пустую строку, а попытка установить `null` приводит к исключению. Поля типа `message`, напротив, могут быть `null`, что означает отсутствие вложенного сообщения.

### 3.4. Перечисления `enum`

`enum` ограничивает поле набором именованных числовых значений. Значения `enum` пишутся в `UPPER_SNAKE_CASE` и обычно получают префикс с именем перечисления. В C# префикс удаляется генератором.

```Protobuf
enum UserStatus {
  USER_STATUS_UNSPECIFIED = 0;
  USER_STATUS_ACTIVE = 1;
  USER_STATUS_BLOCKED = 2;
}
```

Использование:

```Protobuf
message User {
  UserStatus status = 1;
}
```

В `proto3` первое значение перечисления должно иметь номер `0`. Оно используется как значение по умолчанию

Обычно нулевому значению дают имя вроде:

```Protobuf
UNSPECIFIED
UNKNOWN
UNRECOGNIZED
```

### 3.5. Коллекции `repeated`

`repeated` означает, что поле может содержать от нуля до любого количества значений:

```Protobuf
message User {
  repeated string roles = 1;
}
```

Порядок элементов сохраняется:

```cs
["admin", "editor", "reader"]
```

В C# генерируется свойство типа `RepeatedField<T>`:

```cs
public RepeatedField<string> Roles { get; }
```

Оно похоже на `List<T>`, но дополнительно умеет сериализоваться, десериализоваться и глубоко клонироваться

```c
var user = new User();

user.Roles.Add("admin");
user.Roles.Add("editor");
```

Можно использовать initializer:

```cs
var user = new User
{
    Roles =
    {
        "admin",
        "editor"
    }
};
```

`RepeatedField<T>` не допускает элементы `null`, даже когда `T` является ссылочным типом сообщения.

Для `repeated` не отслеживается присутствие:

```
поле отсутствовало
поле было передано как пустая коллекция
```

После десериализации обе ситуации выглядят как пустой `RepeatedField<T>`

Числовые `repeated`-поля в `proto3` по умолчанию используют packed-кодирование, при котором несколько значений упаковываются в один блок без отдельного тега для каждого элемента.

### 3.6. Словари `map`

`map` описывает коллекцию пар ключ–значение:

```protobuf
message User {
  map<string, string> metadata = 1;
}
```

В C# генерируется:

```cs
public MapField<string, string> Metadata { get; }
```

Использование похоже на обычный `Dictionary<TKey, TValue>`:

```cs
user.Metadata["source"] = "mobile";
user.Metadata["language"] = "ru";
```

### 3.7. Вложенные сообщения и перечисления

Тип можно объявить внутри другого сообщения:

```protobuf
message User {
  message Address {
    string city = 1;
    string street = 2;
  }

  Address address = 1;
}
```

Снаружи вложенный тип указывается через родительское сообщение:

```protobuf
message Delivery {
  User.Address address = 1;
}
```

В сгенерированном C# вложенные типы находятся внутри дополнительного класса `Types`:

```cs
User.Types.Address address = new();
```

Пример структуры:

```cs
public sealed partial class User
{
    public static partial class Types
    {
        public sealed partial class Address
        {
        }
    }
}
```

### 3.8. `optional` и присутствие полей

У обычных скалярных полей `proto3` без `optional` присутствие не отслеживается:

```protobuf
message User {
  int32 age = 1;
}
```

После десериализации невозможно отличить:

```
age не передавали
age явно передали как 0
```

Чтобы различать эти состояния, используется `optional`:

```protobuf
message User {
  optional int32 age = 1;
}
```

В C# генерируется не `int?`, а обычное значение вместе с признаком присутствия:

```cs
public int Age { get; set; }

public bool HasAge { get; }

public void ClearAge();
```

```
HasAge = false → поле отсутствует
HasAge = true, Age = 0 → поле присутствует и явно содержит 0
```

Официальная документация рекомендует использовать `optional`, когда нужно явно отслеживать присутствие скалярного поля.

Поля типа `message` уже имеют присутствие по умолчанию:

```protobuf
message User {
  Address address = 1;
}
```

В C#:

```cs
if (user.Address is null)
{
    // Поле address отсутствует
}
```

`repeated` и `map` нельзя объявлять как `optional`, поскольку для них отсутствие представлено пустой коллекцией

### 3.9. Взаимоисключающие поля `oneof`

`oneof` описывает группу полей, из которой одновременно может быть установлено не более одного:

```protobuf
message User {
  oneof contact {
    string email = 1;
    string phone_number = 2;
  }
}
```

Если установить `email`, а затем `phone_number`, значение `email` автоматически очистится:

```cs
var user = new User
{
    Email = "user@example.com"
};

user.PhoneNumber = "+79990000000";

// Email больше не является активным полем oneof
```

Для C# генерируется перечисление, показывающее активное поле:

```cs
public enum ContactOneofCase
{
    None = 0,
    Email = 1,
    PhoneNumber = 2
}

public ContactOneofCase ContactCase { get; }

public void ClearContact();
```

Использование:

```cs
switch (user.ContactCase)
{
    case User.ContactOneofCase.Email:
        Console.WriteLine(user.Email);
        break;

    case User.ContactOneofCase.PhoneNumber:
        Console.WriteLine(user.PhoneNumber);
        break;

    case User.ContactOneofCase.None:
        Console.WriteLine("Контакт не указан");
        break;
}
```

В `oneof` нельзя напрямую помещать `repeated` и `map`. При необходимости коллекцию оборачивают в отдельное сообщени:

Установка одного участника `oneof` очищает остальных, а сгенерированный C# API предоставляет свойство `Case` и метод `Clear`.

## 4. Импорты и организация контрактов

`import` позволяет использовать сообщения и перечисления, объявленные в других `.proto`-файлах

```protobuf
import "common/address.proto";
```

Импорт создаёт зависимость между схемами. Содержимое импортированного файла не копируется внутрь текущего файла: компилятор читает оба контракта и связывает используемые типы.

### Импорт собственных `.proto`-файлов

Допустим, адрес описан отдельно:

```protobuf
// common/address.proto

syntax = "proto3";

package common.v1;

option csharp_namespace = "Common.Contracts.V1";

message Address {
  string city = 1;
  string street = 2;
}
```

Его можно подключить в другой файл:

```protobuf
// users/user.proto

syntax = "proto3";

package users.v1;

option csharp_namespace = "Users.Contracts.V1";

import "common/address.proto";

message User {
  int64 user_id = 1;
  common.v1.Address address = 2;
}
```

Если тип находится в текущем пакете, его можно использовать по короткому имени. Для типа из другого пакета обычно указывают полное имя.

```protobuf
common.v1.Address address = 1;
```


### Прямые и транзитивные зависимости

Обычный `import` не предоставляет импортированные типы следующим файлам автоматически. Транзитивно типы не импортируются, поэтому надо явно указывать зависимости.

`import public` делает импорт транзитивным:

```protobuf
import public "new_address.proto";
```


### Well-known types

Protobuf содержит набор стандартных сообщений в пакете:

```
google.protobuf
```

Они называются **well-known types** и поставляются вместе с Protocol Buffers. Для них не нужно самостоятельно создавать аналоги вроде `MyTimestamp` или копировать стандартные `.proto`-файлы.

Основные типы:

|Импорт|Тип|Назначение|
|---|---|---|
|`google/protobuf/timestamp.proto`|`Timestamp`|момент времени|
|`google/protobuf/duration.proto`|`Duration`|продолжительность|
|`google/protobuf/empty.proto`|`Empty`|пустое сообщение|
|`google/protobuf/any.proto`|`Any`|сообщение произвольного Protobuf-типа|
|`google/protobuf/field_mask.proto`|`FieldMask`|список путей к полям|
|`google/protobuf/struct.proto`|`Struct`, `Value`|динамические JSON-подобные данные|
|`google/protobuf/wrappers.proto`|`Int32Value` и другие|обёртки над скалярными типами|

В C# эти типы находятся в namespace:

```
Google.Protobuf.WellKnownTypes
```


### Wrapper-типы

Wrapper-типы подключаются так:

```protobuf
import "google/protobuf/wrappers.proto";
```

В C# генератор обрабатывает такие поля особым образом:

```
google.protobuf.Int32Value   → int?
google.protobuf.BoolValue    → bool?
google.protobuf.DoubleValue  → double?
google.protobuf.StringValue  → string?
```

Однако wrapper-типы считаются устаревшим подходом для новых контрактов. Для обычного отслеживания присутствия поля рекомендуется `optional`

## 5. Protobuf в .NET и генерация C#-классов

.NET-приложение не работает с `.proto` напрямую. Сначала контракт компилируется в C#-код

### Основные пакеты

`Google.Protobuf` — runtime для работы с сообщениями:

- сериализация и десериализация
- `IMessage<T>`
- `ByteString`
- `RepeatedField<T>`
- `MapField<TKey, TValue>`
- well-known types

`Grpc.Tools` — запускает `protoc` во время сборки и генерирует C#-код

```xml
<ItemGroup>
  <PackageReference Include="Google.Protobuf"
                    Version="..." />

  <PackageReference Include="Grpc.Tools"
                    Version="..."
                    PrivateAssets="All" />
</ItemGroup>
```

`Grpc.Tools` нужен только при сборке, поэтому обычно указывается `PrivateAssets="All"`

### Подключение `.proto`

```xml
<ItemGroup>
  <Protobuf Include="Protos\**\*.proto"
            ProtoRoot="Protos"
            GrpcServices="None" />
</ItemGroup>
```

Здесь:
- `Include`                          $\rightarrow$ обрабатываемые .proto-файлы
- `ProtoRoot`                      $\rightarrow$ корень для разрешения `import`
- `GrpcServices="None"`  $\rightarrow$ генерировать только `message` и `enum`, без gRPC-кода

Значения `GrpcServices`:

- `None`     $\rightarrow$ только Protobuf-типы
- `Client` $\rightarrow$ gRPC-клиент
- `Server` $\rightarrow$ серверная база
- `Both`     $\rightarrow$ клиент и сервер

### Что происходит при сборке


`dotnet build`
$\rightarrow$ `Grpc.Tools` запускает `protoc`
$\rightarrow$ создаются `.cs`-файлы в `obj`
$\rightarrow$ C#-компилятор включает их в сборку

Сгенерированные файлы не редактируют и обычно не добавляют в Git

## 6. Изменение контрактов и обратная совместимость

Клиенты и серверы обновляются не одновременно, поэтому некоторое время в системе могут работать разные версии одного `.proto`-контракта

Protobuf позволяет постепенно изменять схему благодаря номерам полей и поддержке неизвестных полей

### 6.1. Добавление полей

Добавление нового поля является безопасным изменением бинарного контракта:

```protobuf
message User {
  int64 user_id = 1;
  string user_name = 2;

  optional string email = 3;
}
```

Старый клиент не знает о поле `3` и воспринимает его как неизвестное. Новый клиент при чтении старого сообщения увидит, что `email` отсутствует

```
старое сообщение → новый код
email отсутствует

новое сообщение → старый код
email игнорируется как неизвестное поле
```

Если нужно различать отсутствие поля и значение по умолчанию, новое скалярное поле лучше объявлять через `optional`.

### 6.2. Удаление полей

Поле нельзя просто удалить, а затем использовать его номер для другого значения

Было:

```protobuf
message User {
  int64 user_id = 1;
  string user_name = 2;
  string legacy_login = 3;
}
```

После удаления:

```****
message User {
  reserved 3;
  reserved "legacy_login";

  int64 user_id = 1;
  string user_name = 2;
}
```

`reserved` запрещает случайно использовать старый номер или имя

Номер резервируют обязательно. Имя особенно важно, когда сообщения также передаются через ProtoJSON или TextFormat, где используются имена полей.

Во время постепенной миграции поле можно сначала пометить как устаревшее:

```protobuf
string legacy_login = 3 [deprecated = true];
```

Затем перестать его записывать, дождаться обновления потребителей, удалить и зарезервировать

### 6.3. Нельзя менять номера полей

Номер поля является его идентификатором в бинарном формате

```protobuf
// Было
string user_name = 2;

// Стало
string user_name = 5;
```

Для Protobuf это не перенос поля, а удаление поля №2 и добавление нового поля №5

Старый код не увидит поле №5, а новый код не увидит поле №2. Ошибки десериализации обычно не будет, но значение окажется недоступно и будет заменено значением по умолчанию

Ещё опаснее повторно использовать старый номер для другого смысла:

```protobuf
// Было
string email = 3;

// Недопустимо
bool is_blocked = 3;
```

Старые данные могут быть интерпретированы как новое поле или привести к ошибке разбора

Поэтому номера существующих полей не меняют, а номера удалённых полей помещают в `reserved`

### 6.4. Изменение типов

Тип существующего поля лучше не менять:

```protobuf
// Было
int32 age = 1;

// Стало
string age = 1;
```

Одинаковый номер начинает обозначать данные с другим представлением или смыслом

Некоторые изменения бинарно совместимы только при соблюдении ограничений. Например `int32` можно мигрировать в `int64`

Несмотря на совместимость wire format, официальные рекомендации советуют почти никогда не менять тип существующего поля. Надёжнее добавить новое поле с новым номером и постепенно перенести данные.

### 6.5. Изменение `enum`

Добавлять значения в существующий `enum` бинарно безопасно:

```protobuf
enum UserStatus {
  USER_STATUS_UNSPECIFIED = 0;
  USER_STATUS_ACTIVE = 1;
  USER_STATUS_BLOCKED = 2;
  USER_STATUS_DELETED = 3;
}
```

Однако старый прикладной код может не ожидать новое значение, например в `switch`, поэтому неизвестные варианты всё равно нужно обрабатывать

Удалённые значения и их номера резервируют:

```protobuf
enum UserStatus {
  reserved 2;
  reserved "USER_STATUS_BLOCKED";

  USER_STATUS_UNSPECIFIED = 0;
  USER_STATUS_ACTIVE = 1;
}
```

Номер `0` должен оставаться значением без содержательной бизнес-семантики, например `UNSPECIFIED`, чтобы старые сообщения и отсутствующие поля интерпретировались предсказуемо.

### 6.6. Безопасная миграция поля

Например, нужно заменить числовой идентификатор строковым

**1. Добавить новое поле**

```protobuf
message User {
  int64 legacy_external_id = 1;
  optional string external_id = 2;
}
```

**2. Обновить читателей**

Новый код временно поддерживает оба поля:

```protobuf
string externalId = user.HasExternalId
    ? user.ExternalId
    : user.LegacyExternalId.ToString();
```

**3. Обновить отправителей**

Новый код начинает записывать `external_id`, при необходимости временно продолжая заполнять старое поле

**4. Перестать использовать старое поле**

После обновления всех участников старое поле больше не читается и не записывается

**5. Удалить и зарезервировать**

```protobuf
message User {
  reserved 1;
  reserved "legacy_external_id";

  optional string external_id = 2;
}
```

Общий принцип:

```
сначала добавить
→ обновить читателей
→ обновить отправителей
→ прекратить использование старого поля
→ удалить и зарезервировать
```

## 7. Инструменты

### `protoc`

`protoc` — официальный компилятор Protocol Buffers. Он проверяет `.proto`-файлы и запускает генераторы кода для выбранного языка.

```sh
protoc \
  --proto_path=Protos \     # корень для import
  --csharp_out=Generated \  # каталог для сгенерированного C#-кода
  Protos/users/user.proto
```

В обычном .NET-проекте напрямую запускать `protoc` обычно не требуется — это делает `Grpc.Tools` во время сборки

### Protoscope

**Protoscope** — небольшой язык и утилита для представления низкоуровневого wire format Protobuf в читаемом виде. Он полезен для изучения тегов, Varint и бинарного кодирования, а не для обычной разработки приложения.

Например, Protoscope может представить сообщение как:

```
1: 150
2: {"Ivan"}
```

Где `1` и `2` — номера полей

### `dotnet-grpc`

`dotnet-grpc` — глобальная .NET-утилита для управления ссылками на `.proto` в `.csproj`. Она может добавлять, обновлять, удалять и показывать элементы `<Protobuf>`, а также подключать необходимые NuGet-пакеты.

Установка:

```sh
dotnet tool install -g dotnet-grpc
```

Добавление локального файла:

```sh
dotnet grpc add-file Protos/user.proto
```

В результате утилита добавляет в проект примерно такую запись:

```xml
<Protobuf Include="Protos\user.proto"
          GrpcServices="Both" />
```

Редактировать `.csproj` вручную тоже можно, поэтому `dotnet-grpc` не является обязательным

### Buf

**Buf CLI** — сторонний набор инструментов для работы с Protobuf-контрактами

Основные команды:

```sh
buf lint
```

Проверяет стиль и типовые ошибки в `.proto`-файлах. Правила задаются в `buf.yaml`.

```sh
buf breaking --against <предыдущая версия>
```

Сравнивает текущие контракты с предыдущей версией и обнаруживает потенциально несовместимые изменения: удаление полей, изменение типов, перенос типов между файлами и другие нарушения выбранного уровня совместимости.

Buf может проверять разные уровни совместимости:

```
FILE
PACKAGE
WIRE_JSON
WIRE
```

Для публичных или широко используемых контрактов такие проверки полезно запускать в CI, чтобы несовместимое изменение не попало в основную ветку.
