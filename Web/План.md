# `HttpContext`

## 1. Что такое `HttpContext`

- контекст обработки **одного HTTP-запроса**
- создаётся инфраструктурой ASP.NET Core для каждого запроса
- передаётся через middleware pipeline и дальше в endpoint
- объединяет request, response и request-specific state

## 2. Общая структура

Карта основных частей:

```
HttpContext
├── Request
├── Response
├── User
├── RequestServices
├── Connection
├── Items
├── Features
├── RequestAborted
├── TraceIdentifier
└── Session
```

Сразу отметить: не все части обязательны во всех приложениях, некоторые зависят от подключённой инфраструктуры.

## 3. `Request`

- что представляет входящий HTTP-запрос
- основные свойства:
    - `Method`
    - `Scheme`
    - `Host`
    - `Path`
    - `QueryString`
    - `Headers`
    - `Cookies`
    - `Body`
    - `ContentType`
    - `ContentLength`
- без глубокого разбора HTTP semantics

## 4. `Response`

- что представляет формируемый HTTP-ответ
- основные свойства:
    - `StatusCode`
    - `Headers`
    - `Body`
    - `ContentType`
    - `ContentLength`
    - `Cookies`
    - `HasStarted`
- кратко про то, что response формируется постепенно во время обработки запроса

## 5. `User`

- текущий `ClaimsPrincipal`
- информация об аутентифицированном пользователе
- связь с authentication/authorization
- без разбора claims/policies

→ `[[Authentication и Authorization]]`

## 6. `RequestServices`

- `IServiceProvider` scope текущего запроса
- через него разрешаются scoped dependencies
- отличие от `app.Services`

```
app.Services
    → root IServiceProvider

context.RequestServices
    → request scope IServiceProvider
```

→ `[[Dependency Injection]]`

## 7. `Items`

- словарь для request-scoped произвольных данных
- используется для передачи данных между middleware/endpoint в рамках одного запроса
- живёт только пока живёт `HttpContext`

## 8. `Connection`

- информация о текущем соединении
- remote/local IP
- ports
- connection id
- сертификаты клиента при наличии
- без ухода в сокеты и транспорт

## 9. `RequestAborted`

- `CancellationToken`
- сигнал, что запрос больше не нужно продолжать
- например клиент разорвал соединение
- важно передавать в долгие async-операции

## 10. `Features`

- низкоуровневый набор capability-интерфейсов текущего request context
- через него ASP.NET Core расширяет `HttpContext` без разрастания самого класса
- можно назвать `IFeatureCollection`
- глубоко не разбирать

## 11. `TraceIdentifier`

- идентификатор текущего запроса
- используется для correlation/logging/diagnostics

## 12. `Session`

- доступ к session state, если session middleware настроен
- подчеркнуть, что session **не является базово активной сама по себе**

→ отдельная тема при необходимости

## 13. Lifecycle `HttpContext`

Вот это важный раздел:

```
request received
      ↓
HttpContext created / initialized
      ↓
middleware pipeline
      ↓
endpoint
      ↓
response completed
      ↓
HttpContext больше не используется
```

- `HttpContext` относится к одному запросу
- нельзя сохранять ссылку и использовать после завершения запроса
- нельзя бездумно использовать из нескольких потоков параллельно
- request-scoped объекты связаны с тем же lifecycle

## 14. `DefaultHttpContext`

- конкретная стандартная реализация `HttpContext`
- сам `HttpContext` — abstract class
- обычно напрямую создавать не нужно
- полезно знать для тестов и понимания архитектуры

## 15. Общая схема

В конце собрать всё:

```
                    HttpContext
                         │
      ┌────────────┬─────┼─────┬────────────┐
      ↓            ↓     ↓     ↓            ↓
   Request      Response User Services    Connection
      │            │             │
      └────────────┴─────────────┘
                         │
                    request lifetime
```

Я бы именно так и фиксировал. Ключевые темы файла: **что представляет `HttpContext`, что в нём лежит, какие данные request-scoped и сколько он живёт**. Детали DI, auth, session, middleware и routing — только ссылками.
